## 一、今日算法题：分割数组的最大值（Split Array Largest Sum, LC 410）

### 题目

给定一个非负整数数组 `nums` 和整数 `k`，把数组分成 **连续的 k 个子数组**，使得「最大子数组和」**最小化**，返回这个最小的最大和。

```
示例:
输入: nums = [7,2,5,10,8], k = 2
输出: 18
解释: 最优划分 [7,2,5] 和 [10,8]，最大子数组和 = max(14, 18) = 18
```

**约束**：`1 <= k <= nums.length <= 1000`，`0 <= nums[i] <= 10^6`。

### 为什么今天选这道题（主题同构）

今天是多智能体编排日，这道题就是**负载均衡（load balancing）的算法原型**：

| 算法概念 | 多智能体系统对应 |
|---|---|
| 数组元素 = 任务时长 | 每个子任务的 token 数 / 工具调用数 / 运行秒数 |
| 分成 k 个连续子数组 | 任务切成 k 批，分给 k 个 worker |
| 最小化最大子数组和 | 最小化**最慢 worker 的完工时间**（makespan minimization） |
| 「答案越大越容易合法」的单调性 | 预算越宽松调度越可行——和 Day 125 的预算约束一脉相承 |

**工程直觉：多智能体提速的本质不是"人多"，而是"没有短板"。** 10 个 worker 干活，完成时间取决于最慢的那个；子任务切得不均，加多少 agent 都是白搭。这道题就是 makespan 理论的入门模型。

### 思路一：二分答案 + 贪心验证（O(n · log Σ)）

**核心观察——单调性**：设 `feasible(limit)` = "能否切成 ≤k 段，使每段和 ≤ limit"。
- limit 越大，约束越松，越容易满足 ⇒ `feasible` 关于 limit **单调**（false…false true…true）
- 答案就是使 `feasible(limit)=true` 的最小 limit ⇒ **二分答案**

```python
def splitArray(nums, k):
    # 下界：最大单元素（至少有一段装得下最大的那个）
    # 上界：全部元素和（k=1 的情况）
    lo, hi = max(nums), sum(nums)

    def feasible(limit):
        cnt, cur = 1, 0            # cnt=已切分出的段数（从 1 开始）
        for x in nums:
            if cur + x <= limit:   # 当前段装得下 → 继续装
                cur += x
            else:                  # 装不下 → 开新段
                cnt += 1
                cur = x
                if cnt > k:        # 段数超预算 → 此 limit 不可行
                    return False
        return True                # cnt <= k 即可（不是必须恰好 k 段！）

    while lo < hi:
        mid = (lo + hi) // 2
        if feasible(mid):
            hi = mid               # 可行 → 往左压
        else:
            lo = mid + 1           # 不可行 → 往右抬
    return lo
```

**贪心正确性（面试官必追问）**：为什么"能装就装"是对的？
- 反证：设存在合法划分，而贪心在某处开了新段导致段数更多。由于贪心的每段都是"在当前 limit 下尽量装满"，贪心第 i 段的结束位置 **不早于** 任何合法划分第 i 段的结束位置——贪心每段覆盖的元素是合法划分对应段的前缀超集，于是合法划分需要的段数只会 **更多不会更少**。所以贪心用的段数 ≤ 任何划分的段数，贪心若说"要 k+1 段"，那谁都不行。

**复杂度**：每次验证 O(n)，二分 O(log(Σnums − max)) ≈ O(log 10^9) ≈ 30 次 ⇒ 总复杂度 **O(n · log S)**，S=数组和。空间 O(1)。

**易错点（面试必考）**：
- **`feasible` 是 ≤k 段而非恰好 k 段**：切出来的段数如果比 k 少，可以把大段再拆开（拆不会变差），所以 ≤k 就够了——这个"恰好变至多"的松弛是二分段数类问题的通用入口
- `lo` 的初始化必须是 `max(nums)` 不是 `0`——答案至少装得下最大的单元素
- 二分的 while 条件 `lo < hi` + `lo = mid + 1`，返回 `lo`（标准 lower_bound 模板，背熟）
- **溢出**：`sum(nums)` 最大 10^9 在 32 位边缘，Java/C++ 用 `long`；Python 无所谓

### 思路二：DP（O(n²k)，对拍与扩展用）

`dp[i][j]` = 前 i 个元素切成 j 段的最小最大和：
`dp[i][j] = min over p<j of max(dp[p][j-1], prefix[i]-prefix[p])`

O(n²k) 在本题约束下勉强能过，面试里作为"我知道 DP 解法"提及即可，主流解法是二分。

### 连环问：从二分负载均衡到调度系统

**Q1: k 不限、可以任意分段呢？**
- 退化为"最小化最大段和 = 不切" ⇒ 答案是 sum(nums)；或者反过来固定 limit 求最小段数，就是经典的**贪心分段计数**，本题 feasible() 函数本身就是这个能力

**Q2: 任务可以乱序分配（不要求连续）呢？**
- 变成 **P||Cmax 调度问题**（NP-hard）：m 台机器、n 个独立任务、最小化最大完工时间。经典近似算法 **LPT（Longest Processing Time first）**：任务按降序排列，每次分给当前负载最小的机器，近似比 4/3 − 1/(3m)
- LPT 就是"大任务先安排 + 永远补最闲的"——多智能体任务分发的直觉算法版，面试里能说出 LPT + 4/3 近似比直接加分

**Q3: 任务有依赖关系（DAG）呢？**
- List Scheduling（列表调度）：维护就绪队列，机器空了就取下一个就绪任务；关键路径（Critical Path）优先是经典优先级——这就是 Week 19 Day 125 讲的 Planner 拆 DAG 定可并行边的调度算法版

**Q4: 能不能并行验证 / 分布到多台机器？**
- feasible() 是顺序扫描（前缀依赖），不好并行；但 DP 里不同 i 的区间可以并行更新；工程上大数据分片时，每片先本地聚合再二分全局——map-reduce 式两段二分

**Q5: 每个 worker 能力不同（机器异构）呢？**
- 把 limit 按机器能力加权；二分框架不变，feasible 里"当前机器剩余容量"变成逐个跟踪——异构调度是 k8s scheduler 的打分模型（Predicates + Priorities，Day 85 回调）

**Q6: 这套二分框架还能套哪些题？**
- 爱吃香蕉的珂珂（LC 875）、制作 m 束花所需最少天数（LC 1482）、运送包裹的能力（LC 1011，本题孪生题：换成天数 D 就是船运版本）、切割木棍的最小成本升级——**「最小化最大值」+「可行性单调」= 二分答案四件套模板**

## 二、面试技巧：多智能体编排四种模式

### 总纲：先回答"为什么不是一个 agent"，再谈怎么编排

多智能体不是免费的 lunch。每加一个 agent，你就在买三样东西、付三笔税：

| 买到的 | 付出的 |
|---|---|
| **上下文隔离**：子任务在独立 context 里跑，不污染主上下文（Day 124 外部化三件套） | **通信成本**：agent 间消息全是 token，结论回传是有损压缩 |
| **并行提速**：无依赖任务同时跑，吞吐 = 最慢 worker（今天那道题） | **协调开销**：谁来派活？冲突谁裁决？死循环谁兜底？ |
| **认知多样性**：不同角色/视角降低单点盲区 | **误差传播**：一个 agent 的错误结论会被下游当事实放大（error compounding 的社交版） |

**面试第一句话**："单 agent + 好工具 + 好上下文管理能解决的，不要上多智能体；多智能体的收益曲线在任务可分解、可验证、可并行时才转正。"——这句话本身就是架构成熟度的体现。

### 四种编排模式总表

| 模式 | 结构 | 通信拓扑 | 适用 | 致命伤 | 系统类比 |
|---|---|---|---|---|---|
| **主管-工人** Supervisor-Worker | 一个 Supervisor 拆解任务、派发、验收；Worker 专职执行 | 星型，全部消息过中心 | 任务可分解为异质子任务，需要统一验收标准 | Supervisor 单点瓶颈 + 单点失效；中心 context 膨胀 | OS 的进程调度器 / k8s 的 controller |
| **流水线** Pipeline | 阶段固定，每个 agent 只干一类活，输出是下游输入 | 链式，单向无环 | 任务有天然阶段划分（检索→摘要→校验→生成） | 一个 stage 出错全链停摆；阶段间格式契约脆弱 | 编译器 Pass 链 / 工厂流水线 |
| **辩论投票** Debate/Voting | 多个同构或异构 agent 独立作答，互相评审或投票裁决 | 全连接或轮式，多轮 | 答案质量可对比（开放生成、方案设计），需要降低单次生成方差 | 回声室：同质 agent 辩论 = 自己说服自己；轮次开销 | Self-Consistency（Day 118）的组织版 / 代码评审 |
| **市场拍卖** Market/Auction | 任务是资源，agent 是 bidder，出价（能力/成本/置信度）竞标，拍卖机制分配 | 去中心化，广播竞标 | 任务同质可枚举、agent 能力异构且动态变化 | 机制设计复杂；bid 本身有成本；可能失配（没人接的活） | 分布式调度器的负载均衡 / Spot 实例市场 |

### 逐模式深讲

**① 主管-工人（Supervisor-Worker）——生产系统的主流**

- 代表：Claude Code sub-agents（Task tool）、OpenAI Swarm 的 handoff、AutoGen 的 GroupChat 默认拓扑、CrewAI 的 crew 结构
- 关键设计点：**验收标准先于派发**——Supervisor 给 Worker 的指令必须自带 done-criteria（"输出 diff 摘要 + 测试结果 + 未能完成项列表"），否则收回来的是流水账
- **层级深度 ≤2 是经验红线**：Supervisor 再雇 Supervisor，委派链每多一层，意图失真 + 延迟翻倍 + 死循环检测变难
- 致命伤：Supervisor 自己也会 context rot——它要读所有 Worker 的汇报。对策 = 只回传结论不回传流水（Day 124）、汇报结构化（结论/置信度/未决项三行）
- 面试加分：Supervisor 失败模式两种——**委派太粗**（worker 自由发挥翻车）和**委派太细**（把 worker 变成打字机，丧失隔离意义）。好的委派 = 目标 + 约束 + 验收三件套，中间过程零 micromanage

**② 流水线（Pipeline）——编译器思维做 agent**

- 结构：Agent A → Agent B → Agent C，阶段间靠**结构化契约**（schema）连接，不是自然语言闲聊
- 适用：ETL 类任务（抓数据→清洗→分析→出报告）、代码审查（作者 agent → 评审 agent → 测试 agent）
- 关键设计点：**契约即接口**——阶段间传输的是带 schema 的文档（JSON + 类型约束），不是聊天记录。契约变了要有 version（和 microservice API 演进一个道理）
- 失败模式：级联误差——A 的错输出被 B 当真。对策 = 每个 stage 入口做**输入校验**（schema 校验 + 关键字段 sanity check），不合法直接打回上游重出，而不是带病往下传
- 与单 agent 多步的取舍：pipeline 换 agent 的代价是每跳一次全新 context（丢失前面推理），所以**只有当阶段间需要完全不同的"脑回路"（system prompt 差异大）时才值得换 agent**，否则同一 agent 顺序执行更省

**③ 辩论投票（Debate / Voting）——用多样性买方差缩减**

- 结构：N 个 agent 独立产出 → 互评/投票 → 裁决者（或权重机制）收敛
- 理论根基：**Self-Consistency 的组织版**——独立采样 + 多数投票降低方差（Day 118 的 1−(1−p)^N 公式直接复用）。辩论多轮的额外收益来自互相指出盲区，但注意 Kamoi 2024 的冷水：intrinsic self-correction 无外部反馈会掉点——**辩论必须有外部锚**（检索事实、执行结果、测试用例）
- 回声室问题：同底模型同 prompt 换名字"你扮演正方"不叫多样性，叫一个人分饰两角。真正的多样性来源：**不同数据源、不同工具、不同验证器**（一个写代码、一个跑测试、一个查文档），而不是不同人设
- 裁决机制三档：多数投票（便宜粗暴）、judge agent（多一层开销，警惕 judge 也是同源模型 → Day 120 自我偏好偏差）、加权投票（按历史胜率加权——就是 Day 110 按权重随机选择那道题的逆向应用）
- 典型场景：方案设计评审、安全敏感操作前的多方确认（"两个 agent 都觉得这个 rm -rf 没问题才执行"）

**④ 市场拍卖（Market / Auction）——机制设计视角**

- 结构：任务广播 → agent 根据自身能力/负载/置信度出价 → 拍卖规则决定分配（一价/二价密封、英式降价等）
- 代表思想：Camel-AI 的 role-based workforce、早期 Multi-Agent 经济学研究、k8s 的扩展调度器（kube-batch 的 gang scheduling 本质是组竞标）
- 为什么需要它：前三种模式的任务分配都是**静态的**（supervisor 拍脑袋 / pipeline 固定 / 辩论均分），当 agent 能力异构且负载动态变化时，静态分配必然失衡——**今天的算法题就是静态均分的代价模型**
- 机制设计要点：
  - **出价必须包含成本信号**：完成该任务预计消耗多少 token / 多少秒 / 当前队列多长——没有成本信号的出价必然劣化（劣币驱逐良币）
  - **二价拍卖防串谋**：赢者付第二高价，报真实估价是占优策略（Vickrey 经典结论）——agent 诚实地暴露自己的能力边界比"逞强接单"对系统整体更优
  - **未分配任务兜底**：流拍任务进 Supervisor 队列人工/中心处理，不允许任务消失
- 面试里这是"高级谈资"：能提到 mechanism design + Vickrey + 成本真实披露，直接和普通"我知道四种模式"的回答拉开档次

### 通信与共享：编排的底层三板斧

不管选哪种模式，底层只有三种通信原语：

1. **消息传递**（agent → agent 直发）：灵活但 N² 连边爆炸，适合小规模
2. **黑板/共享内存**（共享文档/workspace，各 agent 读写）：解耦生产者消费者，但要注意**写冲突**——需要单 writer 原则或 LWW/版本号（Day 106 CRDT 回调），否则两个 agent 同时改一份文件 = 分布式写写冲突
3. **发布订阅**（事件总线）：观察者模式，适合流水线异步化和进度广播

**记忆共享是重灾区**：多 agent 共享长期记忆时，私有记忆 + 共享黑板是主流折中（Day 126 记忆系统多智能体共享段落）；只传结论不传流水；写入要过重要性过滤（否则 A agent 的废话会污染 B agent 的检索）。

### 失败模式速查表（面试讲故事素材）

| 失败模式 | 症状 | 缓解 |
|---|---|---|
| **循环委托** | A 让 B 干，B 说这不是我职责让 A 自己干，无限 ping-pong | 委派深度计数 + 硬上限；每跳必须产出工件（artifact）才能继续 |
| **Supervisor 过载** | 中心 context 爆炸、响应变慢、验收敷衍 | 分层验收（worker 自检 → 抽样深验）；结论回传 |
| **回声室** | 辩论三轮结论越来越一致但不一定对 | 异构数据源/验证器制造真多样性；外部锚（执行/检索） |
| **级联误差** | pipeline 后端输出系统性偏离 | stage 入口校验 + 打回重出 + 质量指标分段监控 |
| **成本失控** | 多 agent 并行 token 账单爆炸 | 全局预算熔断（Day 122）、按难度路由 agent 档位（小模型干粗活） |
| **死锁互等** | 两个 agent 都在等对方先给信息 | 消息带超时 + 缺省值推进（不能一直 block） |

### 框架速览（知道即可，别背参数）

- **LangGraph**：图结构编排，节点=agent/函数，边=路由条件；适合复杂控制流，学习曲线陡
- **AutoGen（微软）**：对话驱动，GroupChat 里多个 agent 群聊 + manager 选发言者；研究原型快，生产可控性一般
- **CrewAI**：角色扮演式（role/goal/backstory），上手最快，适合 demo；深度控制弱
- **OpenAI Swarm / Agents SDK**：轻量 handoff 路由，适合客服式意图分流
- **Claude Code**：sub-agent（Task tool）+ 文件系统作黑板 + Supervisor=主 agent，工程化程度最高的一档

**面试话术**："框架差异本质是**控制流表达方式**的差异——图（LangGraph）、对话（AutoGen）、角色（CrewAI）、路由（Swarm）；生产选型看四件事：可观测性（每个 agent 的轨迹能不能回放）、失败隔离（一个 agent 挂了会不会拖死全局）、成本控制（预算能不能全局熔断）、状态管理（黑板的一致性怎么保证）。"

### 与 veRL / Agentic RL 的连接（用户的主线）

- 多智能体编排的 RL 版：**群体训练 opponent pool**（Day 114 自博弈收官的延伸）——辩论模式训练时给每个立场维护策略池防坍缩
- rollout 侧：并行 worker 的负载均衡就是今天的算法题——veRL 的 RolloutWorker 组做 partial rollout 凑组基线（Day 113）时，任务切分不均是吞吐杀手
- 奖励侧：多 agent 系统的整体 reward 如何归因到单个 agent = credit assignment 的社交版（Day 116 PRM 的 multi-agent 变体，基本开放问题）

### 今日金句

> **多智能体编排的本质是"组织设计"——你不是在写代码，你是在当 CEO 设计汇报线。主管-工人是科层制，流水线是车间，辩论投票是评审会，市场拍卖是自由竞标。而所有组织设计的铁律在这里同样成立： communication structure follows task structure；先想清楚任务怎么分，再决定谁跟谁说话。**
