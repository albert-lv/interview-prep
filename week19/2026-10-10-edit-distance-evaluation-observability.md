## 一、今日算法题：编辑距离（Edit Distance, LC 72）

### 题目

给定两个字符串 `word1` 和 `word2`，返回将 `word1` 转换成 `word2` 所需的**最少操作数**。允许三种操作：

- **插入**一个字符
- **删除**一个字符
- **替换**一个字符

```
示例 1:
输入: word1 = "horse", word2 = "ros"
输出: 3
解释: horse → rorse (替换 h→r) → rose (删除 r) → ros (删除 e)

示例 2:
输入: word1 = "intention", word2 = "execution"
输出: 5
解释: intention → inention (删除 t) → enention (替换 i→e) → exention (替换 n→x)
      → exenution (替换 n→u) → execution (插入 c)
```

**约束**：`0 <= word1.length, word2.length <= 500`，两单词均只含小写字母。

### 为什么今天选这道题（主题同构）

今天是评估与观测日。轨迹评估（trajectory evaluation）的核心问题是：**给 agent 的实际轨迹和参考轨迹打分"差多少"**——答案就是编辑距离的工程化身：

| 算法概念 | agent 系统对应 |
|---|---|
| 两个字符串 | golden trace ↔ agent 实际轨迹（动作序列） |
| 插入 / 删除 / 替换 | 多走了一步 / 漏了一步 / 走了一条岔路 |
| 最小编辑代价 | 轨迹差异分（trajectory divergence score） |
| 对齐回溯（diff 可视化） | 哪几步对齐、哪几步是 agent 自创、哪几步是参考轨迹被跳过 |

更宏观地看：SWE-bench 判 pass/fail 只看**终点**，编辑距离看**路径**——这道题就是 outcome-based 评估 vs process-based 评估的算法隐喻。SWE-bench 说"两个 patch 都过了测试"，编辑距离说"但一个 3 步解决、一个绕了 30 步"。

**工程直觉：没有 diff 就没有 debug。** 你在终端里每天看的 `git diff`，内核就是 LCS/编辑距离家族的 Myers 算法——评估 agent 的第一步，就是把它的行为变成可 diff 的东西。

### 思路：二维 DP（O(m·n)）

**状态定义**：`dp[i][j]` = `word1` 的前 i 个字符转换成 `word2` 的前 j 个字符的**最少操作数**。

**边界（必背）**：
- `dp[i][0] = i` —— 前 i 个字符全删掉
- `dp[0][j] = j` —— 从零插入 j 个字符

**转移方程**：
```
若 word1[i-1] == word2[j-1]:  dp[i][j] = dp[i-1][j-1]          （末位免费对齐）
否则:                          dp[i][j] = 1 + min(
                                     dp[i-1][j],    删 word1[i-1]
                                     dp[i][j-1],    插 word2[j-1]
                                     dp[i-1][j-1])  替 word1[i-1]→word2[j-1]
```

```python
def minDistance(word1: str, word2: str) -> int:
    m, n = len(word1), len(word2)
    dp = [[0] * (n + 1) for _ in range(m + 1)]

    for i in range(m + 1):
        dp[i][0] = i          # 第一列：删光
    for j in range(n + 1):
        dp[0][j] = j          # 第一行：插满

    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if word1[i-1] == word2[j-1]:
                dp[i][j] = dp[i-1][j-1]              # 末位相同，白嫖
            else:
                dp[i][j] = 1 + min(
                    dp[i-1][j],                      # 删
                    dp[i][j-1],                      # 插
                    dp[i-1][j-1])                    # 替
    return dp[m][n]
```

**"horse" → "ros" 的 DP 表**（行为 word1 前缀，列为 word2 前缀）：

| | "" | r | o | s |
|---|---|---|---|---|
| **""** | 0 | 1 | 2 | 3 |
| **h** | 1 | 1 | 2 | 3 |
| **o** | 2 | 2 | 1 | 2 |
| **r** | 3 | 2 | 2 | 2 |
| **s** | 4 | 3 | 3 | 2 |
| **e** | 5 | 4 | 4 | **3** |

读表技巧：对角线不动 = 免费对齐（h→r 那格是替换所以 +1）；横向 = 插、纵向 = 删。最终右下角 = 3。

**复杂度**：时间 **O(m·n)**，空间 **O(m·n)**；滚动数组优化到 **O(min(m,n))**（每次只依赖上一行，把短串放列方向即可）。

**易错点（面试必考）**：
- **下标错位**：`dp[i][j]` 对应字符 `word1[i-1]` 和 `word2[j-1]`——dp 是 1-indexed 的"前 i 个字符"，字符数组是 0-indexed，想清楚就不乱
- **初始化先行先列**：`dp[0][j]=j` 和 `dp[i][0]=i` 不是可有可无，它是"空串参与"的边界语义，面试官就爱问"第一行代表什么"
- **替换的本质**：替换 = 删+插合一（2 步压成 1 步），所以字符不等时三个候选一起比，别漏了 `dp[i-1][j-1]`
- **滚动数组方向**：只留两行（甚至一行）时，依赖是**上、左、左上**三个方向，必须从前往后扫，不能倒序（对比 0-1 背包的倒序，恰好相反——被问空间优化时这就是区分度）
- 空串边界：`len=0` 时答案是另一个串的长度，代码天然覆盖，但要能口头说出来

### 连环问：从编辑距离到 diff、DNA 与轨迹打分

**Q1: 空间能压到 O(min(m,n)) 吗？**
- 滚动数组只保留上一行：内层循环需要"左上角的旧值"，用一个临时变量在覆盖前存住即可。工业界 diff 工具（Myers O(ND)）把这件事做到了 O(D) 空间——面试答出滚动数组就够，答出 Myers 直接封顶

**Q2: 只允许插入和删除（不允许替换）呢？**
- 最少操作数 = `m + n − 2·LCS`：先对齐最长公共子序列（LCS 部分免费），剩下的 word1 侧全删、word2 侧全插。**git diff 的内核就是这个**——LCS 的一个变体。编辑距离和 LCS 是"双生题"，考一个必带出另一个

**Q3: 怎么输出具体的编辑序列（对齐结果）？**
- parent 指针回溯：填表时记录每个 `dp[i][j]` 是从哪个方向来的，从 `(m,n)` 倒推到 `(0,0)` 得到操作序列；对齐版输出就是 diff 的 `+`/`-`/`|` 三列视图。和 Day 116 单词搜索的回溯一个套路：正向存选择，反向取路径

**Q4: 每种操作代价不同呢？**
- 加权编辑距离：替换代价 ≠ 删+插（比如键盘相邻字母误打替换代价低）；语音识别里混淆矩阵、DNA 比对的 PAM/BLOSUM 打分矩阵都是这个思想；再加"相邻交换算 1 步"就是 Damerau-Levenshtein——拼写检查的标配

**Q5: 这题还有什么真实应用？**
- **拼写检查**：BK-tree 用编辑距离做最近邻检索，词典里找 ≤2 次编辑的候选词
- **语音识别**：Wer（Word Error Rate，词错误率）= 编辑距离 / 总词数，是 ASR 的行业标准指标
- **DNA 序列比对**：生物信息学 daily bread，打分矩阵 + 仿射空位罚分
- **autocorrect / 输入法纠错**：键盘距离加权的编辑距离
- **git diff / code review**：Myers 算法的工业巅峰应用

**Q6: 10⁵ 级 DNA 序列怎么办？**
- O(mn) 时间和表格都装不下 → **Hirschberg 算法**：分治 + 线性空间，把长序列对半切，分别算正向/反向 DP 找最优中切点，递归合并，O(min(m,n)) 空间保持 O(mn) 时间；工程上常用 banded alignment：只算对角线附近 `|i−j| ≤ k` 的带（两个相似序列偏离不会太远），O(k·max(m,n))

**Q7: 回到今天主题——轨迹版的"编辑距离"长什么样？**
- 真实轨迹的元素不是字符，而是 `(state, action, observation)` 三元组。直接套编辑距离有两个坑：①**动作等价性**——"打开文件"和"读文件"是不是同一类操作？要先定义归一化规则（同义工具合并、参数抽象）再算距离；②**代价不对称**——漏一步的代价远大于多走一步。所以生产系统更常用 **rubric 打分 + LLM-judge**（Day 120）做软评估，编辑距离做硬对齐的辅助信号。能说出"什么时候裸 edit distance 不够用"，比会写转移方程更能体现工程判断力

## 二、面试技巧：评估与观测 —— Agent 系统的"考试体系"

### 总纲：先讲"为什么 agent 评估难"，再讲"怎么解"

Agent 评估之所以从"跑个 benchmark"升级成一门工程学科，是因为它同时踩在五个难点上：

1. **输出开放**：不是选择题，没有标准答案可以直接 `==` 比对（除非能执行验证）
2. **路径多样**：同一个任务有 100 条合法路径，终点对了不代表过程健康（今天那道题）
3. **环境交互**：结果依赖外部世界状态，测试环境复现成本高
4. **成本变量**：同一个任务，不同轨迹的 token 消耗能差 10 倍——"做对了"和"做得起"是两回事
5. **非确定性**：temperature > 0 时单次结果不可信，必须 N 次统计分布

**面试第一句话**："评估 agent 的第一步不是选 benchmark，而是把'成功'定义成可测量的东西——可分三级：可执行验证（测试过没过）> 规则验证（格式/约束对不对）> 模型验证（judge 打分），成本递增、覆盖递增（Day 120 四类验证器成本谱直接复用）。"

### 1. 离线 Benchmark 生态：SWE-bench 及其家族

**SWE-bench（2023.10，Princeton）——agent 评估的 ImageNet 时刻**：

- **构造**：从 12 个真实 Python 仓库（Django/Flask/scikit-learn 等）挖 2294 个已解决的 GitHub issue，把 issue 文本 + 修复前的 repo 快照给模型，要求产出 patch
- **判分双门**：**FAIL_TO_PASS**（修复后新增的测试必须过 = 真修了 bug）+ **PASS_TO_PASS**（原有测试不能挂 = 没修出新 bug）。这个双门设计是灵魂——只有 F2P 会鼓励投机（把旧测试删了），只有 P2P 会鼓励躺平（什么都不改）
- **指标**：Resolved rate（一个 issue 双门全过才算 resolved）
- **SWE-bench Verified（2024.08，OpenAI 合作）**：人工筛掉题面模糊/环境跑不通的题，留 500 道高质量样本——教训是**原始 benchmark 有噪声，人工精选子集才是可比的尺子**
- **演进线**：Multimodal（截图版 issue）→ Multilingual（Java/TypeScript/Go，直击 Python 偏置）→ Lite（快速迭代子集）→ Pro（长程任务）。每代都在补上一代的偏置

**生态全景（按任务域）**：

| Benchmark | 域 | 判分方式 | 一句话 |
|---|---|---|---|
| SWE-bench | 真实 repo 修 bug | 执行测试 | 工业界事实标准，scaffold 差异巨大 |
| WebArena | 网页任务 | 终态断言 | 自建沙箱网站，抗"背答案" |
| OSWorld | 真实 OS 操作 | 环境状态检查 | Day 125 提过，22%→40%+ |
| GAIA | 通用助理 | 短答案精确比对 | Meta/HuggingFace，考检索+推理组合 |
| τ-bench | 工具+用户对话 | 数据库终态 | Sierra 出品，多轮一致性 |
| BFCL | 函数调用 | AST 比对 | 工具调用的单项赛 |

**污染问题（contamination）——benchmark 的慢性毒药**：
- SWE-bench 的题全部来自公开 GitHub，模型预训练大概率见过 issue 和修复 patch → 分数通胀
- 对策三板斧：**时间切分**（只用模型 cutoff 之后的新 issue）、**私密 held-out**（内部题库不公开）、**canary 检测**（往训练数据里埋特定字符串看是否泄出）
- 呼应 Day 120 的 Goodhart 四幕剧：benchmark 一旦成为招聘/融资叙事，scaffold 过拟合 benchmark 就开始了——"在 SWE-bench 上调出来的 agent 换一批题可能现原形"

### 2. 三轴评估框架：Success / Cost / Reliability

单报一个"成功率"是新手，三维一起报才是工程：

| 轴 | 核心指标 | 关键细节 |
|---|---|---|
| **成功率** | pass@1，按难度分层报告 | 不能只报平均——"简单题 95% + 难题 5%"和"全在中等题 50%"是两个系统；要画难度-通过率曲线 |
| **成本** | tokens、$、wall-clock、步数 | 报"平均 + P95"（长尾任务才是账单杀手）；成本要和成功率联立看：同成功率比成本，同成本比成功率 |
| **可靠性** | **pass^k**（k 次全对的概率）、方差 | 见下方重点辨析 |

**pass@k vs pass^k——面试高频辨析，一句话讲清**：
- **pass@k**：k 次采样**至少对一次**的概率 = 1−(1−p)^k，衡量**能力上限**——论文刷榜、Best-of-N 的弹药（Day 118 的公式原样复用）
- **pass^k**：k 次采样**全对**的概率 = p^k，衡量**可靠性下限**——生产部署的真实体验：用户不会采样 k 次取最好，单次失败就是事故
- **工程意义**：提高 pass@1 同时压缩方差，才能把 pass^k 抬上去；Self-Consistency 多数投票本质是把 pass@k 的上限折成接近 pass^k 的部署能力（Day 118 收尾闭环）
- 金句版："论文看 pass@k 的上限，上线看 pass^k 的下限；agent 工程的主要矛盾，是让下限追上上限。"

### 3. 轨迹级评估（Trajectory Evaluation）—— 今天的主角

**轨迹 = Day 122 状态图的显式落地**：`(state, action, observation)` 序列。终局评估只看最后状态到没到，轨迹评估看整条路径健不健康。

**两个层次**：

**① 终局评估（outcome-based）**
- 优点：客观、便宜、和真实目标对齐（测试过没过、数据库终态对不对）
- 缺点：**归因黑洞**——挂了不知道挂在哪一步（Day 116 credit assignment 的评估版）；对了也不知道是不是蒙的
- 适用：可执行验证场景（SWE-bench 就是这个层次的天花板）

**② 过程评估（process-based）**
- **步数效率**：golden trace 3 步解决，agent 用了 30 步——终点一样，过程成本差 10 倍。这就是今天编辑距离的对偶视角
- **动作健康度**：无效工具调用率（参数错误的调用）、重复动作率（同一个 grep 搜三遍 = 死循环前兆，Day 123 的死循环检测）、观察忽略率（observation 里明明有答案却再问一遍）
- **轨迹相似度**：与 golden trace 做对齐（编辑距离家族）——适合有标准流程的任务（客服 SOP、运维 runbook）
- **LLM-as-judge on trajectory**：按 rubric 逐步打分（"第 4 步的检索是否合理"）。优点是能评开放轨迹，缺点是贵 + 自我偏好偏差（Day 120）+ judge 也可能看错——**轨迹 judge 的准确率本身也要被评估**（judge 的 judge，套娃但必要）

**轨迹数据的隐藏价值：它是 RL 燃料**。失败轨迹 = Reflexion 的反思原料（Day 123）；批量轨迹 = GRPO rollout 数据源（Day 112）；轨迹筛选 = R1 拒绝采样精修（Day 112 配方里的关键一步）。**评估系统做扎实了，训练数据管线就是它的副产品**——这是"eval 是开发另一半"最硬的论据。

### 4. 可观测性三支柱的 Agent 版

传统三支柱在 agent 系统里各长什么样：

| 支柱 | 传统系统 | Agent 系统 |
|---|---|---|
| **Traces** | 请求链路 span | **逐步轨迹**：每步的 input/output/tool_call/latency/token_cost 落盘（OpenTelemetry GenAI 语义约定 + Langfuse/Langsmith/Braintrust） |
| **Metrics** | QPS/延迟 | pass@1 趋势、工具错误率、步数分布、context 利用率、token burn/step |
| **Logs** | 应用日志 | **Trajectory replay（回放）**：任意一次运行完整重放——debug 必需（Day 125 computer use 录屏的工程化），也是评估 harness 的输入 |

**回放是 eval 与 observability 的铰链**：离线 eval = 批量回放 + 自动打分；在线观测 = 持续回放 + 抽样打分。同一个 trajectory store，两个用途。

**生产评估流水线（把评估做进 CI，面试加分项）**：
1. **黄金数据集回归**：prompt/模型/scaffold 任何变更 → 跑固定回归集，像单测一样卡通过率门禁
2. **A/B + canary**：新模型/新 prompt 小流量灰度，pass^k 和成本双指标观察
3. **线上反馈闭环**：用户纠正 → 进纠错记忆（Day 126）→ 精选进下一轮训练集——评估系统驱动数据飞轮

### 5. 与 veRL / Agentic RL 的连接（用户的主线）

- **eval harness = reward function 的镜像**：SWE-bench 式的"跑测试给 0/1"就是可验证奖励的工程形态（Day 112 的可验证奖励四原则）。**环境接口设计直接决定 RL 可行性**——reward 太稀疏（只有终局 pass）训练就慢，所以要过程信号（PRM，Day 116）和步级 shaping（Day 113 per-turn reward）
- **trajectory store = rollout 数据集**：veRL 的 rollout 日志系统本身就是评估系统（Day 113 监控六指标的评估版）；评估不达标的数据要能被定位、被归因、被过滤
- **agent-arena 视角**：如果做多 agent 竞技/评测平台，今天的三轴框架就是平台的核心指标设计——排行榜要防 Goodhart，就要多 benchmark 轮换 + held-out 题（呼应 Day 127 外部锚）

| 128 | 编辑距离 | 评估与观测 | 不能衡量就不能改进；eval 是开发的另一半 |

**七剑合璧的主线公式**：

```
agent 系统能力 = 状态搜索（122）× 上下文管理（124）× 工具交互（125）
              × 记忆（126）× 组织编排（127）× 失败恢复（123）× 评估闭环（128）
```

七天其实是一个闭环：搜索给你路径，上下文给你显存，工具给你手脚，记忆给你经验，编排给你规模，恢复给你韧性，**评估给你真相**——没有最后一环，前面六环都在自我感动。

### 今日金句

> **Demoware 与 productionware 之间，隔着一条叫 observability 的河。如果你不能衡量一个 agent，你就不能改进它——评估不是开发的尾声，评估是开发的另一半。离线 benchmark 给你入场券，轨迹级评估给你调试语言，线上可观测性给你改进闭环。三个都齐了，agent 才配叫工程系统。**
