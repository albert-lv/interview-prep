## 1) 今日算法题

### 钥匙和迷宫（Shortest Path to Get All Keys）

**题意**：给你一个 `m × n` 的网格 `grid`：

- `.` 是空地，`#` 是墙，`@` 是起点（恰好一个）；
- 小写字母 `'a'~'f'` 是**钥匙**，大写字母 `'A'~'F'` 是对应的**锁**（`a` 开 `A`，以此类推）；
- 每步可以上下左右移动到相邻格子，**墙不能走，锁必须有对应钥匙才能进入**，捡到钥匙后可以开对应的锁（钥匙永久有效，锁也可以反复穿过）。

返回拿到**全部钥匙**所需的最少移动步数；如果不可能，返回 `-1`。（钥匙数量 `k ≤ 6`。）

```
输入: grid = ["@.a..","###.#","b.A.B"]
输出: 3
解释: @ → a（2 步）→ A（第 3 步开 a 锁）→ b... 
     实际最优路径: @ → a → A → b → B → 终点方向,共 3 步拿到 a、b 两把钥匙 
     (注: 题目只要求集齐全部钥匙,不要求到达特定出口)

输入: grid = ["@..aA","..B#.","....b"]
输出: 6
解释: 先绕路拿 b,再回头开 B,最后拿 a——"绕远路"反而是最优,贪心会翻车。
```

**关键约束**：`1 ≤ m, n ≤ 30`，钥匙数 `k ≤ 6`。**这题 BFS 是显然的，难在"状态怎么定义"**——也是它今天能进 Week 19 的原因。

### 思路：状态增强 BFS——`(行, 列, 钥匙集合)` 才是完整状态

第一眼很容易写出 `(r, c)` 的裸 BFS，然后直接 WA。错因一句话：**同一个格子，带着不同钥匙到达，是截然不同的两个状态**。

- 你在 `(3,5)` 没钥匙 → 面前 `B` 门是死路；
- 你在 `(3,5)` 拿着 `b` → 同一扇门就是通路，后面整片区域向你敞开。

如果只按 `(r,c)` 去重，BFS 会错误地丢弃"带钥匙二进宫"的路径（第一次到某格往往没带钥匙、无法穿门，但它是"最近"的，把后续更优的带钥匙状态全给visited 掉了），返回次优甚至 `-1`。

**正确建模：状态 = `(r, c, mask)`**

1. `mask` 是一个 `k` 位二进制数：第 `i` 位为 1 表示已拿到第 `i` 把钥匙（`'a'`→bit0，`'b'`→bit1……）。`k ≤ 6` → `mask ∈ [0, 64)`，状态空间 `m·n·2^k ≤ 30·30·64 ≈ 5.8 万`，随便装。
2. **状态转移三规则**（对邻居 `ch = grid[nr][nc]`）：
   - 是 `#` → 跳过；
   - 是大写字母（锁）且 `mask` 里**没有**对应钥匙位 → 跳过（此路对我当前状态不通）；
   - 是小写字母（钥匙）→ 新状态 mask 置对应位： `nmask = mask | (1 << (ch - 'a'))`；
   - 其余（`.` / `@` / 已有钥匙的锁）→ mask 不变，正常入队。
3. **visited 存三元组** `(r, c, mask)`；`mask == (1<<k)-1`（全集）出队即返 `steps`。
4. 逐层展开（一次处理一整层）保证第一次集齐就是最少步数。

> 💡 **和 Week 19 的同构（今天的核心）**：这道题的 `mask` 就是 **agent 的 state 设计第一课**——你的状态里**必须包含"你已经拥有了什么"（能力、信息、权限），而不只是"你在哪"**。锁门就是 tool gating：光有路径不够，得有前置能力（precondition）。后面面试技巧部分会看到：ReAct 的失败、Plan-and-Execute 的 replan、Reflexion 的反思，全都建立在「状态里带没带全信息」这一个问题之上。

### 代码

**Python（面试推荐写法）：**

```python
from collections import deque

class Solution:
    def shortestPathAllKeys(self, grid: list[str]) -> int:
        m, n = len(grid), len(grid[0])
        k, sr, sc = 0, 0, 0
        for r in range(m):
            for c in range(n):
                ch = grid[r][c]
                if ch == '@':
                    sr, sc = r, c
                elif 'a' <= ch <= 'f':
                    k += 1

        full = (1 << k) - 1
        start = (sr, sc, 0)
        queue = deque([start])
        seen = {start}
        steps = 0

        while queue:
            for _ in range(len(queue)):
                r, c, mask = queue.popleft()
                if mask == full:
                    return steps
                for dr, dc in ((1,0), (-1,0), (0,1), (0,-1)):
                    nr, nc = r + dr, c + dc
                    if not (0 <= nr < m and 0 <= nc < n):
                        continue
                    ch = grid[nr][nc]
                    if ch == '#':
                        continue
                    # 锁门且无钥匙 → 此状态不可通行
                    if 'A' <= ch <= 'F' and not (mask >> (ord(ch) - ord('A'))) & 1:
                        continue
                    nmask = mask
                    if 'a' <= ch <= 'f':
                        nmask |= 1 << (ord(ch) - ord('a'))
                    state = (nr, nc, nmask)
                    if state not in seen:
                        seen.add(state)
                        queue.append(state)
            steps += 1
        return -1
```

**Go（工程向，struct 状态三元组）：**

```go
func shortestPathAllKeys(grid []string) int {
    m, n := len(grid), len(grid[0])
    k, sr, sc := 0, 0, 0
    for r := 0; r < m; r++ {
        for c := 0; c < n; c++ {
            ch := grid[r][c]
            if ch == '@' {
                sr, sc = r, c
            } else if ch >= 'a' && ch <= 'f' {
                k++
            }
        }
    }
    full := (1 << k) - 1
    type state struct{ r, c, mask int }
    q := []state{{sr, sc, 0}}
    seen := map[state]bool{{sr, sc, 0}: true}
    dirs := [][2]int{{1, 0}, {-1, 0}, {0, 1}, {0, -1}}

    for steps := 0; len(q) > 0; steps++ {
        for sz := len(q); sz > 0; sz-- {
            cur := q[0]
            q = q[1:]
            if cur.mask == full {
                return steps
            }
            for _, d := range dirs {
                nr, nc := cur.r+d[0], cur.c+d[1]
                if nr < 0 || nr >= m || nc < 0 || nc >= n || grid[nr][nc] == '#' {
                    continue
                }
                ch := grid[nr][nc]
                if ch >= 'A' && ch <= 'F' && cur.mask>>(ch-'A')&1 == 0 {
                    continue // 锁门且无钥匙
                }
                nmask := cur.mask
                if ch >= 'a' && ch <= 'f' {
                    nmask |= 1 << (ch - 'a')
                }
                ns := state{nr, nc, nmask}
                if !seen[ns] {
                    seen[ns] = true
                    q = append(q, ns)
                }
            }
        }
    }
    return -1
}
```

### 复杂度

- **时间**：状态数上界 `m·n·2^k`，每状态 4 条边 → **O(m·n·2^k)**，约 5.8 万 × 4，稳过。
- **空间**：`seen` 最坏装下全部增强状态 → **O(m·n·2^k)**。

> 📌 面试表达：「这题复杂度不在图上，在**状态定义**上——`(r,c)` 是 900 个状态，带上 mask 就是 5.8 万。多出来的维度不是负担，是**信息**：mask 让"二进宫"的合理路径不再被 visited 误杀。这和 agent 系统里 context 必须携带'已获得的能力'是同一个道理。」

### 面试官连环问（这题是"状态设计意识"的试金石）

1. **「只用 `(r,c)` 去重会错在哪？举个反例。」** → 上面的 `@..aA / ..B#. / ....b` 就是：`@` 右侧先摸到 `a` 很近，但没拿 `b` 开不了 `B`；必须绕下方拿 `b` 再折返。若按 `(r,c)` 去重，折返回到已访问格子的路径被剪，永远凑不齐钥匙。**同一个物理位置、不同信息集 = 不同状态**，这是信息搜索（informed search）的入门课。
2. **「钥匙数 k 不再 ≤6 怎么办？」** → 状态数 `2^k` 指数爆炸，精确 BFS 不可行；此时转**启发式搜索**：A*，h = 未收集钥匙数（每步最多捡一把，可采纳、永不高估），配合迭代加深 / IDA*；k 大时该问题本身是 NP-hard（可看成带资源约束的最短路径），工程上用近似算法 + 强剪枝。
3. **「怎么扩展到多机器人协同拿钥匙？」** → 状态变成联合状态 `(pos₁, pos₂, …, mask)`，状态数 ` (mn)^t · 2^k` 爆炸；实际工程用分配-规划两段式（先把钥匙分给机器人 = 任务分配，再各自规划 = 单 agent 问题）——这就是 Day 127 多智能体编排"主管-工人"模式的算法版。
4. **「如果钥匙会过期/只能用一次？」** → `mask` 不够用了，要换成带计数的 multiset 状态（每把钥匙的剩余次数进状态），状态空间进一步膨胀；或者改建模为路径约束满足问题。考察的是：**状态设计跟随资源语义**，语义一变状态维度就得重构。
5. **「和 LC 1293（消障碍穿墙）什么关系？」** → 同族题：状态增强 BFS 的两大原型——**能力型**（本题 mask = 已获能力）与**预算型**（1293 的 `(r,c,k)` = 剩余预算）。看到"捡东西/有限次特权/带资源"就该条件反射：`状态 = 位置 + 资源账本`。
6. **「为什么 BFS 不用 DFS？」** → 求最少步数，无权图分层展开第一次到达即最优；DFS 适合"能否集齐"的存在性问题。若要输出**所有**集齐路径（全部最优方案），BFS 到目标层后在该层内回溯收集。

## 2) 面试技巧

### Agent 架构三范式深讲：ReAct / Plan-and-Execute / Reflexion 🎭

Day 122 说了「agent 是进程」，今天给这个进程选**骨架**。所谓"三范式"，是 2022~2023 年奠定智能体架构格局的三篇工作，至今仍是所有 agent 框架（LangChain、AutoGen、OpenAI Agents SDK、Claude Code 的内核）的源代码级原型。**面试 agent 岗，这道题几乎必考："讲讲 ReAct 和 Plan-and-Execute 的区别，什么时候用哪个？"**

#### 三范式总表（先背这张，细节往下展开）

| 维度 | **ReAct** | **Plan-and-Execute** | **Reflexion** |
|---|---|---|---|
| 核心循环 | 想一步→做一步→看反馈，交替进行 | 先出完整计划→按计划逐步执行→失败再重规划 | 执行→评估→**用文字写反思**→存记忆→带反思重试 |
| 出处 | Yao et al. 2022（Google Brain / Princeton，ICLR 2023） | Plan-and-Solve 2023（零样本提示版）/ BabyAGI 2023 / LangChain 2023.05 实现 | Shinn et al. 2023（NeurIPS 2023） |
| 规划粒度 | **局部**：每次只决定下一步 | **全局**：一次买断整个方案 | 不规划，**复盘**后交给下一轮循环 |
| 环境要求 | 反馈便宜、步数少、动态环境 | 目标明确、步骤多、环境静态或缓变 | 有**明确的成败信号**（测试过/没过） |
| 典型战绩 | ALFWorld 文本游戏成功率 70%+ 档，远超纯动作模仿学习基线 | 多步推理任务上显著优于一次性 CoT | HumanEval 上 GPT-4 pass@1 从 80% 档推到 **91% 档** |
| 致命伤 | error compounding + 死循环 + 上下文膨胀 | 计划一错全链路错 + 重规划触发器难设计 | 反馈垃圾→反思垃圾；记忆膨胀；重试不保证跳出 |
| 系统类比 | **解释器 / event loop**（逐条取指执行） | **Pipeline / 批量编译**（先全量计划再跑） | **Retry + postmortem 文化**（失败复盘进知识库） |

#### 范式一：ReAct —— 把"想"和"做"编成一个环

**论文**：*ReAct: Synergizing Reasoning and Acting in Language Models*（Yao et al., 2022.10）。

**核心结构**：模型交替产出 `Thought`（我观察到/我推理出）→ `Action`（调用工具 / 发出动作）→ `Observation`（环境反馈），环直到任务完成。Thought 的两个作用：从观察里**抽关键信息**（对抗 observation 噪声）+ 给行动**做铺垫与自我提醒**（"我需要先找钥匙再开这个门"——今天算法题的直觉！）。

**什么时候选它**：
- 任务步数少（≤5 步）或**没法提前规划**（环境会回话，比如和人对话、浏览网页）；
- 反馈便宜且信息量大（一次搜索/一次 API 调用就能验证方向）；
- 走错一步的代价小（可以撤回，比如查询类操作）。

**失败模式（面试爱问，背熟）**：
1. **Error compounding**：一步错步步错——ReAct 没有全局账本，局部最优决策串成全局灾难（对应今天算法题里"贪心拿最近钥匙"的翻车）；
2. **死循环**：模型重复同一个 Thought-Action 对（尤其工具返回错误时），上下文越来越长但毫无进展——**必须配循环检测**；
3. **上下文腐化**：Observation 不断累积，关键信息被稀释（context rot，Day 122 两大敌人之一）；
4. **过度思考/行动比例失衡**：有些模型在每个 Action 前写一大段 Thought，token 烧穿预算（Week 18 的 compute budget 思想在这里依然成立）。

#### 范式二：Plan-and-Execute —— 规划一次，执行到底

**出处两条线**：学术上是 *Plan-and-Solve Prompting*（Wang et al., ICML 2023，零样本"先制定计划再逐步求解"）；工程上病毒式传播的是 **BabyAGI**（2023.03，任务生成→优先级排序→执行的三段循环）和 LangChain 的 `PlanAndExecute` agent（2023.05，规划器产出步骤列表 → 执行器逐步执行 → 完成后 replan）。

**核心结构**：**Planner**（通常是大模型一次调用，产出 `[step1, step2, …]`）→ **Executor**（逐步执行，可以是另一个更便宜/更专的模型）→ **Replanner**（执行不下去或环境变了 → 重新出计划）。

**什么时候选它**：
- 步骤多（10+ 步）且目标清晰，规划一次的**成本可以被摊薄**；
- 环境静态或变化缓慢（计划不会立刻过期）；
- 任务可分解性强（每步相对独立，DAG 依赖明显）。

**失败模式（同样要背）**：
1. **早期错误无反馈**：计划第一步就错了，后面九步全是精美地执行错误——execution 阶段没有逐步校验（除非加 verifier checkpoint）；
2. **计划粒度玄学**：太细（每步都写"点击按钮"）→ 环境一抖就断；太粗（"然后修好它"）→ 等于没规划。**经验粒度 = 模型对"一步能稳做成什么"的置信边界**；
3. **不会自己 replan**：这是它相对 ReAct 最大的短板——**replanner 的触发器设计是工程核心**：执行失败率超阈值？某步置信度低于阈值？环境 observation 与计划假设冲突（diff 检测）？触发器太敏感 = 退化成 ReAct，太迟钝 = 带着错误计划一路狂奔。

> 📌 一句话区分 ReAct 和 P&E：**ReAct 把规划揉进每一步（想得勤、走得慢、抗变化）；P&E 把规划一次性买断（想得省、走得快、怕变化）。** 面试官追问"区别"时，先抛这句再展开。

#### 范式三：Reflexion —— 失败不是终点，是资产

**论文**：*Reflexion: Language Agents with Verbal Reinforcement Learning*（Shinn et al., NeurIPS 2023）。Day 118 讲过它的思想，今天是架构位：**Reflexion 不改变行动策略本身，它在行动策略外面包一层"复盘-记忆-重试"**。

**核心结构**：**Actor**（执行，ReAct 或任意策略）→ **Evaluator**（打分：测试过没过 / 任务完成度，产生成败信号）→ **Self-Reflection**（模型针对失败轨迹写一段文字复盘："我失败是因为假设了 X，实际环境是 Y，下次应该先检查 Z"）→ 写入 **episodic memory**（滑窗，通常只留最近几条反思）→ 下一轮重试时把反思塞进 prompt。

**为什么算"verbal RL"**：传统 RL 更新权重，Reflexion 更新**上下文**——用自然语言承载"策略梯度"，零训练成本。这正 Week 18 的 test-time compute 思想在 agent 层的落地：**用推理时的计算量换通过率**。

**什么时候选它**：有**便宜且明确的验证器**的场景——代码有单测、数学有答案、游戏有分数。信号越干净，反思越准。反过来，开放创作类任务没有对错信号，Reflexion 就是无源之水（呼应 Day 116：每题配最便宜的够用验证器）。

**失败模式**：
1. **垃圾进垃圾出**：Evaluator 信号不准 → 反思归因错误 → 下轮带着错误结论继续撞墙；
2. **错误归因**：把运气当规律（"上次失败因为周二"）——反思文本本身没人审核；
3. **记忆膨胀与失配**：旧反思与新情境不匹配，塞在 context 里稀释注意力；滑窗大小是玄学参数；
4. **重试不保证收敛**：可能三次失败三次不同原因，也可能三次同一原因——所以它常配**最大重试次数 + 升级人工**的熔断。

#### 选型决策树（面试现场手画版）

```
任务能提前完整规划吗？
├─ 不能（环境会回话/步骤少/动态）→ ReAct
│    └─ 步数多、上下文易腐 → ReAct + 摘要压缩 + 循环检测 + 步数预算
└─ 能 → Plan-and-Execute
     └─ 执行中环境会变吗？→ 会：加 replan 触发器 / 每步 verifier checkpoint
有明确的成败验证器吗？
└─ 有 → 最外层包 Reflexion（重试 + 反思记忆 + 熔断上限）
```

**生产系统的真相：三者从来是叠加态，不是选择题。** 典型形态是**分层架构**：

```
Planner（低频，全局目标 → 子任务 DAG）        ← P&E 的 Planner
   └─ Executor 层：每个子任务一个 ReAct 循环    ← ReAct
        （工具调用、观察、局部纠错）
   └─ 失败后：Evaluator 打回 → Reflexion 写复盘  ← Reflexion
        → 带反思重试 N 次 → 仍败则升级人工/换路线
全局预算：总步数 / 总 token / 总时长的硬熔断      ← Week 18 的账本思想
```

Claude Code 的 Plan Mode、编码 agent 的"先列 todo 再逐条勾"就是这套：plan 显式化成持久 artifact（不是飘在上下文里的一句话），executor 是 ReAct 循环，单测失败触发反思重试——**你能讲出这个映射，面试官会眼睛一亮。**

#### 高频连环问（每题一句话速答 + 展开钩子）

1. **「ReAct 的 Thought 要不要对外可见？」** → 产品上不输出（过程不等于产物，隐藏推理只给摘要）；多智能体场景**必须小心**：你的 Thought 会被对手 agent 读到（提示词注入/策略泄露），该场景要么脱敏要么私有。
2. **「怎么检测 agent 死循环？」** → 状态指纹：最近 K 步的 (action, observation 摘要) 序列做哈希去重，重复即熔断；连续相同 action 计数；observation 信息增益为 0 检测。这套判据成本极低，生产必备。
3. **「P&E 的 replan 触发器怎么设计？」** → 三件套：执行失败率阈值 + 每步 verifier 检查点（只验关键步，成本可控）+ 环境 diff（observation 与计划假设显式冲突）。本质是在"计划新鲜度"和"规划成本"之间定价——太敏感退化成 ReAct，太迟钝带着错误计划狂奔。
4. **「Reflexion 的反思塞进 context 为什么可能越帮越忙？」** → 注意力稀释 + 情境错配 + 错误归因三重风险。缓解：反思走**检索式**取用（按当前任务相似度取，而不是全塞）、反思也要被验证（归因是否被后续成功证实）、滑窗 + 定期总结。
5. **「为什么不一开始就上多智能体？」** → OpenAI 等团队的工程指南都建议**从单 agent + tools 起步**：多 agent 的调试复杂度、错误归因链、可观测成本都指数上升，单 agent 能覆盖 80% 场景；等任务真出现**天然并行 + 上下文隔离**需求再拆（Day 127 细讲）。
6. **「用框架还是手写 loop？」** → Demo 用 LangChain/LangGraph 快速验证；生产往往**手写状态机**——20 行的显式 loop 比框架黑盒可控得多，状态可持久化、每步可观测、失败可回放。框架的价值是协议与生态（如 MCP、tracing），不是替你决定控制流。
7. **「三范式在 veRL / agentic RL 里对应什么？」**（Week 17 回调）→ rollout 时 agent 的推理策略就是这三范式的某种组合：Planner 输出轨迹骨架、ReAct 逐 turn 采样、失败轨迹 + Reflexion 复盘后**重新 rollout**——训练数据本身就是"反思后重试"的产物。Day 113 说"失败轨迹不能丢"，现在你知道为什么了：**它们是 Reflexion 的燃料**。
8. **「讲一个你设计过/见过的 agent 失败故事。」** → 万能模板：现象（60% 概率在某类任务死循环）→ 归因（observation 无信息增益时模型倾向重复上一步）→ 方案（状态指纹熔断 + 最大步数 + 失败分类重试）→ 数据（死循环率 60%→15%，成本降 40%）。**带数字、有归因、有迭代**，这比"我跑通了 SWE-bench"值钱十倍。
