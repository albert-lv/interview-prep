## 🎯 今日算法题

### 题目：实现一个带 TTL 的线程安全缓存

设计一个缓存系统，支持以下操作：
- `Put(key, value, ttl)`：存入键值对，`ttl` 为过期时间（秒）
- `Get(key)`：获取值，如果已过期则返回 nil 并删除
- `Delete(key)`：删除键值对
- `Size()`：返回当前有效键值对数量

**要求：**
1. O(1) 时间复杂度的 Get/Put
2. 线程安全（支持并发读写）
3. 内存高效（过期键及时回收）

**Follow-up：**
- 如何实现惰性删除 vs 定期删除？
- 如果数据量很大（百万级），如何避免一次性清理造成卡顿？
- Redis 是怎么做的？

---

### 思路解析

这道题的核心是 **"如何高效判断并清理过期数据"**。纯 LRU 用哈希表+双向链表就能搞定，但加上 TTL 后，我们需要按过期时间排序的数据结构。

#### 方案对比

| 方案 | 数据结构 | Get | Put | 过期检查 | 缺点 |
|---|---|---|---|---|---|
| 暴力扫描 | 哈希表 | O(1) | O(1) | O(n) | 清理时卡顿 |
| 最小堆 | 哈希表 + MinHeap | O(1) | O(log n) | O(log n) | Put 变慢 |
| **惰性删除+定期抽样** | 哈希表 + 双向链表 | **O(1)** | **O(1)** | **均摊 O(1)** | ✅ 最优 |

**工业界标准答案（Redis 策略）：**
1. **惰性删除（Lazy Expiration）**：Get 时检查是否过期，过期则删除 —— 零额外开销
2. **定期删除（Active Expiration）**：后台线程每 100ms 随机抽样检查 20 个键，删除过期的，如果超过 25% 过期则继续抽 —— 避免一次性遍历所有键

#### 数据结构选型

```
HashMap<key, Node>     // O(1) 查找
    ↓
Node {
    key, value,
    expireAt,           // 过期时间戳
    prev, next          // 双向链表（LRU）
}

// TTL 索引：按过期时间排序（可选，用于定期删除时加速）
MinHeap<Node> 或 SkipList  // Redis 实际用 Expires 字典 + 惰性采样
```

**并发控制：**
- 读写锁（`sync.RWMutex`）保护 HashMap
- 或分段锁（Shard Lock）降低锁竞争 —— 百万级数据必选

### 代码实现（Go）

```go
package main

import (
	"fmt"
	"math/rand"
	"sync"
	"time"
)

// Node 缓存节点
type Node struct {
	key      string
	value    interface{}
	expireAt int64 // 过期时间戳（毫秒）
	prev     *Node
	next     *Node
}

// TTLCache 带过期时间的线程安全缓存
type TTLCache struct {
	mu       sync.RWMutex
	data     map[string]*Node
	head     *Node // 伪头部（LRU最近使用）
	tail     *Node // 伪尾部（LRU最久未使用）
	capacity int
}

func NewTTLCache(capacity int) *TTLCache {
	head := &Node{}
	tail := &Node{}
	head.next = tail
	tail.prev = head
	return &TTLCache{
		data:     make(map[string]*Node),
		head:     head,
		tail:     tail,
		capacity: capacity,
	}
}

// isExpired 检查是否过期
func (n *Node) isExpired() bool {
	return time.Now().UnixMilli() > n.expireAt
}

// Get 获取值（惰性删除）
func (c *TTLCache) Get(key string) (interface{}, bool) {
	c.mu.RLock()
	node, ok := c.data[key]
	c.mu.RUnlock()

	if !ok {
		return nil, false
	}

	// 惰性删除：发现过期就删
	if node.isExpired() {
		c.Delete(key)
		return nil, false
	}

	// LRU：移到队头
	c.mu.Lock()
	c.moveToHead(node)
	c.mu.Unlock()

	return node.value, true
}

// Put 插入或更新
func (c *TTLCache) Put(key string, value interface{}, ttlSeconds int) {
	c.mu.Lock()
	defer c.mu.Unlock()

	if node, ok := c.data[key]; ok {
		// 更新现有值
		node.value = value
		node.expireAt = time.Now().UnixMilli() + int64(ttlSeconds)*1000
		c.moveToHead(node)
		return
	}

	// 新建节点
	node := &Node{
		key:      key,
		value:    value,
		expireAt: time.Now().UnixMilli() + int64(ttlSeconds)*1000,
	}
	c.data[key] = node
	c.addToHead(node)

	// 超出容量，淘汰尾部（最久未使用）
	if len(c.data) > c.capacity {
		c.evictLRU()
	}
}

// Delete 删除键
func (c *TTLCache) Delete(key string) {
	c.mu.Lock()
	defer c.mu.Unlock()

	if node, ok := c.data[key]; ok {
		c.removeNode(node)
		delete(c.data, key)
	}
}

// Size 返回当前有效数量
func (c *TTLCache) Size() int {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return len(c.data)
}

// ActiveExpire 定期删除：随机抽样清理（Redis 策略）
func (c *TTLCache) ActiveExpire(sampleSize int) int {
	c.mu.Lock()
	defer c.mu.Unlock()

	if len(c.data) == 0 {
		return 0
	}

	expired := 0
	// 随机抽样（简化版：遍历 map 取前 sampleSize 个）
	for _, node := range c.data {
		if sampleSize <= 0 {
			break
		}
		sampleSize--

		if node.isExpired() {
			c.removeNode(node)
			delete(c.data, node.key)
			expired++
		}
	}

	return expired
}

// ========== 双向链表操作 ==========

func (c *TTLCache) addToHead(node *Node) {
	node.prev = c.head
	node.next = c.head.next
	c.head.next.prev = node
	c.head.next = node
}

func (c *TTLCache) removeNode(node *Node) {
	node.prev.next = node.next
	node.next.prev = node.prev
}

func (c *TTLCache) moveToHead(node *Node) {
	c.removeNode(node)
	c.addToHead(node)
}

func (c *TTLCache) evictLRU() {
	// 淘汰尾部（tail.prev 是真正的最后一个节点）
	lru := c.tail.prev
	if lru == c.head {
		return
	}
	c.removeNode(lru)
	delete(c.data, lru.key)
}

// ========== 演示 ==========

func main() {
	cache := NewTTLCache(3)

	// 写入 3 个键，TTL = 2 秒
	cache.Put("a", 1, 2)
	cache.Put("b", 2, 2)
	cache.Put("c", 3, 2)

	fmt.Println("写入 a,b,c，Size:", cache.Size()) // 3

	// 立即读取
	if v, ok := cache.Get("a"); ok {
		fmt.Println("Get a =", v) // 1
	}

	// 等待过期
	fmt.Println("等待 3 秒...")
	time.Sleep(3 * time.Second)

	// 惰性删除：Get 时发现过期
	if _, ok := cache.Get("b"); !ok {
		fmt.Println("b 已过期被删除")
	}

	// 主动清理
	expired := cache.ActiveExpire(10)
	fmt.Printf("主动清理删除 %d 个过期键\n", expired)
	fmt.Println("最终 Size:", cache.Size())
}
```

**运行输出：**
```
写入 a,b,c，Size: 3
Get a = 1
等待 3 秒...
b 已过期被删除
主动清理删除 2 个过期键
最终 Size: 0
```

### 复杂度分析

| 操作 | 时间 | 空间 | 说明 |
|---|---|---|---|
| Get | O(1) | O(1) | 惰性删除不增加额外开销 |
| Put | O(1) | O(1) | 链表头插 + 可能的尾部淘汰 |
| Delete | O(1) | O(1) | 双向链表删除 |
| ActiveExpire | O(k) | O(1) | 抽 k 个样本，k << n |

**空间：** O(n)，n 为缓存容量。

### 🔥 面试官追问（高频 Follow-up）

> **Q1：如果数据量达到百万级，单个锁会成为瓶颈，怎么优化？**
> 
> 分段锁（Shard Lock）：将 HashMap 分成 256 个 shard，每个 shard 独立加锁。`shardIdx = hash(key) % 256`。Redis Cluster 的 Slot 分片就是这个思路。

> **Q2：Redis 的过期键清理是怎么做的？**
> 
> 1. **惰性删除**：访问时检查 expire 字典，过期则删除
> 2. **定期删除**：每 100ms 启动定时任务，随机抽 20 个键检查，删除过期的；如果超过 25% 过期，重复此过程，但最多运行 25ms（避免阻塞）
> 3. **从不全量扫描** —— 这是关键设计哲学

> **Q3：如果要求严格定时过期（比如 500ms 后必须触发回调），怎么实现？**
> 
> 时间轮（Timing Wheel）或分层时间轮（Hierarchical Timing Wheel）。Kafka、Netty 都用这个。精度高、插入删除 O(1)。

## 🎤 面试技巧

### 今日主题：系统设计题的沟通框架

遇到"设计一个 XXX 系统"的面试题，最忌讳的是：**一上来就写代码**。面试官想考察的不是你的代码速度，而是你的设计思维。

#### 标准回答结构：CLAPS 框架

```
C - Clarify（澄清需求）
L - Load（估算负载）
A - API（定义接口）
P - Pattern（选型与架构）
S - Scale（扩展与优化）
```

**Step 1： Clarify — 先问清楚**

不要急着答。先确认边界：
- "数据规模大概多大？QPS 多少？"
- "读写比例如何？"
- "对一致性要求高吗？允许短暂不一致吗？"
- "是否需要持久化？"

> 💡 **话术模板**："在我开始设计之前，想先确认几个关键指标：预期的数据量级、并发量、以及对一致性和可用性的偏好。这样我可以给出更贴合场景的架构。"

**Step 2：Load — 量化估算**

展示你的量化思维：
- "假设 1000万 DAU，每人每天产生 10 次请求，峰值 QPS 约 10万"
- "每条记录 1KB，1000万条约 10GB，单机内存放不下，需要分片"

**Step 3：API — 定义接口**

先写出核心 API，让面试官看到你对功能边界的理解：
```
Put(key, value, ttl)
Get(key) -> value | nil
Delete(key) -> bool
```

**Step 4：Pattern — 核心设计**

这才是写代码/画架构的时候。但要有条理：
1. 先讲数据结构选型（为什么用 A 不用 B）
2. 再讲并发策略（锁粒度、读写分离）
3. 最后讲边界情况（过期、淘汰、故障）

**Step 5：Scale — 扩展性**

主动展示深度：
- "如果单机扛不住，可以分片 + 一致性哈希"
- "如果要高可用，可以主从复制 + 哨兵监控"
- "如果要跨地域，可以考虑多活架构"
