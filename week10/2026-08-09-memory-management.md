## 二、核心知识：内存管理

### 2.1 物理内存 vs 虚拟内存

| 维度 | 物理内存 | 虚拟内存 |
|------|---------|---------|
| 地址空间 | 物理地址（RAM 真实地址） | 逻辑地址（每个进程独立） |
| 隔离性 | 无隔离，直接访问硬件 | 进程间完全隔离 |
| 容量限制 | 受物理 RAM 大小限制 | 可远大于物理内存（磁盘 swap 扩展） |
| 分配粒度 | 按字节/页 | 按虚拟页 |

**为什么要虚拟内存？**
1. **隔离性** — 进程 A 无法直接访问进程 B 的内存
2. **简化编程** — 每个进程都认为自己独占整个地址空间
3. **内存超载** — 运行总虚拟内存 > 物理内存的程序
4. **共享与保护** — 代码段共享（如 libc），敏感区域只读/不可执行

### 2.2 分页机制（Paging）

**核心思想**: 将虚拟地址空间和物理内存都切成固定大小的**页**（Page，通常 4KB）。

```
虚拟地址 [页号 | 页内偏移]
            ↓         ↓
       页表查询    直接透传
            ↓         ↓
物理地址 [页框号 | 页内偏移]
```

**页表（Page Table）结构**：
- 每个进程一张页表（多级页表优化空间）
- 页表项（PTE）包含：物理页框号 + 标志位（存在位、读写权限、脏位、访问位）

**多级页表（x86-64 为例）**：
```
虚拟地址: [PML4 | PDPT | PD | PT | Offset]
            9bit  9bit   9bit  9bit  12bit
```
- 4 级页表遍历：CR3 → PML4 → PDPT → PD → PT → 物理页
- 每级 512 项 × 8B = 4KB，刚好一页
- **问题**: 每次内存访问需要 4 次内存读取（页表也在内存中）

### 2.3 TLB — 翻译后备缓冲器

**问题**: 页表在内存中，查页表本身也要访问内存 → 每次访存变成 5 次内存访问（4 次查表 + 1 次真正访存），太慢。

**TLB 解法**: CPU 内部的**高速缓存**，缓存近期用过的「虚拟页号 → 物理页框」映射。

| 特性 | 说明 |
|------|------|
| 位置 | CPU 芯片内（L1 Cache 级别） |
| 容量 | 通常 64-1024 项 |
| 命中率 | > 99%（程序访问具有局部性） |
| 失效处理 | TLB miss → 硬件/软件遍历页表 → 回填 TLB |
| 刷新时机 | 进程切换时（或 ASID 区分进程避免刷新） |

**TLB 与 Cache 的协作**：
```
CPU 发出虚拟地址
    ↓
TLB 查找（并行）
    ↓
命中? → 直接得到物理地址 → 查 Cache/内存
未命中? → 遍历页表 → 回填 TLB → 继续
```

### 2.4 页面置换算法

当物理内存满了，需要把某些页换出到磁盘（swap），腾出空间。

| 算法 | 思想 | 特点 |
|------|------|------|
| **OPT** | 换出最久不被访问的页 | 理论最优，不可实现（需要预知未来） |
| **FIFO** | 先来的先走 | 简单，但有 Belady 异常（页框增多反而缺页增多） |
| **LRU** | 最近最少使用 | 接近 OPT，需要精确记录访问时间 |
| **Clock（时钟/二次机会）** | LRU 近似，用访问位 | 环形链表 + 扫描，实现高效 |
| **LFU** | 最少使用次数 | 容易受历史影响，不常用 |

**Linux 实际策略**: 改进的 Clock 算法（LRU 近似）+ Active/Inactive 双链表。

### 2.5 内存分配策略

**堆内存分配**（用户空间）：

| 分配器 | 策略 | 适用场景 |
|--------|------|---------|
| ptmalloc (glibc) | 分箱 + 合并 | 通用，但多线程有锁竞争 |
| jemalloc (Facebook) | 按大小分级 + 线程缓存 | 多线程、小块分配频繁 |
| tcmalloc (Google) | 线程本地缓存 + 中心堆 | 高并发、小块分配 |
| mimalloc (Microsoft) | 空闲列表分段 | 极致性能、安全性 |

**内核内存分配**（Linux slab）：
- **Slab 分配器**: 为常用对象（task_struct、inode 等）预分配对象池，避免频繁分配/释放
- **Slub（现代默认）**: Slab 的简化版，减少元数据开销

### 2.6 内存碎片

| 类型 | 原因 | 解决 |
|------|------|------|
| **外部碎片** | 分配/释放不连续，空闲块分散 | 分页（固定大小页框）天然避免 |
| **内部碎片** | 分配的页 > 实际需求，页内浪费 | 多级页表、段页式（已淘汰） |

## 三、面试高频题速记

### Q1: 什么是虚拟内存？为什么要用虚拟内存？

**回答框架**（定义 → 核心机制 → 三大好处）：

> 虚拟内存是操作系统为每个进程提供的**独立、连续、超大**的地址空间抽象。
> 
> 核心机制是**分页**：CPU 的 MMU 将虚拟地址通过页表转换为物理地址，配合 TLB 加速翻译。
> 
> 三大核心价值：
> 1. **隔离性** — 进程互不可见，一个进程崩溃不影响其他进程
> 2. **简化编程** — 每个进程都认为自己独占完整地址空间，从 0 开始编址
> 3. **内存超载** — 总虚拟内存可以远大于物理内存，不活跃页换出到磁盘 swap

### Q2: 页表有多大？多级页表解决了什么问题？

> 如果单级页表：64 位系统、4KB 页 → 页表项数 = 2⁶⁴ / 2¹² = 2⁵² 项，每项 8B → **页表占 32 PB**，不可能。
> 
> **多级页表**按需分配：只给实际用到的虚拟地址空间建立页表。比如程序只用了 1GB 虚拟内存，只需要 1GB / 4KB = 262K 个 PTE，多级后仅需几页。
> 
> 代价：TLB miss 时需要多次内存访问遍历页表。

### Q3: TLB 是什么？如果 TLB miss 会发生什么？

> TLB 是 CPU 内部的高速缓存，存储「虚拟页号 → 物理页框」映射。
> 
> **TLB hit**: 直接翻译，近乎零开销。
> **TLB miss**: CPU 需要遍历页表（硬件遍历或操作系统处理），找到映射后回填 TLB，再继续执行。
> 
> 优化手段：
> - **大页（Huge Page）**: 2MB/1GB 大页减少页表项数，提升 TLB 覆盖率
> - **ASID（Address Space ID）**: 进程切换时不刷新 TLB，不同进程用 ASID 区分

### Q4: 进程切换时 TLB 怎么办？

> 有两种策略：
> 1. **刷新 TLB** — 简单，但代价高（切换后大量 TLB miss）
> 2. **ASID 标记** — TLB 项带上进程 ID，切换时不刷新，只匹配当前 ASID 的项
> 
> 现代 CPU（x86 PCID、ARM ASID）都采用方案 2。

### Q5: 页面置换算法你知道哪些？Linux 用什么？

> 经典算法：OPT（理论最优）、FIFO（有 Belady 异常）、LRU（接近最优）、Clock（LRU 近似，实现简单）。
> 
> Linux 使用改进的 LRU 近似算法：
> - **Active 链表** — 近期访问过的页
> - **Inactive 链表** — 疑似可回收的页
> - 页在 Active 和 Inactive 之间移动，Inactive 尾部的页被回收
> - 支持 swap 和文件页缓存的统一回收（kswapd 后台线程）

### Q6: malloc 分配的内存，操作系统立即分配物理页吗？

> **不一定** — Linux 采用**按需分页（Demand Paging）**：
> 1. `malloc` → 只分配虚拟地址空间，页表项标记为「不存在」
> 2. 第一次访问该页 → 触发**缺页异常（Page Fault）**
> 3. 操作系统分配物理页框，建立页表映射，恢复执行
> 
> 这种延迟分配节省了物理内存，但首次访问有 Page Fault 开销。
