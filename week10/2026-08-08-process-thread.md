## 今日算法题

### 1226. 哲学家就餐问题（Dining Philosophers）

**题目描述**

5 个哲学家围坐在一张圆桌前，每人左右各有一根筷子。哲学家只有两种状态：**思考** 或 **吃饭**。吃饭时必须同时拿到左右两根筷子。请设计一个并发算法，让哲学家们交替思考和吃饭，且**不会死锁**、**不会饿死**。

LeetCode 原题给出了 5 个线程（对应 5 个哲学家）并发调用 `wantsToEat(philosopher, pickLeftFork, pickRightFork, eat, putLeftFork, putRightFork)`，你需要实现哲学家拿筷子的逻辑。

**核心考点**

- 死锁产生的四个条件（互斥、占有等待、不可剥夺、循环等待）
- 破坏死锁条件的策略
- 资源分配的顺序化（破除循环等待）
- 信号量 / 互斥锁的合理使用

**解题思路**

经典的死锁预防有三种主流策略：

1. **限制同时进餐人数**（资源剥夺思路）：最多允许 4 个哲学家同时尝试拿筷子，这样至少有一人一定能拿到两根筷子吃完放下，打破循环等待。
2. **编号策略**（打破循环等待）：给筷子编号，要求每个哲学家总是先拿编号小的筷子，再拿编号大的。最后一个哲学家（5号）先拿右边（1号筷子，编号小）再拿左边（5号筷子，编号大），从而破除循环等待链。
3. **互斥锁保护**（简单粗暴）：用一个全局锁保护"拿筷子"的动作，但并发度几乎为 1，不推荐。

面试中最优雅、最常考的是 **策略 2：编号法**。代码简洁，无需额外限制并发数，且不会饿死。

**代码示例（策略 2：编号法）**

```python
import threading

class DiningPhilosophers:
    def __init__(self):
        # 5 把筷子，每把一个锁
        self.forks = [threading.Lock() for _ in range(5)]

    def wantsToEat(self,
                   philosopher: int,
                   pickLeftFork: 'Callable[[], None]',
                   pickRightFork: 'Callable[[], None]',
                   eat: 'Callable[[], None]',
                   putLeftFork: 'Callable[[], None]',
                   putRightFork: 'Callable[[], None]') -> None:
        
        left = philosopher               # 左手边筷子编号
        right = (philosopher + 1) % 5    # 右手边筷子编号
        
        # 关键：总是先拿编号小的筷子，打破循环等待
        first, second = (left, right) if left < right else (right, left)
        
        with self.forks[first]:
            with self.forks[second]:
                pickLeftFork()
                pickRightFork()
                eat()
                putLeftFork()
                putRightFork()
```

**复杂度分析**

- 时间复杂度：O(1) — 每次操作固定获取两把锁
- 空间复杂度：O(1) — 仅需常数额外空间
- 并发度：理论最高可达 2 个哲学家同时吃饭（5把筷子最多支持 2 人各持2把）

**拓展思考**

- 如果要求"公平性"（防止某个哲学家长期拿不到筷子/饿死），编号法天然保证公平吗？**不保证**。公平需要引入队列或令牌机制。
- 策略1（限制人数为4）如何用信号量实现？提示：`sem = threading.Semaphore(4)`，每个哲学家进场先 `acquire`。
- 策略3（互斥锁）的 TPS 是多少？几乎是串行，5 个哲学家并发等于 1 个在吃饭。

## 面试技巧

### 🎯 OS 高频面试题速记

| 问题 | 一句话核心 | 延伸点 |
|------|-----------|--------|
| 进程 vs 线程 | 进程是资源分配单位，线程是调度执行单位 | 切换开销、通信方式、共享资源 |
| 进程状态转换 | 就绪 → 运行 → 阻塞 → 就绪 | 调度器触发、中断、系统调用 |
| 协程 vs 线程 | 协程是用户态轻量线程，由程序调度 | Go goroutine、Python asyncio、无锁切换 |
| 进程间通信 | 管道、消息队列、共享内存、信号、Socket | 共享内存最快，但需要同步机制 |
| 线程同步机制 | 互斥锁、信号量、条件变量、读写锁 | 自旋锁 vs 互斥锁适用场景 |

### 🗣️ 答题表达框架：STAR 变体（OS 版）

回答 OS 概念题时，按这个结构组织语言，面试官听起来会很舒服：

1. **定义先行**："首先，XX 是...（一句话定义）"
2. **对比差异**："它与 YY 的核心区别在于...（最多列 3 点）"
3. **场景落地**："在实际工程中，典型的应用场景是..."
4. **踩坑预警**："这里有一个常见的误区/坑点是..."

**示例：进程 vs 线程**

> "首先，进程是操作系统进行资源分配和调度的基本单位，拥有独立的地址空间；线程是 CPU 调度的基本单位，共享进程的地址空间。
>
> 核心区别有三点：一是**资源占用**，进程切换需要切换页表、刷新 TLB，开销远大于线程；二是**通信方式**，线程间可以直接读写共享变量，进程间需要用 IPC；三是**崩溃影响**，一个线程崩溃可能导致整个进程退出，而进程间相互隔离。
>
> 实际工程中，比如一个 Web 服务器，通常采用**多进程+多线程**模型：多个 worker 进程监听不同端口或做隔离，每个进程内再用线程池处理请求。
>
> 一个常见坑点是：多线程共享内存虽然快，但如果对临界区保护不当，会出现数据竞争。所以必须用锁或原子操作保护。"

### ⚡ 快速判断：这道题在考什么？

OS 面试题往往不是考"你会不会背"，而是考你能不能**把概念和工程场景挂钩**。遇到概念题，快速问自己三个问题：

1. **为什么要设计这个机制？**（解决了什么问题）
2. **代价是什么？**（时间、空间、复杂度）
3. **工程上怎么选的？**（什么场景用 A，什么场景用 B）

比如面试官问"select/poll/epoll 区别"，不要只背定义。要讲清楚：
- 为什么需要 epoll？（fd 多了之后 select 的 O(n) 轮询太慢）
- 代价是什么？（epoll 需要内核维护红黑树+就绪链表，内存占用大一点）
- 工程怎么选？（高并发长连接用 epoll，少量 fd 用 select 也够）
