## 1. 今日算法题

### 题目：滑动窗口最大值（Sliding Window Maximum）

**题目描述：**
给你一个整数数组 `nums`，有一个大小为 `k` 的滑动窗口从数组的最左侧移动到最右侧。你只可以看到在滑动窗口内的 `k` 个数字。滑动窗口每次只向右移动一位。

返回滑动窗口中的最大值。

**示例：**
```
输入: nums = [1,3,-1,-3,5,3,6,7], k = 3
输出: [3,3,5,5,6,7]
解释:
滑动窗口的位置                最大值
---------------               -----
[1  3  -1] -3  5  3  6  7     3
 1 [3  -1  -3] 5  3  6  7     3
 1  3 [-1  -3  5] 3  6  7     5
 1  3  -1 [-3  5  3] 6  7     5
 1  3  -1  -3 [5  3  6] 7     6
 1  3  -1  -3  5 [3  6  7]    7
```

**为什么选这道题：**
TCP 可靠传输的核心机制之一就是**滑动窗口（Sliding Window）**。理解滑动窗口的数据结构实现，对掌握 TCP 流量控制、拥塞控制有直接的认知关联。这道题是单调队列的经典应用，也是面试极高频题。

---

### 解题思路

**核心思想：单调递减队列**

TCP 的滑动窗口本质上是在维护一个"有效数据范围"，并在这个范围内做决策。这道题要求 O(n) 时间复杂度，不能用暴力 O(n×k) 的解法。

单调队列的关键洞察：
1. **队列维护窗口内元素的「候选最大值」** —— 按值递减排列
2. **队首永远是当前窗口的最大值**
3. **新元素入队时，从队尾弹出所有比它小的元素**（这些元素永无出头之日）
4. **队首元素滑出窗口时，弹出队首**

这和 TCP 的滑动窗口很像：窗口在移动，我们需要在 O(1) 时间内知道窗口内的状态。

**TCP 联想（面试加分点）：**
- TCP 的**发送窗口** = min(拥塞窗口 cwnd, 接收窗口 rwnd)
- 窗口内分成四段：已发送已确认 | 已发送未确认 | 允许发送但尚未发送 | 不允许发送
- 滑动窗口协议（Go-Back-N vs 选择性重传）本质上是在做空间换时间的优化

---

### 代码实现（Go）

```go
func maxSlidingWindow(nums []int, k int) []int {
    n := len(nums)
    if n == 0 || k == 0 {
        return []int{}
    }
    
    result := make([]int, 0, n-k+1)
    // deque 存储的是下标，而非值，方便判断元素是否滑出窗口
    deque := make([]int, 0)
    
    for i := 0; i < n; i++ {
        // 1. 移除队尾所有小于当前值的元素（维护单调递减）
        for len(deque) > 0 && nums[deque[len(deque)-1]] <= nums[i] {
            deque = deque[:len(deque)-1]
        }
        
        // 2. 当前元素入队
        deque = append(deque, i)
        
        // 3. 队首元素滑出窗口，移除
        if deque[0] <= i-k {
            deque = deque[1:]
        }
        
        // 4. 窗口形成后，队首即为最大值
        if i >= k-1 {
            result = append(result, nums[deque[0]])
        }
    }
    
    return result
}
```

### 复杂度分析

| 指标 | 复杂度 | 说明 |
|------|--------|------|
| 时间 | O(n) | 每个元素最多入队一次、出队一次 |
| 空间 | O(k) | 队列最多存储 k 个元素的下标 |

**面试常追问：**
- "为什么不能直接堆？" → 堆删除非堆顶元素是 O(k)，滑动窗口需要移除「过期」元素。
- "单调队列和单调栈的区别？" → 队列两端都可操作，栈只能栈顶；滑动窗口需要队首出队。
- "如果题目改成求窗口内第 K 大？" → 需要平衡树/双堆，复杂度上升到 O(n log k)。

### 🔥 TCP 三次握手与四次挥手（面试必考，必须手绘）

**三次握手（建立连接）：**
```
客户端                    服务端
  |    SYN=1, seq=x       |
  | --------------------> |  （第一次：客户端请求建立连接）
  |                       |
  |  SYN=1, ACK=1, seq=y, |
  |      ack=x+1          |
  | <-------------------- |  （第二次：服务端同意，并请求建立反向连接）
  |                       |
  |    ACK=1, seq=x+1,    |
  |      ack=y+1          |
  | --------------------> |  （第三次：客户端确认，连接建立）
```

**为什么是三次？**
> "两次不够，四次多余。"

- **两次的问题**：客户端发 SYN 后，服务端回 SYN+ACK，如果只有两次，服务端无法确认自己的 SYN 被客户端收到了。如果服务端 SYN 在网络中丢失，服务端会以为连接已建立，客户端却认为没建立 → **半开连接，资源泄漏**。
- **四次没必要**：三次已经做到了「双方都能确认对方收发能力正常」，第四次握手合并进了第三次（ACK 同时确认了对方的 SYN）。

**四次挥手（断开连接）：**
```
客户端                    服务端
  |    FIN=1, seq=u       |
  | --------------------> |  （第一次：客户端数据发完了）
  |                       |
  |    ACK=1, seq=v,      |
  |      ack=u+1          |
  | <-------------------- |  （第二次：服务端确认，但可能还有数据要发）
  |                       |
  |    [服务端继续发送数据]  |
  |                       |
  |    FIN=1, seq=w,      |
  |      ack=u+1          |
  | <-------------------- |  （第三次：服务端也发完了）
  |                       |
  |    ACK=1, seq=u+1,    |
  |      ack=w+1          |
  | --------------------> |  （第四次：客户端确认）
  |                       |
  |    TIME_WAIT(2MSL)    |  （等待确保最后一个 ACK 被对方收到）
```

**为什么是四次？**
> "因为 TCP 是全双工的，两个方向要分别关闭。"

- 客户端发 FIN → 只表示「我不再发数据了」，但我还可以收
- 服务端可能还有数据没发完，所以不能立刻回 FIN
- 必须等服务端也发完数据，再发 FIN
- 所以中间多了一次「ACK 确认 + 等待数据发完 + 再发 FIN」的过程

**TIME_WAIT 为什么 2MSL？**
- MSL = Maximum Segment Lifetime，报文最大生存时间（Linux 默认 60s，所以 TIME_WAIT 120s）
- **原因 1**：确保最后一个 ACK 能被对方收到。如果 ACK 丢了，服务端会重发 FIN，客户端在 2MSL 内能收到并重发 ACK。
- **原因 2**：防止「已失效的连接请求报文」出现在本连接中。2MSL 后，网络中所有旧的报文都死透了，不会干扰新连接。

### 🔥 TCP 滑动窗口与流量控制

**发送窗口 = min(拥塞窗口 cwnd, 接收窗口 rwnd)**

```
        已发送已确认 | 已发送未确认 | 可发送 | 不可发送
        <---------->|<----------->|<----->|<-------->
                     ↑              ↑
                   已发送未确认首    允许发送但未发送首
```

**面试表达模板：**
> "TCP 的流量控制通过滑动窗口实现。发送方维护一个发送窗口，大小由接收方的接收窗口（rwnd）和网络的拥塞窗口（cwnd）共同决定，取两者较小值。窗口分为四个区域：已发送已确认、已发送未确认、允许发送但尚未发送、暂不允许发送。已发送未确认的区域需要等待 ACK，如果超时则重传。"

---

### 🔥 TCP 拥塞控制：慢启动 + 拥塞避免 + 快重传 + 快恢复

```
拥塞窗口 cwnd
    ↑
    │      ┌─────────┐
    │     /  拥塞避免  \        ← 线性增长，+1/cwnd per ACK
    │    /   (线性增长)  \
    │   /                \
    │  /                  \
    │ /   ┌───┐            \
    │/   /     \            \
    │   / 慢启动 \            \
    │  / (指数增长)\            \
    │ /             \            \
    └──────────────────────────────→ 时间
      ↑           ↑
    慢启动阈值    拥塞窗口阈值
    ssthresh
```

**慢启动（Slow Start）：**
- 初始 cwnd = 1 MSS（有些实现是 2/4/10 MSS）
- 每收到一个 ACK，cwnd += 1 MSS
- 指数增长：1 → 2 → 4 → 8 → ...

**拥塞避免（Congestion Avoidance）：**
- 当 cwnd >= ssthresh，进入线性增长
- 每 RTT，cwnd += 1 MSS
- 线性增长更保守，避免网络拥塞

**快重传（Fast Retransmit）：**
- 收到 3 个重复 ACK → 立刻重传，不等超时
- 不用等 RTO（Retransmission Timeout）

**快恢复（Fast Recovery）：**
- 收到 3 个重复 ACK → ssthresh = cwnd / 2，cwnd = ssthresh + 3
- 然后线性增长（不是慢启动的指数增长）
- 避免从 1 开始重新慢启动，更高效

**面试速记口诀：**
> "慢启动指数涨，到阈值变线性。三个 dup ACK 快重传，ssthresh 砍半进快恢复。"

### 🔥 TCP vs UDP 对比（面试高频速记表）

| 特性 | TCP | UDP |
|------|-----|-----|
| **连接** | 面向连接（三次握手） | 无连接 |
| **可靠性** | 可靠传输（ACK、重传、序号） | 不可靠，尽最大努力交付 |
| **顺序性** | 保证数据有序到达 | 不保证顺序 |
| **流量控制** | 有（滑动窗口） | 无 |
| **拥塞控制** | 有（慢启动/拥塞避免） | 无 |
| **头部开销** | 20 字节 | 8 字节 |
| **传输效率** | 较低（建立连接、确认、重传开销） | 极高 |
| **应用场景** | HTTP/HTTPS、FTP、SMTP、数据库 | DNS、视频直播、在线游戏、VoIP、QUIC |

**面试加分点 —— UDP 为什么在某些场景优于 TCP？**
1. **实时性要求高的场景**（直播、游戏）：TCP 的拥塞控制会导致卡顿，UDP 丢包就丢了，下一帧更重要
2. **DNS**：查询包极小，一次往返就够了，TCP 三次握手反而慢
3. **QUIC（HTTP/3）**：基于 UDP 实现，解决 TCP 队头阻塞问题
4. **内网/可控网络**：丢包率低，UDP 的简单性反而是优势

### 🔥 TCP 队头阻塞与 HTTP/2、HTTP/3

**TCP 队头阻塞（Head-of-Line Blocking）：**
- TCP 保证有序，如果第 3 个包丢了，第 4、5、6 个包即使到了也必须等第 3 个包重传
- 应用层无法处理后续数据

**HTTP/2 的多路复用 + TCP 队头阻塞：**
- HTTP/2 在一个 TCP 连接上 multiplex 多个 stream
- 但底层还是一个 TCP 连接，TCP 层面的队头阻塞依然存在
- 一个 stream 的数据包丢失，所有 stream 都要等

**HTTP/3 的解决方案（QUIC）：**
- QUIC 基于 UDP，在应用层实现可靠传输
- 每个 stream 有独立的序号和重传机制
- 一个 stream 丢包，不影响其他 stream
- 连接迁移：IP 变了也能保持连接（TCP 四元组变化 = 连接断开）

**面试表达：**
> "HTTP/2 虽然支持多路复用，但底层 TCP 的队头阻塞问题没解决。HTTP/3 改用 QUIC 协议，基于 UDP 在应用层实现可靠传输，每个 stream 独立管理序号和重传，彻底解决了队头阻塞，还支持连接迁移。"

### 🔥 高频面试题速答

**Q1: TCP 粘包/拆包怎么解决？**
> "TCP 是面向字节流的，没有消息边界，所以会出现粘包。解决方案：1）固定长度消息；2）分隔符（如换行符，但消息内容不能含分隔符）；3）长度前缀（最常用，先读 4 字节长度，再读对应长度数据）。"

**Q2: 为什么 SYN/FIN 各消耗一个序号？**
> "SYN 和 FIN 都需要被确认（ACK），而 TCP 的确认机制是按序号进行的。如果没有消耗序号，ACK 就不知道该确认什么。SYN 占 1 个序号，FIN 也占 1 个序号，这样对方的 ACK 才能明确确认收到了这个控制报文。"

**Q3: CLOSE_WAIT 状态过多怎么排查？**
> "CLOSE_WAIT 是被动关闭方收到 FIN 后进入的状态，表示『我知道你要关了，但我还有数据要发』。如果大量连接卡在 CLOSE_WAIT，通常是应用程序没有调用 close()。排查：1）netstat -n | grep CLOSE_WAIT | wc -l 看数量；2）用 lsof -p <pid> 看进程打开的文件描述符；3）检查代码里 socket 是否在异常分支漏了 close。"

**Q4: TIME_WAIT 过多怎么解决？**
> "TIME_WAIT 是主动关闭方最后进入的状态，持续 2MSL。大量 TIME_WAIT 会占用端口（默认端口范围 32768-61000 约 2.8w 个）。解决方案：1）开启 tcp_tw_reuse（允许复用 TIME_WAIT 端口给新连接，需开启 tcp_timestamps）；2）调低 tcp_fin_timeout；3）改用长连接减少短连接频率；4）让客户端主动关闭连接（变成客户端有 TIME_WAIT）。"
