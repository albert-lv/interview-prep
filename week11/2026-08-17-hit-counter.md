## 🎯 今日算法题：设计点击量统计器（Design Hit Counter）

### 题目描述

设计一个点击量统计器，支持以下操作：

- `hit(timestamp)` — 记录在 `timestamp` 时刻发生了一次点击
- `getHits(timestamp)` — 返回过去 **300 秒**（即 `timestamp - 299` 到 `timestamp`）内的点击次数

约束：
- 时间戳单调递增（`timestamp` 按调用顺序非递减）
- 需要高效支持高频调用

> 💡 这题是 **滑动时间窗口** 的经典模型，与限流器、监控系统的计数模块同根同源。

---

### 解题思路

#### 方法：循环数组（最优解）

核心观察：
- 只需要保留最近 300 秒的数据，更早的数据可以丢弃
- 用大小为 300 的循环数组，每个槽位记录 `(timestamp, count)`
- 均摊 **O(1)** 时间复杂度，**O(300)** = **O(1)** 空间

**为什么不用普通队列？**
- 队列方案需要清理过期元素，最坏情况下一次 `getHits` 要弹出大量旧数据，均摊虽然 O(1)，但存在尖峰
- 循环数组直接覆盖，每次操作严格 O(1)，性能更稳定

**循环数组的核心逻辑：**
1. `idx = timestamp % 300` 定位槽位
2. 如果该槽位的时间戳不是当前时间戳，说明是旧数据，直接覆盖
3. 如果是同一时间戳，累加计数

---

### 代码实现

```python
class HitCounter:
    def __init__(self):
        # 300 个槽位，每个槽位存 [timestamp, count]
        self.data = [[0, 0] for _ in range(300)]

    def hit(self, timestamp: int) -> None:
        idx = timestamp % 300
        if self.data[idx][0] != timestamp:
            # 该槽位是旧数据，覆盖
            self.data[idx] = [timestamp, 1]
        else:
            # 同一时间戳，累加
            self.data[idx][1] += 1

    def getHits(self, timestamp: int) -> int:
        total = 0
        for ts, cnt in self.data:
            # 只统计在 [timestamp - 299, timestamp] 范围内的点击
            if ts > 0 and timestamp - ts < 300:
                total += cnt
        return total
```

```java
public class HitCounter {
    private int[][] data; // [timestamp, count]

    public HitCounter() {
        data = new int[300][2];
    }

    public void hit(int timestamp) {
        int idx = timestamp % 300;
        if (data[idx][0] != timestamp) {
            data[idx][0] = timestamp;
            data[idx][1] = 1;
        } else {
            data[idx][1]++;
        }
    }

    public int getHits(int timestamp) {
        int total = 0;
        for (int[] slot : data) {
            if (slot[0] > 0 && timestamp - slot[0] < 300) {
                total += slot[1];
            }
        }
        return total;
    }
}
```

---

### 复杂度分析

| 操作 | 时间 | 空间 |
|------|------|------|
| `hit()` | **O(1)** | O(1) |
| `getHits()` | **O(300)** = **O(1)** | O(1) |

> ⚠️ `getHits` 是 O(300) 不是 O(n)，300 是常数。

### 🔥 Follow-up 升级：多机分布式 Hit Counter

**面试官**：如果系统部署在 10 台机器上，怎么统计全局 QPS？

**回答框架**：

1. **本地聚合** — 每台机器维护自己的计数器，定期（如 1 秒）将本地统计推送到中心服务
2. **中心聚合** — 中心服务收集各节点数据，汇总计算全局 QPS
3. **时间对齐** — 所有节点使用 NTP 同步时钟，或按固定时间窗口（如每整秒）上报，避免边界误差
4. **近似 acceptable** — 监控场景允许少量误差，可用 Redis HyperLogLog 做 UV 统计，用 Redis Counter 做 PV 统计

> 💡 面试时说清楚「监控场景可以近似，交易场景必须精确」，体现你对不同业务场景的理解。

---

### 💬 面试官爱问的延伸

| 问题 | 一句话速答 |
|------|-----------|
| 如果时间戳不是单调递增的？ | 需要有序结构（TreeMap）或排序后处理，复杂度上升 |
| 如果需要查询任意时间范围，不是固定的 300 秒？ | 用树状数组或线段树，支持 O(log n) 范围查询 |
| 如果 hit 调用量是 10万/秒？ | 循环数组方案完全能扛，单次操作 O(1)，无锁可进一步优化 |
| 分布式场景下如何保证精确？ | 每台机器本地计数 + 定时上报 + 中心汇总；精确场景用 Redis 原子计数 |

## 🎤 面试技巧：数据库分库分表策略深度解析

> 分库分表是数据库扛不住压力时的终极武器，也是面试中最爱考的「兜底方案」。

---

### 1. 什么时候该分库分表？

**单表数据量阈值**（经验值）：
- MySQL 单表 **500万~1000万行** 或 **10GB+** 时，考虑拆分
- 不是绝对标准，取决于查询复杂度、索引设计、硬件配置

**典型症状**：
- 查询变慢，EXPLAIN 出现大量 rows scanned
- 索引无法完全加载到内存，磁盘 IO 飙升
- 单库连接数打满，频繁出现 `Too many connections`
- 单点故障风险高，备份恢复时间太长

> 💡 面试官爱问：你们公司什么时候拆的？答具体数据比背理论有说服力。

---

### 2. 垂直拆分 vs 水平拆分

| 维度 | 垂直拆分 | 水平拆分 |
|------|---------|---------|
| **拆分依据** | 按列（字段）拆分 | 按行（数据）拆分 |
| **典型场景** | 用户表 50 个字段，拆成 `user_basic` + `user_profile` + `user_auth` | 用户表 1 亿行，拆成 `user_0` ~ `user_1023` |
| **解决什么问题** | 单表字段过多、冷热数据分离、权限隔离 | 单表数据量过大、单库性能瓶颈 |
| **复杂度** | 低（业务层改表名即可） | 高（需要路由、分布式事务） |

**垂直拆分示例**：
```sql
-- 拆分前：user 表 50+ 字段
user(id, name, avatar, phone, email, address, id_card, preference, ...)

-- 拆分后：
user_basic(id, name, avatar, phone)      -- 高频访问
user_profile(id, address, preference)    -- 低频访问
user_auth(id, email, id_card, password)  -- 敏感数据，单独权限控制
```

**水平拆分示例**：
```sql
-- 按 user_id % 1024 拆分
user_0: id in (0, 1024, 2048, ...)
user_1: id in (1, 1025, 2049, ...)
...
user_1023
```

### 3. 分片键选择：决定拆分成败的关键

**好的分片键标准**：
1. **高频查询条件** — 80% 的查询带这个条件
2. **数据分布均匀** — 避免热点（如按时间分片导致最新分片被打爆）
3. **业务无关** — 最好是内部 ID，不因业务规则变化而失效

**常见分片键策略**：

| 策略 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| **哈希分片** | `shard = hash(user_id) % N` | 分布均匀，简单 | 扩容需迁移大量数据（一致性哈希可缓解） |
| **范围分片** | `shard = time / 7`（按周） | 支持范围查询，扩容简单（加新分片即可） | 容易热点（最新分片压力大） |
| **列表分片** | 按地区：`beijing` → shard_0, `shanghai` → shard_1 | 符合业务逻辑 | 分布不均匀，某地区数据量大时倾斜 |
| **组合分片** | 先按时间分，再哈希 | 兼顾范围和均匀 | 复杂度最高 |

> 🔥 **面试高频坑**：用自增 ID 做分片键 → 数据永远集中在最后一个分片（热点）。用 UUID 做分片键 → 查询时必须带 UUID，无法按用户ID查。

---

### 4. 全局 ID 生成

分库分表后，自增 ID 会冲突，需要全局唯一 ID。

**方案对比**（Day 49 详细讲过 Snowflake，此处速查）：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Snowflake** | 趋势递增，高性能 | 依赖时钟，时钟回拨会乱 |
| **号段模式**（美团 Leaf） | 稳定可靠，DB 压力小 | 需要维护号段表 |
| **Redis incr** | 简单 | 单点瓶颈，非趋势递增 |
| **UUID** | 最简单 | 无序，索引性能差，太长 |

**推荐**：高并发用 Snowflake + 号段模式兜底；一般场景用号段模式足够。

---

### 5. 跨分片查询的四种解法

分库分表后，不带分片键的查询就是噩梦。

| 场景 | 解决方案 |
|------|---------|
| **分页查询** | 各分片取 Top N，内存归并排序；或用 ES 做搜索引擎 |
| **聚合查询（SUM/COUNT）** | 各分片计算，汇总再聚合；或预计算 + 离线数仓 |
| **JOIN 查询** | 避免跨库 JOIN；冗余字段（反范式）；或应用层组装 |
| **全局表** | 小表（如配置表）在每个分片复制一份，避免跨库查 |

> 💡 **面试官**：分库分表后怎么做全局分页？
> 
> **你**：如果数据量不大，各分片取 Top N 内存归并；如果数据量大，用游标分页（如按 ID > last_id LIMIT N）；搜索类用 Elasticsearch 做异构索引。

---

### 6. 扩容迁移：如何平滑扩容？

**难点**：从 4 个分片扩到 8 个，数据要重新分布，不能停机。

**平滑迁移方案**：

1. **双写阶段**
   - 旧分片继续服务
   - 新分片同步写入（异步复制或业务双写）
   - 读仍然走旧分片

2. **数据校验**
   - 对比新旧分片数据一致性
   - 修复不一致数据

3. **切读阶段**
   - 灰度切换读取流量到新分片
   - 监控错误率、延迟

4. **停写旧分片**
   - 确认新分片稳定后，停止写入旧分片
   - 保留旧分片一段时间（回滚保险）

> 💡 也可以用 **一致性哈希**（Day 51 讲过）减少迁移量，扩容时只需迁移约 1/N 的数据。

### 7. 分库分表中间件选型

| 中间件 | 类型 | 特点 |
|--------|------|------|
| **ShardingSphere** | 代理 + JDBC | Apache 顶级项目，生态完善，支持分片/读写分离/加密 |
| **MyCAT** | 代理 | 老牌，社区成熟，配置较繁琐 |
| **Vitess** | 代理 | YouTube 开源，云原生，K8s 友好 |
| **TiDB** | NewSQL | 自动分片，兼容 MySQL 协议，分布式事务 |

> 💡 面试官问「你们怎么做的」，答中间件选型 + 自研路由层都可以，关键是说清楚决策依据。

### 算法题速记
```
Hit Counter — 循环数组 O(1)
  ├─ 300 槽位: [timestamp, count]
  ├─ idx = timestamp % 300
  ├─ 旧数据直接覆盖，新时间戳累加
  └─ getHits: 遍历 300 槽，累加未过期的

Follow-up 分布式: 本地聚合 + 定时上报 + 中心汇总
```

### 分库分表速记
```
拆前症状: 单表 1000万+ / 查询慢 / 连接数满

垂直拆分: 按字段拆，冷热分离，简单
水平拆分: 按行拆，解决数据量，复杂

分片键: 高频查询 + 分布均匀 + 业务无关
  ├─ 哈希: 均匀，扩容难
  ├─ 范围: 易热点，扩容简单
  └─ 组合: 最佳，最复杂

跨片查询解法:
  ├─ 分页: 内存归并 / 游标 / ES
  ├─ JOIN: 避免 / 冗余 / 应用层组装
  └─ 全局表: 小表每个分片复制一份

扩容迁移: 双写 → 校验 → 切读 → 停旧
```
