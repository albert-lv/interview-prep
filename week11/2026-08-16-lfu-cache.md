## 1. 今日算法题：LFU 缓存（Least Frequently Used Cache）

### 题目描述

设计并实现一个 **LFU（最不经常使用）缓存** 数据结构。它应该支持以下操作：

- `get(key)` — 如果 key 存在于缓存中，则返回其值，否则返回 -1。
- `put(key, value)` — 如果 key 不存在，插入 `(key, value)`；如果 key 已存在，更新其值。当缓存达到其容量时，应该在插入新项之前，**移除最不经常使用的项**。如果存在多个最不经常使用的项（频率相同），则移除其中 **最久未使用** 的那个。

**要求**：`get` 和 `put` 操作的时间复杂度均为 **O(1)**。

> 🔗 LeetCode 460. LFU Cache

### 示例

```
LFUCache lfu = new LFUCache(2);
lfu.put(1, 1);           // cache: {1=1} freq(1)=1
lfu.put(2, 2);           // cache: {1=1, 2=2} freq(1)=1, freq(2)=1
lfu.get(1);              // 返回 1，freq(1)=2
lfu.put(3, 3);           // 容量已满，移除 key 2（freq=1，最久未用）
                         // cache: {1=1, 3=3}
lfu.get(2);              // 返回 -1（已移除）
lfu.get(3);              // 返回 3，freq(3)=2
lfu.put(4, 4);           // freq(1)=2, freq(3)=2，移除 key 1（更早使用）
                         // cache: {3=3, 4=4}
lfu.get(1);              // 返回 -1
lfu.get(3);              // 返回 3
lfu.get(4);              // 返回 4
```

---

### 思路解析

LFU 比 LRU 复杂一个维度：不仅要维护使用顺序，还要维护**访问频率**。两个 O(1) 操作叠加，需要精心设计数据结构。

#### 核心观察

1. **每个 key 有一个频率 counter**，每次访问 +1
2. **相同频率的 key 组织在一起**，按使用时间排序（频率相同时淘汰最旧的）
3. **需要 O(1) 找到最小频率**，以便淘汰

#### 数据结构组合

```
┌─────────────────────────────────────────────────────┐
│  key → (value, freq)          哈希表，O(1) 访问      │
│  minFreq → 当前最小频率        整型变量               │
│  freq → 双向链表(按使用时间排序)  哈希表，每个频率一个链表 │
└─────────────────────────────────────────────────────┘
```

**为什么用双向链表？**
- 需要在任意位置 O(1) 删除节点（key 被更新或淘汰时）
- 需要维护使用顺序（链头 = 最新，链尾 = 最旧）
- 需要支持在头部插入新节点

#### 操作逻辑

**`get(key)`：**
1. key 不存在 → 返回 -1
2. key 存在 → 从当前频率链表移除，加入 `freq+1` 链表头部
3. 如果当前频率链表变空且等于 minFreq → minFreq++
4. 返回 value

**`put(key, value)`：**
1. key 已存在 → 更新 value，执行一次 `get` 逻辑（频率 +1）
2. key 不存在：
   - 容量已满 → 从 `minFreq` 链表尾部淘汰一个
   - 插入新 key，频率 = 1，加入 freq=1 链表头部
   - minFreq = 1

### 代码实现（Go）

```go
package main

// Node 双向链表节点
type Node struct {
	key, value int
	freq       int
	prev, next *Node
}

// DoublyLinkedList 双向链表（按使用时间排序，头新尾旧）
type DoublyLinkedList struct {
	head, tail *Node
	size       int
}

func NewDoublyLinkedList() *DoublyLinkedList {
	h := &Node{}
	t := &Node{}
	h.next = t
	t.prev = h
	return &DoublyLinkedList{head: h, tail: t}
}

// 在头部插入（最新使用的）
func (dll *DoublyLinkedList) AddToHead(node *Node) {
	node.next = dll.head.next
	node.prev = dll.head
	dll.head.next.prev = node
	dll.head.next = node
	dll.size++
}

// 移除指定节点
func (dll *DoublyLinkedList) Remove(node *Node) {
	node.prev.next = node.next
	node.next.prev = node.prev
	dll.size--
}

// 移除尾部（最旧的）
func (dll *DoublyLinkedList) RemoveTail() *Node {
	if dll.size == 0 {
		return nil
	}
	node := dll.tail.prev
	dll.Remove(node)
	return node
}

type LFUCache struct {
	capacity int
	minFreq  int
	keyMap   map[int]*Node      // key → node
	freqMap  map[int]*DoublyLinkedList // freq → 链表
}

func Constructor(capacity int) LFUCache {
	return LFUCache{
		capacity: capacity,
		minFreq:  0,
		keyMap:   make(map[int]*Node),
		freqMap:  make(map[int]*DoublyLinkedList),
	}
}

func (this *LFUCache) Get(key int) int {
	node, ok := this.keyMap[key]
	if !ok {
		return -1
	}
	this.increaseFreq(node)
	return node.value
}

func (this *LFUCache) Put(key int, value int) {
	if this.capacity == 0 {
		return
	}

	// key 已存在：更新值 + 增加频率
	if node, ok := this.keyMap[key]; ok {
		node.value = value
		this.increaseFreq(node)
		return
	}

	// 容量已满：淘汰
	if len(this.keyMap) >= this.capacity {
		list := this.freqMap[this.minFreq]
		removed := list.RemoveTail()
		delete(this.keyMap, removed.key)
		if list.size == 0 {
			delete(this.freqMap, this.minFreq)
		}
	}

	// 插入新节点，频率 = 1
	newNode := &Node{key: key, value: value, freq: 1}
	this.keyMap[key] = newNode
	if this.freqMap[1] == nil {
		this.freqMap[1] = NewDoublyLinkedList()
	}
	this.freqMap[1].AddToHead(newNode)
	this.minFreq = 1
}

// 增加节点频率
func (this *LFUCache) increaseFreq(node *Node) {
	freq := node.freq
	list := this.freqMap[freq]
	list.Remove(node)

	// 如果当前频率链表空了，且是最小频率
	if list.size == 0 && freq == this.minFreq {
		this.minFreq++
		delete(this.freqMap, freq)
	}

	// 加入高一级的频率链表
	node.freq++
	if this.freqMap[node.freq] == nil {
		this.freqMap[node.freq] = NewDoublyLinkedList()
	}
	this.freqMap[node.freq].AddToHead(node)
}
```

**验证：**

```go
func main() {
	lfu := Constructor(2)
	lfu.Put(1, 1)
	lfu.Put(2, 2)
	println(lfu.Get(1))       // 1
	lfu.Put(3, 3)             // 淘汰 key 2
	println(lfu.Get(2))       // -1
	println(lfu.Get(3))       // 3
	lfu.Put(4, 4)             // 淘汰 key 1
	println(lfu.Get(1))       // -1
	println(lfu.Get(3))       // 3
	println(lfu.Get(4))       // 4
}
```

### 复杂度分析

| 操作 | 时间复杂度 | 空间复杂度 |
|---|---|---|
| `get` | **O(1)** — 哈希表 + 双向链表操作 | O(capacity) |
| `put` | **O(1)** — 同上，淘汰也是链表尾部 O(1) | O(capacity) |

> 💡 **关键**：每个节点只会被移动有限次（频率递增），均摊 O(1)。

### 面试官 follow-up

**Q1：LFU vs LRU，什么时候用哪个？**

> 🎯 **答**：LRU 保护"最近使用"的，适合局部性好的场景（比如用户浏览页面）。LFU 保护"访问频繁"的，适合有明显热点数据的场景（比如热门商品、热点新闻）。Redis 的 maxmemory-policy 同时支持 `allkeys-lru` 和 `allkeys-lfu`。

**Q2：LFU 有个问题——"历史包袱"。一个 key 曾经很热门，后来没人访问了，但频率很高，一直占着坑。怎么解决？**

> 🎯 **答**：Redis 的 LFU 实现用了一个 trick——**频率随时间衰减**。具体做法是：
> - 频率用 8bit 存储（0-255）
> - 每隔一段时间（可配置），所有 key 的频率按对数衰减
> - 新访问时，增长也是 log 级别的（低频容易涨，高频难涨）
> 
> 这样热点能自然消退，不会永远霸占缓存。

**Q3：如果容量很大（百万级），这个数据结构有什么问题？**

> 🎯 **答**：`freqMap` 可能膨胀——如果访问模式很分散，每个 key 频率都不同，可能有成千上万个链表。但实际中，热点数据频率分布通常是幂律分布（少数 key 频率极高），所以问题不大。如果真需要优化，可以合并低频链表（比如 freq > 100 的统一存），或用跳表/TreeMap 替代。

## 2. 面试技巧：数据库连接池 + SQL 优化

### 2.1 数据库连接池设计

面试中经常被问到"为什么需要连接池"和"连接池关键参数"。

#### 为什么不用一个连接走到底？

```
┌────────────────────────────────────────────────┐
│  不用连接池：每次 SQL 都新建 TCP 连接              │
│  TCP 三次握手 + MySQL 认证 ≈ 50-100ms              │
│  SQL 执行可能只要 1ms，但连接成本是 100x           │
└────────────────────────────────────────────────┘
                        ↓
┌────────────────────────────────────────────────┐
│  用连接池：连接复用，预热后几乎零成本获取           │
│  连接 = 预热好的长连接，用完后归还                  │
│  就像线程池，核心是「复用」不是「新建」             │
└────────────────────────────────────────────────┘
```

#### 连接池核心参数（以 HikariCP 为例）

| 参数 | 作用 | 调优建议 |
|---|---|---|
| `maximumPoolSize` | 最大连接数 | 公式：`(CPU核数 * 2) + 有效磁盘数`，一般 10-20 |
| `minimumIdle` | 最小空闲连接 | 建议 = maximumPoolSize，避免频繁创建销毁 |
| `connectionTimeout` | 获取连接等待超时 | 默认 30s，建议 5-10s，快速失败 |
| `idleTimeout` | 空闲连接回收时间 | 默认 10min，太短频繁重建，太长占资源 |
| `maxLifetime` | 连接最大存活时间 | 必须 < 数据库 wait_timeout，建议 30min |
| `keepaliveTime` | 保活探测间隔 | 防止连接被防火墙/NAT 静默断开 |

> ⚠️ **经典坑**：连接池 `maxLifetime` > MySQL `wait_timeout`（默认 8h），导致连接被服务端静默关闭，客户端拿到 "stale connection"，执行 SQL 时报 `Communications link failure`。

#### 面试官高频问

**Q：连接池设置多大合适？**

> 🎯 **答**：不是越大越好。连接是稀缺资源：
> - 每个连接占用内存（MySQL 每个连接约 256KB-几MB线程栈）
> - 连接数过多 → CPU 上下文切换开销、锁竞争加剧
> - 经验公式：`(core_count * 2) + effective_spindle_count`
> - 实际上线前用压测验证，看 `Threads_running` 和 `QPS` 的平衡点

### 2.2 SQL 优化 Checklist

#### 第一步：先看执行计划

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 10086 ORDER BY created_at DESC LIMIT 10;
```

关注这些列：

| 列 | 看什么 |
|---|---|
| `type` | 至少 `range`，避免 `ALL`（全表扫描） |
| `key` | 实际使用的索引 |
| `rows` | 扫描行数，越小越好 |
| `Extra` | 警惕 `Using filesort`、`Using temporary` |

#### 第二步：索引优化黄金法则

```sql
-- ❌ 最左前缀失效：索引 (a, b, c)
WHERE b = 1 AND c = 2;     -- 跳过 a，不走索引
WHERE a = 1 AND c = 2;     -- 只走 a，b 断了

-- ❌ 函数/类型转换导致失效
WHERE DATE(created_at) = '2024-01-01';  -- 对列做函数
WHERE user_id = '10086';                 -- 字符串查 int 列

-- ❌ LIKE 前缀通配
WHERE name LIKE '%小明%';   -- 不走索引
WHERE name LIKE '小明%';    -- ✅ 走索引

-- ✅ 覆盖索引：查询列全在索引里
SELECT user_id, created_at FROM orders 
WHERE user_id = 10086;     -- 如果索引是 (user_id, created_at)，不需要回表

-- ✅ 索引下推（ICP）：WHERE 条件在索引层过滤
-- MySQL 5.6+ 自动优化，EXPLAIN 看到 Using index condition
```

#### 第三步：常见优化手段

| 问题 | 解决 |
|---|---|
| 大偏移分页 `LIMIT 100000, 10` | 游标分页 `WHERE id > ? LIMIT 10`，或延迟关联 |
| `SELECT *` | 只查需要的列，减少 IO 和内存 |
| 大表 JOIN | 确保 JOIN 条件有索引，小表驱动大表 |
| `OR` 条件 | 改写为 `UNION ALL`，或确保每个分支都能走索引 |
| `NOT IN` / `!=` | 考虑用 `NOT EXISTS` 或 `LEFT JOIN` + `IS NULL` |
| 批量插入 | `INSERT INTO ... VALUES (...), (...), (...)` 一次多条 |

#### 第四步：慢查询排查 SOP

```
1. 开启慢查询日志：slow_query_log = ON, long_query_time = 1s
2. 用 pt-query-digest 分析日志，找到最耗时的 SQL
3. EXPLAIN 看执行计划，确认索引使用情况
4. 检查索引是否生效（SHOW INDEX FROM table）
5. 优化：加索引 / 改写 SQL / 分表 / 引入缓存
6. 验证：对比优化前后的 EXPLAIN 和 实际执行时间
```

### 2.3 数据库面试话术模板

**Q：一条 SQL 执行慢，怎么排查？**

> 🎯 **答**：我的排查思路是「先定位，再分析，后优化」：
> 1. **定位**：看慢查询日志，用 `pt-query-digest` 找到 Top SQL
> 2. **分析**：`EXPLAIN` 看执行计划，关注 `type`、`key`、`rows`、`Extra`
> 3. **根因**：
>    - 没走索引 → 检查是否违反最左前缀、函数操作、类型隐转
>    - 走了索引但扫描行多 → 索引选择性不够，考虑联合索引
>    - 有 `Using filesort` / `Using temporary` → 优化 ORDER BY / GROUP BY
> 4. **优化**：加索引、改写 SQL、引入缓存、或者归档历史数据
> 5. **验证**：对比优化前后的执行时间和扫描行数

**Q：什么情况下索引会失效？**

> 🎯 **答**：最常见的五种：
> 1. **违反最左前缀** — 联合索引 `(a,b,c)`，查询跳过 `a`
> 2. **对索引列做函数/计算** — `WHERE DATE(col) = 'xxx'`
> 3. **隐式类型转换** — 字符串查 int 列，或反过来
> 4. **`LIKE` 前缀通配** — `%xxx`
> 5. **`!=` / `<>` / `NOT IN`** — 优化器可能选择全表扫描
> 
> 另外，数据分布不均匀（比如性别字段）时，索引可能不被选择。

**Q：MySQL 主从延迟怎么解决？**

> 🎯 **答**：主从延迟的成因和解决分三层：
> - **写入层**：主库单线程 binlog dump，从库单线程 SQL 线程回放 → 升级到并行复制（MySQL 5.7+ `slave_parallel_workers`）
> - **网络层**：主从异地 → 尽量同机房，或半同步改异步（权衡一致性）
> - **业务层**：读操作强制走主库（`SELECT /*+ MASTER */`），或延迟敏感业务不加从库读
> 
> 监控指标看 `Seconds_Behind_Master`，持续 > 1s 就要告警。

**练习 2**：把上面的 LFU 改成支持 TTL（参考 Day 69），即每个 key 有过期时间，过期后自动失效。提示：频率链表 + 时间轮 / 最小堆。

**练习 3**：分析下面这条 SQL 为什么慢，如何优化：

```sql
SELECT * FROM orders 
WHERE YEAR(created_at) = 2024 
  AND status = 'paid'
ORDER BY amount DESC 
LIMIT 10000, 10;
```

> 答案：① `YEAR(created_at)` 函数导致索引失效；② `SELECT *` 回表；③ `LIMIT 10000, 10` 大偏移。优化：`created_at >= '2024-01-01' AND created_at < '2025-01-01'`，加 `(status, created_at, amount)` 联合索引，游标分页。
