## 今日题目

**设计一个短链服务（如 bit.ly、tinyurl）**

给定一个长 URL，生成一个唯一的短 URL；用户访问短 URL 时，重定向到原始长 URL。

**功能要求**:
- 生成短链：输入长 URL，输出短链（如 `https://short.ly/abc123`）
- 重定向：访问短链，301/302 跳转到原始 URL
- 自定义短链（可选）：用户可指定自定义后缀
- 过期时间（可选）：短链可设置 TTL
- 访问统计（可选）：记录点击量

**非功能要求**:
- 高可用、低延迟（重定向 < 10ms）
- 短链长度尽可能短（6-8 字符）
- 支持 10 亿+ 短链，日读写比约 100:1

### 2. 数据库设计

**方案：关系型数据库（如 MySQL）+ 缓存**

```sql
CREATE TABLE url_mappings (
    id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    short_code      VARCHAR(10) NOT NULL UNIQUE,     -- 短码，如 "abc123"
    long_url        VARCHAR(2048) NOT NULL,          -- 原始长 URL
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at      TIMESTAMP NULL,                  -- 过期时间
    click_count     BIGINT DEFAULT 0,                -- 点击次数
    user_id         BIGINT NULL,                     -- 可选：归属用户
    
    INDEX idx_short_code (short_code),               -- 短码查询
    INDEX idx_expires_at (expires_at)                -- 清理过期数据
) ENGINE=InnoDB;
```

**容量估算**:
- 单条记录 ≈ 2KB
- 10 亿条 ≈ 2TB
- 需要分库分表：按 `short_code` 哈希分片，或按时间范围分表

### 3. 短码生成算法（核心！面试重点）

有三种主流方案，面试时要比较优劣：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **哈希法** | MD5/SHA-256 长 URL，取前 6-8 位 | 简单、无状态 | 哈希冲突需处理、不可逆推 |
| **Base62 编码** | 自增 ID → Base62（0-9a-zA-Z） | 简单、可逆、无冲突 | 依赖全局自增 ID、短码可预测 |
| **发号器** | 分布式 ID 生成器（Snowflake 等）→ Base62 | 无冲突、高性能 | 系统复杂度略高 |

**推荐方案：发号器 + Base62**

```python
# Base62 编解码
BASE62 = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode_base62(num: int) -> str:
    """将整数编码为 Base62 字符串"""
    if num == 0:
        return BASE62[0]
    result = []
    while num > 0:
        result.append(BASE62[num % 62])
        num //= 62
    return ''.join(reversed(result))

def decode_base62(s: str) -> int:
    """将 Base62 字符串解码为整数"""
    result = 0
    for char in s:
        result = result * 62 + BASE62.index(char)
    return result

# 示例
print(encode_base62(1000000))   # "4c92"
print(decode_base62("4c92"))     # 1000000
```

**6 位 Base62 可表示**: 62⁶ ≈ **568 亿** 个短码，完全够用。

#### 发号器设计

利用 Day 49 的 Snowflake 或号段模式：

```
方案 A：数据库自增 ID（最简单）
- 单库：AUTO_INCREMENT
- 分库：各库设置不同步长（如库1: 1,3,5... 库2: 2,4,6...）

方案 B：Redis 原子自增（高性能）
- INCR short_url_id  → 返回唯一 ID
- 可预分配一批 ID 到内存，减少 Redis 压力

方案 C：号段模式（推荐，兼顾性能和可用性）
- 服务启动时从数据库申请一个号段 [start, end]
- 本地内存分配，用完再申请
- 双缓冲：快用完时异步申请下一段
```

### 5. 缓存策略（重定向 < 10ms 的关键）

**读多写少场景，缓存是灵魂。**

```python
# 重定向流程（带缓存）
async def redirect(short_code: str):
    # 1. 查本地缓存（Caffeine/Guava Cache，TTL 10min）
    long_url = local_cache.get(short_code)
    if long_url:
        return 302, long_url
    
    # 2. 查 Redis（分布式缓存，TTL 24h）
    long_url = redis.get(f"url:{short_code}")
    if long_url:
        local_cache.set(short_code, long_url)
        return 302, long_url
    
    # 3. 查数据库
    record = db.query("SELECT long_url FROM url_mappings WHERE short_code = ?", short_code)
    if not record:
        return 404, "Not Found"
    
    # 4. 回填缓存
    redis.setex(f"url:{short_code}", 86400, record.long_url)
    local_cache.set(short_code, record.long_url)
    return 302, record.long_url
```

**缓存一致性**：
- 写路径：生成短链时，只写 DB，不提前写 Cache（防止未生效的短链被缓存）
- 过期：短链设置 TTL，到期后从 DB 和 Cache 删除
- 更新：短链一般不支持修改，如需修改，先删 Cache 再更新 DB

### 6. 扩展性设计

| 问题 | 解决方案 |
|------|----------|
| 读 QPS 过高 | CDN + 多级缓存 + 读写分离 |
| 写 QPS 过高 | 发号器预分配 + 异步写 DB |
| 数据量过大 | 按时间分表，冷数据归档到对象存储（S3/OSS） |
| 全球部署 | 多区域部署，短码全局唯一，就近重定向 |
| 自定义短链冲突 | 先查 DB 确认唯一性，冲突返回 409 |

## 代码示例（简化版）

```python
import hashlib
import base62  # pip install pybase62
from datetime import datetime, timedelta
from typing import Optional

class ShortUrlService:
    def __init__(self, db, redis, id_generator):
        self.db = db
        self.redis = redis
        self.id_generator = id_generator  # 发号器
    
    def shorten(self, long_url: str, custom_alias: Optional[str] = None, 
                expires_in_days: int = 30) -> str:
        """生成短链"""
        # 自定义短链
        if custom_alias:
            if self.db.exists(custom_alias):
                raise ValueError("Custom alias already exists")
            short_code = custom_alias
        else:
            # 发号器生成唯一 ID，Base62 编码
            unique_id = self.id_generator.next_id()
            short_code = base62.encode(unique_id)
        
        expires_at = datetime.now() + timedelta(days=expires_in_days)
        
        # 写入数据库
        self.db.execute(
            "INSERT INTO url_mappings (short_code, long_url, expires_at) VALUES (?, ?, ?)",
            (short_code, long_url, expires_at)
        )
        
        return f"https://short.ly/{short_code}"
    
    def redirect(self, short_code: str) -> Optional[str]:
        """短链重定向"""
        # 先查缓存
        cache_key = f"url:{short_code}"
        long_url = self.redis.get(cache_key)
        if long_url:
            return long_url
        
        # 查数据库
        record = self.db.query_one(
            "SELECT long_url, expires_at FROM url_mappings WHERE short_code = ?",
            short_code
        )
        if not record or record['expires_at'] < datetime.now():
            return None
        
        # 回填缓存
        self.redis.setex(cache_key, 86400, record['long_url'])
        return record['long_url']
```

## 复杂度分析

| 操作 | 时间复杂度 | 空间复杂度 | 说明 |
|------|-----------|-----------|------|
| 生成短链 | O(1) 均摊 | O(1) | 发号器 + Base62 编码 |
| 重定向（缓存命中） | O(1) | O(1) | Redis/本地缓存 |
| 重定向（缓存未命中） | O(1) | O(1) | DB 索引查询 |
| Base62 编解码 | O(log₆₂ N) | O(log₆₂ N) | 约等于 O(1)，实际最多 6-8 次循环 |

## 面试技巧

### 🎯 如何开场（30 秒抓住面试官）

> "短链服务是典型的读多写少系统，日读写比约 100:1。核心是两点：
> 1. **生成**：如何快速生成唯一、可逆、不冲突的短码
> 2. **查询**：如何支持高并发重定向，延迟 < 10ms
> 我的思路是用发号器 + Base62 生成短码，CDN + 多级缓存支撑查询。"

### 🎯 加分项（面试官眼睛会亮）

1. **提到布隆过滤器**（Day 48 学的！）
   > "为防止缓存穿透，可以在缓存层前加布隆过滤器，快速判断短码是否存在，避免无效 DB 查询。"

2. **提到一致性哈希**（Day 51 学的！）
   > "如果 Cache 集群扩容，可以用一致性哈希减少数据迁移。"

3. **301 vs 302 的选择**
   - **301**：永久重定向，浏览器缓存，减少服务端压力，但无法统计点击量
   - **302**：临时重定向，每次经过服务端，可统计，但压力更大
   - **面试回答**："看业务需求。如果要做分析统计，用 302；如果纯引流，用 301。"

4. **安全性考虑**
   - 短码可预测问题：自增 ID 生成的短码容易被遍历，可加入随机偏移
   - 恶意 URL：生成时扫描黑名单（钓鱼、色情、诈骗）
   - 速率限制：防止刷短链（Day 50 的限流器！）

### 🎯 常见追问

**Q: 如果发号器挂了怎么办？**
> "号段模式可以解决这个问题。服务启动时预分配一个号段到内存，发号器挂了也不影响当前服务。双缓冲机制：用到 80% 时异步申请下一段。"

**Q: 短链过期怎么清理？**
> "三种方式：
> 1. 惰性删除：访问时检查过期时间
> 2. 定时任务：每天扫描过期数据，批量删除
> 3. TTL + 归档：过期短链移到冷存储，释放主库空间"

**Q: 如何支持 10 亿+ 短链？**
> "按时间分表（如每月一张表），短码中包含时间信息（如前 2 位表示年份），路由到对应表。冷数据（1 年以上）归档到对象存储。"
