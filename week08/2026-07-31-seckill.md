## 今日算法题：设计秒杀系统

### 题目描述
设计一个支持高并发秒杀活动的系统，要求：
1. 同一时间可能有百万级用户抢购限量商品（如 10000 件）
2. 保证库存不超卖、不少卖
3. 系统不能崩溃，需保护后端数据库
4. 用户体验：前 N 名成功下单，其余收到友好提示

### 核心挑战
| 挑战 | 说明 |
|------|------|
| 流量洪峰 | 秒杀开始时 QPS 可能从几百飙升到百万 |
| 库存一致性 | 高并发下不能超卖，也不能少卖 |
| 系统稳定性 | 不能让非秒杀流量受影响 |
| 公平性 | 先到先得，避免刷单/脚本 |

### 系统架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                         用户层                               │
│    CDN 静态资源 → 秒杀按钮倒计时 → 验证码/风控              │
└────────────────────┬────────────────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────────────────┐
│                      接入层 (Nginx/网关)                     │
│  - 限流：漏桶/令牌桶，拦截明显超出容量的请求                │
│  - 负载均衡：均匀分发到应用层                               │
│  - 静态页面缓存：商品详情页完全静态化                       │
└────────────────────┬────────────────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────────────────┐
│                      应用层 (Seckill Service)               │
│  - 库存预扣：Redis 原子 decr，失败直接返回"已售罄"         │
│  - 异步下单：MQ 削峰，写入订单服务                          │
│  - 本地缓存：热点数据本地缓存，减少 Redis 压力               │
└────────────────────┬────────────────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────────────────┐
│                      数据层                                  │
│  Redis：库存计数器 + 用户去重集合 + 限流计数                │
│  MQ (Kafka/RocketMQ)：异步订单，削峰填谷                   │
│  MySQL：最终订单数据 + 库存一致性校验（兜底）                │
└─────────────────────────────────────────────────────────────┘
```

### 关键实现细节

#### 1. Redis 库存预扣（防超卖核心）

```python
import redis

r = redis.Redis()

# 初始化库存（活动开始前）
r.set("seckill:stock:1001", 10000)

# 秒杀时：原子 decr
def seckill(user_id, item_id):
    stock_key = f"seckill:stock:{item_id}"
    user_key = f"seckill:users:{item_id}"
    
    # 1. 用户是否已抢购过？（去重）
    if r.sismember(user_key, user_id):
        return {"success": False, "msg": "您已经参与过秒杀"}
    
    # 2. 原子扣减库存（核心！）
    # Lua 脚本保证原子性：查库存 -> 扣减 -> 记录用户
    lua_script = """
    local stock = tonumber(redis.call('get', KEYS[1]))
    if stock == nil or stock <= 0 then
        return -1  -- 库存不足
    end
    redis.call('decr', KEYS[1])
    redis.call('sadd', KEYS[2], ARGV[1])
    return stock - 1
    """
    
    remaining = r.eval(lua_script, 2, stock_key, user_key, user_id)
    
    if remaining == -1:
        return {"success": False, "msg": "商品已售罄"}
    
    # 3. 发送 MQ，异步创建订单
    send_order_mq(user_id, item_id)
    
    return {
        "success": True, 
        "msg": "抢购成功，正在生成订单",
        "remaining": remaining
    }
```

#### 2. 为什么必须用 Lua / 分布式锁？

```
❌ 错误写法（非原子）：
   stock = r.get(key)          # 读：100
   if stock > 0:
       r.decr(key)             # 写：99
   # 并发时：两个线程同时读到 100，都扣减 → 超卖！

✅ 正确做法：
   - Lua 脚本（Redis 单线程执行脚本）
   - 或 Redis + WATCH/MULTI/EXEC（乐观锁，失败重试）
   - 或 Redisson 分布式锁（适合更复杂场景）
```

#### 4. 多级限流策略

| 层级 | 策略 | 目的 |
|------|------|------|
| 客户端 | 验证码、答题、按钮置灰 | 防脚本，减少无效请求 |
| CDN/WAF | IP 限流、黑白名单 | 拦截明显恶意流量 |
| 网关 | 令牌桶，QPS 限制为预估峰值的 1.5 倍 | 保护后端 |
| 应用 | Redis 库存预扣，无库存直接拒绝 | 避免打到 MQ/DB |
| MQ | 消费速率控制，防止 DB 被打挂 | 最终一致性兜底 |

### 复杂度分析

| 指标 | 值 | 说明 |
|------|------|------|
| 库存扣减 | O(1) | Redis 单命令 |
| Lua 脚本 | O(1) | 原子执行，无竞态 |
| MQ 生产 | O(1) | 异步，不阻塞 |
| 整体吞吐 | 10w+ QPS | 纯 Redis 支撑 |

### 扩展追问

**Q：Redis 挂了怎么办？**
- 主从 + Sentinel 自动故障转移
- 库存数据可预热，重启后从 DB 恢复
- 降级方案：直接返回"活动太火爆，请稍后再试"

**Q：如何防止超卖？**
- 第一层：Redis 原子扣减（Lua）
- 第二层：MQ 消费时幂等校验
- 第三层：MySQL 唯一索引/乐观锁兜底
- 宁可少卖（拒绝），不可超卖（赔偿）

**Q：秒杀前如何预热？**
- 商品详情页推 CDN，完全静态化
- 库存数据提前加载到 Redis
- 热点 Key 分散（如 `stock:1001:0` ~ `stock:1001:99`）

## 面试技巧

### 🎯 秒杀系统的面试话术框架

**开场（30秒定调）：**
> "秒杀系统的核心矛盾是**有限库存 + 无限流量**，设计思路是**层层过滤，逐层削峰**——尽量在前端拦截掉不可能成功的请求，只让少量请求到达数据库。"

**分阶段展开：**
1. **流量过滤层**：验证码、答题、CDN、Nginx 限流
2. **库存扣减层**：Redis + Lua 原子操作（必讲！）
3. **异步处理层**：MQ 削峰，保护 DB
4. **兜底一致性层**：幂等 + 对账 + 补偿

### 💡 面试官常挖坑

| 坑 | 怎么填 |
|----|--------|
| "直接用 MySQL 行锁不行吗？" | 行锁粒度太细，秒杀时全部竞争同一行，MySQL 扛不住（单点 ~2k QPS） |
| "Redis 扣减后 DB 失败了怎么办？" | 设计补偿机制：MQ 消费失败可重试；超时未支付自动释放库存 |
| "怎么保证公平性？" | 按请求到达 Redis 的先后顺序（单线程模型天然公平） |
| "如果 Redis 单机热点 Key 扛不住？" | 本地缓存 + Key 分片（`stock:item:0` ~ `stock:item:99`） |

### 📝 画图建议

面试时推荐画出这个流程：
```
用户请求 → 验证码 → Nginx限流 → [Redis Lua扣库存] → 成功 → MQ → 订单服务 → MySQL
                                    ↓ 失败
                              直接返回"已售罄"
```

把 **Redis Lua 扣减** 圈出来强调——这是区分懂行和不懂的分水岭。
