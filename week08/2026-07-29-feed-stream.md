# Day 53 — 设计 Feed 流系统（Feed/Timeline System）

> 经典程度：⭐⭐⭐⭐⭐ | Twitter、微博、朋友圈的底层架构面试必考题

---

## 一、问题背景

设计一个类似 Twitter 或微博的 Feed 流系统，核心需求：

- 用户可以 **发布推文/微博**（Post）
- 用户可以 **关注（Follow）/取关（Unfollow）** 其他用户
- 用户可以查看自己的 **时间线（Timeline/Home Feed）**，按时间倒序展示关注者的内容
- 支持高并发：读远大于写（典型社交产品读写比 100:1 甚至更高）

---

## 二、核心难点与方案对比

Feed 流设计的灵魂拷问：**推（Push）还是拉（Pull）？**

### 2.1 推模式（Fan-out on Write）

**思路：** 用户发一条内容时，立即推送到所有粉丝的 Timeline 缓存中。

- 粉丝读取 Timeline → 直接读自己的收件箱，O(1)
- 发内容时 → 写入 N 个粉丝的收件箱，O(粉丝数)

**优点：**
- 读极快，简单直接

**缺点：**
- 大 V 发一条微博，要推送给千万粉丝，写入量爆炸
- 存储冗余，同一条内容存 N 份

### 2.2 拉模式（Fan-out on Read）

**思路：** 用户刷新 Timeline 时，实时聚合所有关注者的最新内容，排序返回。

- 发内容 → 只写自己的发件箱
- 读 Timeline → 拉取关注列表 → 分别读取每个人的发件箱 → 合并排序

**优点：**
- 写轻量，无冗余存储
- 天然支持动态关注关系变化

**缺点：**
- 读操作重，关注人多时延迟高
- 很难做全局排序（按时间/按热度）

### 2.3 混合模式（推拉结合）—— 工业界主流

**核心策略：**

| 用户类型 | 方案 |
|---------|------|
| 普通用户（粉丝少） | **推模式** — 发内容时直接推送到粉丝收件箱 |
| 大 V（粉丝多） | **拉模式** — 粉丝读 Timeline 时，临时拉取大 V 的发件箱合并 |

> Twitter 早期纯推，后来改成混合。微博也是典型的推拉结合。

** Timeline 读取流程：**
1. 从收件箱（Inbox）读出已推送的普通用户内容
2. 从发件箱（Outbox）拉取关注的大 V 内容
3. 两路数据按时间排序合并
4. 返回前 N 条（如 50 条）

## 三、系统架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                         客户端                               │
└─────────────────────────┬───────────────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────────────┐
│                    API Gateway / LB                          │
└─────────────────────────┬───────────────────────────────────┘
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  Post Service│ │Follow Service│ │Feed Service  │
│   (发帖)      │ │  (关注关系)   │ │(Timeline查询)│
└──────┬───────┘ └──────┬───────┘ └──────┬───────┘
       │                │                │
       ▼                ▼                ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  Content DB  │ │ Relation DB  │ │  Redis Cache │
│ (MySQL/NoSQL)│ │   (图数据库)  │ │ (Timeline)   │
└──────────────┘ └──────────────┘ └──────────────┘
```

### 3.1 数据模型

**用户表（User）**
```sql
user_id (PK) | username | created_at
```

**关注关系表（Follow）**
```sql
follower_id | followee_id | created_at
-- 联合索引 (follower_id, followee_id)
-- 或者使用图数据库（Neo4j）
```

**内容表（Post/Content）**
```sql
post_id (PK) | user_id | content | media_url | created_at
-- 按 user_id + created_at 分片/索引
```

**Timeline 缓存（Redis / 内存）**
```
Key: timeline:{user_id}
结构: Sorted Set (ZSET)
  - Score: publish_timestamp
  - Member: post_id
-- 只保留最近 N 条（如 1000 条），超出截断
```

### 3.2 关键流程

**发布内容：**
```
1. 内容写入 Content DB
2. 异步推送到粉丝 Timeline（Redis ZSET）
   - 获取粉丝列表
   - 对每个粉丝的 timeline:{fan_id} ZADD post_id score=now
   - 大 V 不走推送，标记为 "pull_required"
3. 写入自己的发件箱 outbox:{user_id}
```

**读取 Timeline：**
```
1. 从 Redis 读取 timeline:{user_id}（已推内容）
2. 检查关注的大 V 列表
3. 对每个大 V，从 outbox:{v_user_id} 拉取最近几条
4. 合并、按时间排序、返回前 50 条
```

## 四、深度优化点

### 4.1 大 V 的拉取优化

- 大 V 发件箱也用 Redis ZSET 缓存，O(log N) 读取
- 限制大 V 拉取条数（如每人最多 3 条）
- 使用本地缓存（Caffeine/Guava）缓存大 V 最近内容

### 4.2 时间线预计算（Timeline Pre-computation）

- 用户冷启动/长时间未登录 → Timeline 为空或过期
- 后台任务定期为活跃用户预计算 Timeline
- 使用 Kafka 削峰，异步消费关注关系变更事件

### 4.3 分页与游标

**不要用 offset 分页！**

```
# 错误：?page=3&size=20
# 正确：?cursor=1689234567890&limit=20

读取时记录最后一条的 timestamp 作为 cursor
下一页：?cursor=1689234567890&limit=20
```

原因：
- 新内容不断插入，offset 会导致重复/跳页
- 游标（Cursor）基于时间戳，稳定可靠

### 4.4 多机房/就近部署

- Timeline 数据按用户地域分片
- 跨机房复制延迟可能导致粉丝看到内容有延迟（社交场景可接受）

### 4.5 热度排序（非纯时间序）

如果需要 "For You" 个性化排序：
- 先拉取候选集（几百到几千条）
- 送入排序模型（机器学习打分）
- 重排序后返回

> 注意：纯时间线（Timeline）和推荐流（For You）是两个不同的系统。

## 五、复杂度分析

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 发布内容（普通用户） | O(F) | F = 粉丝数，Redis Pipeline 批量写入 |
| 发布内容（大 V） | O(1) | 只写入自己的发件箱 |
| 读取 Timeline | O(K + V × M) | K = 收件箱条数, V = 关注大 V 数, M = 每人大 V 拉取条数 |
| 关注用户 | O(1) | 写入关系表 |
| 取关用户 | O(1) + 异步清理 | 关系表删除 + 可选清理 Timeline 中该用户内容 |

## 六、面试话术模板

### 开场（30 秒定调）
> "Feed 流的核心矛盾是**读放大 vs 写放大**的权衡。我先分析业务特点：社交产品读远大于写，用户分布不均（存在大 V）。我倾向于采用**推拉结合的混合模式**——普通用户用推模式保证读性能，大 V 用拉模式避免写放大。"

### 中间展开
1. **先画数据流** — 发内容走什么路径，读 Timeline 走什么路径
2. **解释为什么选混合模式** — 对比纯推/纯拉的优劣，体现权衡思维
3. **提到 Redis ZSET** — 时间线天然适合有序集合，面试官知道你懂数据结构选型
4. **抛出 Cursor 分页** — 比 offset 高级，体现工程经验

### 应对追问
- **Q: 大 V 的粉丝数动态变化，怎么判定是不是大 V？**
  - A: 可以设阈值（如 1 万粉丝），或者根据发布频率+粉丝数综合评分。也可以让用户手动配置（微博的超级粉丝）。

- **Q: 用户突然关注了一个大 V，Timeline 怎么更新？**
  - A: 首次关注时异步拉取该大 V 最近 N 条内容合并到收件箱。后续走正常的拉模式。

- **Q: 限流了怎么做？**
  - A: 结合我们 Day 50 学的限流器，发帖频率、拉取频率都可以限。大 V 内容拉取可以走 CDN/边缘缓存。

---

## 七、一句话总结

> Feed 流的本质是个 **"收件箱设计问题"** — 推模式把复杂度放在写，拉模式放在读，混合模式根据用户体量动态选择。记住三个关键词：**推拉结合、Redis ZSET、Cursor 分页**。
