# Day 54 — 设计即时通讯系统（Instant Messaging System）

> 经典程度：⭐⭐⭐⭐⭐ | 微信、WhatsApp、钉钉的底层架构面试必考题

---

## 一、问题背景

设计一个即时通讯系统（IM），核心需求：

- 用户之间可以**发送文本/图片/语音/视频消息**
- 支持**单聊（P2P）**和**群聊（Group Chat）**
- 消息需要**可靠送达**（不丢消息）且**有序到达**
- 支持**在线状态（Presence）**显示：在线/离线/正在输入...
- 支持**消息历史记录**存储与同步
- 支持**多端登录**（手机、PC、Web 同时在线）
- 高并发：日活数亿用户，峰值每秒数百万消息

---

## 二、核心难点与方案对比

### 2.1 消息投递模型

**读扩散（Pull）vs 写扩散（Push）**

| 模式 | 思路 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **写扩散（Push）** | 发消息时写到所有接收方的收件箱 | 读快，收件箱直接取 | 群聊写放大严重 | 单聊、小群（微信早期） |
| **读扩散（Pull）** | 发消息只写一份，接收方按需拉取 | 存储省，无写放大 | 读重，需聚合 | 大群、公众号（微信后期） |
| **混合模式** | 单聊/小群写扩散，大群读扩散 | 兼顾读写性能 | 实现复杂 | 微信现网方案 |

> 微信的演进：早期纯写扩散 → 群人数多了以后改成混合模式。大群（500人+）用读扩散，避免一条消息写500份。

### 2.2 消息可靠性保障

**核心问题：消息不丢、不乱序、不重复**

| 问题 | 解决方案 |
|------|----------|
| **消息丢失** | ACK 确认机制 + 重传 + 离线消息存储 |
| **消息乱序** | 服务端全局序列号（Sequence ID）或时间戳 + 接收方排序 |
| **消息重复** | 消息去重 ID（client_msg_id）+ 接收端幂等处理 |

**ACK 机制：**
```
客户端发送消息 → 服务端存储 → 返回 ACK
客户端未收到 ACK → 定时重传（带相同 client_msg_id）
```

**Sequence ID 设计：**
- 每个用户/每个会话维护一个自增序列号
- 消息按 seq 严格递增，接收方按 seq 排序展示
- 断线重连后，用 last_ack_seq 向服务端拉取缺失消息

## 三、系统架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                        客户端                                │
│     (iOS / Android / PC / Web)                               │
└─────────────────────────┬───────────────────────────────────┘
                          │ 长连接(WebSocket/TCP)
┌─────────────────────────▼───────────────────────────────────┐
│                   Gateway 网关层                             │
│         (负载均衡 + 连接管理 + 协议解析)                      │
└─────────────────────────┬───────────────────────────────────┘
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  Msg Service │ │ Group Service│ │ Push Service │
│   (消息存储)  │ │   (群聊逻辑)  │ │  (离线推送)  │
└──────┬───────┘ └──────┬───────┘ └──────┬───────┘
       │                │                │
       ▼                ▼                ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ Message Store│ │ Group Member │ │  Push Queue  │
│  (消息主存)   │ │    Store     │ │ (APNs/FCM)   │
└──────────────┘ └──────────────┘ └──────────────┘
       │
       ▼
┌──────────────┐
│  Sync Queue  │
│ (多端同步)    │
└──────────────┘
```

### 3.1 核心组件

**Gateway 网关层**
- 维护客户端长连接（WebSocket / 自定义 TCP 协议）
- 心跳检测：客户端每 30s 发送心跳，服务端 90s 未收到认为断线
- 用户 ID → Gateway 节点映射（一致性哈希路由）

**Msg Service 消息服务**
- 消息存储与查询
- 消息序列号分配
- 离线消息管理

**Sync Service 同步服务**
- 多端登录时，各端消息同步
- 采用增量同步机制（类似微信的 Sync Protocol）

### 3.2 消息存储设计

**消息表（Message）**
```sql
msg_id (PK)       | 全局唯一消息ID
client_msg_id     | 客户端生成的去重ID（UUID）
conversation_id   | 会话ID（单聊：userA_userB，群聊：group_id）
sender_id         | 发送者
receiver_id       | 接收者（单聊）/ 群ID（群聊）
content           | 消息内容（或对象存储URL）
msg_type          | text/image/voice/video
seq               | 会话内自增序列号
created_at        | 发送时间
status            | sending/sent/delivered/read
```

**会话列表表（Conversation）**
```sql
conversation_id   | 会话ID
user_id           | 所属用户
peer_id           | 对方ID（单聊）/ 群ID（群聊）
unread_count      | 未读数
last_msg_id       | 最后一条消息ID
last_msg_time     | 最后消息时间
```

**离线消息表（Offline Message）**
```sql
user_id           | 接收用户
msg_id            | 消息ID
delivery_status   | pending/delivered
-- 用户上线后批量拉取，拉取后删除或标记
```

### 3.3 消息流转流程

**发送消息：**
```
1. 客户端生成 client_msg_id（UUID），带上本地 seq
2. 通过长连接发送到 Gateway
3. Gateway 路由到 Msg Service
4. Msg Service：
   a. 去重检查（client_msg_id）
   b. 分配全局 seq
   c. 写入 Message Store
   d. 如果是群聊，调用 Group Service 获取成员列表
5. 推送：
   a. 接收方在线 → 通过 Gateway 长连接推送
   b. 接收方离线 → 写入 Offline Message + 调用 Push Service 发通知
6. 返回 ACK 给发送方
```

**接收消息：**
```
1. 客户端在线时，Gateway 直接推送
2. 客户端返回 ACK
3. 客户端离线时，上线后发送 sync 请求
4. 服务端返回 last_ack_seq 之后的所有消息
```

## 四、深度优化点

### 4.1 消息存储分层

| 存储层级 | 数据 | 存储介质 | 保留时间 |
|---------|------|---------|---------|
| **热数据** | 最近7天消息 | Redis / 内存 | 7天 |
| **温数据** | 近期消息 | SSD（TiDB/MySQL） | 3-6个月 |
| **冷数据** | 历史消息 | 对象存储（S3/OSS） | 永久 |

> 用户拉取历史消息时，先查热缓存，未命中再查温/冷存储。

### 4.2 大群优化（>500人）

- **读扩散模式**：群消息只存一份，成员各自拉取
- **消息摘要**：大群不存已读状态，降低存储压力
- **推送合并**：大群消息批量推送，减少网络请求
- **@消息优先**：只有 @我 的消息才强推送，普通消息弱提示

### 4.3 多端同步协议

微信采用的是类 IMAP 的增量同步协议：

```
客户端存储：last_sync_seq
同步请求：GET /sync?seq=12345
服务端返回：seq 12346 ~ 12500 的所有增量数据
客户端更新：last_sync_seq = 12500
```

关键点：
- 每个设备独立维护 sync_seq
- 同步内容包括：新消息、已读状态变更、会话列表更新
- 断网恢复后自动增量同步，无需全量拉取

### 4.4 消息撤回与删除

**撤回（Recall）：**
- 发送方在限定时间内（如 2 分钟）可撤回
- 服务端标记消息状态为 recalled
- 推送撤回指令给接收方，客户端展示 "消息已撤回"

**删除（Delete）：**
- 仅删除本地：客户端自行删除
- 双向删除：需服务端配合，标记对双方不可见

### 4.5 已读回执（Read Receipt）

- 单聊：对方打开会话后发送已读请求，更新消息的 read_status
- 群聊：可选开启，存储每个成员的已读状态（大群不建议）
- 优化：已读状态不随消息主表存储，单独用 Bitmap 或 Counter

## 五、复杂度分析

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 发送单聊消息 | O(1) | 写消息表 + 推送 |
| 发送群聊消息（小群） | O(M) | M = 群成员数，写扩散到各收件箱 |
| 发送群聊消息（大群） | O(1) | 读扩散，只写一份 |
| 拉取历史消息 | O(K) | K = 拉取条数，热数据直接返回 |
| 同步离线消息 | O(N) | N = 离线期间消息数，通常有限制 |
| 消息已读 | O(1) | 更新状态表 |

## 六、面试话术模板

### 开场（30 秒定调）
> "IM 系统的核心挑战是**可靠投递 + 高并发 + 多端同步**。我会从三个层面展开：首先设计消息的投递模型（推拉选择），然后保障消息可靠性（ACK + 序列号 + 去重），最后处理多端同步和扩展性问题。"

### 中间展开
1. **先讲单聊，再讲群聊** — 单聊简单（写扩散），群聊复杂（大群用读扩散）
2. **强调 ACK + client_msg_id** — 这是消息可靠性的核心，面试官必问
3. **提到 Seq 机制** — 保证消息有序，支持断线重连增量同步
4. **抛出冷热分层存储** — 体现你对海量数据存储的经验

### 应对追问

- **Q: 如何保证消息绝对有序？**
  - A: 单聊用会话级 seq（一个会话一个自增序列），由服务端统一分配。群聊同理。客户端按 seq 排序展示，不依赖发送时间。

- **Q: 用户换设备登录，怎么同步历史消息？**
  - A: 新设备首次登录全量拉取最近 N 条（如100条），之后走增量同步。历史消息按需拉取，下滑加载更多时请求对象存储。

- **Q: 弱网环境下消息发送失败怎么办？**
  - A: 客户端本地先存"发送中"状态，定时重试（指数退避）。重传时带相同 client_msg_id，服务端去重。超过最大重试次数标记为发送失败，用户可手动重试。

- **Q: 如何支持已读回执又不压垮系统？**
  - A: 单聊默认开启，群聊可选且大群建议关闭。已读状态单独存储，不用每条消息都更新。可以用用户级别的 last_read_msg_id，查询时比对即可。

---

## 七、一句话总结

> IM 系统的本质是 **"可靠的消息管道"** — 核心三板斧：**ACK 保障可达、Seq 保障有序、client_msg_id 保障幂等**。单聊写扩散简单直接，大群读扩散避免爆炸，多端用增量同步保持状态一致。
