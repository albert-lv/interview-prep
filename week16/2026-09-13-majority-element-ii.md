## 今日算法题

### 多数元素 II（Majority Element II）

**题目来源**：[LeetCode 229](https://leetcode.cn/problems/majority-element-ii/)

**描述**：给定一个大小为 `n` 的整数数组，找出其中所有出现次数超过 `⌊n/3⌋` 的元素。

**进阶**：要求时间复杂度 `O(n)`，空间复杂度 `O(1)`。

**示例**：
```
输入: nums = [3,2,3]
输出: [3]

输入: nums = [1,1,1,3,3,2,2,2]
输出: [1,2]
```

---

### 解题思路：Boyer-Moore 投票算法扩展

核心洞察：如果某个元素出现次数超过 `n/3`，那么最多只有 **2 个**这样的元素。

推广到一般情况：出现次数超过 `n/k` 的元素，最多有 `k-1` 个。

**算法步骤**：

1. **候选阶段**：维护最多 2 个候选者及其计数器
   - 遇到相同元素 → 对应计数器 +1
   - 遇到不同元素 → 两个计数器都 -1（同归于尽）
   - 计数器归零 → 更换候选者

2. **验证阶段**：遍历数组统计两个候选者的真实出现次数，确认是否超过 `n/3`

**为什么有效？**

想象三国战场：魏蜀吴三方混战。每次三个不同国家各损失一兵（同归于尽）。如果某国兵力超过总兵力的 1/3，它一定能活到最后。

> 💡 这就是摩尔投票的本质：**配对抵消**。非目标元素之间互相消耗，目标元素因为数量优势必然幸存。

---

### 代码实现

```go
package main

func majorityElement(nums []int) []int {
    // 第一阶段的候选人可能为 nil，我们用特殊值处理
    // 实际实现中需要区分"候选人为0"和"没有候选人"
    var candidate1, candidate2 int
    count1, count2 := 0, 0

    // 阶段一：找候选人
    for _, num := range nums {
        if count1 > 0 && num == candidate1 {
            count1++
        } else if count2 > 0 && num == candidate2 {
            count2++
        } else if count1 == 0 {
            candidate1 = num
            count1 = 1
        } else if count2 == 0 {
            candidate2 = num
            count2 = 1
        } else {
            // 三方不同，同归于尽
            count1--
            count2--
        }
    }

    // 阶段二：验证真实次数
    count1, count2 = 0, 0
    for _, num := range nums {
        if num == candidate1 {
            count1++
        } else if num == candidate2 {
            count2++
        }
    }

    n := len(nums)
    result := []int{}
    if count1 > n/3 {
        result = append(result, candidate1)
    }
    if count2 > n/3 {
        result = append(result, candidate2)
    }
    return result
}
```

**复杂度分析**：
- **时间**：`O(n)` — 两次线性扫描
- **空间**：`O(1)` — 只维护两个候选者

### 面试官追问

> 💬 **追问 1**：如果要求超过 `n/k` 的元素呢？
>
> 🎯 维护 `k-1` 个候选者，每次 `k` 个不同元素同归于尽。时间 `O(nk)`，空间 `O(k)`。

> 💬 **追问 2**：数据流场景下怎么做？（元素逐个到达，无法二次遍历）
>
> 🎯 无法验证阶段，只能输出候选者。用于**近似统计**，比如找出可疑的热门商品 ID，再异步验证。大数据场景常用（Flink/Spark Streaming）。

> 💬 **追问 3**：如果元素范围很小（比如 0-100），有没有更快的方法？
>
> 🎯 用计数数组或哈希表，`O(n)` 时间 `O(1)` 空间（范围固定），一次扫描即可。

## 面试技巧 — Raft 共识算法

### 为什么需要共识算法？

分布式系统中，多个节点对某个值达成一致是核心问题：
- 选谁当主节点？
- 这条日志到底写没写成功？
- 系统现在该切换到新配置吗？

**Raft** 的设计目标：**比 Paxos 更容易理解**，同时保证等价的安全性和可用性。

---

### Raft 核心机制：三驾马车

```
┌─────────────────────────────────────────────┐
│              Raft 节点状态机                  │
│                                             │
│   ┌─────────┐    超时未收到心跳    ┌────────┐ │
│   │Follower │ ──────────────────→ │Candidate│ │
│   │  (随从)  │ ←───────────────── │ (候选人)│ │
│   └────┬────┘   发现更高任期 Leader └────┬───┘ │
│        │                                │     │
│        │         获得多数票             │     │
│        │         ┌──────────┐          │     │
│        └────────→│  Leader  │←─────────┘     │
│                  │ (领导者)  │                │
│                  └────┬─────┘                │
│                       │                      │
│              发送心跳 / 日志复制              │
└─────────────────────────────────────────────┘
```

#### 1. 领导者选举（Leader Election）

**触发条件**：Follower 在 `election timeout`（通常 150-300ms 随机）内未收到 Leader 心跳。

**选举流程**：
1. Follower 自增当前任期（term），变为 Candidate
2. 给自己投票，并向其他节点发送 `RequestVote` RPC
3. 获得 **多数票**（超过半数节点）→ 成为 Leader
4. 立即向所有节点发送心跳，宣告主权

**关键约束**：
- 每个任期，每个节点最多投一票
- Candidate 的日志必须 **至少和新**（term 更大，或 term 相同但 index 更长）
- 投票采用 **先到先得** 原则

> ⚠️ **脑裂防护**：如果多个 Candidate 同时发起选举，可能都无法获得多数票 → 选举超时后自增 term 重试。随机超时时间（150-300ms）大幅降低冲突概率。

#### 2. 日志复制（Log Replication）

**写请求流程**：
```
Client → Leader → 写入本地日志 → 并行发送 AppendEntries RPC
                                          ↓
                               收到多数节点确认 → 提交（commit）
                                          ↓
                               应用到状态机 → 返回 Client 成功
```

**日志结构**：每条日志 = `(term, index, command)`
- `term`：该日志条目是在哪个 leader 任期写入的
- `index`：日志在序列中的位置
- `command`：实际要执行的指令

**一致性保证**：
- Leader 永远不会覆盖或删除自己的日志
- 如果两个日志的 term 和 index 相同，它们存储的命令一定相同
- 如果某条日志已提交，那么它之前的所有日志也都已提交

#### 3. 安全性（Safety）

**选举限制**：只有日志足够新的 Candidate 才能当选。

这意味着：**已提交的日志永远不会丢失**。

具体判定"日志至少和新"：
- 比较最后一条日志的 term，term 大的更新
- term 相同，比较 index，index 大的更新

### Raft vs Paxos：面试速答

| 维度 | Raft | Paxos |
|------|------|-------|
| **理解难度** | 清晰的三阶段拆分（选举/复制/安全） | 数学证明导向，多角色交互复杂 |
| **工程实现** | etcd/Consul/TiKV 都用它 | ZooKeeper（ZAB 变种）、Chubby |
| **Leader** | 强 Leader 模型 | Multi-Paxos 也选 Leader，但本质不同 |
| **性能** | 单 Leader 可能成为瓶颈 | 理论更通用，但实现复杂 |
| **面试推荐** | ⭐ 首选，讲清楚就好 | 了解 Basic Paxos 两个阶段即可 |

> 💡 **面试金句**："Raft 是通过强 Leader 模型简化了共识问题 —— 所有写请求走 Leader，Leader 负责日志排序和复制，这样就把分布式共识降级为单节点的日志管理问题。"

### 高频面试连环问

> 💬 **Q1：Raft 如何处理 Leader 崩溃？**
>
> 🎯 Follower 超时未收到心跳 → 变为 Candidate 发起选举 → 新 Leader 产生。旧 Leader 恢复后发现自己 term 落后，自动降级为 Follower。

> 💬 **Q2：网络分区（脑裂）时会发生什么？**
>
> 🎯 假设 5 节点集群，分区为 [A,B] 和 [C,D,E]。
> - 小分区 [A,B] 无法获得多数票（3票），无法选举出 Leader，拒绝写请求
> - 大分区 [C,D,E] 可以选出 Leader，继续服务
> - 网络恢复后，小分区的节点发现新 Leader term 更高，自动同步缺失日志
> - **Raft 保证安全性：已提交的日志不会丢失，未提交的日志可能被丢弃**

> 💬 **Q3：Raft 的日志压缩怎么做？**
>
> 🎯 日志无限增长会撑爆磁盘 → 定期做 **Snapshot 快照**。Leader 发送 `InstallSnapshot` RPC 给落后太多的 Follower，直接传快照而不是逐条日志。

> 💬 **Q4：成员变更（动态增删节点）怎么保证安全？**
>
> 🎯 直接切换配置可能导致**两个独立多数集**（新旧配置各有一个多数）。Raft 采用 **联合共识（Joint Consensus）**：
> - 过渡阶段：日志需要新旧配置**同时达到多数**才能提交
> - 完全安全后，再切换到新配置

> 💬 **Q5：Raft 和 2PC 有什么区别？**
>
> 🎯 2PC 是**分布式事务协议**，解决"多个节点同时成功或失败"；Raft 是**共识协议**，解决"多个节点对同一个值达成一致"。2PC 的协调者单点故障是硬伤；Raft 通过选举机制自动恢复 Leader。

---

### 一句话速记

```
Raft = 强 Leader + 日志复制 + 多数确认 + 任期隔离

选举：超时随机化 → 先到先得投票 → 日志新者优先
复制：Leader 本地写 → 并行发 RPC → 多数确认 → 提交
安全：选举限制保证已提交日志不丢，网络分区小分区拒绝服务
```
