## 1) 今日算法题

### 多数元素（Majority Element）

**题意**：给定一个大小为 `n` 的数组，找到其中出现次数 **超过 `n/2` 次** 的元素。假设它总是存在。

```
输入: nums = [2,2,1,1,1,2,2]
输出: 2
```

### 思路：Boyer-Moore 投票算法

本周 Day 101 已经用「多数元素 II」做过 > n/3 的推广，今天回到最经典版本，把投票的本质彻底吃透：

- **配对抵消**：把数组看成一场擂台赛，候选人 `candidate` 自带 `count` 血量。
- 血量 > 0 时遇到别人 → 同归于尽（count--）；血量为 0 → 换候选人重新上场（count=1）。
- 最终站着的候选人就是多数元素 —— 因为多数元素的数量超过一半，它跟谁配对都耗得起。

```
[2, 2, 1, 1, 1, 2, 2]
 2(1) 2(2) →1(1) →1(0 换) 1(1) →2(0 换) 2(1)
 最后候选 = 2 ✓
```

### 代码

**Go：**

```go
func majorityElement(nums []int) int {
    candidate, count := 0, 0
    for _, num := range nums {
        if count == 0 {
            candidate = num
        }
        if num == candidate {
            count++
        } else {
            count--
        }
    }
    // 题目保证存在，无需二次验证
    return candidate
}
```

**Python：**

```python
def majorityElement(nums):
    count = 0
    candidate = None
    for num in nums:
        if count == 0:
            candidate = num
        count += 1 if num == candidate else -1
    return candidate
```

### 复杂度

- **时间**：O(n)，一次遍历
- **空间**：O(1)，只用两个变量

> 💡 **如果题目不保证存在**：先投票出候选，再遍历一次计数验证 `count > n/2`，两次遍历依然是 O(n)/O(1)。

> 💡 **为什么今天选它**：Boyer-Moore 投票和 Raft 选举共享同一个直觉 —— **少数派经不起消耗战**。前者比票数，后者比拿到多数派票；配对抵消 ≈ 日志复制时旧 Leader 的未提交日志被覆盖。一道算法题，顺手把共识协议的底层直觉复习了。

## 2) 面试技巧 — Week 16 分布式系统核心协议综合复习

六天内容一锅端：一张表 + 三路线 + 连环问通关。

### 📊 六大协议一张总表

| 协议 | 解决什么 | 一句话核心 | 代表系统 |
|---|---|---|---|
| **Raft** | 共识（易实现版） | 强 Leader，三驾马车：选举 / 日志复制 / 安全性，多数派交集保证不丢已提交 | etcd、Consul、TiKV |
| **Paxos** | 共识（理论最优） | 两阶段 Prepare + Accept，多数派交集，活锁靠随机退避 | Chubby |
| **Gossip** | 成员发现 & 最终一致 | 反熵（存量对齐）+ 谣传（增量广播），O(log n) 轮收敛 | Cassandra、Consul(Serf) |
| **分布式锁** | 跨节点互斥 | 三要素：互斥 · 防死锁（TTL）· 防误删（唯一 value + Lua），高级：看门狗 + fencing token | Redlock、ZK、etcd |
| **CRDT** | AP 场景冲突收敛 | 三定律：交换 + 结合 + 幂等，数学保证无需协调 | Redis CRDB、Figma、Apple Notes |
| **OT** | 协同编辑意图保持 | transform 操作变换重算坐标，CCI 模型（收敛·因果·意图保持） | Google Docs |

### 🗺️ 三条主线串起全周

**主线一：为什么需要共识？**
CAP 告诉你 P 必选、分区时 C/A 二选一（Day 102）→ 选了 C 就得有个"说了算的" → Raft/Paxos 就是造这个"说了算的"（Day 101/103）。

**主线二：不强求一致怎么办？**
AP 路线：Gossip 传播成员和状态（Day 104）→ 并发写必然冲突 → 三条冲突解决路线：
1. **避免冲突**：强一致排队（Raft/Paxos，牺牲可用性）
2. **检测 + 仲裁**：向量时钟发现并发 → LWW/仲裁裁决（Dynamo 路线，LWW 三坑：丢更新 · 时钟漂移 · 语义丢失，HLC 改进）
3. **结构收敛**：CRDT / OT 让冲突自动消失（数学/变换保证）

**主线三：锁 —— 互斥的特殊共识**
分布式锁打分表六要素：互斥 · 防死锁 · 容错 · 谁加谁删 · 看门狗续约 · fencing token（Day 105）。Redis 锁四代演进背熟：SETNX 死锁 → SET NX EX + Lua 删 → 看门狗 → Redlock 多数派（以及 Kleppmann vs Antirez 争议，知道存在即可）。

### 🎤 高频连环问通关速答

**Q1：Raft 和 Paxos 到底什么区别？**
> Paxos 是"理论上证明可行"，Raft 是"工程上让你写得出来"。Raft 强 Leader 简化了活锁和日志管理；Paxos 允许无 Leader 提案，理论更通用但实现地狱。生产选 Raft，面试聊 Paxos 显深度。

**Q2：多数派为什么是 n/2+1 而不是别的？**
> 任意两个多数派必然有交集，交集节点不可能对同一提案号投出两票 → 唯一值被确定。n/2 可能完全不相交，安全性直接崩。

**Q3：网络分区时 Raft 集群会发生什么？**
> 拿到多数派的分区继续服务（选举/复制照常），少数派拒绝写（无法提交）。分区恢复后，少数派节点以新 Leader 日志为准回滚未提交条目 —— 这就是选举限制（候选日志至少和新）存在的意义。

**Q4：Gossip 和 Raft 分工怎么理解？**
> Gossip 管"谁活着"（成员发现，AP 没关系），Raft 管"数据听谁的"（共识，必须 CP）。Cassandra = Gossip 选成员 + 读写仲裁；Consul = Serf(Gossip) 成员 + Raft 数据。

**Q5：LWW 有什么问题？怎么改？**
> 三坑：① 并发写丢更新（只留时间戳大的）② NTP 漂移导致"未来"覆盖"过去" ③ 语义丢失（A 先加 B 后删，LWW 只看时间戳）。改进：HLC（物理+逻辑时钟混合）降低漂移敏感度，或者干脆上 CRDT 让两个写都活下来。

**Q6：CRDT 三定律默写！**
> **交换律**（顺序无关）+ **结合律**（分组无关）+ **幂等律**（重复无害）。State-based (CvRDT) 全量合并 vs Op-based (CmRDT) 广播操作。G-Counter 逐分量取 max，PN-Counter 双计数器，OR-Set 加元素带唯一 tag —— "加赢过没看到的删"。

**Q7：Google Docs 为什么选 OT 不选 CRDT？**
> OT 出现更早更成熟（90 年代），意图保持（Intent Preservation）更强，配合中心服务器模型（操作先过服务器再变换分发）天然适配；CRDT 实现简单、去中心化是后发优势（Figma / Apple Notes 在用）。

**Q8：Redis 做分布式锁别人误删我的锁怎么办？**
> 三件套：SET NX EX 原子加锁 + value 存唯一 ID + 释放时用 Lua 脚本校验 value 再删（`if redis.call("get",key)==ARGV[1] then del`）。再往上：看门狗每 TTL/3 续约防业务没跑完锁到期，fencing token 把校验下沉到资源端。

**Q9：AP 系统为什么做不好分布式锁？**
> 锁错了的代价是**两个客户端同时进入临界区**，这对银行扣款是事故不是降级。AP 优先可用性，复制延迟/冲突仲裁期间可能两个节点都自认持锁 → 必须选 CP（ZK/etcd/Redis 单主）。

**Q10：向量时钟怎么判断并发？**
> 两向量时钟互相都不 ≥ 对方（每个分量都 ≤ 且不严格小）→ 并发冲突；否则存在因果先后，小的可以覆盖大的。Lamport 时钟只有全序没有并发表达，这就是它不够的痛点。

### 🧭 收尾话术：如果被问"讲讲分布式一致性"

```
「分布式一致性本质是在 CAP 的 C 和 A 之间选位置：
 要 CP 就用共识协议造单一事实源 —— Raft 工程首选，Paxos 理论标杆；
 要 AP 就用 Gossip 传播 + 冲突解决三路线：避免冲突（强一致）、
 检测仲裁（向量时钟+LWW）、结构收敛（CRDT/OT）。
 而分布式锁、幂等这些，都是一致性需求在具体场景的投影。」
```

> 一段话覆盖全周 6 天内容，面试官点头的那种。
