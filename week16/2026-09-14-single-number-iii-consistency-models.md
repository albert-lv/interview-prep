## 今日算法题

### 只出现一次的数字 III（Single Number III）

**题目来源**：[LeetCode 260](https://leetcode.cn/problems/single-number-iii/)

**描述**：给定一个整数数组 `nums`，其中**恰好有两个**元素只出现一次，其余所有元素均出现两次。找出只出现一次的那两个元素。要求时间复杂度 `O(n)`，空间复杂度 `O(1)`。

**示例**：
```
输入: nums = [1,2,1,3,2,5]
输出: [3,5]
解释: [5,3] 也是有效答案

输入: nums = [-1,0]
输出: [-1,0]
```

---

### 解题思路：位运算 — 异或的分治艺术

先回忆前置知识：**只出现一次的数字 I**（一个唯一数，其余成对），全员异或即可——相同数异或得 0，最后剩下的就是答案。

现在有两个唯一数 `a` 和 `b`，全员异或的结果是 `a ^ b`，拆不开。怎么办？

**关键洞察**：`a ^ b` 的二进制中，至少有一位是 1（a ≠ b）。找到这个**区分位**（任意一个为 1 的 bit），按这一位把数组分成两组：

- 区分位为 0 的组：a 在其中，b 不在 → 组内全员异或得到 a
- 区分位为 1 的组：b 在其中，a 不在 → 组内全员异或得到 b

而重复元素的两个副本必然被分到同一组（二进制完全相同），在组内互相抵消。**问题被降解成了两个 Single Number I。**

**算法步骤**：

1. 全员异或得到 `xor = a ^ b`
2. 取 `xor` 中任意一个为 1 的位：`mask = xor & (-xor)`（lowbit，取出最低位的 1）
3. 遍历数组，按 `num & mask` 是否为 0 分成两组，分别异或
4. 两个结果就是答案

---

### 代码实现

```go
package main

import "fmt"

func singleNumber(nums []int) []int {
    xor := 0
    for _, num := range nums {
        xor ^= num
    }
    // lowbit：取出 xor 二进制中最低位的 1
    // 原理：-xor 是 xor 的补码（取反 +1），与原数按位与只剩最低位的 1
    mask := xor & (-xor)

    a, b := 0, 0
    for _, num := range nums {
        if num&mask == 0 {
            a ^= num
        } else {
            b ^= num
        }
    }
    return []int{a, b}
}

func main() {
    fmt.Println(singleNumber([]int{1, 2, 1, 3, 2, 5})) // [3 5]
    fmt.Println(singleNumber([]int{-1, 0}))            // [-1 0]
}
```

```python
def single_number(nums):
    xor = 0
    for num in nums:
        xor ^= num
    mask = xor & (-xor)          # 最低位的 1
    a = b = 0
    for num in nums:
        if num & mask == 0:
            a ^= num
        else:
            b ^= num
    return [a, b]
```

### 复杂度分析

| 维度 | 结果 | 说明 |
|---|---|---|
| 时间复杂度 | **O(n)** | 两遍遍历，异或 O(1) |
| 空间复杂度 | **O(1)** | 只用常数变量 |

> 💡 lowbit 是经典位运算技巧：`x & (-x)` 取出最低位的 1。在树状数组里也用同一招。

### 面试官会怎么追问

> 💬 **面试官**：如果"恰好两个唯一"改成"恰好 k 个唯一"（其余成对），还能做吗？

🎯 **你**：位运算方法依赖"按位分组后问题独立降解"，k > 2 时不好直接拆。通用解法是哈希计数 O(n) 空间。但如果 k 很小且内存受限，可以**逐位投票**：统计每一位上 1 出现的次数，模 2 后逐位还原每个唯一数——不过需要知道唯一数个数。本质上这暴露了一个信息论下界：**要分离 k 个唯一数，需要至少 log k 次"线性扫描级别的信息"**。

> 💬 **面试官**：负数怎么办？lowbit 对负数有效吗？

🎯 **你**：有效。补码表示下 `-x = ~x + 1`，`x & (-x)` 对正负数都成立。比如 `x = -6`（…1010），`-x = 6`（…0110），`x & (-x) = 2`，同样取出最低位的 1。Go/Python/Java 都无需特判。

> 💬 **面试官**：不用 lowbit，怎么找区分位？

🎯 **你**：可以从最高位往最低位扫（`1<<31, 1<<30, ...`），第一个满足 `xor & (1<<i) != 0` 的位就是区分位。效率一样 O(1)（固定位宽）。lowbit 只是更优雅的一行写法。

## 面试技巧

### 分布式一致性模型与 CAP/BASE

分布式系统面试的"魂"就在这里：**一致性和可用性不可兼得，你要做的是知道自己在哪条曲线上选择了哪个点。**

---

### 1. 一致性模型光谱（由强到弱）

| 一致性级别 | 保证内容 | 代表系统 |
|---|---|---|
| **线性一致性**（Linearizability） | 所有操作看起来都在**调用与返回之间的某个瞬间**原子生效，全局单一时间线 | ZooKeeper、etcd、单节点 Redis |
| **顺序一致性**（Sequential） | 所有进程看到**同一顺序**的操作，但不要求与实时序一致 | —（理论基准） |
| **因果一致性**（Causal） | 有**因果关系**的操作（读写同 key、消息传递）顺序全局一致 | COPS、DynamoDB 的会话一致性 |
| **最终一致性**（Eventual） | 无更新后经过足够时间，所有副本收敛到相同值 | Cassandra、DynamoDB、CouchDB |

**记忆锚点**：
- 线性一致性 = **实时 + 原子**（ strongest，代价最高）
- 顺序一致性 = 顺序统一，但允许"时间弯曲"（弱化实时性）
- 因果一致性 = 只保证**有逻辑依赖的**操作不乱序
- 最终一致性 = 只保证**收敛**，中间随便乱

**一句话区分线性与顺序**：线性一致性下，如果操作 A 在真实时间中先于 B 完成，那 B 必须能看到 A 的效果；顺序一致性只要求**大家看到的顺序都一样**，哪怕这个顺序与真实时间不符。

---

### 2. CAP 定理：不是三选二，是分区时的二选一

**正式表述**：分布式系统最多只能同时满足以下三项中的两项：

- **C（Consistency）**：一致性，每次读都读到最近一次写入的值（或报错）
- **A（Availability）**：可用性，每次请求都能收到非错误响应（不保证数据最新）
- **P（Partition Tolerance）**：分区容错，网络分区（丢包/延迟/断链）时系统仍能运行

**面试必说的核心认知**：

> 🎯 **P 不是"可选"的，是必选。** 网络一定会分区（拜占庭将军：消息可能延迟、丢失、重复），所以 CAP 的真实含义是：**当分区发生时，你要在 C 和 A 之间二选一。**

- 选 C（拒绝/阻塞请求直到分区恢复）→ **CP 系统**：ZooKeeper、etcd、HBase、MongoDB（默认）
- 选 A（继续服务，可能返回旧数据）→ **AP 系统**：Cassandra、DynamoDB、Eureka、CouchDB

**典型场景速答**：

| 场景 | 系统类型 | 理由 |
|---|---|---|
| 服务注册发现 | AP（Eureka）/ CP（ZK） | 注册中心挂了不能导致全服务瘫痪 |
| 分布式锁 / 选主 | CP（etcd/ZK） | 锁必须强一致，宁可不可用也不能错发锁 |
| 会话缓存 | AP（Redis 主从 + 哨兵，异步复制） | 读旧会话数据好过 5xx |
| 银行转账 | 严格一致 + 事务补偿 | 正确性 > 可用性 |

---

### 3. BASE 理论：对 ACID 的柔性妥协

BASE 是 AP 系统的理论框架，三个词：

- **BA（Basically Available）**：**基本**可用——允许部分失败（限流、降级、熔断），但不整体瘫痪
- **S（Soft State）**：**软状态**——允许中间状态（副本不一致）在一段时间内存在
- **E（Eventually Consistent）**：**最终一致**——软状态结束后，所有副本将收敛

**与 ACID 的对照记忆**：

| ACID（单机事务） | BASE（分布式） |
|---|---|
| 强一致 | 最终一致 |
| 事务要么全成要么全败 | 允许中间态 |
| 隔离性 | 软状态 |
| 持久性 | 基本可用（牺牲可用性保证持久） |

> 💡 面试金句：**"BASE 是 CAP 中 AP 的延伸，是对互联网场景高并发、高可用需求的工程回应——不是放弃一致性，而是接受'收敛需要时间'。"**

---

### 4. PACELC：CAP 的实战加强版

CAP 只描述分区时的情况，PACELC 补上了**正常时**的权衡：

> **P**artition：如果发生分区
> **A** 还是 **C**？E**L**se（否则）：**L**atency 还是 **C**onsistency？

| 系统 | 分区时 | 正常时 | 解读 |
|---|---|---|---|
| Cassandra / Dynamo | A | L | 永远优先低延迟，最终一致性兜底 |
| ZooKeeper / etcd | C | C | 永远选一致，代价是写延迟 |
| MongoDB | C | C | 强一致配置下，写必须走主节点 |
| PNUTS | A | C | 分区时可用，正常时一致（按 record master 路由） |

面试中提 PACELC 是**加分项**：说明你不只背 CAP 结论，还理解系统在"无分区时也在做一致性 vs 延迟的取舍"。

---

### 5. 读己之写 / 单调读 / 会话一致性（工程落地四件套）

最终一致性下，客户端体验靠这些"**会话级保证**"维持：

| 保证 | 含义 | 实现手段 |
|---|---|---|
| **读己之写**（Read Your Writes） | 自己写的，自己再读必须看到 | 写后短时间内读主 / 版本戳校验 / quorum R+W>N |
| **单调读**（Monotonic Read） | 不会读到比之前更旧的数据 | 读粘滞副本（sticky session） |
| **单调写**（Monotonic Write） | 同一客户端的写按发起顺序生效 | 路由到同一分区 / 版本向量排序 |
| **写后读一致**（Read After Write） | 等价于读己之写的跨会话推广 | quorum 读写 + 向量时钟 |

### 6. 高频连环问速答模板

> 💬 **Q：CAP 中 C 和 ACID 的 C 是一回事吗？**

🎯 A：**不是。** CAP 的 C 是**单一一致性**（所有节点同一时刻看到同一份数据），ACID 的 C 是**约束一致性**（事务执行前后数据库满足所有完整性约束）。一个是"多副本对齐"，一个是"数据合法"。

> 💬 **Q：Redis 是 CP 还是 AP？**

🎯 A：分情况。**单机 Redis** 线性一致（单点天然满足）；**主从 + 异步复制**是 AP（主挂了，从提升可能丢数据）；**Redis Cluster** 默认 AP，但用 WAIT 命令可以逼近 CP。而 **etcd/ZK 用 Raft/Paxos 共识，是 CP**——这是分布式共识协议与主从复制的本质区别：**共识协议保证多数派确认后才提交，主从复制是 fire-and-forget。**

> 💬 **Q：既然 AP 系统最终一致，那怎么实现分布式锁？**

🎯 A：**不要用 AP 系统做分布式锁。** 分布式锁必须 CP——锁错发的代价（两个客户端同时拿到锁）远大于短暂不可用。所以选 etcd/ZK/Redis RedLock（RedLock 有争议，GC pause 会破坏其假设）。锁的本质是**共识问题**，而 AP 系统设计上就放弃了共识。

> 💬 **Q：怎么在 AP 系统上实现"读己之写"？**

🎯 A：三种手段——
> 1. **版本戳 + 读等待**：写返回 version，读时若副本 version < 写 version 则等待/重定向主
> 2. **Quorum 读写**：R + W > N，读写集合必有交集
> 3. **会话粘滞**：写后一小段时间内的读都路由到主副本

> 💬 **Q：CAP 是 2000 年提出的，现在还有效吗？**

🎯 A：有效，但要理解它的**前提假设是单变量——网络分区**。现实中的系统往往提供更细粒度的一致性选择（如 DynamoDB 的 per-request consistency、Cassandra 的 ANY/ONE/QUORUM/ALL 读写级别），本质上是把 CAP 的极端二选一变成**可调光谱**。
