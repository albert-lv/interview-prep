## 一、今日算法题：滑动窗口最大值（LC 239 · Sliding Window Maximum）

### 题目

给定整数数组 `nums` 和滑动窗口大小 `k`，返回每个窗口位置的最大值。窗口从数组最左侧滑动到最右侧，每次只移动一格。

```
示例: nums = [1,3,-1,-3,5,3,6,7], k = 3
窗口过程: [1,3,-1]→3  [3,-1,-3]→3  [-1,-3,5]→5  [-3,5,3]→5  [5,3,6]→6  [3,6,7]→7
输出: [3,3,5,5,6,7]
```

约束：`1 ≤ k ≤ nums.length ≤ 10⁵`，`-10⁴ ≤ nums[i] ≤ 10⁴`。**暴力 O(nk) 会超时，要求 O(n)。**

### 思路：单调双端队列

**关键观察：窗口向右滑动时，左侧出界的元素和右侧新进的元素，让「重新扫描整个窗口找最大值」变成重复劳动。能不能让结构自己记住「当前窗口里谁还能当最大值」？**

单调队列的核心不变量：**队列从头到尾（队头→队尾）对应的值单调递减**。维护两条纪律：

1. **入队纪律**：新元素 `x` 进来时，从队尾弹出所有比 `x` 小的元素再入队。为什么敢弹？因为那些小元素比 `x` 早进窗口（会更早出界），**有 `x` 在的日子里它们永远轮不到当最大值**——它们对「最大值」这个问题已经死了。
2. **出队纪律**：窗口滑动导致下标 `i-k` 出界时，如果队头正好是它，队头出队。队头永远是当前窗口最大值的下标。

```
nums = [1,3,-1,-3,5,3,6,7], k = 3

i=0 x=1   队列: [0(1)]          窗口未满
i=1 x=3   弹出 1 → 队列: [1(3)] 窗口未满     ← 1 被 3 杀死
i=2 x=-1  队列: [1(3), 2(-1)]   窗口满 → ans=[3]
i=3 x=-3  队头 1(3) 出界? i-k=0, 队头是1, 不出界
          队列: [1(3),2(-1),3(-3)] → ans=[3,3]
i=4 x=5   弹出 -1,-3,3 → 队列: [4(5)]        ← 一次弹三个
          → ans=[3,3,5]
i=5 x=3   队列: [4(5),5(3)] → ans=[3,3,5,5]
i=6 x=6   弹出 3,5 → 队列: [6(6)] → ans=[3,3,5,5,6]
i=7 x=7   弹出 6 → 队列: [7(7)] → ans=[3,3,5,5,6,7]
```

**为什么这是 O(n)**：每个元素最多入队一次、出队一次（出队只有两种死法：被更大的后来者杀死，或正常出界），摊还分析每个元素 O(1)，总 O(n)。这是「单调栈/单调队列」家族的通用复杂度论证——**和并查集的路径压缩一样，要说「摊还」二字**。

### 代码（Go）

```go
func maxSlidingWindow(nums []int, k int) []int {
    n := len(nums)
    ans := make([]int, 0, n-k+1)
    q := make([]int, 0, k) // 存下标，值单调递减

    for i, x := range nums {
        // 入队纪律：杀死所有比自己小且更老的元素
        for len(q) > 0 && nums[q[len(q)-1]] <= x {
            q = q[:len(q)-1]
        }
        q = append(q, i)

        // 出队纪律：队头出界
        if q[0] <= i-k {
            q = q[1:]
        }

        // 窗口形成后开始收答案
        if i >= k-1 {
            ans = append(ans, nums[q[0]])
        }
    }
    return ans
}
```

### 复杂度

- 时间 **O(n)**：每个元素入队一次、被弹出最多一次（摊还）。
- 空间 **O(k)**：队列最多同时存 k 个下标。

### 工程映射：单调队列 = 熔断器的滑动窗口计数器

这道题不是「又一个数据结构 trick」，它是**熔断器（Circuit Breaker）计数器的裸机模型**：

- **滑动窗口** = 熔断器的统计窗口（Polly/Resilience4j 默认「最近 10 秒内」或「最近 N 次调用」）；
- **窗口内取最大值** = 窗口内最坏信号决定系统行为——熔断器看的是「窗口内失败次数是否超阈值」，Redis 的 sliding window rate limiter 用的是「窗口内请求计数」，本质都是**固定长度窗口上的聚合统计**；
- **杀死比自己小的元素** = 信号衰减：5 分钟前的 500ms 延迟 spike，被最近 3 次健康响应覆盖后不再驱动决策——**旧信号不能无限期绑架当前判断**；
- **队头即答案** = O(1) 读路径：熔断器每次请求都要查「当前该不该放行」，判定必须是常数时间，不能每次重扫窗口。

更进一步，窗口聚合三兄弟在工程里各司其职：**最大值 → 熔断判定（最坏信号）/ 求和 → 限流计数（吞吐配额）/ 平均值 → 延迟基线（告警阈值）**。LC 239 是三者里唯一需要「消灭过期候选」的，所以用单调队列；求和用前缀和差值就行（固定窗口滑动的 O(1) 技巧）。

### 进阶阶梯六连

1. **动态窗口 / 双端可变**：窗口大小由外部信号决定（如「错误率升高时把统计窗口从 10s 缩到 2s 提高灵敏度」）→ 单调队列不变，出界判断从 `i-k` 改成「队头时间戳 < now - window」。工程读法：**自适应熔断窗口**，Netflix 的并发熔断器就是这么调灵敏度的。
2. **求窗口第 K 大**：单调队列直接报废（它只保最大值）→ 需要双堆（维护 k 个最大）或平衡树（窗口内 multiset），O(n log k)。诚实答「最大值有特殊结构，第 K 大没有」= 对结构边界的清晰认知。
3. **多路流并行窗口**：N 个服务各出一个指标流，全局熔断要「任一服务窗口内失败率超阈值即熔断」→ N 个单调队列并行扫，或归并成时间事件流统一入队。面试加分句：**「多流窗口的难点不在结构在时钟——各服务时钟漂移会让窗口边界错位，先对齐时间戳」**（呼应 Day 155 Lamport 全序）。
4. **加权窗口**：老信号权重衰减（exponential decay window）→ 单调性被破坏（衰减后的大小关系会翻转），单调队列失效，退化为定时重建的桶聚合。工程读法：**衰减窗口用桶，固定窗口用队列——结构跟着权重语义选**。
5. **在线 percentile**：窗口内 P99 延迟（告警系统的真实需求）→ 精确解需要平衡树 O(n log k)；工程近似用 t-digest 或桶直方图（误差换 O(1)）。这是面试官区分「背过题」和「做过系统」的标准一题。
6. **回到本题的最大坑**：写成「每次入队时只弹一个队尾」或「出界判断用 `q[0] == i-k`」（漏掉队头早已不是 i-k 的情况）——窗口题的三个经典 bug：**越界用 `<=` 不是 `==`、弹队列用 `for` 不是 `if`、收答案从 `i >= k-1` 开始不是 `i >= 0`**。

## 二、面试技巧：容错分类与自动恢复

### 1. 故障分类学：三档进阶（把 Day 151 的表升级成决策表）

| 档位 | 定义 | Agent 世界的实例 | 检测手段 | 恢复手段 | 重试安全吗 |
|---|---|---|---|---|---|
| **Crash** | 进程消失 | 容器 OOM、进程被 kill、机器掉线 | 心跳消失 | 重启 / checkpoint 恢复 / 副本接管（Day 154） | ✅ 天然安全（什么都没做成就死了） |
| **Omission** | 活着但没响应/没进展 | LLM API 超时、队列堆积、agent 空转烧 token（Day 155 进展探针） | 超时 + 进展 counter | 重试 + 幂等 + 降级 | ⚠️ **必须幂等**（可能做成了但响应丢了） |
| **Byzantine** | 任意偏离协议，包括说谎 | 幻觉自信陈述、日志篡改（METR 7%）、伪装研究（Day 151） | 交叉验证 + 行为基线 | 隔离 / 投票 / kill switch | ❌ 绝不（重试=给作恶节点更多机会） |

**面试时这张表的正确用法是「先分类、再谈恢复」**。被问「这个接口不稳定怎么办」，第一句话永远是：「先问清它怎么个不稳定法——挂掉、超时、还是返回错数据？三种情况的治疗方案完全不同。」直接答「加重试」的候选人，等于没分类就开抗生素。

### 2. 重试设计四件套：指数退避 + 抖动 + 预算上限 + 错误分类

裸重试是分布式系统的最常见事故源。生产级重试四件套：

1. **指数退避**：`delay = base × 2^attempt`（base 一般 100ms~1s）。为什么不是固定间隔：固定间隔下，后端恢复瞬间所有客户端同时重试 → **重试风暴（retry storm）**把刚恢复的后端再次打挂——雪崩的第二种形态（第一种是级联，见下）。指数退避让客户端在时间上自动错开。
2. **抖动（jitter）**：`delay = base × 2^attempt × (1 + random×0.5)`。**没有抖动的指数退避只是把风暴的周期拉长，没有消灭同相性**。AWS 的工程规范原话：「FullJitter 把重试峰值摊平一个数量级」。
3. **预算上限**：重试次数硬顶（一般 ≤3 次）+ **总超时预算**（整次调用链有 deadline，单次重试不能超过剩余预算的一半）。没有预算上限的重试 = 把一次 1s 的故障放大成 30s 的悬挂。
4. **错误分类**：只有**瞬态错误**（timeout / 429 / 5xx / connection reset）值得重试；**永久错误**（4xx 参数错、权限不足、schema 校验失败）重试多少次都是失败，应立即 fail-fast。腾讯云 2026 工程实践的原文口径：「重试仅针对瞬态错误，永久错误立即失败避免浪费资源」。

**面试金句**：「重试是承认'我不知道刚才成没成'——所以重试的完整公式是 `retry + idempotency + backoff + budget`，缺一就是事故。」

### 3. 幂等：重试的前提，不是可选项

Omission 故障的本质：**请求可能到达了，响应可能丢了**。此时重试 = 第二次执行同一个写操作——没有幂等，就是双扣款、双发邮件、双建 issue（Day 150 支付账本的 idempotency key 同构）。

幂等实现三档（按面试时能讲清的深度排）：

- **幂等键**：调用方生成唯一 key（`task_id + agent_id + counter`），服务端按 key 去重，重复请求返回首次结果。工程细节：key 要带进**同一次重试的所有 attempt**（重试时换新 key = 自己去掉了幂等性）；key 要带 TTL（至少覆盖最大重试窗口）。
- **自然幂等**：读操作天然幂等；`SET x=5` 幂等而 `x+=1` 不幂等（所以状态恢复优先快照+绝对值，少记 delta）。
- **去重副作用**：无法去重的下游（发邮件、发短信），用「outbox 模式」——业务写入和「待发任务」同事务落库，后台 worker 异步投递，天然支持重放。

**Agent 时代的特殊性**：LLM 调用本身**不是幂等的**（temperature > 0 时同一 prompt 两次输出不同）。对「重试 LLM 调用」要补一句：「要么 temperature=0 的变体可视为准幂等，要么把重试收敛在**工具调用层**（工具幂等）而不是模型层」——这是 2026 年面试官会追问的新坑。

### 4. 熔断器三态状态机：Closed → Open → Half-Open

熔断器是「失败次数驱动的自动断路器」，三态状态机（必须能默画）：

```
            失败率/次数超阈值 (如 最近10次失败≥5)
  ┌──────┐ ──────────────────────────────▶ ┌──────┐
  │CLOSED│                                  │ OPEN │
  │ 闭合  │ ◀── 半开探测成功 (连续N次成功) ── │ 断开 │
  └──┬───┘                                  └──┬───┘
     │                                         │ 冷却期到 (如 30s)
     │ 正常放行                                ▼
     │                                  ┌──────────┐
     └──── 探测失败立即跳闸 ◀────────── │ HALF-OPEN│
                                       │ 半开试探 │
                                       └──────────┘
```

- **Closed**：请求正常通过，计数器在**滑动窗口**内累计失败次数（=今天的 LC 239：窗口聚合判定）。窗口计数的好处：早高峰的一次性故障不会在晚高峰仍压着熔断不放——**旧信号自动衰减出窗**，和单调队列「杀死过期候选」同一个思想。
- **Open**：请求直接 fail-fast（返回降级响应），**不放行真实调用**。为什么宁可报错也不试试：服务已经病了，每个试探请求都在消耗它最后的处理能力，也在消耗调用方的超时预算——**熔断的本质是止损**。
- **Half-Open**：冷却期过后放行**有限探测流量**（1 个或 N 个请求），全部成功 → Closed；任何一个失败 → 重新计时冷却。**Half-Open 是状态机里最考验实现的状态**：并发探测要把流量窗口收紧到 1，否则 100 个并发请求同时涌入病服务 = 重试风暴的另一种形态。

**进阶追问三板斧**：①三个参数怎么定（窗口大小 / 阈值 / 冷却期）——答案是「**从混沌实验来，不从拍脑袋来**」：注入 200ms 延迟看熔断是否触发、掐表验证冷却期足够病服务恢复；②**熔断之后干什么**——降级响应（缓存数据/只读模式/排队异步处理），Day 155 的 kill switch 四步里的「处置」在量产系统里 99% 是降级而不是全停；③**熔断器自己怎么被监控**——S-1 原话「监控系统发生过被无意关闭，未来仍可能再次发生」，熔断器的状态迁移必须进审计日志（Day 149 哈希链），**熔断跳闸而不告警 = 故障被悄悄吞掉**。

### 5. 恢复策略矩阵：什么故障用什么药

| 故障层 | 典型时延要求 | 策略 | Agent 世界实例 |
|---|---|---|---|
| 瞬时层（毫秒~秒） | 用户无感知 | 重试（退避+抖动+预算）+ 超时 | LLM API 429/5xx 自动重试 |
| 执行层（秒~分钟） | 可感知但可接受 | checkpoint 恢复 / 替代路径 / 降级 | 工具调用失败换备用工具；从最近 checkpoint resume（Day 154） |
| 系统性（分钟~小时） | 业务受损 | 回滚到已知良好版本 / 人工接管 / kill switch | 模型版本回滚（隐性回归，Day 152）；行为异常 agent 熔断隔离 |

阿里云 2026 年 AgentOps 实践的三层自愈架构就是这个矩阵的产品化（瞬时层：指数退避重试、熔断器、超时控制；执行层：检查点恢复、替代路径、降级策略；系统层：自动回滚、人工审核、模型切换）。**面试话术：「恢复策略按故障的 TTL 分层——层数不是越多越好，每层都有成本，层间要有明确的升级条件」**。

### 6. 自动恢复的成本账：恢复动作本身可能扩大故障

最容易被忽略的第四问：**恢复是有副作用的医疗行为**。

- **重试风暴放大后端压力**（上面已述）；
- **副本接管放大状态不一致**：多副本同时写同一资源 → 需要 leader 选举或幂等去重，否则恢复比原故障更糟；
- **自动回滚放大数据问题**：新版本已写入新 schema 的数据，回滚到旧版本代码读不了 → 「前滚修复（roll-forward）优于回滚」的原则；
- **自动恢复循环（flapping）**：服务抖动 → 熔断 → 半开恢复 → 又抖 → 又熔断，进入振荡。工程对策：冷却期指数增长（断路器抖一次，冷却期 ×2）、**单位时间最大恢复次数**、连续 N 次自动恢复失败后锁定为人工状态。

S-1 的「未对齐行为可能在被发现前复合放大」就是这个账的极端版：**恢复每多绕一圈，故障的传播半径就多一圈**。所以 kill switch 的处置顺序（Day 155 四步：取证 → 分级判定 → 处置熔断 → 入册回归）里，「分级判定」一步存在的全部意义就是**别让恢复动作比故障本身更莽**。

### 7. 模拟面试速答五连

- **Q1：下游接口 P99 延迟飙升，你怎么处理？**
  先分类：是全局还是单实例（单实例 = 灰度/热点问题，摘流量即可）？是网络层还是应用层（错误率伴随上升 = 应用层，纯延迟 = 队列/GC/依赖）？止血三板斧：超时收紧防悬挂、熔断降级防拖累主链路、降级缓存保读路径。恢复后做复盘：窗口内最大延迟（今天算法题的工程版）进告警基线。**收尾一句：「延迟问题的第一原则是别让等它的人无限等下去——超时本身就是一种容错」**。

- **Q2：重试和熔断什么关系？能不能只要一个？**
  重试解决「偶发瞬时故障」，熔断解决「持续故障下保护双方」。只要重试不要熔断 = 后端持续故障时客户端以指数增长的速率持续打它（重试次数 × 请求量），重试风暴把故障放大成全站事故；只要熔断不要重试 = 浪费掉 99% 的偶发抖动（一次超时就熔断，系统永远在抖动）。**两者是串联的：重试在调用内（小尺度），熔断在调用外（大尺度），重试失败计数喂给熔断器，熔断器开门后重试自动失去意义**。

- **Q3：幂等键怎么设计？agent 场景有什么特殊？**
  构成：`{task_id}:{agent_id}:{op_counter}` 或内容哈希 `{user}:{tool}:{canonical_args}`；要求：重试复用同一 key、TTL > 最大重试窗口、服务端去重存储带原子性（SETNX）。Agent 特殊处：①LLM 调用本身非幂等（temperature>0），幂等要做在**工具/副作用层**；②多 agent 并发写同一资源时幂等键会碰撞 → 需要「意图级」key 而非「调用级」key；③写入是用户触发的（表单提交）时 key 随表单生成，agent 自主决定写入时 key 由账本树生成（Day 150 task_id 主键体系）。

- **Q4：熔断器跳闸了但监控没告警，可能是什么原因？**
  这正是 S-1 点名的故障：「监控被无意关闭/配置错误」。排查方向：①熔断器状态迁移是否进日志（很多实现只记 metric 不记事件，而 metric 采集管道本身可能断）；②告警规则是否依赖了被熔断的同一条链路（监控系统自己依赖业务系统 = 自举失败）；③半开探测流量是否被负载均衡稀释（探测请求打到健康实例，结论失真）。**答出「用混沌演练验证：手动触发熔断，检查告警链路是否报警」= 标准动作**。

- **Q5：设计一个 7×24 coding agent 的自动恢复系统。**
  分层答：瞬时层——LLM/工具调用重试（退避+抖动+预算，错误分类）；执行层——checkpoint 自动保存（Day 154）+ 从最近 checkpoint resume + 工具失败替代路径；系统层——行为基线偏离触发自动暂停 → 隔离实例取证（Day 155）→ 人工接管或 kill switch；全局——恢复次数/flapping 监控、每次自动恢复进审计日志。**最后一定要补：「自动恢复的边界是『恢复动作的副作用大于收益』——超过这个边界，宁可挂起等人，不要自作聪明」**。

### 8. 今日金句

> **故障分类决定治疗方案：crash 靠重启、omission 靠幂等重试、Byzantine 靠不信任任何单节点。重试的完整公式是退避 + 抖动 + 预算 + 幂等，缺一都是事故；熔断器的完整生命周期是窗口计数、跳闸止损、半开试探，每一跳都要进审计。而 Anthropic 在 S-1 里那句「过去我们未能察觉，将来也可能在研发速度显著加快之后才察觉到」，是整个容错工程最诚实的边界声明——容错系统自己会坏（监控被无意关闭），恢复动作自己会闯祸（重试风暴、flapping），所以当系统复杂到连制造它的人都无法实时察觉它的变化时，工程上唯一可靠的姿势只剩下：每一层故障都假设上一层保护已失效，每一次恢复都预设它可能扩大故障，每一台熔断器都被另一双眼睛看着。运动员不能兼任裁判，而裁判席上，也必须坐着两个人。**
