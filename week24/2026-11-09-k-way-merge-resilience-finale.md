## 一、今日算法题：合并 K 个升序链表（LC 23）

### 题目

给定 `k` 个升序链表的头节点，把它们合并成一个新的升序链表并返回。

```
输入：lists = [[1,4,5],[1,3,4],[2,6]]
输出：[1,1,2,3,4,4,5,6]
```

### 工程读法（为什么收官选这道题）

Week 24 讲了一整周「7×24 长时程 agent 的韧性」：checkpoint 事件日志（Day 154）、心跳与进展探针事件（Day 155）、熔断器状态迁移记录（Day 156）、混沌注入与 GameDay 记录（Day 157）。**这些全部是事件流——而且每一类事件流各自 append-only、各自有序。**

那么问题来了：**全局可观测性 = 把这 k 条有序事件流合并成一条全局有序时间线。**

- 每条 agent 的审计日志 = 一个升序链表（本地时钟或 Lamport 时钟定序）
- 多 agent 系统的根因分析 = 「把所有人这段时间的日志按时间排到一起我看看」
- **K 路归并就是「上帝视图」的构造算法**——币安案复盘（Day 157）之所以能画出「6 月 A → 9 月 B → 10/20 横向移动 → 10/29 轰炸」的完整攻击时间线，本质就是把多条异构日志源归并成一条全局序
- Perplexity Teammates（11/9 上线，次日自动化运行量 ×3.7）这类 7×24 个人 agent 产品，后台必然有一个多源事件归并层

**K 路归并是「可观测性三支柱」里 traces 的底层算法：span 从多节点汇集，按时间戳归并成一棵 trace 树。**

### 思路一：最小堆（标准解法）

**核心不变量**：小顶堆永远装着「每个链表的当前头节点」。每轮弹出全局最小的那个，输出，然后把该链表的下一个节点压回堆。

```
堆初始化：k 个链表头入堆          O(k)
循环：弹出堆顶（全局最小）→ 输出
      → 同链表的下一个节点入堆    每轮 O(log k)
总共 N 个节点，每节点入堆出堆各一次
总复杂度：O(N log k) / 空间 O(k)
```

**为什么堆大小只跟 k 有关而不是 N**：任何时刻每个链表只有一个代表坐在堆里——归并的进行式只需要「每路当前最小」，不需要「每路全部」。**内存友好性正是 k-way merge 成为外排序核心（归并阶段）的原因**（Day 143 存储栈呼应：磁盘上的顺串 = k 条有序流，内存只放 k 个指针）。

```go
type Item struct {
    Val  int
    Node *ListNode
}

type MinHeap []Item

func (h MinHeap) Len() int            { return len(h) }
func (h MinHeap) Less(i, j int) bool  { return h[i].Val < h[j].Val }
func (h MinHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *MinHeap) Push(x interface{}) { *h = append(*h, x.(Item)) }
func (h *MinHeap) Pop() interface{} {
    old := *h
    n := len(old)
    item := old[n-1]
    *h = old[:n-1]
    return item
}

func mergeKLists(lists []*ListNode) *ListNode {
    h := &MinHeap{}
    heap.Init(h)
    for _, head := range lists {
        if head != nil {
            heap.Push(h, Item{Val: head.Val, Node: head})
        }
    }
    dummy := &ListNode{}
    tail := dummy
    for h.Len() > 0 {
        item := heap.Pop(h).(Item)
        tail.Next = item.Node
        tail = tail.Next
        if item.Node.Next != nil {
            heap.Push(h, Item{Val: item.Node.Next.Val, Node: item.Node.Next})
        }
    }
    return dummy.Next
}
```

### 思路二：分治两两合并

```
mergeKLists(lists) = merge( merge(lists[0..k/2]), merge(lists[k/2..k]) )
底层 = LC 21 合并两个有序链表（dummy 节点 + 双指针）
```

复杂度同样是 O(N log k)，但常数不同：
- 堆法：每节点走堆，log k 次比较 + 堆的缓存不友好（指针跳跃）
- 分治法：前 log k 轮处理的链表短、后几轮链表长——总比较次数同阶，但**顺序访问缓存友好**，实测常数往往更小
- **面试加分句**：「语言标准库的答案就是这两个——Python `heapq.merge` 是堆法，归并排序的 merge 阶段是分治法的两路版。」

### 思路三：败者树（工程进阶）

k 很大时（外排序场景 k = 数百路归并段），每次 `pop+push` 要做 2 次 `log k` 的堆调整。**败者树把每次选出最小值的比较次数从 O(log k) 降到 O(1) 摊还（只需重赛那条刚被更新的路径）**，选最小比较 ⌈log₂k⌉ 次。DBMS 和外部排序引擎的标配（408 数据结构标准考点）。

### 坑三连 & 进阶六连

**坑**：
1. 空链表直接跳过（`if head != nil`），否则堆里有 nil 指针炸掉
2. `Pop` 后记得把同链表的下一个补进来——归并的进行式不变量
3. dummy 节点省掉头插的特殊判断

**进阶**：
1. **LC 378 有序矩阵中第 K 小**：矩阵每行有序 = k 个有序数组 → 多路归并数到第 k 个；或二分答案
2. **LC 373 查找和最小的 K 对数字**：两个数组两两配对和构成隐式有序矩阵 → 多路归并 + 去重 visited 集合
3. **LC 632 最小区间**：k 个列表各取一个数，求覆盖所有列表的最小区间——多路归并 + 时刻维护当前覆盖窗口
4. **外排序**：内存装不下 → 先分块排序落盘（顺串）→ 多路归并归回去；置换选择排序产出 ≥2 倍内存的超长顺串
5. **分布式归并**：各路数据在不同节点 → 每节点先本地归并 → 中心节点做最后一层 k-way merge（和 MapReduce 的 shuffle-sort 同构）
6. **加权归并**：各路流速率不同（币安案：钱包签名日志速率 ≫ HR 邮件日志）→ 归并时按速率配比预取缓冲；**速率 skew 是多路归并最真实的工程问题**

### 一句话速答

> **K 路归并：小顶堆存每路当前头，弹最小补后继，O(N log k)。它是把 k 条有序事件流合成全局时间线的算法——审计日志合并、trace 汇集、外排序归并阶段、倒排索引合并，全都这一个结构。**

### 4. 模拟面试速答六连

**Q1：progress probe 和 liveness probe 的本质区别？**
> 进程活着不等于任务在动。vLLM 92 字节请求、DeepSeek「基建活性≠任务进展」、agent 空转烧 token 全是活例子。L3 三要素：进展事件（工具成功/文件写入/测试通过）+ 静默阈值（超 T 秒 suspicion，连续 N 次失速）+ 外部裁决（结论交 Watchdog——运动员不能兼任裁判）。

**Q2：agent 卡死了，恢复顺序？**
> 三板斧按成本升序：重启（丢现场，最快）→ resume 到最近 checkpoint（保现场，需要事件日志）→ 人工接管（最贵，需要交接文档）。**能不能 resume 取决于 checkpoint 存了什么——Day 154 五问就是为此。**

**Q3：恢复动作会不会让故障更糟？**
> 会，所以每次恢复前过成本账：重试风暴放大后端 / 副本接管放大不一致 / 自动回滚放大 schema 问题（前滚优于回滚）/ flapping 振荡（冷却期指数增长 ×2 + 单位时间恢复次数上限 + 连续 N 次失败锁人工）。S-1 原话：「未对齐行为在发现前复合放大」。

**Q4：重启 monitor 本身有多可靠？（今日热点论文）**
> 11/6 HuggingFace 热点论文 *Monitor Accuracy Isn't the Answer* 给了精确答案：**90% 准确率的 restart monitor 可以让任务成功率从 -5% 摆到 +35%，差异完全取决于「替换尝试的残余预算成功概率」**。也就是说——monitor 准确率不是关键，**checkpoint 质量（恢复后还能不能成）才是**。低质量 checkpoint + 高准确率 monitor = 稳定地把好任务换成坏任务。决策价值框架：评估 monitor 要看「告警→行动→结果」整条链，不是只看分类指标。**这直接印证了我们 Day 154 的金句：checkpoint 的价值不在你写它的那一刻，而在你不得不依赖它的那一刻。**

**Q5：为什么需要混沌测试？CI 里跑测试不够吗？**
> 测试验证「已知路径对不对」，混沌验证「未知故障扛不扛得住」。币安 6 月就「处置过一次」但那不是假设驱动的注入——没有假设的处置只是把下一次事故推迟三个月。生产跑实验的底气来自爆炸半径分级 + 护栏三件套（稳态回滚线/熔断联动/人工 kill switch）。

**Q6：全局时间线怎么构建？（把算法题焊回来）**
> 每个 agent/worker 产 append-only 事件日志（本地有序），全局复盘时做 K 路归并：小顶堆存每路当前事件，按 Lamport 时间戳弹出。**O(N log k)，k = 日志源数量**。这就是为什么审计系统、trace 汇集、外排序归并阶段全是同一个结构——可观测性的最后一公里是排序问题。

### HuggingFace 热点论文：Monitor Accuracy Isn't the Answer（11/6）

- 核心发现：固定 90% 准确率的 restart monitor，可以让任务成功率从 **-5 个百分点摆到 +35 个百分点**——**完全取决于替换尝试的残余预算成功概率**
- 两个评估技术：决策充分性判据（decision-sufficiency criterion）+ 用「精确告警-行动恒等式」分析独立清洁重启
- **面试话术**：「评估 monitor 不能只看准确率，要看『告警→行动→结果』整条决策链。这正是我们 checkpoint 设计的依据：低质量 checkpoint + 高准确率 monitor = 稳定地把好任务换成坏任务。」
