## 一、今日算法题：数据流的中位数（LC 295 · Find Median from Data Stream）

### 题目

设计一个数据结构，支持两种操作：

- `addNum(num)`：从数据流中添加一个整数（数据流长度可达 10⁵）
- `findMedian()`：返回目前所有元素的中位数

要求：`addNum` O(log n)，`findMedian` O(1)。

**为什么这道题出现在混沌工程这一天**：混沌工程的第一原则是「围绕稳态建立假设」，而稳态从来不是"平均值不飘"——**稳态是"延迟的 P50/P99 不越线、错误率的滑动分位数不超阈值"**。币安案发当晚，如果监控系统盯的不是"单笔转账是否超大"（阈值检测，事后才触发），而是**"签名速率/授权速率在滑动窗口内相对稳态分位数的偏离"**（分位数检测，EIP-7702 的 50 连发 Nonce 轰炸在第 3~5 个签名时就是 10σ 异常），熔断可以早 15 分钟触发。在线中位数就是这类检测器的原子结构。

### 核心思路：双堆平衡

把数据流劈成两半：

```
        ┌─────────── 大顶堆 maxHeap（存较小的一半）───────────┐
...  ← 堆顶 = 较小一半的最大值 = 左半边的"门槛"
        │ median 候选区 │
...  堆顶 = 较大一半的最小值 = 右半边的"门槛" →
        └─────────── 小顶堆 minHeap（存较大的一半）───────────┘
```

**核心不变量（面试官最爱追问，一句话背下来）**：

> maxHeap 存较小一半、minHeap 存较大一半；任何时候 `size(maxHeap) == size(minHeap)`（偶数个，中位数 = 两堆顶平均）或 `size(maxHeap) == size(minHeap) + 1`（奇数个，中位数 = maxHeap 堆顶）。

插入纪律（两种写法都行，选一种背熟）：

- **写法 A（先插 maxHeap 再平衡）**：新元素进 maxHeap → 如果 maxHeap 比 minHeap 大 1 以上，把 maxHeap 堆顶弹给 minHeap → 保证 `maxHeap.size() ∈ {minHeap.size(), minHeap.size()+1}`
- **写法 B（按大小分流再矫正）**：`num <= maxHeap.top()` 进 maxHeap，否则进 minHeap → 再矫正两堆大小差 ≤ 1

**中位数读取**（O(1)）：奇数取 maxHeap 堆顶；偶数取两堆顶平均。

### Go 实现

```go
type MedianFinder struct {
    maxHeap IntHeap // 大顶堆：较小的一半
    minHeap IntHeap // 小顶堆：较大的一半
}

func Constructor() MedianFinder {
    return MedianFinder{
        maxHeap: IntHeap{less: func(a, b int) bool { return a > b }}, // 大顶
        minHeap: IntHeap{less: func(a, b int) bool { return a < b }}, // 小顶
    }
}

// 插入 O(log n)
func (mf *MedianFinder) AddNum(num int) {
    if mf.maxHeap.Len() == 0 || num <= mf.maxHeap.Top() {
        heap.Push(&mf.maxHeap, num)
    } else {
        heap.Push(&mf.minHeap, num)
    }
    // 矫正：保证 maxHeap.size == minHeap.size 或 +1
    if mf.maxHeap.Len() > mf.minHeap.Len()+1 {
        heap.Push(&mf.minHeap, heap.Pop(&mf.maxHeap).(int))
    } else if mf.maxHeap.Len() < mf.minHeap.Len() {
        heap.Push(&mf.maxHeap, heap.Pop(&mf.minHeap).(int))
    }
}

// 读取 O(1)
func (mf *MedianFinder) FindMedian() float64 {
    if mf.maxHeap.Len() > mf.minHeap.Len() {
        return float64(mf.maxHeap.Top())
    }
    return float64(mf.maxHeap.Top()+mf.minHeap.Top()) / 2.0
}

// 通用堆
type IntHeap struct {
    nums []int
    less func(a, b int) bool
}
func (h IntHeap) Len() int            { return len(h.nums) }
func (h IntHeap) Less(i, j int) bool { return h.less(h.nums[i], h.nums[j]) }
func (h IntHeap) Swap(i, j int)      { h.nums[i], h.nums[j] = h.nums[j], h.nums[i] }
func (h *IntHeap) Push(x any)         { h.nums = append(h.nums, x.(int)) }
func (h *IntHeap) Pop() any {
    old := h.nums
    n := len(old)
    x := old[n-1]
    h.nums = old[:n-1]
    return x
}
func (h *IntHeap) Top() int { return h.nums[0] }
```

### 复杂度

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `addNum` | O(log n) | 一次堆插入，最多一次堆间转移 |
| `findMedian` | **O(1)** | 读堆顶，不排序、不扫描 |
| 空间 | O(n) | 所有元素都要驻留 |

### 面试追问阶梯（进阶六连）

1. **滑动窗口中位数（LC 480）**：数据流只保留最近 k 个，求窗口中位数 → 双堆 + **延迟删除**：出堆时先查"待删表"（哈希计数），堆顶是过期元素就懒弹出。窗口分位数检测器的完整形态——币安案的监控如果做这个，50 连发 Nonce 轰炸在窗口里就是明显的右尾偏移。
2. **固定容量 Top-K / P99**：中位数是 P50 的特例 → 推广到 P99 用 **t-digest 或分桶直方图**（误差换 O(1) 内存）。"背过题的人答双堆，做过系统的人答 sketch"——跟 Day 156 进阶⑤同构。
3. **两个有序数组的中位数（LC 4）**：双堆不可用时（两个已排序流合并），**二分答案**：在短数组里二分划分点 i，长数组对应划分点 j = (m+n+1)/2 − i，校验 `A[i-1] <= B[j] && B[j-1] <= A[i]`。O(log min(m,n))——分治思路的分位数版。
4. **分布式数据流中位数**：多台机器各收一部分流 → 每台维护本地 sketch（t-digest），中心节点合并 sketch 求近似中位数。**不可精确**（数据量大到流过来就要聚合），答"精确是伪需求， sketches + 误差界才是真答案"。
5. **加权中位数**：每个数带权重 → 双堆存"权重前缀和"，平衡不变量改成 `w(maxHeap) ∈ {w(minHeap), ...}`。故障注入的每个样本本来就该带权重（生产流量权重 10× 演练流量）。
6. **最小化与中位数的距离和（LC 462）**：绝对差之和在中位数处取最小——统计学事实的算法化，一句话考点。

### 工程映射：双堆 = 稳态监控的分位数检测器

混沌实验的全过程都靠实时分位数指标做裁判：

- 注入延迟 → 看 **P99 滑动分位数**是否越线（不是均值！均值被 99% 的正常请求平均得毫无波动）
- 注入错误 → 看**错误率窗口分位数**（币安案：签名速率的分位数偏离）
- 恢复观测 → 看 P50 回到稳态基线的**时间** = MTTR 的直接度量
- **双堆是这一切的原子结构**：所有 sketch（t-digest、GK、HdrHistogram）都是"双堆思想的内存受限版"

## 二、面试技巧：混沌测试与故障注入——用币安 63.4 亿美元买教训

### 0. 先立框架：混沌工程四原则（Principles of Chaos，必背）

1. **围绕稳态行为建立假设**（Build a Hypothesis around Steady State）——不说"系统不会崩"，说"在注入 X 期间，稳态指标 M 的偏离不超过阈值 T"
2. **模拟真实世界事件**（Vary Real-world Events）——不是瞎搞，注入的必须是"真实可能发生的故障形状"
3. **在生产运行实验**（Run Experiments in Production）——staging 与生产的拓扑、流量、权限永远不同；生产注入靠爆炸半径控制兜底
4. **持续自动化**（Automate Experiments to Run Continuously）——混沌不是一次活动，是 CI/CD 的一部分

**币安案的全局读法**：攻击者花了 4 个月，替币安做了一场**超大规模、超真实、但币安完全不知情的混沌实验**。而币安在 6 月就"做过一次小实验"（检测到工程师 A 设备异常并处置）——但那次实验**没有假设、没有复盘入册、没有沉淀注入形状库**，于是同一个故障形状 9 月换个入口再注入一次，成功了。这就是混沌工程第一原则被违反的代价：**没有假设的处置，只是把下一次事故推迟了三个月。**

**三层教训（面试直接搬）**：

- **检测≠假设**：6 月的处置是"看到了→修了"，不是"假设了→验证了"。混沌工程第一原则要求每次真实故障（或未遂事件）都被转写成一次带假设的注入实验：**"如果身份暴露，下一步攻击会怎么来？"**——把这个问题写进形状库，9 月的假面试就有 50% 概率被拦（员工安全意识培训会覆盖"下载作业"场景）。
- **内部工具=最大的盲区**：攻击者用币安自己的内部 AI 工具做横向移动。你给 agent 团队的所有工具（代码搜索、远程协助、凭证代理）都应该做"假设工具被攻陷"的注入演练——Day 151 的 METR 案同款教训（agent 自建留言板=环境给了不该给的能力）。
- **速率分位数 > 金额阈值**：EIP-7702 的 50 连发在"金额"维度上是离散的（前几笔可能不大），在"速率"维度上是爆炸的。监控维度选择错误 = 检测器对着错误的轴报警。**混沌实验的稳态指标选择，决定真实事故里你多早被叫醒。**

### 2. 故障注入形状库（Fault Injection Shape Library）

**经典四层形状（基础设施层→应用层→数据层→行为层）**：

```
L0 资源层：CPU 满载 / 内存耗尽 / 磁盘写满 / FD 泄漏 / 时钟跳变（闰秒、NTP 回拨）
L1 网络层：延迟注入（固定/抖动/拥塞排队）/ 丢包 / 分区 / DNS 污染 / 带宽限制
L2 依赖层：依赖服务 5xx / 超时 / 返回脏数据 / 返回陈旧数据 / 依赖半可用（5 个挂 2 个）
L3 应用层：进程 kill / panic / 死锁 / 慢查询 / 队列积压 / 缓存雪崩 / GC 停顿
L4 数据层：schema 变更回滚 / 脏写 / 副本不一致 / 时钟偏移导致乱序
L5 行为层（agent 时代新增）：决策退化 / 工具链故障 / 上下文溢出 / 协作失序（详见下节）
```

**注入的元数据三件套（每一条形状必须带）**：

```yaml
- shape: 依赖超时
  hypothesis: 注入 500ms 延迟后，P99 延迟不超过稳态基线 +1s，错误率 < 1%
  blast_radius: 单个可用区 / 5% 流量 / 单个 agent 实例
  steady_state: P50=120ms, P99=380ms, err=0.1%（基线来自过去 7 天稳态分位数——今天算法题）
  abort: 错误率 > 5% 或用户可见失败即自动回滚
  rollback: 恢复网络规则 + 验证稳态指标回到基线 ±10%
```

**没有假设的注入只是破坏**（Day 147 原话，今天有了 63 亿美元的注脚）。

### 3. Agent 时代的五类特有注入形状（2026 新题库）

来自社区实践（腾讯云 7 月技术文章 + AgentChaos 论文 ASE 2026）的共识清单，**面试说出这五个就是今年满分答案**：

1. **决策质量退化**：LLM API 返回格式 200 全对但语义偏移（"优先走高速"被换成"优先走国道"）——注入方式：代理层替换关键实体。最阴险，因为日志里什么异常都没有。
2. **工具调用链故障**：第 N 步工具超时看 agent 会不会无限重试烧爆 token / 工具返回格式正确但数据过时 / 5 个工具挂 2 个看降级策略。
3. **上下文窗口溢出**：中间轮注入大段无关文档（模拟 RAG 召回噪声），看 agent 是否"忘掉"第一轮约束。实测 Claude Sonnet 5 驱动的审批 agent 在上下文超 80K 时会用"模型常识"替代原始审批规则。
4. **多 agent 协作失序**：某个 worker 延迟 30 秒 / 两个 worker 返回矛盾结论 / planner 下发格式错误的子任务——看编排链能不能刹车（Alphalab 的 Munder Difflin 对照实验：验收标准是协调者做到"停止 merge + 保留证据 + 暂停依赖 + 升级人工"四件事，不是"其他 agent 猜到它想干什么"）。
5. **说谎者注入**：部署被指示"在不被发现前提下偏离协议"的 agent，验收 = **系统最终决策没有被它单独改变**（Day 151 的 f<n/3 语义，AgentChaos 的 value faults 工程版）。

实现位置：**不修改 agent 源码，在 LLM HTTP API 代理层拦截**（Envoy+Lua / Go 中间件 / Chaos Mesh 3.x 自定义 CRD）。AgentChaos 的三个语义类别直接背诵：**crash faults（调用失败）/ omission faults（删关键字段）/ value faults（换成合法但错误的值）**——运行时确认 fault 真的触发了才算数，没走到故障点的任务不进鲁棒性统计。

### 4. 爆炸半径控制（Blast Radius）

混沌工程的伦理核心：**你可以在生产搞破坏，但破坏的边界必须你来画**。

- **分级**：单机 → 单可用区 → 5% 流量 → 单租户 → 内部账号 → 全量（永远不到这一步）
- **币安案的反向教训**：攻击者的爆炸半径 = 5 个热钱包 × 4 小时。币安事后清除 EIP-7702 委托 = 手动压缩爆炸半径。如果事前做过"假设签名权限被滥用"的注入演练，压缩动作可以是自动的，且时延从"首例异常后 N 分钟"压到"协议授权后 N 秒"。
- **护栏三件套**：稳态指标自动回滚线（abort condition）+ 熔断器联动（Day 156 三态状态机）+ 人工一键 kill switch（Day 155 CrowdStrike 范式：授权管理员触发+全程审计）。
- **agent 系统专项**：注入的 agent 必须打演练标签（演练身份证书 ≠ 生产身份），所有演练动作进独立审计流，防止演练流量污染生产账本（Day 150 的账本树会把演练记成成本——预算上下文里要有"演练科目"）。

### 5. 稳态假设与监控对照

- **稳态不是"不宕机"，是"关键指标在基线分布内"**——用分位数说话：P50/P99 延迟、错误率、进展速率（Day 155 agent 第四信号）的 7 天滑动基线。
- **对照组思维**：混沌实验要有"未注入的对照组"（同时间段同流量的 canary 集群）——否则你分不清是注入起效还是本来就在抖。
- **币安案对照**：案发当晚如果有"签名速率分位数"稳态假设（基线：每小时 N 个签名，P99 间隔 T 秒），50 连发会在第 3 个签名时触发 abort。实际监控是"单笔金额阈值"——维度错了，检测延迟以分钟计，而攻击者只需要 20 分钟。
- **指标选择口诀**：**速率看分位数、金额看阈值、状态看快照、行为看基线**。

### 6. GameDay 完整流程（拿币安案当剧本反向演练）

```
T-7 天   计划：选定形状（例：内部工具权限被滥用）+ 写假设 + 定爆炸半径 + 拉好护栏
T-1 天   基线：确认稳态指标基线（过去 7 天分位数）+ 通知值班 + 冻结发布
T0       注入：按计划注入，掐表记录
T0+观测  对照：监控面板 vs 假设逐条核对；自动 abort 条件挂好
T0+结束  回滚：撤销注入 → 验证稳态恢复 → 记录恢复时长 = MTTR
T+1 天   复盘：产出两份清单各加一行——注入形状库 + 探针形状库
         （每次 GameDay 的强制交付物，不是可选的）
T+7 天   回归：把本次发现的缺陷写成回归用例进混沌 CI（下次发布前自动跑）
```

**节奏**：最小可行版每月一次、每次 2 个形状（Day 151 原话）。币安如果在 6 月事件后做了这一次 GameDay（形状：社工注入+身份暴露链式假设），9 月就大概率不会发生。

### 7. 从混沌工程到韧性工程（Resilience Engineering）

2026 年的新叙事：混沌不是目的，**韧性**才是。三句话区分：

- **混沌工程**问：系统坏的时候会怎样？（inject & observe）
- **韧性工程**问：系统在部分失效时还能不能交付核心价值？（degrade gracefully）
- **SRE 实践**问：恢复要多快？（MTTR = 检测时延 + 决策时延 + 执行时延）

落地参考系：

- **Netflix Chaos Monkey**（开山：随机杀实例）→ **Chaos Kong**（杀整个 region）→ 2026 年的 **Chaos Mesh 3.x**（故障图谱模拟级联传播）与 **Gremlin Foresight AI**（10/10 发布：基于十年 Failure Atlas 数据库的 AI 驱动注入——注入方案自动生成，呼应 GPT-6 Cyber 在攻击侧的自动化：**攻防两侧都在 AI 化，手工混沌团队会被机器双杀**）
- **Amazon「故障免疫指数」**：把团队应对故障的能力量化成 KPI——混沌演练次数 × 发现缺陷数 × MTTR 改善，进团队绩效
- **阿里/腾讯 2026 口径**：未经过混沌验证的系统视为不可靠——进 CI/CD 门禁

### 8. 币安案的事后动作 vs 混沌工程的验收标准

币安事后做了（CNBC 11/4 采访 Teng）：关闭入口、全新环境重建钱包系统、**重建被利用的内部工具**、换设备、撤凭证、升级监测。

用混沌工程语言做验收检查表：

| 币安动作 | 混沌工程验收问句 | 状态 |
|---|---|---|
| 重建内部工具 | 重建后第一件事是否做了"假设工具再被攻陷"的注入测试？ | 未知——**重建 ≠ 验证** |
| 升级监测 | 监测维度是否从金额阈值补上了速率分位数？ | 未知 |
| 全员安全培训 | 是否把 6 月/9 月两个形状写成演练剧本全员跑过？ | 未知 |
| 冻结 30 亿+全用户报销 | 韧性指标：核心业务（提现）在攻击下保住了吗？中断 4+ 小时 | 部分达标 |

**重建后的系统是新系统，新系统的第一次故障注入应该是自己做的**——否则就是等着攻击者来帮你做第二次。

### 9. 模拟面试速答五连

**Q1：设计一个 agent 系统的混沌测试方案，你会先注入哪三个形状？**

> ① **工具链故障**（第 N 次工具调用超时，验收 = agent 不退化死循环烧 token，有预算熔断）——AgentChaos omission faults，成本最低收益最高 ② **说谎者注入**（一个 worker 返回格式完美但语义偏移的结论，验收 = 最终决策不被它单独改变 = f<n/3 语义）——拜占庭检测器的效果验收 ③ **kill switch 演练**（随机时刻让 supervisor 广播异常指令，掐表检测→告警→隔离全链路时延）——Day 151 原话：不演练=没有。每次注入带假设+爆炸半径+自动 abort；每月一次每次两项；复盘产出形状库+探针库两份清单。

**Q2：币安案如果重来，混沌工程能在哪个环节拦住？**

> 诚实答：**混沌工程拦不住第一次社工**（6 月），因为社工的对象是人。但 6 月事件是免费的故障注入样本，按第一原则必须转写为带假设的实验——"假设攻击者已掌握钱包团队身份信息，下一步会做什么？"剧本里会出现：定向钓鱼（9 月形状）、内部工具武器化（10/20 形状）、协议级授权滥用（10/29 形状）。**三个形状各做一次 2 小时 GameDay，总成本不到被盗金额的千万分之一。** 混沌工程的价值从来不是阻止初次入侵，而是把"初次入侵必然升级为 63 亿损失"改成"初次入侵止步于第一个形状"。

**Q3：怎么说服业务方在生产环境做故障注入？**

> 三板斧：① 爆炸半径数字说话（首个实验只动 1 台 staging 同构实例的 1% 流量，abort 线挂好，理论上用户零感知）② 币安/Cloudflare/AWS 的公开复盘背书（"未经过混沌验证的系统视为不可靠"已是行业口径）③ 从演练收益算账——一次 GameDay 发现 1 个"监控维度选错"级别的缺陷（币安案：金额阈值 vs 速率分位数），可能等于避免一次 7 位数事故。合规侧再补一刀：中国 AI 安全国标征求意见稿已把"事件响应+持续审计"写进生命周期要求（11/4 彭博），混沌演练是响应能力的验证手段。

**Q4：稳态指标怎么选？为什么不能只看错误率？**

> 错误率是最迟钝的指标——币安案里签名速率爆炸时错误率还是 0（签名都是合法的！）。稳态指标四件套：**延迟分位数（P50/P99）+ 错误率 + 饱和度（CPU/队列/连接池）+ 业务速率（单位时间的签名/授权/转账笔数及其分位数）**。今天算法题就是业务速率分位数的原子结构。口诀：速率看分位数、金额看阈值、状态看快照、行为看基线。对照组必须有（同流量未注入 canary），否则分不清注入起效和天然抖动。

**Q5：混沌实验和压测、故障演练（fire drill）的区别？**

> 压测问**容量边界**（QPS 到多少会崩），混沌问**容错行为**（在正常工作负载下，注入单个故障，系统能否维持稳态+优雅降级）；fire drill 是**已知剧本的走查**（按下火警看大家跑不跑），混沌是**带假设的科学实验**（注入 X，预测 Y 在 Z 时间内发生 W 变化，验证+记录偏差）。三者互补：压测保证平时扛得住，混沌保证出事死得慢，演练保证人知道按钮在哪。币安案 10/30 清除 EIP-7702 委托 = fire drill 做到了（人工切断链路）；缺的是混沌（事前验证"授权滥用形状"能否被自动检测）。

### 今日金句

> **币安用 63.4 亿美元给全行业上了一课：攻击者一直在做混沌实验——他们的注入形状库每天都在更新（社工、供应链、内部工具武器化、协议级授权轰炸），而防御方的形状库更新速度决定了损失的天花板。混沌工程的全部要义只有两句话：第一，没有假设的注入只是破坏，没有注入的假设只是祈祷；第二，每一次真实事故（哪怕是未遂）都是免费的故障注入样本，转写它、演练它、把它变成回归用例，否则同一个形状会在三个月后换个入口再来一次——币安的 6 月和 9 月，就是同一个形状的两行记录。而你写的每一条监控规则，最好都是某次注入实验教你的。**
