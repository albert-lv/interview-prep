## 一、今日算法题：从机票列表重建完整行程（LC 332 · Reconstruct Itinerary）

### 题目

给定一组机票 `tickets`，每张票表示为 `[出发机场, 到达机场]`（可能有重复）。**所有机票必须从 `JFK` 出发按顺序用掉恰好一次**，返回按字典序最小的完整行程。

```
示例 1: tickets = [["MUC","LHR"],["JFK","MUC"],["SFO","SJC"],["LHR","SFO"]]
输出: ["JFK","MUC","LHR","SFO","SJC"]

示例 2: tickets = [["JFK","SFO"],["JFK","ATL"],["SFO","ATL"],["ATL","JFK"],["ATL","SFO"]]
输出: ["JFK","ATL","JFK","SFO","ATL","SFO"]   ← 不是 ["JFK","JFK",...]，JFK<ATL? 不，ATL<JFK 但首站固定 JFK；第二站 ATL<SFO ✓
```

约束：保证至少存在一个有效行程（欧拉路径必然存在）。

### 为什么是这道题（工程映射）

今天是可观测性日。可观测性三支柱（metrics/logs/traces）之上还有一个终极形态——**可重放性（replayability）**：

- **每张机票 = 一条审计事件**：`[from, to]` 就是「agent 在状态 from 执行动作，迁移到状态 to」；
- **重建行程 = 从 append-only 事件日志重放完整执行轨迹**：给你全部事件，你要能还原 agent 从头到尾「去过哪、按什么顺序」——**出了事，这是复盘和取证的基本功**（Day 149 审计哈希链保证事件「没被篡改」，今天 LC 332 保证事件「能被还原成轨迹」——事件溯源的两个支柱）;
- **字典序最小 = 确定性重放**：同一批事件可能有多种合法排序，工程上必须约定一个确定规则（时间戳/序列号/字典序），否则两次重放结论不一致，复盘就不可信;
- **死胡同先走 = 后序遍历**：这个不起眼的技巧，和 checkpoint/恢复的回放顺序遥相呼应（Day 154：恢复点回放也必须按依赖逆序）。

### 思路：Hierholzer 算法——「死胡同先走」

**欧拉路径存在条件**（面试必问）：有向图中
- 起点：出度 − 入度 = 1；终点：入度 − 出度 = 1；其余顶点出入度相等。
- 且所有边连通（度 > 0 的顶点在同一弱连通分量）。

LC 332 保证有解，所以可以跳过判定——但 **follow-up 一定会让你处理无解/允许重复走的版本**（见进阶）。

**核心观察（死胡同先走）**：当你走进一个「出度已耗尽」的机场，你就再也出不来了——所以**这条边一定是整场行程的最后一段**。由此得到 Hierholzer：

1. 建图，邻接表用**小顶堆**（天然字典序）；
2. 从 JFK 出发 DFS：只要当前机场还有出边，就贪心地飞向字典序最小的目的地；
3. **后序收集**：DFS 回溯时才把机场加入 `route`——死胡同最先落进 `route`；
4. **逆序输出**：`route[::-1]` 就是答案。

**为什么贪心不翻车**：反证。假设字典序最小的下一跳会把我们带进死胡同而漏掉别的边——但死胡同边本来就必须最后走，先走它恰好合法；若它在行程中段根本不该出现，那它的终点出度 > 0，DFS 还会从那里继续，不会「困死」。归纳可得 Hierholzer 对欧拉路径永远正确。**这是「局部贪心 + 全局回溯修正」的典范**，和 LC 134 加油站（Day 75 思路同款）气质相通。

### 代码（Python 递归版 · 7 行核心）

```python
from collections import defaultdict
import heapq

class Solution:
    def findItinerary(self, tickets: list[list[str]]) -> list[str]:
        graph = defaultdict(list)
        for src, dst in tickets:
            heapq.heappush(graph[src], dst)      # 小顶堆 = 字典序贪心

        route = []
        def visit(airport: str) -> None:
            while graph[airport]:                # 还有出边就继续飞
                visit(heapq.heappop(graph[airport]))
            route.append(airport)                # 后序：死胡同先落
        visit("JFK")
        return route[::-1]                       # 逆序 = 正序行程
```

### 代码（迭代版 · 面试防栈溢出加分项）

```python
class Solution:
    def findItinerary(self, tickets):
        graph = defaultdict(list)
        for src, dst in sorted(tickets, reverse=True):   # 逆序插入
            graph[src].append(dst)                        # 弹出即最小
        stack, route = ["JFK"], []
        while stack:
            while graph[stack[-1]]:
                stack.append(graph[stack[-1]].pop())
            route.append(stack.pop())                     # 死胡同出栈
        return route[::-1]
```

### 手动追踪（示例 2，理解后序的关键）

```
JFK → ATL(字典序最小) → JFK(回) → SFO → ATL(回) → SFO(死胡同)
DFS 回溯顺序压栈 route: SFO, ATL, SFO, JFK, ATL, JFK
逆序: [JFK, ATL, JFK, SFO, ATL, SFO] ✓
```

### 复杂度

| 项 | 复杂度 | 说明 |
|---|---|---|
| 时间 | **O(E log E)** | E 条边各入堆/出堆一次，堆操作 log E |
| 空间 | **O(E)** | 邻接表 + 递归栈 |

（也有桶排序 + 链表的 O(E) 解法——字母表固定时用计数排序替代堆，面试提一句即加分。）

### 常见坑 & 边界 case

- ❌ **前序收集**：DFS 到达就 append，得到的不是欧拉路径——必须是**后序**（所有出边耗尽才落盘）；
- ❌ **用 visited 集合判重**：机票是**多重边**（两张 JFK→ATL 是两张票），visited 会把第二张票吃掉；
- ❌ **排序后正向遍历数组**：弹掉一个目的地后数组结构变了，链表/堆才是正解；
- ⚠️ 递归深度 = E（票很多时 Python 默认 1000 会爆），迭代版是保险；
- ⚠️ 「JFK 固定起点」是题目给的；若面试官问「任意起点」，先扫一遍度数找起点（欧拉条件）。

### 进阶（面试官的下一问）

1. **非欧拉情形**：不允许剩票时无解 → 允许临时加返程票 = 中国邮路问题（CPP，有向多项式、混合图 NP-hard）——**这就是「允许 agent 重放时补操作」的代价模型**；
2. **分布式全序**：事件分散在多节点、只有偏序 → Lamport 时钟 / 向量时钟，重建的是拓扑序而非唯一序——**这正是分布式 tracing 的 span 排序问题**;
3. **增量重放**：新事件不断到达，不必从头重放——**从最近的 checkpoint 状态开始重放增量事件**（呼应 Day 154：快照 + 日志 = 状态持久化的完全体）;
4. **部分事件丢失/乱序**：重建不唯一 → 输出**全部候选**或按置信度排序——根因分析的日常：监控数据丢了，你能给出几种可能的事故链？
5. **加权版本**：机票带出发时间，求最早回到起点的行程 → Dijkstra 变种 + 时间约束；
6. **拆成 k 段行程**：k 个 agent 并行执行 = 一条欧拉路径切成 k 段 = **分布式 tracing 的 span 树**——今天的题图就是明天（Day 156 容错）的 trace 视图。

## 二、面试技巧：心跳与健康检查 × 可观测性

### 1. 活性 vs 进展：三层探针模型（面试第一问）

DeepSeek Super-agent Watchdog 的论断是全行业共识：**进程活着 ≠ 服务能答 ≠ 任务有进展**。落地为 k8s 风格的三层探针：

| 层 | 探针 | 回答的问题 | 失败动作 |
|---|---|---|---|
| L1 活性 | `/healthz` | 进程死没死？（事件循环是否还在转） | 重启进程 |
| L2 就绪 | `/readyz` | 能不能接活？（依赖是否可用：DB/模型 API/队列） | 摘出负载均衡，不分配新任务 |
| L3 进展 | `/progress` | 手里的活有没有在动？（最近进展事件时间戳 + 步数计数器） | 通知 Watchdog → 换策略/换人/熔断 |

**L3 是 agent 时代的新物种**。vLLM 的教训（Day 147：92 字节请求测出「/health 全绿但服务答不了题」）在 agent 身上更严重：一个 agent 进程完全可能空转烧 token——循环重试同一个失败工具调用、在无关网页间跳转、陷入自我重复的推理。**基建活性 ≠ 任务进展，L3 探针就是这句话的产品化。**

**L3 设计三要素**（背下来）：
- **进展事件**：每完成一个有意义的步骤（工具调用成功/文件写入/测试通过）就推进 progress counter 并刷新时间戳；
- **静默阈值**：超过 T 秒无进展事件 → 可疑（suspicion）；连续 N 次可疑 → 判定失速（失速 ≠ 失败：也许正在跑长任务，所以要有白名单机制）;
- **外部裁决**：探针结论交给 Watchdog（主系统之外的独立控制回路）决定换人/重试/熔断——**运动员不能兼任裁判**。

### 2. 健康检查的「92 字节请求」测试集（第二问）

面试官：「你怎么验证健康检查本身是对的？」

答案：**探针必须答真实业务，不能答探针自己。** 测试集三件套：
1. **合成请求**：最小完整业务请求（92 字节之于 vLLM = 一次最短 agent 步：一次工具调用 + 一次解析）；
2. **对照断言**：响应必须包含业务正确性字段（不只是 200，而是结果真的对）；
3. **定期竞态**：健康检查通过 ≠ 用户体验正常——把探针结果与真实用户成功率（真实用户监控/RUM）做 diff，探针全绿但错误率飙升 = 探针盲区报警（这正是 CrowdStrike 要把 agent 钩子/网络/运行时三层拼成一个 Agent Graph 的原因：**单层观测必然有盲区，盲区要靠跨层 diff 逼出来**）。

### 3. SWIM gossip 快速回顾（第三问 · Day 149 呼应）

集群规模上去后，心跳不能是中心化的「所有节点 ping 一个 master」。SWIM 三件套：
- **probe**：每个节点随机挑节点发 ping，K 个间接节点帮传（避免网络分区误杀）；
- **suspicion**：超时不是立刻宣告死亡，而是标记可疑、传播嫌疑——**静默即 suspicion，不是静默即死亡**（反例：GC 停顿 30 秒的节点被误杀，数据副本震荡）;
- ** disseminate**：成员变更通过 gossip 感染式传播。

映射到 agent 系统：multi-agent 集群的成员健康表就是 SWIM 表的语义，只是「心跳」从 TCP ping 变成了「进展事件」。

### 4. 可观测性三支柱 + 黄金信号（第四问）

| 支柱 | 回答 | agent 系统里的形态 |
|---|---|---|
| **Metrics**（聚合指标） | 有没有病？ | 任务成功率、P50/P95 步数、token/美元消耗速率、进展事件速率 |
| **Logs**（离散事件） | 发生了什么？ | 结构化 JSON 事件：谁在何时对什么做了什么（参数 + 结果 + 耗时） |
| **Traces**（因果链） | 病在哪条链路上？ | 一次任务执行 = trace 树：planning span → tool span → 子 agent span |

三套经典方法论，按场景选：
- **四个黄金信号**（Google SRE）：延迟、流量、错误、饱和度——面向**用户**的服务；
- **RED**：Rate/Errors/Duration——面向**请求**的微服务；
- **USE**：Utilization/Saturation/Errors——面向**资源**的（GPU/队列/连接池）。

agent 特有的第四个信号：**进展速率（progress rate = 进展事件/分钟）**——和黄金信号并列的「agent 黄金五信号」。

### 5. 事件溯源：可观测性的终极形态（第五问 · 呼应今天的题）

**Metrics 告诉你有没有病，traces 告诉你病在哪条链路上，可重放性告诉你这个病是怎么得的。** 事件溯源（event sourcing）三件套：

1. **append-only 事件日志**：系统状态的每一次变化都是一条不可变事件（谁/何时/何参数/何结果）——Day 149 的哈希链保证它**没被篡改**；
2. **确定性重放**：给定初始状态 + 事件流，重放得到终态（LC 332：行程 = 按确定规则从事件流重建）——要求**重放确定性**（同样的输入必须得到同样的输出：这就是为什么要用字典序/时间戳/序列号定全序）；
3. **快照 + 增量**：从最近 checkpoint 起重放增量（Day 154），否则 7×24 的 agent 复盘一次要重放三个月。

面试话术：「状态快照（Day 154）是照片，事件日志（今天）是录像带；合规审计要录像，根因分析要录像，**混沌测试的故障注入验证也要靠录像回放对比预期轨迹**（Day 151 的 kill switch 演练就是这么验的）。所以生产级 agent 系统的存储层不是二选一，是 snapshot + event log 双写。」

### 6. 「先观测后熔断，熔断本身也要被观测」（第六问 · 今天的行业注脚）

CrowdStrike Kill Switch + 自律公约第四条给出的行业范式：

- **熔断的触发条件必须来自观测**（运行监测发现偏离 → 行为管控按策略判定 → 异常熔断执行），不能是拍脑袋；
- **熔断动作本身要进审计跟踪**：谁、何时、因为什么信号、对哪个 agent、做了什么操作（终止/阻重启/断网）——不然熔断器会成为新的攻击面（恶意触发 kill switch = 拒绝服务）；
- **熔断后留取证现场**：agent 的最后状态、事件日志、trace 树封存——**kill 掉不是终点，复盘入册（投毒库 + 回归集，Day 153 Q6）才是**；
- **用户最终控制权**：公约第六条——重要事项的 kill switch 按钮要在用户手里，不是只在安全团队手里。

### 7. 模拟面试三连

**Q1：面试官：「你设计一个 7×24 的 coding agent，健康检查怎么做？」**

> 🎯 参考答：三层探针。L1 活性看进程和事件循环；L2 就绪看依赖（仓库可访问、API 配额、工具链可用）；L3 进展是 agent 特有的——我要求 agent 每完成一个有意义的步（工具调用成功/测试通过/文件落盘）就推进 progress counter 并刷新时间戳，静默超过阈值先标记 suspicion 再判定失速。关键是 L3 的结论**不交给 agent 自己处理**，而是交给外部 Watchdog：换策略、回滚到上一个 checkpoint、或触发熔断。DeepSeek 的 Super-agent 架构就是这么做的——许多异常不是进程崩溃，而是模型陷入无效循环，基建活性不等于任务进展。最后，健康检查本身要用「92 字节请求」式的合成业务请求验证，探针全绿但真实成功率掉线时，要报警探针盲区而不是沾沾自喜。

**Q2：「可观测性三支柱你怎么落地到 agent 系统？」**

> 🎯 参考答：metrics 用黄金信号加一个 agent 特有的进展速率；logs 要求结构化事件带全上下文（agent_id、task_id、工具参数、结果、token 成本），这是我们后续审计和重放的原料；traces 把一次任务执行建成 span 树——一个关键认知是**单层观测有盲区**：只看 agent 层钩子会漏模型响应，只看网络层会漏主机执行，所以 CrowdStrike 的 Agent Graph 要把 agent 钩子、端点网络、运行时可见性拼在同一视图。往上再进一步是事件溯源：append-only 日志 + 哈希链防篡改 + 确定性重放，快照和事件双写——照片和录像带都要。

**Q3：「发现 agent 行为异常，你的处置顺序是什么？」**

> 🎯 参考答：四步——观测取证、分级判定、处置熔断、入册回归。**先取证后处置**：封存当前状态、事件日志、trace 树（中断前先留现场）；判定分级区分「环境故障/能力边界/提示注入/模型作恶」四象限（Day 151 的分类学），不同象限处置不同；处置走 kill switch 标准动作：就地终止、阻止重启、切断网络访问，触发必须授权人执行且全程审计跟踪；最后复盘归因，产出物进投毒样本库和回归测试集——熔断不是终点，入册才是。这也是 11/4 乌镇《智能体发展自律公约》第四条「运行监测、行为管控、异常熔断」的行业级写法。

### 8. 高频速答五连

- **「liveness 和 readiness 探针区别？」** → liveness 失败重启进程（治假死），readiness 失败摘流量（治依赖故障）；最忌讳用同一端点——依赖挂了导致 liveness 失败，然后所有实例被同时重启雪崩。
- **「SWIM 相比集中式心跳的优势？」** → 无单点、无全网风暴、suspicion 机制抗网络抖动误杀；代价是收敛慢（秒~十秒级），成员表是最终一致。
- **「为什么需要 progress probe，光 heartbeat 不够吗？」** → heartbeat 证明线程活着，progress 证明**任务**活着（92 字节请求：/health 全绿但服务答不了题）；agent 最常见的故障模式是活得好好的但在空转。
- **「metrics 和 traces 怎么选？」** → metrics 便宜聚合先行（报警靠它），traces 贵而全（定位靠它）；原则：先 metrics 发现哪个服务坏了，再 traces 看哪条链路坏了——别拿 trace 做聚合，也别拿 metric 做根因。
- **「事件溯源的最大代价是什么？」** → 重放确定性约束会否决很多「方便」的写法（随机数、时钟、外部调用都要可注入/可 mock），且事件 schema 演进要做版本迁移；收益是审计/复盘/测试三路回本。

### 10. 今日金句

> **可观测性的最高标准不是让你看到系统的实时状态，而是让你能把整场执行从第一个事件开始逐事件重放出来。metrics 告诉你有没有病，traces 告诉你病在哪条链路上，而可重放性告诉你这个病是怎么得的——前两者是体检报告，重放是监控录像。一个不能被重放的 agent，出了事你连它「去过哪、按什么顺序」都说不清；而健康检查的全部要义只有一句话：进程活着不等于任务在动，所以要有第三层探针盯着「进展」，并且把「要不要熔断」的裁决权放在系统之外的 Watchdog 手里——运动员不能兼任裁判。这周的行业新闻把这两件事同时产品化了：CrowdStrike 给 agent 装上了关闭按钮，乌镇公约把「运行监测、行为管控、异常熔断」写进了行规。观测是熔断的前提，审计是熔断的边界。**
