## 一、今日算法题：随机数索引（LC 398）

### 题目

给定一个可能包含重复元素的整数数组 `nums`，设计一个支持如下操作的类：

- `Solution(int[] nums)`：使用数组 nums 初始化对象；
- `int pick(int target)`：从 nums 中等概率随机输出一个满足 `nums[i] == target` 的下标 `i`。

```
输入：["Solution", "pick", "pick", "pick"]
     [[[1, 2, 3, 3, 3]], [3], [1], [3]]
输出：[null, 4, 0, 2]
解释：pick(3) 应在 {2, 3, 4} 中等概率返回其一；
     pick(1) 只能返回 0。
```

**约束**：调用次数可能非常多；数组很大，**不能一次性预处理全量索引列表**（内存装不下或数据是流式的）。

### 工程读法（为什么开营选这道题）

Week 26 讲评估与数据工程。评估的第一个工程问题是：**评测集从哪来？**

你的 agent 系统每天产出百万条 rollout 轨迹，人工评估团队一天只能精评 1000 条。怎么选这 1000 条？答案是**蓄水池抽样**：每条轨迹流过时以 `k/n` 的概率进池，全程 O(1) 内存、一次遍历、严格均匀——**不需要知道流有多长，不需要存下所有轨迹，每条轨迹被选中的概率严格相等**。

- **Uber 那 4 单**（11/4 TechCrunch）就是一堂基线测量课：一个 3.2 亿月活的 App 里，全季度最忙一周只有 4 人用 AI agent 叫车成功。这个数字之所以震撼，恰恰因为 Uber 老老实实 instrument 了「调用来源」这个维度——**没有 instrument 就没有基线，没有基线就只剩发布会口径**。你系统里的「agent 轨迹占比」仪表盘，就是那个 instrument。
- **采样偏差是评估的头号死因**。Visa 基准（11/5）选了 15 个购物场景做评估，整体通过率 57.2%——但「54% 的失败 run 仍然完成购买」说明它的「失败」定义里混着「买了但流程不规范」。场景怎么选、怎么分层、怎么加权，比模型跑多少分重要得多。
- **分层蓄水池**是工程答案：按任务类型 × 难度 × 模型版本分层，层内做蓄水池抽样——防的就是「简单任务淹没难任务」这种最经典的评估集污染。

### 思路：蓄水池抽样（Reservoir Sampling）

朴素想法：先扫一遍数出 target 出现次数 `m`，再 `rand.Intn(m)` 挑第几个——**需要两次遍历**，数据流场景第二次遍历时数据可能已经流走。

蓄水池抽样只用一次遍历，维护两个变量：

```
count = 0          // 到当前为止 target 出现了几次
result = -1        // 当前选中的下标

遍历到第 i 个等于 target 的元素时：
    count++
    以 1/count 的概率用 i 替换 result
```

**为什么每个下标等概率？** 对第 i 个 target 元素（1-indexed，共 n 个）：

- 第 i 个元素**入选**的概率：遍历到它时以 `1/i` 被选中；
- 之后**存活**的概率：第 t 个元素（t > i）到来时，替换概率是 `1/t`，存活概率 `1 - 1/t = (t-1)/t`；
- 最终留下的概率 = `1/i × i/(i+1) × (i+1)/(i+2) × ... × (n-1)/n = 1/n`。

分子分母 telescope 相消，**每个元素留下的概率严格 = 1/n**。归纳一句话：**第 i 个到来时，它应该和前面 i-1 个被选中的那个五五开——1/i 正是「后来者和先来者平权」的概率。**

### Go 实现

```go
import (
    "math/rand"
    "time"
)

type Solution struct {
    nums []int
    rng  *rand.Rand
}

func Constructor(nums []int) Solution {
    return Solution{
        nums: nums,
        rng:  rand.New(rand.NewSource(time.Now().UnixNano())),
    }
}

// Pick: 蓄水池抽样 k=1 的特化版，O(n) 时间 O(1) 额外空间
func (s *Solution) Pick(target int) int {
    count := 0
    result := -1
    for i, v := range s.nums {
        if v != target {
            continue
        }
        count++
        // 以 1/count 的概率替换：新来者与旧选中者平权
        if s.rng.Intn(count) == 0 {
            result = i
        }
    }
    return result
}
```

**通用 k 槽蓄水池**（面试官必问 follow-up，直接背）：

```go
// ReservoirSample: 从流中均匀采样 k 个，O(n) 时间 O(k) 空间
func ReservoirSample(stream []int, k int) []int {
    res := make([]int, 0, k)
    for i, x := range stream {
        if i < k {
            res = append(res, x) // 前 k 个直接进池
        } else if j := rand.Intn(i + 1); j < k {
            res[j] = x // 第 i 个元素以 k/(i+1) 概率挤掉池中某个
        }
    }
    return res
}
```

正确性：对第 i 个元素（1-indexed，i > k），入选概率 `k/i`，之后每个 t > i 的轮次存活概率 `1 - k/t × 1/k = 1 - 1/t`，最终 `k/i × i/(i+1) × ... × (n-1)/n = k/n`。前 k 个对称地也是 `k/n`。

### 复杂度

| 指标 | 朴素两次遍历 | 蓄水池抽样 |
|---|---|---|
| 时间 | O(n) 两次遍历 | O(n) 一次遍历 |
| 空间 | O(m) 存全部 target 下标 | **O(1)** |
| 流式支持 | ❌ 数据流走就没了 | ✅ |
| 均匀性 | 严格 | 严格（证明可写） |

### 面试三坑

① **概率写错**：写成 `rand.Intn(n)` 或固定 0.5 替换——均匀性当场死亡。正确是 `Intn(count) == 0`，分母是**当前已见的个数**，不是数组长度。面试时把 `1/i` 的归纳说出来，比背代码值钱十倍。

② **「那我用哈希表存全部下标再随机取一个呢？」**——如果数组能装进内存、调用次数极多，预处理 O(n) + 每次 O(1) 确实是更优工程解，**主动说出这个 trade-off 是加分项**；但题目场景（流式 / 内存受限 / 数组可变）正是蓄水池存在的理由。不要为算法而算法。

③ **k 槽版忘记前 k 个直接入池**：写成 `if j := rand.Intn(i+1); j < k` 从 i=0 开始——`rand.Intn(1)` 恒 0，前 k 个会以混乱方式覆盖自己，必须 `if i < k` 先注满。

### 进阶六连

① **LC 382 链表随机节点**——同题链表版，遍历到第 i 个节点以 1/i 概率替换答案，O(1) 空间（链表根本没法预存下标）。面试官最爱考的「蓄水池 + 不支持随机访问」组合。

② **加权蓄水池抽样（A-Res / A-ExpJ）**——每条轨迹带权重（如按 reward 绝对值、按任务难度、按 token 成本），让高价值轨迹进评估池概率更高但又不确定性漏掉低价值轨迹。工程对应：**评估预算 80% 给主分布 + 20% 探索长尾**，而不是全押一头。

③ **分布式并行蓄水池**——百万 worker 各自抽样，中心节点按各分片流长度加权合并（分片 i 采了 k_i 条、流过 n_i 条，合并权重 ∝ n_i）。Go 标准库 `math/rand/v2` 的 `PCG` 可给每个 worker 独立种子，可复现、可审计——**采样的随机种子要写进评估报告，否则一次人工评估无法复现**。

④ **分层蓄水池（stratified reservoir）**——按任务类型/难度/模型版本分桶，每桶独立蓄水池，最后按 strata 配额合并。防「简单题淹没难题」，是 Visa 那种场景型基准的第一修复手段。统计学术语叫 stratified sampling，层内 SRS（简单随机抽样），层间按配额——置信区间比纯随机更窄。

⑤ **均匀性事后检验**——采完 1000 条怎么验证自己采对了？卡方检验（观察频数 vs 期望频数）、KS 检验（采样时间分布 vs 源分布）、或对已知分布的合成流跑回放。**「我抽的是均匀的」必须是一个可检验的假设，不是一个祈祷**。

⑥ **滑动窗口采样**——只采样最近 7 天的轨迹（评估时效性）：固定容量池 + 过期驱逐 = 蓄水池 + LRU 时钟。工程对应：**评估集要滚动保鲜，三个月前的轨迹测不出今天的模型**。

## 二、面试技巧：Agent 评估与数据工程实战（第一课）

### 本周五堂现场课（全部来自最近 10 天的新闻）

**第 1 课 · 测量先于评估（Uber 的 4 单）**。TechCrunch 11/4 报道：Uber 高管透露，上季度 AI agent 打车**最忙的一周只有 4 个人用、共 4 单成功**。在一个 3.2 亿月活用户的 App 里，这个数字残酷得可爱——但它是**真实的**，因为 Uber 真的数了。面试时被问「如何评估 agent 功能的效果」，第一句话永远是：**先确认你能测量它**（调用来源打标、流量占比仪表盘、端到端成功漏斗）。**没有 instrument 的评估 = 发布会文学**。

**第 2 课 · 指标定义先于指标计算（Visa 的 54%）**。Visa 11/5 发布 Agentic Commerce Benchmark：22 个模型跑 15 个购物场景，整体通过率 57.2%，最好的模型 82.2%。但报告里最值钱的一行是：**54% 判定为失败的 run，最终仍然完成了购买**。也就是说按「任务完成」算成功率有 57%，按「合规完成」算可能接近 100% 或远低于 57%——**先定义什么叫失败，再谈失败率**。面试话术：指标设计三问——**这个指标最大化时系统会变成什么形状？（Goodhart）这个指标的分子分母各是什么口径？（Visa 陷阱）这个指标翻车前最后一个预警信号是什么？**

**第 3 课 · 检查输出，不听推理（GPT-6 Astra 的 10% vs 16%）**。Futurism 11/5 披露：OpenAI 内部一份隐藏 rubric 显示，GPT-6 Astra 在「AI 安全研究任务」上的 rubric 完成率从上一代模型的 16% 掉到 10%——而官方发布说明对此只字未提（没有说谎，只是没有发布）。这是评估哲学的教科书句：**check its output rather than its reasoning**。模型的自我报告（「我完成了安全审查」）不可信，rubric 上的勾选（实际交付物）才可信。工程推论：judge 打分只看**可验证的工件**（diff、测试通过记录、引用文献），不听模型的结论陈词。

**第 4 课 · 声称 ≠ 验证（DeepMind RSA 的 1,600x 注脚）**。11/9 DeepMind 官宣两个 AI agent 复现了 1024 位 RSA 签名攻击，新闻稿的标题数字是「原需 1,380 CPU core-year 的攻击用 391 core-year 完成，**加速 1,600 倍**」。技术社区随后逐条核对原始论文（ePrint 2026/2131）：**1,600x 是把论文里的理论假设直接做除法得到的算术换算，实际跑通的是 3.5x；论文攻击模型需要 2³² 次签名 oracle 查询，现实中一次都没执行过**（论文自己也承认 "Even 4096-bit RSA does not appear to meet a 128-bit security level **in this attack model**"）。没有任何人说 DeepMind 造假——但**「理论上限」和「实测结果」之间的距离，就是评测团队存在的意义**。面试话术：厂商报告数字时，三问拆解——**什么口径（哪个 split/什么 scaffold）、什么成本（token/美元/时延）、复现了吗（开源脚本/可跑复现）**。

**第 5 课 · 跑自己的 eval（Fable 5.2 的 69.9%）**。Claude Fable 5.2 发布（11/9）：新闻稿印着的 SWE v2 Verified 是 **69.9%**，API 降价 20%。厂商自报基准的合规用法是：把它当**候选假设**而不是结论——用你自己的 holdout 任务集、你自己的 scaffold、你自己的成本口径复跑一遍，得到 cost per resolved task 才是你系统里的真实数字。**别人的 benchmark 是别人系统的影子**。

### 评估系统设计五层漏斗（面试可画）

```
L1 声明层  vendor claim（Fable 69.9% / DeepMind 1,600x）
   ↓ 三问拆解：口径？成本？复现了吗？
L2 复现层  自己的 eval harness + 私有 holdout（防数据污染）
   ↓ 分层蓄水池采样
L3 基准层  私有基准集滚动保鲜（7 天窗口采样，LC 398 的滑动窗口版）
   ↓ rubric 只看可验证工件
L4 采样层  线上影子流量人工精评（Uber instrument 同款）
   ↓ 双盲 + 隐蔽 rubric
L5 审计层  评估结论必须能触发决策（模型发/不发、阈值调不调）
```

一句话记住：**评估的价值 = 它触发的决策数量。不能触发任何决策的评估，是行为艺术。**

### 模拟面试速答五连

**Q1：怎么评估你们 agent 的真实能力？**
三层递进：公开基准（会被刷，只作候选假设）→ 私有 holdout 集（每月滚动更新防污染，分层蓄水池采样保分布）→ 线上影子流量精评（1-5% 采样，rubric 只看可验证工件）。收尾一句：每个数字都带置信区间和采样日期。

**Q2：厂商说他家模型 SWE-bench 69.9%，你怎么用？**
三问拆解：哪个 split、什么 scaffold（scaffold 不同分数可差 10 个点）、平均成本多少（cost per resolved task 比裸分重要）。然后用自家 holdout 复跑，只信自己的数字——**69.9% 是别人系统的影子，不是你系统的样子**。

**Q3：人工评估只有 1000 条/天的预算，百万条轨迹怎么选？**
分层蓄水池：按任务类型 × 难度 × 模型版本分桶，层内 LC 398 式等概率采样，层间按配额合并。三个理由：分布保真（简单题不淹没难题）、可追溯（随机种子入报告，评估可复现）、事后可检验（卡方/KS 验证均匀性）。

**Q4：judge 模型自己也是 LLM，怎么防它被骗？**
四件套：双盲（judge 不看模型自我结论，只看交付物 diff/测试记录/引用）、隐蔽 rubric（judge 不知道哪些项在打分，防 GPT-6 Astra 式「对着 rubric 表演」）、ensemble（2-3 个异构 judge 投票，Day 144 同一盲点三次复印警告）、人工校准集（holdout 人工精评 100 条，算 Fleiss' kappa ≥ 0.6 才信 judge 全量分）。

**Q5：评估发现模型在某隐蔽维度退步了（类似 Astra 的 10%），处置流程？**
三步：①确认信号（换 judge 复测、查采样偏差、查 rubric 版本）→ ②冻结发布管道上该维度的「已验证」标签 → ③写进回归集，下个版本必须过这条线才发。关键是第 ② 步——**评估的全部意义就在于它能卡住发布**；卡不住发布的评估等于没有。

### 今日金句

「Uber 用 4 单车告诉我们：测量先于叙事；Visa 用 54% 告诉我们：定义先于指标；GPT-6 Astra 用 10% vs 16% 告诉我们：工件先于陈词；DeepMind 的 1,600x 告诉我们：复现先于采信。评估的全部要义，是把『我觉得它变强了』翻译成『在第几号 holdout 集上、哪个口径、提升几个点、置信区间多少、花了多少 token』。**所有不能触发决策的评估，都是行为艺术。**」
