## 一、今日算法题：Merkle Tree（默克尔树 · 可审计性的数据结构根基）

### 题目

设计一个评估平台的**数据完整性引擎**，要求支持三种操作：

```
1. Build(chunks [][]byte) → 构建 Merkle Tree，返回根哈希 root
   - 输入：评估数据集的 N 个数据块（题目/答案/元信息分块）
2. InclusionProof(idx) → 返回第 idx 个数据块的「包含性证明」
   - 一个长度为 ceil(log2 N) 的兄弟哈希序列（含方向位）
3. VerifyInclusion(chunk, proof, root) → 仅给定数据块+证明+根，验证该块确实在树中
   - 不下载整棵树，O(log N) 完成验证

示例：
chunks = ["eval-item-001", "eval-item-002", ..., "eval-item-1000"]
root = Build(chunks)  →  32 字节哈希 = 整个数据集的身份指纹

一年后审计：某份评测报告声称基于该数据集评测
→ 平台只需重算各块证明，Verify 全过 = 数据集未被篡改
→ 任何一块被改过一个字节 → 根哈希不同 → 证明失败
```

**为什么收官选这道题**：Week 26 收官设计题的三个定语——**可审计、可复用、统计上诚实**——Merkle Tree 是「可审计」三个字的数据结构根基。前四天解决了评估的「科学问题」（怎么采样、怎么定指标、怎么防污染、怎么做统计推断），今天解决「信任问题」：**你怎么证明这份评测报告用的就是这份数据集、这个结果出自这次运行、这个决策有迹可循？** Git 的对象库、证书透明度（CT）日志、区块链的区块头，跑的都是同一个数据结构。

### 思路：自底向上哈希配对 + 递归包含证明

```
构建（O(N)）：
1. 每个数据块哈希成叶子：leaf_i = H(0x00 || chunk_i)     ← 叶子加前缀
2. 相邻两个节点配对哈希：parent = H(0x01 || left || right)  ← 内部节点加前缀
   奇数个节点时，最后一个复制自己和自己配对
3. 重复直到只剩一个哈希 = Merkle Root（32 字节 = 整棵树的指纹）

包含性证明（O(log N)）：
要证明 chunk_idx 在树中，从叶子到根收集路径上的「兄弟哈希」：
  idx 每升一层，把当前层的兄弟哈希 + 方向位（兄弟在左/右）入证明
  idx /= 2
证明长度 = 树高 = ceil(log2 N)。100 万块数据只需 ~20 个哈希。

验证（O(log N)，只需数据块 + 证明 + 根）：
cur = H(0x00 || chunk)
for step in proof:                      // 从叶子往根走
    if step.IsLeft:  cur = H(0x01 || step.Sibling || cur)
    else:            cur = H(0x01 || cur || step.Sibling)
return cur == root                      // 根匹配 = 证明成立
```

**核心不变量**：想伪造一个「不在树里」的块的证明，必须找到 SHA-256 碰撞，或让假的兄弟哈希一路配到真根——计算上不可行。**根哈希就是整个数据集的承诺（commitment），证明就是开锁的钥匙，验证不需要信任任何中间方**。

### Go 实现

```go
// merkle.go —— Merkle Tree：可审计评估平台的数据完整性引擎
// go run merkle.go
package main

import (
	"bytes"
	"crypto/sha256"
	"fmt"
)

type Hash [32]byte

// ---------- 哈希原语：域名分隔前缀防「第二原像攻击」 ----------
// 叶子和内部节点用不同前缀，否则攻击者可以拿某个内部节点
// 伪装成叶子，伪造「某数据块存在」的证明
func hashLeaf(data []byte) Hash {
	return sha256.Sum256(append([]byte{0x00}, data...))
}

func hashNode(left, right Hash) Hash {
	buf := make([]byte, 0, 65)
	buf = append(buf, 0x01)
	buf = append(buf, left[:]...)
	buf = append(buf, right[:]...)
	return sha256.Sum256(buf)
}

// ---------- 证明步骤：必须带方向位（兄弟在左还是右） ----------
type ProofStep struct {
	Sibling Hash
	IsLeft  bool // true = 兄弟在左，当前节点是右子
}

type MerkleTree struct {
	Levels [][][32]byte // Levels[0] = 叶子层，最后一层 = 根
	Root   Hash
}

// Build：自底向上配对哈希，O(N) 时间、O(N) 空间
func Build(chunks [][]byte) *MerkleTree {
	n := len(chunks)
	if n == 0 {
		return nil
	}
	leaves := make([]Hash, n)
	for i, c := range chunks {
		leaves[i] = hashLeaf(c)
	}
	levels := [][][32]byte{leaves}
	cur := leaves
	for len(cur) > 1 {
		next := make([]Hash, 0, (len(cur)+1)/2)
		for i := 0; i < len(cur); i += 2 {
			right := cur[i] // 奇数节点：复制自己和自己配对
			if i+1 < len(cur) {
				right = cur[i+1]
			}
			next = append(next, hashNode(cur[i], right))
		}
		levels = append(levels, next)
		cur = next
	}
	return &MerkleTree{Levels: levels, Root: cur[0]}
}

// InclusionProof：收集 idx 到根路径上的所有兄弟，O(log N)
func (t *MerkleTree) InclusionProof(idx int) []ProofStep {
	var proof []ProofStep
	for lvl := 0; lvl < len(t.Levels)-1; lvl++ {
		layer := t.Levels[lvl]
		var sib Hash
		isLeft := idx%2 == 1 // idx 是右子 → 兄弟在左
		if idx%2 == 0 {
			if idx+1 < len(layer) {
				sib = layer[idx+1]
			} else {
				sib = layer[idx] // 奇数末尾：兄弟是自己（复制配对）
			}
		} else {
			sib = layer[idx-1]
		}
		proof = append(proof, ProofStep{Sibling: sib, IsLeft: isLeft})
		idx /= 2
	}
	return proof
}

// VerifyInclusion：无需整棵树，O(log N) 重算到根比对
func VerifyInclusion(chunk []byte, proof []ProofStep, root Hash) bool {
	cur := hashLeaf(chunk)
	for _, step := range proof {
		if step.IsLeft {
			cur = hashNode(step.Sibling, cur)
		} else {
			cur = hashNode(cur, step.Sibling)
		}
	}
	return cur == root
}

func main() {
	// 模拟一个评估数据集：1000 个 eval item 分块
	var chunks [][]byte
	for i := 1; i <= 1000; i++ {
		chunks = append(chunks, []byte(fmt.Sprintf("eval-item-%04d", i)))
	}
	tree := Build(chunks)
	fmt.Printf("数据集指纹 root = %x...\n", tree.Root[:8])
	fmt.Printf("树高 = %d 层（1000 块 → 证明长度 ≤ %d）\n",
		len(tree.Levels), len(tree.Levels)-1)

	// 审计场景 1：验证第 42 号数据块确实在数据集里
	proof := tree.InclusionProof(41)
	ok := VerifyInclusion(chunks[41], proof, tree.Root)
	fmt.Printf("[审计1] item-0042 包含证明有效？%v（只传了 %d 个哈希）\n", ok, len(proof))

	// 审计场景 2：有人篡改了第 42 号块（改一个字符）
	tampered := []byte("eval-item-004X")
	ok2 := VerifyInclusion(tampered, proof, tree.Root)
	fmt.Printf("[审计2] 篡改后的块能通过验证吗？%v ← 一个字节都别想混过去\n", ok2)

	// 审计场景 3：伪造一个不在树里的块
	forged := []byte("eval-item-9999")
	ok3 := VerifyInclusion(forged, proof, tree.Root)
	fmt.Printf("[审计3] 伪造块能通过验证吗？%v\n", ok3)
}
```

### 复杂度

| 操作 | 时间 | 空间 | 说明 |
|---|---|---|---|
| Build | **O(N)** | **O(N)** | 自底向上配对哈希；存储可优化为只留根+按需重建 |
| InclusionProof | **O(log N)** | **O(log N)** | 只收集路径兄弟，不碰其他分支 |
| Verify | **O(log N)** | **O(log N)** | 无需整棵树 = 轻客户端可验证，这是灵魂 |

对比「把整棵树的哈希列表都给对方验」：N=100 万时，朴素方案要传 32MB，Merkle 证明只传 **20 × 32B = 640 字节**。

### 面试三坑

1. **奇数节点不复制配对 → 根哈希不确定**。N 个叶子若 N 不是 2 的幂，最后一层必有奇数节点。协议必须写明「复制自己和自己配对」（比特币做法），否则两家实现算出的 root 不同，一切对账失败。**工程话术：填充规则是协议的一部分，不是实现细节**。
2. **叶子和内部节点用同一个哈希函数不加前缀 → 第二原像攻击**。攻击者观察到某内部节点的值 = H(H(a)||H(b))，可以把它伪装成一个「数据块」，伪造该块在树中的证明。正确做法：**叶子 H(0x00||data)、内部节点 H(0x01||l||r)**，两个哈希空间不相交。面试官问「Merkle tree 有什么已知攻击面」，这就是标准答案。
3. **证明不带方向位 → 验证无法重算**。只知道兄弟哈希、不知道它在左在右，两个配法得出两个不同的父哈希，验证必然失败。ProofStep 必须带 IsLeft。**升级追问**：两个叶子交换位置（数据块顺序变了）会怎样？→ 根全变。Merkle Tree 是 **ordered** 结构，数据集语义的「集合」要先把叶子排序或哈希去重（sorted Merkle tree）。

### 进阶六连

1. **审计日志哈希链（append-only hash chain）**：每行 `h_i = H(h_{i-1} || entry_i)`，改任何一行全链断裂。比 Merkle 简单一个量级，是评估平台「不可抵赖」的**最小实现**——每次评测报告的元信息（数据集 root / 模型版本 / scaffold 版本 / 采样种子 / 分数）追加进链，任何事后篡改都会改变链尾。**面试话术：哈希链保序、Merkle 保集合，证书透明度（CT）日志就是两者组合**。
2. **Sorted Merkle Tree + 不存在证明**：叶子按哈希排序后，可以证明「某个元素**不在**集合里」——给出它排序位置的相邻两个叶子路径即可（O(log N)）。应用：证明「这份训练语料里**没有**某 benchmark 题目」（Day 166 污染检测的审计版——MinHash 说「像」，Merkle 说「在或不在」）。
3. **Merkle Mountain Range（MMR）**：评估日志是持续追加的，每次重算全树太贵。MMR 让新叶子**只追加、不重算**，根随高度更新，历史证明永久有效。 rolling 评估平台（每天新数据进来）的标准结构。
4. **稀疏 Merkle Tree（SMT）**：2^256 个叶子位置、默认空值，键值存在性证明 = 稀疏路径。以太坊状态树、verkle tree 的思路。面试遇到「怎么证明某个 key 有/没有某个 value 且证明很小」就上它。
5. **Content-addressed 去重**：IPFS / Git 对象库本质 = 内容寻址存储，chunk 级哈希天然去重。和 Day 166 的 MinHash 是**互补关系**：MinHash 抓「相似」（近似重复、改写污染），Merkle/内容寻址抓「相同」（精确重复、版本一致性）。评估数据集的去重管线两者都要。
6. **分布式根对账**：多副本评估集群各自 Build，只交换 32 字节 root 就知道数据集是否一致——Day 160 权重同步「Merkle 先校验后切换」的同构。百万 worker 场景下，**root 交换是唯一能 O(1) 确认全局一致性的手段**。

### 工程映射：可审计 Agent 评估平台三件套

- **数据集版本 = Merkle Root**：每次评估运行记录 `(dataset_root, scaffold_version, model_version, seed, score)` 五元组——**root 就是那个「可复现性」的锚点**。一年后别人质疑分数，重算各块证明即可自证；换一版数据 = 换 root = 不可抵赖。
- **评测报告哈希链**：每次评测报告的元信息追加进 append-only 链，发布决策链式留痕。「这个模型为什么能上线？」→ 链上查得到：哪份报告、哪个 root、哪次 SRM 检查、谁点的头。**可审计不是事后补 PPT，是写入路径的副产品**。
- **污染检测回执**：MinHash 命中某疑似污染段 → 定位 chunk → 用 Merkle proof 证明「这段确实在某版本数据集里」→ 审计闭环。评测日志（Day 166 的教训：评测日志 = 生产密钥级资产）本身也进树，读取要留痕。

### 3. 混合模拟面试：设计一套可审计、可复用、统计上诚实的 Agent 评估平台

**四步答法**（30 秒定调 → 分层展开 → 三性落地 → 治理兜底）：

**① 三澄清**
- 评估对象是什么（模型版本？agent 系统？prompt 迭代？）——决定指标体系和 scaffold 锁定策略；
- 这个评估要触发什么决策（选型/发布/灰度放量/融资背书）——Day 165 铁律：**答不出触发什么决策，评估还没设计完**；
- SLA 与预算（每天多少评测调用、judge 预算上限、报告时延要求）——决定采样规模和缓存策略。

**② 五层架构（每层假设上一层已失效）**
- **采样层**：分层蓄水池（任务类型 × 难度 × 模型版本分桶），滑动窗口保鲜，种子写进报告。失效假设：分布漂移永远存在；
- **指标层**：复合指标五问定成分与权重；judge 四级火箭做校准（黄金集 κ≥0.6、rubric 三测、双盲+位置偏置清洗、canary 漂移监测）。失效假设：judge 会过时、会被谄媚（今日 UNESCO 报告）、会对着 rubric 表演；
- **数据层**：MinHash + N-gram 污染检测进 CI；canary 串埋点；私有 holdout 三层隔离；评测日志保密等级 = 生产密钥。失效假设：泄漏迟早发生，防线要纵深；
- **决策层**：SRM 检查是第一道关（χ²>3.84 实验直接作废）；功效分析前置（基线 p/MDE/power 必填，反推样本量）；peeking 平台级禁止（固定样本量或 mSPRT 二选一）；指标分三层做多重比较校正（守门 Bonferroni / 探索 BH）。失效假设：噪声永远想冒充信号；
- **审计层（今日新增）**：五元组留痕 + 报告哈希链 + 数据集 Merkle root。失效假设：**人会撒谎、会遗忘、会离职——系统不能依赖任何人的记忆**。

**③ 三性落地（对应题目三个定语，逐条给出机制）**
- **可审计** = 五元组 + 哈希链 + Merkle root 三件套。任何分数都能回答「哪个数据集（root）、哪版 scaffold、哪个模型、什么种子、谁签发的」；
- **可复用** = 数据集版本化（root 即版本）+ 评测资产跨 run 流通（judge 校准集复用、canary 串跨项目复用、失败样本库反哺 rubric）。复用的前提是**语义稳定**：每次复用都校验 root，防止「同名不同库」；
- **统计上诚实** = Day 167 四件套：SRM 先行、功效前置、peeking 平台强制、多重比较分层。**统计诚实不是态度，是默认值**——平台默认行为必须是「不显著就不能上线」，人工要解锁必须留痕。

**④ 治理兜底**
- 发布门槛：差值 CI 不含 0 + SRM 通过 + 守门指标全绿，三条件缺一，发布按钮置灰；
- 熔断：judge 漂移超 2σ → 自动冻结该 judge 签发的报告；数据集 root 变更未登记 → 阻断评测；
- 审计日志独立部署（熔断发生时审计不能一起死），所有例外操作留痕。

**收尾点睛（时事）**：「这套平台昨晚刚被史上最大 IPO 预演过一遍——Anthropic 的簿记（6 倍超额认购）是有偏估计，$83 超区间定价证实了偏的方向，今晚开盘才是 n=1 的无偏观察。**评估平台的全部工作，就是让自己的『定价』远离簿记偏置：先查 SRM，再算功效，管住 peeking——然后才敢把 $83 写进报告。**」

### 4. 模拟面试速答五连

- **Q1：面试官说「我们要上线新模型，你跑个评估证明它更好」——你的第一反应？**
  先问三个问题再写一行代码：这个「更好」触发什么决策（灰度 10% 还是全量）？预声明的 MDE 是多少（低于 MDE 的提升即使显著也不值得激动）？对照组的基线通过率最近一次校准是什么时候？——**把「跑个评估」翻译成「设计一个功效足够的实验」是 Week 26 全部五天的浓缩**。答完三个问题才谈采样、指标、judge、统计。
- **Q2：评测报告一切正常，但半年后被人质疑分数造假，你怎么自证？**
  哈希链 + Merkle root 的自证路径：报告元信息在链上（改一行全链断）→ 重跑数据集各块的包含性证明（root 匹配 = 数据没换）→ 五元组里有种子和 scaffold 版本，任何人可复跑。**审计的精髓：自证成本 O(log N)，伪造成本 = 破解 SHA-256**。没有这套机制 = 你的诚实没有证据，只有声明。
- **Q3：judge 给两个模型打分，A 8 分 B 7 分，怎么证明这个差距是真的？**
  Day 165+167 合答：四步——交换顺序重评（位置偏置清洗，>10% 不一致结论作废）→ 各采 ≥100 条 bootstrap 差值 CI（含 0 报「无法区分」）→ 黄金集交叉验证 judge 在 7/8 分附近的分辨率（相邻分值一致率）→ 异构 judge ensemble 复测，独立 judge 同向才收结论。**单 judge 单轮打分 = 轶事不是数据**。补一刀：若该 judge 有谄媚史（UNESCO 报告级别的问题），结论权重直接降档。
- **Q4：评估平台的成本爆炸（judge API 账单一个月翻三倍），先砍什么？**
  Day 167 纪律：先看 SRM 和功效——**很多实验根本不用跑满样本量，CUPED 前置指标回归调整能省 30-50%**；judge 分层（便宜 judge 全量预筛、贵 judge 只复核高杠杆子集）；缓存分层（确定性 reward 全缓存，LFU+TTL）；规则前置（能程序验证的零 LLM 成本）。**绝不砍三样：SRM 检查、审计留痕、canary 监测**——砍成本砍重复和宽度，不砍诚实。
- **Q5：Gemini 4 Carbon 这种「第一名但贵 15 倍且总超时」的模型，你的评估报告怎么写？**
  三个分列：① 准确率 × cost 的联合指标（cost-per-correct 才是决策变量，accuracy 单独看是行为艺术）；② 失败模式分列（超时 vs 答错分开统计——Gemini 4 Carbon「几乎从不放弃但常超时」，混在一起会系统性高估它）；③ 明确写下评测的 timeout 预算口径（几秒？重试几次？），因为**「谁更准」的答案依赖「允许多久」的前提**。报告里把口径藏起来 = 下一个 Qwen4-Max 式信任危机。
