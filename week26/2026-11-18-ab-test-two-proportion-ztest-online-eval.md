## 一、今日算法题：双比例 z 检验（A/B 检验引擎 · LC 无 · 统计推断核心）

### 题目

设计一个线上评估的 **A/B 检验引擎**，服务模型上线决策：

```
输入：
- 对照组（baseline 模型）：n1 次评估调用，x1 次通过
- 实验组（新模型）：       n2 次评估调用，x2 次通过

要求实现：
1. Test(x1, n1, x2, n2) → 返回 z 统计量、p-value、通过率差值的 95% 置信区间
2. RequiredSampleSize(p, mde, alpha, power) → 给定基准通过率 p、
   希望检出的最小提升 mde、显著性水平 alpha、功效 power，
   返回每组所需最小样本量
3. DetectSRM(actual1, actual2, expectedRatio) → 样本比例不匹配检测

示例：
Test(582, 1000, 620, 1000)
// p1=0.582, p2=0.620, diff=+0.038
// z ≈ 1.79, p ≈ 0.074 → 不显著（p > 0.05）
// 95% CI ≈ [-0.003, +0.079] → 区间跨 0，结论一致

RequiredSampleSize(0.5, 0.05, 0.05, 0.8) → ≈ 1568 每组
// 若每天只有 500 次评估调用 → 一组要跑 3 天以上才能出结论
```

**为什么选这题**：Week 26 前三天解决了「评估集怎么选」「指标怎么定」「数据干不干净」，今天是最后一个问题：**新模型分数比旧模型高 2 个点，能上线吗？** 2 个点可能是真实提升，也可能是抽样噪声——A/B 检验就是要把这句话变成可计算的数学对象。线上评估 = 每天无数个小样本实验，**统计显著性判断是评估平台的操作系统内核**。

### 思路：合并比例 + 正态近似

**双比例 z 检验**的核心三步：

```
1. 合并比例（零假设 H0：两组通过率相同）：
   p_pool = (x1 + x2) / (n1 + n2)

2. 标准误（在 H0 下，两组共享同一个 p）：
   SE = sqrt( p_pool × (1 - p_pool) × (1/n1 + 1/n2) )

3. z 统计量 = 观测差异 / 标准误：
   z = (p1 - p2) / SE
   p-value = 2 × (1 - Φ(|z|))      // Φ = 标准正态 CDF
```

**置信区间用非合并 SE**（这是面试分水岭）：

```
SE_CI = sqrt( p1(1-p1)/n1 + p2(1-p2)/n2 )    // 不用 p_pool
CI = (p1 - p2) ± 1.96 × SE_CI
```

**功效分析（样本量计算）**——评估平台的「排期器」：

```
n = [ z_α × sqrt(2 × p̄ × (1-p̄)) + z_power × sqrt(p1(1-p1) + p2(1-p2)) ]² / mde²

p̄ = (p1 + p2)/2，p2 = p1 + mde（要检出的最小差异）
z_α = 1.96（双侧 α=0.05），z_power = 0.84（power=80%）
```

**SRM 检测**（Sample Ratio Mismatch，工程上最重要也最容易被忽略）：

```
期望比例 r = n1/(n1+n2)，实际观察 o1 = actual1/(actual1+actual2)
χ² = (actual1 - E1)²/E1 + (actual2 - E2)²/E2，E1 = r×N，E2 = (1-r)×N
若 χ² > 3.84（df=1，α=0.05）→ 分流有 bug，实验作废
```

### Go 实现

```go
package main

import (
	"fmt"
	"math"
)

// ---------- 标准正态 CDF ----------
func normalCDF(z float64) float64 {
	return 0.5 * (1.0 + math.Erf(z/math.Sqrt2))
}

func normalQuantile(p float64) float64 {
	// Acklam 近似：标准正态分位数
	a := []float64{-3.969683028665376e+01, 2.209460984245205e+02,
		-2.759285104469687e+02, 1.383577518672690e+02,
		-3.066479806614716e+01, 2.506628277459239e+00}
	b := []float64{-5.447609879822406e+01, 1.615858368580409e+02,
		-1.556989798598866e+02, 6.680131188771972e+01,
		-1.328068155288572e+01}
	c := []float64{-7.784894002430293e-03, -3.223964580411365e-01,
		-2.400758277161838e+00, -2.549732539343734e+00,
		4.374664141464968e+00, 2.938163982698783e+00}
	d := []float64{7.784695709041462e-03, 3.224671290700398e-01,
		2.445134137142996e+00, 3.754408661907416e+00}
	pl, ph := 0.02425, 1-0.02425
	switch {
	case p < pl:
		q := math.Sqrt(-2 * math.Log(p))
		return (((((c[0]*q+c[1])*q+c[2])*q+c[3])*q+c[4])*q + c[5]) /
			((((d[0]*q+d[1])*q+d[2])*q+d[3])*q + 1)
	case p > ph:
		q := math.Sqrt(-2 * math.Log(1-p))
		return -(((((c[0]*q+c[1])*q+c[2])*q+c[3])*q+c[4])*q + c[5]) /
			((((d[0]*q+d[1])*q+d[2])*q+d[3])*q + 1)
	default:
		q := p - 0.5
		r := q * q
		return (((((a[0]*r+a[1])*r+a[2])*r+a[3])*r+a[4])*r + a[5]) * q /
			(((((b[0]*r+b[1])*r+b[2])*r+b[3])*r+b[4])*r + 1)
	}
}

// ---------- 1. 双比例 z 检验 ----------
type ABResult struct {
	P1, P2    float64 // 两组通过率
	Diff      float64 // p1 - p2
	Z         float64
	PValue    float64
	CILow     float64 // 差值 95% CI 下界
	CIHigh    float64
	Significant bool  // p < 0.05
}

func ABTest(x1, n1, x2, n2 int) ABResult {
	p1 := float64(x1) / float64(n1)
	p2 := float64(x2) / float64(n2)

	// 检验统计量：H0 下用合并比例
	pPool := float64(x1+x2) / float64(n1+n2)
	sePool := math.Sqrt(pPool * (1 - pPool) * (1.0/float64(n1) + 1.0/float64(n2)))
	z := (p1 - p2) / sePool
	pValue := 2 * (1 - normalCDF(math.Abs(z)))

	// 置信区间：用各组自身比例（unpooled SE）
	seCI := math.Sqrt(p1*(1-p1)/float64(n1) + p2*(1-p2)/float64(n2))
	diff := p1 - p2

	return ABResult{
		P1: p1, P2: p2, Diff: diff,
		Z: z, PValue: pValue,
		CILow:     diff - 1.96*seCI,
		CIHigh:    diff + 1.96*seCI,
		Significant: pValue < 0.05,
	}
}

// ---------- 2. 功效分析：每组所需样本量 ----------
// p = 基准通过率，mde = 要检出的最小提升，power=0.8 → z=0.84
func RequiredSampleSize(p, mde, alpha, power float64) float64 {
	za := normalQuantile(1 - alpha/2)   // 0.05 双侧 → 1.96
	zp := normalQuantile(power)          // 0.8 → 0.8416
	p2 := p + mde
	pBar := (p + p2) / 2
	num := za*math.Sqrt(2*pBar*(1-pBar)) + zp*math.Sqrt(p*(1-p)+p2*(1-p2))
	return math.Pow(num, 2) / (mde * mde)
}

// ---------- 3. SRM 检测：分流是否按预期比例 ----------
func DetectSRM(actual1, actual2 int, expectedRatio float64) (chi2 float64, ok bool) {
	total := float64(actual1 + actual2)
	e1 := expectedRatio * total
	e2 := (1 - expectedRatio) * total
	chi2 = math.Pow(float64(actual1)-e1, 2)/e1 + math.Pow(float64(actual2)-e2, 2)/e2
	return chi2, chi2 < 3.84 // df=1, α=0.05 的临界值
}

func main() {
	r := ABTest(582, 1000, 620, 1000)
	fmt.Printf("diff=%+.3f  z=%+.2f  p=%.3f  CI=[%+.3f, %+.3f]  sig=%v\n",
		r.Diff, r.Z, r.PValue, r.CILow, r.CIHigh, r.Significant)
	// diff=+0.038  z=+1.79  p=0.074  CI=[-0.003, +0.079]  sig=false
	// 结论：+3.8 个点不足以排除噪声，继续攒样本

	n := RequiredSampleSize(0.5, 0.05, 0.05, 0.8)
	fmt.Printf("required n per group: %.0f\n", n) // ≈ 1568

	chi2, ok := DetectSRM(4820, 5180, 0.5)
	fmt.Printf("SRM chi2=%.2f ok=%v\n", chi2, ok)
	// chi2=6.48 > 3.84 → 分流有 bug，本实验作废
}
```

### 复杂度

| 操作 | 时间 | 空间 |
|---|---|---|
| ABTest | **O(1)** | O(1) |
| RequiredSampleSize | **O(1)** | O(1) |
| DetectSRM | **O(1)** | O(1) |

全是闭式解（closed-form）——统计检验的优雅之处：**结论来自公式，不来自模拟**。工程上 z 检验 + 正态近似在 n×p ≥ 5 且 n×(1-p) ≥ 5 时成立（样本太小换 Fisher 精确检验）。

### 面试追问

> 💬 **面试官：p-value = 0.074 到底说明了什么？**

🎯 **教科书级回答**：

> 「在『新旧模型真实通过率相同』的零假设下，观察到当前这么大（或更大）差异的概率是 7.4%。**它不能告诉我们新模型更好的概率是 92.6%**——这是最常见的误读。p-value 衡量的是『数据与 H0 的相容程度』，不是『H1 为真的概率』。所以 0.074 的结论是：**证据不足以在 5% 水平拒绝 H0，继续攒样本或承认检不出 3.8 个点的差异**。面试官如果继续追问贝叶斯，就上 Bayes factor。」

> 💬 **面试官：置信区间为什么用 unpooled SE，检验却用 pooled SE？**

🎯 **一句话抓住本质**：

> 「检验问的是『H0 成立时差异有多反常』——H0 说两组同分布，所以用一个合并的 p 估计标准误。**区间问的是『真实差异可能在哪』——这时两组参数自由，必须各自估计方差再相加**。用 pooled SE 算区间会在 H0 附近系统性低估不确定性——这就是『检验显著但区间跨 0』矛盾的来源，面试时说得出这个 = 统计功底过关。」

> 💬 **面试官：实验跑到一半 p=0.049，能停吗？**

🎯 **peeking 问题，工程高危**：

> 「不能。每天看一眼数据、显著了就停 = 多重检验，第一类错误率会膨胀到 20-30%（模拟可证）。标准做法三选一：① **固定样本量**（用功效分析算出 n 再跑，Day 164 的蓄水池抽样决定上限）；② **序贯检验**（mSPRT / alpha-spending：把 α 预算按信息量递增分配，每次 peek 花一点）；③ **always-valid p-value**。工程话术：**peeking 的诱惑来自 KPI 压力，统计纪律是给工程上的刹车**。」

> 💬 **面试官：两组样本量必须 50/50 吗？**

🎯 **不对称分流**：

> 「不必。统计上最优比例不是 50/50 而是 √ 比例：n1/n2 = √(σ1²/σ2²) ≈ √(p1(1-p1)/p2(1-p2))。线上评估的实际约束是『新模型流量有限』——把 90% 流量给 baseline 10% 给新模型，CI 宽度只比 50/50 差 ~1.6 倍，但新模型风险敞口降到 1/9。**风险不对称时用小流量试水 + 渐进放量 = 灰度发布的统计版本**。」

## 二、面试技巧：线上评估与统计显著性

### 2.1 英伟达财报夜 = 一场市场自定价的 A/B 检验

昨晚的英伟达财报是**用统计思维读新闻的完美教材**：

**① 多重指标 = 多重比较问题。** 华尔街同时盯至少 6 个指标：营收、EPS、数据中心收入、毛利率、下季指引、回购。**6 个指标同时「beat」的概率在 H0（公司只是正常波动）下远比单指标低**——用 Bonferroni 粗略校正：单指标 5% 显著 → 6 指标至少一个「显著 beat」的概率 ≈ 1 - 0.95⁶ ≈ 26%。所以「6 项全 beat」才是真正强的信号（昨晚：5/6 beat，毛利率指引下调）。**面试话术：「单指标显著可能是噪声，多维同向显著才是结构信号——这就是为什么我的评估平台报告 vector 而不是 scalar。」**

**② 期权隐含波动 = 市场自己设定的显著性阈值。** 期权定价 ±8.5% 意味着市场说「营收/EPS 落在 ±8.5% 内的反应 = 不显著，超出才算意外」。实际 +3% **落在区间之内**——所以盘前 +3% 的真实读法是：**beat 幅度低于市场定价的「最小可检差异」（MDE）**。市场用真金白银做了功效分析。

**③ 「beat 但跌」模式被证伪的统计意义。** 过去 4 季度 3 次 beat 后跌（小样本 n=4），昨晚是第 5 次观察。**1/4 → 2/5 的提升离统计显著远得很**——但叙事已经改写。这正是评估平台的日常：一个 n=5 的实验推翻一个被广泛引用的「规律」。**教训：小样本模式 + 强叙事 = 统计地雷，工程上叫 recency bias。**

**④ 毛利率信号 = 混合效应。** 营收 beat（+6.1%）+ 毛利率指引下滑（74.9%→71-72%）同时发生 = **处理效应在不同指标上方向相反**。市场最终给 +3% = 市场内部对指标加权后的净效应。映射到模型评估：**新模型代码通过率 +5 个点、推理成本 +15%——你能不能上线，取决于决策者的效用函数，不是单一指标**（Day 165「评估价值 = 触发的决策数量」的统计版）。

### 2.2 Anthropic 今天定价：n=1 实验的定价艺术

今天 Anthropic 定价，明天开盘 = **n=1 实验的第一个无偏观察值**：

- **簿记阶段 = 有偏估计**：6-7 倍超额认购是承销商的「训练集」——机构报价有策略性夸大（知道会按比例配售，报高价博配额）。**这相当于评估中的「标注偏置」（Day 165）**。
- **开盘价 = holdout**：明天散户和二级市场的交易才是无偏信号。**第一天波动服从期权对冲 + 动量 + 散户 FOMO 的混合分布——方差极大，单日观察几乎无信息量**。所以「首日涨 20% = 定价低了 / 首日破发 = 定价高了」的即时判断 = **用 n=1 的观察做功效不足的结论**。
- **统计上诚实的读法**：定价当晚看区间（$70-78 vs 顶格 vs 超区间），挂牌后看**首周累积分布**而不是首日点位。**把单日冲击和趋势分离 = 时间序列思维进评估**。

### 2.3 工程四件套：SRM / peeking / power / CUPED

把 A/B 检验落到评估平台的四个工程必备：

**① SRM 是第一道关（比显著性更早）**：分流 bug（缓存命中导致实验组拿到旧模型、路由 sticky session 失衡、某 region 全进了对照组）会让 p-value 完全不可信。**上线实验先看 SRM χ²，过了再看差异**——顺序不能反。

**② peeking 纪律 = 平台级强制**：评估平台应支持「锁定样本量跑满」和「序贯检验」两种模式，**默认禁止人工随时看数叫停**。一个 20 个 PM 随时能看的 dashboard = 隐形的多重检验机器。

**③ 功效分析前置到实验设计**：跑实验前必填三参数——基线通过率 p、MDE（最小可检差异）、期望 power。平台直接反推「每组需要多少样本、按当前流量要跑几天」。**跑了一个 n=200、MDE=5% 的实验 = 注定检不出任何东西的行为艺术**。英伟达期权 ±8.5% 就是市场做的功效分析：MDE 定 8.5%。

**④ CUPED 方差缩减（加分项）**：线上评估的方差大头来自任务难度差异，不是模型差异。CUPED = 用实验前的「前置指标」（同一批任务在旧模型上的历史通过率）做协变量回归调整，**样本量可省 30-50%**。工程实现：评估集固定（Day 164 的分层蓄水池），每组任务都带「历史难度分」，分析时用 ANCOVA 调整。**说出 CUPED = 把统计检验从教科书拉进工程现场**。

### 2.4 多重比较校正：发布评审的隐形炸弹

评估平台最容易翻车的地方：**一次发布评审跑 20 个指标，挑 2 个显著的写进报告**。

```
场景：新模型 vs 旧模型，20 个评测维度（代码/数学/写作/安全/...各 5 项）
即使两模型完全相同（全局 H0），
期望「恰好至少 1 个 p < 0.05」的次数 = 20 × 0.05 = 1 个。

所以每次发布报告看到 1-2 个「显著提升」= 完全符合纯噪声预期。
```

**三种校正（面试按场景选）**：

| 方法 | 控制目标 | 适用场景 | 代价 |
|---|---|---|---|
| **Bonferroni**（α/m） | 族错误率 FWER | 安全/合规指标（一个都不能错报） | 最保守，功效损失大 |
| **Holm**（逐步下调） | FWER，比 Bonferroni 强 | 中等规模指标族（m < 50） | 依然保守 |
| **Benjamini-Hochberg** | 错误发现率 FDR | 探索性分析/几十个维度扫描 | 允许少量假阳性，功效最好 |

**面试话术**：

> 「发布评审的指标分两层：**守门指标**（安全、正确性——用 Bonferroni，宁缺毋滥）和**观测指标**（体验、风格——用 BH，宁观勿弃）。英伟达昨晚就是混合结论：营收（守门）beat 用最高标准看依然显著，毛利率（观测）miss 被加权后稀释。**指标体系不分层 = 每个发布决策都在多重检验裸奔。**」

### 2.5 置信区间 vs p-value：评审话术的分水岭

评估报告里写「p = 0.04，显著提升」还是「提升 +2.1 个点 [+0.1, +4.1]」？**后者才是工程语言**：

- p-value 只答「有没有」，CI 告诉你「有多大、误差多少」。**上线决策需要效应量，不只是显著性**。
- CI 的宽度 = 决策风险度。[+0.1, +4.1] 意味着「可能几乎没提升，也可能翻倍」——**这种结果该配灰度放量而不是全量**。
- **CI 不相交规则**（Day 165 讲 ECI 时提过）：两个模型各自带 CI，CI 重叠 ≠ 无差异，但**两独立样本的差值 CI 跨 0 = 无显著差异**。报告里永远给差值 CI。

## 三、速答五连

> **Q1: 新模型通过率 +3.8 个点，p = 0.074，产品经理催上线，你怎么回？**
> 三步：① 效应量够不够业务价值——3.8 个点若低于预先声明的 MDE，即使 p<0.05 也不该激动；② CI [−0.3, +7.9] 跨 0 = 数据没说清，要么加样本（按功效分析补到每组 ~1568），要么灰度 10% 流量继续观察；③ 给 PM 看 SRM 检查 + 分流一致性记录——实验本身的可信度先于结论。**「不显著 ≠ 没效果，显著 ≠ 有效果大」——统计纪律保护的是长期决策质量。**

> **Q2: 实验组 4820 次调用 vs 对照组 5180 次（期望 50/50），先看什么？**
> SRM χ² = 6.48 > 3.84 → 分流有 bug，实验作废重跑。可能原因：sticky routing 把老用户全送对照组、某 region 缓存只命中实验组、超时重试策略不对称。**SRM 是 A/B 检验的心电图——它异常时，p-value 是尸体上的化妆。**

> **Q3: 通过率 1% 的冷启动场景，普通 z 检验失效怎么办？**
> n×p < 5 时正态近似失效 → **Fisher 精确检验**（超几何分布闭式解）。但更好的工程解是**换指标**：通过率 1% 时直接评估 pass/fail 效率太低，改用「部分得分」「reward 均值」「分级通过率」（把二值变成多值/连续），方差结构完全不同。**统计方法失效往往是指标设计的报警器。**

> **Q4: 线上 A/B 实验里用户互相影响（社交网络、共享 agent 环境）怎么办？**
> 标准 A/B 假设独立同分布，互相影响 = 干扰（interference）→ 估计有偏。解法：**switchback 实验**（时间片随机而非用户随机：整集群同一时刻全用版本 A，下一时刻全切 B，成对比较相邻时间片）+ 聚类随机（cluster-randomized，按 workspace/租户为单位分流）。**评估 agent 平台时，agent 之间共享环境 = 天然干扰源，switchback 是标配。**

> **Q5: 面试官问「统计显著和业务显著的区别」？**
> 「统计显著回答『这是真的吗』，业务显著回答『这值得做吗』。+0.05 个点通过率，n=10 万时 p=0.001 高度显著——但如果每提升 1 个点只值 1 万美元/年，0.05 个点 = 500 美元，覆盖不了实验本身的工程成本。**上线决策 = 效应量 × CI 宽度 × 业务权重，p-value 只是入场券。**」
