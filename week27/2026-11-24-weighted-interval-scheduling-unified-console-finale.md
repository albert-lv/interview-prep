## 一、今日算法题：规划兼职工作（LC 1235 · 加权区间调度）

### 题目

你有 `n` 份工作，`startTime[i]`、`endTime[i]`、`profit[i]` 分别表示第 `i` 份工作的开始时间、结束时间和收益。**同一时间只能做一份工作**（两份工作时间重叠则不能同时选，首尾相接 `[1,3)` 与 `[3,5)` 可以共存）。返回你能获得的最大收益。

```
输入：startTime = [1,2,3,3], endTime = [3,4,5,6], profit = [50,10,40,70]
输出：120
解释：选工作 0（[1,3)，收益 50）+ 工作 3（[3,6)，收益 70）= 120
```

### 思路：排序 + DP + 二分（贪心在这里正式下课）

这道题是**贪心与 DP 的分水岭题**，也是 Week 27 收官的算法注脚：

- **无权版本**（数最多能接多少份工作）：按 end 升序 + 每次挑最早结束且兼容的 → 贪心成立，交换论证可证（Day 171 骨架）。
- **加权版本**（本题）：贪心**失败**。反例一目了然：

```
A=[1,2,5]  B=[2,9,100]  C=[6,7,5]
贪心按 end 最早选 A（end=2），然后只能选 C → 总收益 10
最优：A + B 首尾相接 → 105（B 的收益 100 被贪心永久错过）
```

**为什么贪心失效**：按 end 最早选等价于假设「每个时间槽的价值密度相同」，但收益权重不同，选 A 的机会成本是堵死 B 的 7 个小时——**局部「 earliest 」决策没有全局记账**。这正是 Day 172 的核心命题「不能每笔交易局部最优，DP 的价值就是全局记账」在调度世界的孪生版。

**正确解法**：

1. 按 `end` 升序排序。
2. `dp[i]` = 只考虑前 `i` 份工作的最大收益（`dp[0] = 0`）。
3. 对第 `i` 份工作 `j = i-1`，二分出 `p(i)` = 最后一个 `end <= start[j]` 的工作位置（即与它兼容的最远前缀）。
4. 决策：**不做** `dp[i-1]` vs **做** `profit[j] + dp[p(i)]`。
5. 答案 `dp[n]`。

```go
type Job struct{ Start, End, Profit int }

func JobScheduling(start, end, profit []int) int {
    n := len(start)
    jobs := make([]Job, n)
    for i := 0; i < n; i++ { jobs[i] = Job{start[i], end[i], profit[i]} }
    sort.Slice(jobs, func(i, j int) bool { return jobs[i].End < jobs[j].End })
    ends := make([]int, n)
    for i := 0; i < n; i++ { ends[i] = jobs[i].End }

    dp := make([]int, n+1)
    for i := 1; i <= n; i++ {
        j := i - 1
        // 二分：最后一个 end <= jobs[j].Start 的位置
        lo, hi := 0, n-1
        for lo < hi {
            mid := (lo + hi + 1) / 2
            if ends[mid] <= jobs[j].Start { lo = mid } else { hi = mid - 1 }
        }
        p := 0
        if ends[lo] <= jobs[j].Start { p = lo + 1 }
        dp[i] = max(dp[i-1], jobs[j].Profit+dp[p])
    }
    return dp[n]
}
```

### 实测（Go 全跑通 ✓）

```
例1 DP = 120    例1 贪心 = 90    ← end 最早贪心在官方例上就是错的
反例 DP = 105（A+B 首尾相接）   反例 贪心 = 10（错过 B 的 100）
例2 DP = 6      链式 DP = 20     重叠 DP = 8（全重叠只能取最大者）
```

### 复杂度

- 时间 **O(n log n)**：排序 O(n log n) + n 次二分 O(log n)。
- 空间 **O(n)**（`dp` 只依赖前缀，可滚动但需二分随机访问 ends，保留数组最自然）。

### 面试三坑

1. **用「按 end 最早」的贪心解加权版** = 直接挂。被追问「为什么不能贪心」要答出本质：*交换论证在无权版本里交换两份工作数量不变，加权版交换后总收益会变，论证链断裂*。**无权贪心 = 计数问题；加权 DP = 决策问题**，一字之差两个世界。
2. **二分边界**：找「最后一个 `end <= start`」，用 `lo < hi` + `mid = (lo+hi+1)/2` 向上取整模板，配合 `ends[lo] <= start` 的判据；`dp` 下标比 job 下标多 1（`dp[i]` 是前 i 个），`p` 记得 +1 对齐，否则 dp[p] 错位一个收益。被问「能不能 lower_bound」：可以，找「第一个 `end > start`」再退一格，语义等价，写顺一个即可。
3. **首尾相接算不算重叠**：`[1,3)` 与 `[3,5)` 兼容。本题是半开区间语义，判据 `end <= start`；如果面试官改口「同时开始算冲突」就把判据改成 `end <= start` 依然成立（开始时刻不会冲突），但如果他说「同刻结束和开始冲突」要立刻把判据调成 `<`。***区间题的边界语义永远是第一追问***。

### 进阶六连

1. **多机版本（k 台机器，最多 k 条并行轨道）**：单机的「兼容」变成「存在一条轨道放得下」。最小化轨道数 = 区间划分数 = 最大重叠数（扫描线 + 堆，Day 25 已练）；加权多机 = 每台跑一条加权调度 = NP-hard（k 是输入的一部分，Partition 归约），工程上 = 先按最大重叠数定 k，再单机 DP 或 LPT 分配（Day 169）。
2. **在线版本（黑五直播版）**：工作流式到达、deadline 前必须决定接不接。不能 DP（未来未知），退化为：按「收益密度 profit/时长」排序接单 + 已接单集合内做 eviction（新工作收益 > 集合内最低收益且能放下就替换）= 保底竞争比策略；被问就说「离线最优解是 DP 的上界，在线策略用它做 shadow benchmark 评估损失」。
3. **带资源需求（异构 GPU）**：每份工作还要 `gpu_i` 张卡 + 机器容量 C → 二维约束（时间 + 资源）→ 近似：先按时间单层 DP 选出候选集，再装箱检查可行性（Day 169 Bin Packing 对偶），不可行则回退剔除最低「收益密度」工作。**分层解耦两个约束，不要直接上二维 DP 爆炸**。
4. **可变收益曲线（推理定价版）**：工作收益 = `tokens × 单价(t)`，单价随时间（峰谷电价）变化 → 同一份工作放在不同时段收益不同 → 状态里加时间维度：`dp[t] = max(dp[t-1], max over j end at t of (dp[start_j] + tokens_j × price(t)))`，按 end 分组取 max = O(n log n + T)。这就是 Day 171 峰谷电价调度的收益视角。
5. **k 项限制**：最多只能接 k 份工作（预算/配额）→ `dp[i][k]` 二维，转移 `dp[i][k] = max(dp[i-1][k], profit + dp[p(i)][k-1])`，O(nk log n)——LC 188 的区间版：*「最多 k 次」的约束换了个战场回来*。
6. **输出方案而不只是数值**：回溯 dp 数组，从 `dp[n]` 往前推：若 `dp[i] != dp[i-1]` 说明第 i 个被选中，跳到 `dp[p(i)]`。面试常被补一刀「我要知道接了哪些单」，提前写好回溯 = 展示工程完整度。

## 二、工程映射：成本-容量-路由一体化控制台的本体

本周四面框架（Day 169 路由 → Day 170 容量 → Day 171 电力 → Day 172 成本归因）在收官日合流成一道设计题：

> **「给推理集群做一套成本-容量-路由一体化控制台」**

加权区间调度就是这个控制台的**微观决策内核**：每个推理请求/批量任务是一个 `[到达, 截止]` 时间窗 + 资源需求 + 收益（或成本）的工作，调度器在时间轴上决定**接哪些、放哪台、什么时机跑**——收益最大化即集群利润最大化，本质是同一个 DP：

| 算法概念 | 控制台实体 |
|---|---|
| Job `[start, end)` | 推理请求的时间窗（SLA deadline 前必须完成） |
| Profit | 收入（合同价 × 完成率）− 运行成本（七行账单，Day 172） |
| 单机调度 | 单卡/单节点的连续批处理序列 |
| 多机 k 轨道 | 卡池容量（Day 170 水位线） |
| 时间窗 + 峰谷电价 | Day 171 潮汐：把可时移任务挪进便宜槽位 |
| DP vs 贪心 | 接单要全局记账（毛利对账），不能只按「最早结束/最短任务」贪心 |

**一体化控制台三层架构**（收官综合答案框架）：

1. **度量层（Instrumentation）**：没有它一切优化都是行为艺术——每请求五元组（模型版本/路由路径/时延分位/成本归因/缓存命中）入湖，输出 Day 172 的七行账单和 Day 170 的 (λ, P99) 散点。Week 26 教训：*没有 instrumentation 就没有评估*。
2. **决策层（Optimization）**：离线 = 加权区间调度 DP 求影子最优解（上界 benchmark）；在线 = 分层启发式（路由 PoT/LL → 容量水位线限流 → 可时移任务进低价槽）。离线给上界，在线测差距，差距 >10% 才值得换更贵的求解器。
3. **治理层（Governance）**：绿黄红水位线自动扩缩容（Day 170）、熔断三旋钮（Day 156 复用）、合规第四本账校验（BIS 规则：请求目的地白名单，Day 172）、审计哈希链留痕（Week 26 Merkle）。
