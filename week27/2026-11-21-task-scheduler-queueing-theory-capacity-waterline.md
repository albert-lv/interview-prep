## 一、今日算法题：任务调度器（LC 621 · 带冷却期的调度）

### 题目

给你一个字符数组 `tasks`（每个字符代表一类任务，可重复），以及非负整数 `n`（**冷却时间**：**相同任务**之间必须至少有 `n` 个时间单位的间隔，期间可以执行其他任务或空转）。返回完成所有任务所需的**最短时间**。

```
输入：tasks = ["A","A","A","B","B","B"], n = 2
输出：8
解释：A → B → 空转 → A → B → 空转 → A → B
     （两个 A 之间至少隔 2 个单位，空转也要计时）
```

**工程语境**：这就是 **GPU batch 调度里「KV cache 换入换出空窗」的抽象**——同一模型权重刚在 GPU A 上跑完一个大 batch，把它换下来、换另一个模型上来有固定开销（n 个时间单位），期间 GPU 空转；**令牌桶限速器**同理：同一 key 的令牌发放有最小间隔。**问「最短完成时间」= 问「队列排多长、空转多少」——冷却调度是排队论的最小可计算模型**。

### 思路 A：数学公式法（O(N)）——「最热任务定骨架，其余填肉」

**关键观察**：最短时间由**出现次数最多的任务**决定。设最高频次 `maxFreq = f`，共有 `cnt` 个任务达到这个频次。

把最热的任务当骨架，按 `(n+1)` 大小的框架铺开（任务 + n 个冷却位）：

```
框架 1: A _ _     ← A 之后必须跟 n=2 个非 A
框架 2: A _ _
框架 3: A B       ← 最后一个框架不满，冷却位可以被其他任务占用
```

- 前 `f-1` 个框架：每个占满 `(n+1)` 格（不够的用空转/其他任务填）
- 最后 1 个框架：只放 `cnt` 个「并列最热」的任务，**不需要尾随冷却**

$$\text{answer} = \max\big( (f-1)\times(n+1) + cnt,\ \ len(tasks) \big)$$

**为什么要和 `len(tasks)` 取 max**：当任务种类足够多时，冷却约束自然被其他任务填满，答案退化为「任务总数」（排队的长度由供给决定，约束不起作用——这就是 ρ<1 时队列≈0 的算法版）。

**复杂度**：计数 O(N)，O(1) 额外空间（26 种任务）。

### 思路 B：最大堆模拟（O(N·log k)）——通用解法，面试加分项

公式法只能处理「同构冷却」（所有任务同一个 n）。工程上冷却约束通常是**异构**的（模型 A 切换 5ms、模型 B 切换 50ms），这时公式失效，必须模拟：

```
每一轮（一个时间单位）：
1. 从「可用堆」（冷却已到期的任务）里弹出频次最高的执行，频次-1
2. 它进入「冷冻室」：n 个单位后才能回来（记录解冻时刻）
3. 时间 +1，把冷冻室到期的任务放回可用堆
4. 可用堆为空且冷冻室有货 → 时间直接快进到最近解冻时刻（空转）
```

**复杂度**：每个任务进堆出堆各一次，O(N·log k)，k = 任务种类数。

### Go 实现（两种方法都给出）

```go
package main

import "container/heap"

// ---------- 方法一：数学公式 O(N) ----------
func leastInterval(tasks []byte, n int) int {
    freq := make([]int, 26)
    maxFreq, cntMax := 0, 0
    for _, t := range tasks {
        freq[t-'A']++
        if freq[t-'A'] > maxFreq {
            maxFreq, cntMax = freq[t-'A'], 1
        } else if freq[t-'A'] == maxFreq {
            cntMax++
        }
    }
    byFramework := (maxFreq-1)*(n+1) + cntMax // 框架法骨架
    if len(tasks) > byFramework {
        return len(tasks) // 任务够多，冷却自然被填满
    }
    return byFramework
}

// ---------- 方法二：最大堆模拟（支持异构冷却） ----------
type item struct{ freq int; readyAt int } // readyAt = 解冻时刻
type maxHeap []item
func (h maxHeap) Len() int { return len(h) }
func (h maxHeap) Less(i, j int) bool { return h[i].freq > h[j].freq }
func (h maxHeap) Swap(i, j int) { h[i], h[j] = h[j], h[i] }
func (h *maxHeap) Push(x any) { *h = append(*h, x.(item)) }
func (h *maxHeap) Pop() any { old := *h; v := old[len(old)-1]; *h = old[:len(old)-1]; return v }

func leastIntervalHeap(tasks []byte, n int) int {
    freq := make([]int, 26)
    for _, t := range tasks { freq[t-'A']++ }
    h := &maxHeap{}
    for _, f := range freq { if f > 0 { heap.Push(h, item{f, 0}) } }
    time := 0
    freezer := []item{} // 简易冷冻室（工程上用按 readyAt 排序的小根堆）
    for h.Len() > 0 || len(freezer) > 0 {
        // 解冻：把 readyAt <= time 的放回可用堆
        for i := 0; i < len(freezer); i++ {
            if freezer[i].readyAt <= time {
                heap.Push(h, freezer[i])
                freezer = append(freezer[:i], freezer[i+1:]...)
                i--
            }
        }
        if h.Len() == 0 { // 全体在冷冻 → 快进时间
            next := freezer[0].readyAt
            for _, it := range freezer { if it.readyAt < next { next = it.readyAt } }
            time = next
            continue
        }
        cur := heap.Pop(h).(item)
        if cur.freq > 1 {
            freezer = append(freezer, item{cur.freq - 1, time + n + 1})
        }
        time++
    }
    return time
}
```

### 面试三坑

1. **忘记和 `len(tasks)` 取 max**——例：`tasks=["A","B","C","D"], n=2`，框架法给 `(1-1)*3+1=1`，显然答案应为 4。这是面试官的第一道钓鱼题，**记住：冷却约束是下限约束，任务总量是上限约束，答案取两者更大**。
2. **公式法被问「冷却时间不同怎么办」答不上来**——标准答案：「公式依赖同构冷却假设，异构时退化为**基于堆的事件模拟**，把解冻时刻放进小根堆；再进一步（不同机器不同冷却）就是带回溯的调度问题，工程上用贪心+局部搜索近似」。展示你知道**每个 closed-form 公式背后都有假设边界**。
3. **空转计时不计错**——最后一个框架不满时不补空转到 `n+1`（因为不需要再冷却了）；手推 `["A","A","A","B","B","B"], n=2 → 8` 和 `["A","A","A","B","B","B"], n=3 → 10`，跟面试官对齐计数口径。

### 进阶六连（ interviewer 加菜时的弹药库 ）

1. **异构冷却矩阵**：`cooldown[i][j]` = 任务 i 之后接任务 j 需要的间隔（模型切换代价矩阵）。公式彻底失效，事件模拟 + 状态压缩 DP / 贪心 + 局部搜索；这题退化后就是「带 sequence-dependent setup time 的调度」，车间调度（job-shop）文献一大本营。
2. **多机版（回到昨天的 makespan）**：m 台机器、带冷却的最短完工 = 冷却约束 + List Scheduling 结合；近似比分析是开放问题的简化版，面试话术「约束叠加时近似比不再相乘，要重新论证」。
3. **LC 358 Rearrange String k Distance Apart**：LC 621 的字符串版（任意两个相同字符距离 ≥ k），公式 `(f-1)*k + cnt` 同构；如果要求**不能空转**（必须用别的字符填），就是经典的**可行重排判定**（频次最高 ≤ (N+1)/2）。
4. **无限任务流 + 最小化空转率**（在线版）：任务持续到达、冷却约束永续——这就是**带 setup 时间的服务台排队模型（M/G/1 with setup）**，有空转率下界公式；工程映射 = 模型切换开销 vs 单模型 batch 深度的 trade-off。
5. **优先级反转问题**：高优任务来了但同类任务在冷却 → 等还是打断？映射 = 推理网关的优先级抢占 vs KV cache 保留成本。
6. **概率冷却**：每次执行后有 p 概率需要冷却（散热抖动）→ 期望完成时间 = 确定性骨架 × 修正系数；面试里展示「把确定性模型推广到随机模型」的思维方式即可，不必算出 closed-form。

### 工程映射：推理集群的「冷却」无处不在

| 场景 | 「任务」 | 「冷却 n」 | 对应算法 |
|---|---|---|---|
| 模型切换空窗 | batch | KV/权重换入换出延迟 | 堆模拟 + 模型黏性（减少切换） |
| 令牌桶限速 | 请求 key | 最小间隔 | 公式法直接算周期 |
| 熔断恢复 | 下游服务 | 半开探测间隔（Day 156） | 事件模拟 |
| GPU 散热降频 | 密集 kernel | 降频窗口 | 概率版 |
| 重试退避 | 失败请求 | exponential backoff | 冷冻室按 readyAt 排序 |

**一句话**：LC 621 是「离散排队 + 约束调度」的最小完备模型——公式法教你**闭式解的假设边界**，堆模拟教你**通用工程解法**。

## 二、面试技巧：排队论与容量水位线 —— 「P99 的钱全在队列里」

### 1. Little's Law 深入：L = λW，稳态第一公式

**陈述**：稳态系统里，**在途数量 L = 到达率 λ × 平均驻留时间 W**。与分布无关、与服务规则无关——只要系统稳态、守恒（不丢请求），它就成立。

**三个面试必考的边界条件**（公式本身一秒背出，边界才是分水岭）：

- **稳态**：λ < 有效服务容量。ρ ≥ 1 时队列无限增长，L=λW 里的 W→∞，公式形式上成立但没有有限解。**先判断 ρ 再套公式**。
- **守恒**：适用于封闭子系统。绕过队列直接失败的请求（超时丢弃）不算进 W——**线上你看到的「平均延迟下降」可能只是超时把长尾截掉了**（幸存者偏差，呼应 Day 164 测量先于叙事）。
- **W 是均值**：Little's Law 对 P99 不直接成立。知道 L 和 λ 只能算出平均驻留时间——**这就是为什么容量设计必须再用 M/M/m 或实测分布补一刀尾部分析**。

**速算肌肉记忆**（背这三个）：
- 1000 QPS × 平均 500ms ⇒ **500 个在途请求**（网关并发连接数就是这么估的）
- 峰值 2000 QPS × 2s ⇒ **4000 在途**——均值涨 2 倍、W 涨 4 倍时，在途暴涨 8 倍，连接池/队列容量设计要按峰值乘积算，不是按均值
- 推理集群：每卡 decode 吞吐 40 tok/s、平均生成 800 token ⇒ 单卡同时在编请求 = 40/800 的倒数 = **20 并发**（batch size 20 时吞吐饱和）——「并发数 = 服务率 × 服务时间」是容量规划的第一行心算

### 2. M/M/1 与利用率陷阱：ρ→1 是深渊

单服务台、泊松到达、指数服务（M/M/1）：

$$\rho = \frac{\lambda}{\mu}, \quad W_q = \frac{\rho}{\mu-\lambda} = \frac{1}{\mu}\cdot\frac{\rho}{1-\rho}, \quad W = \frac{1}{\mu-\lambda}$$

**等待时间随 ρ 的爆炸表**（背下来，面试直接报数）：

| ρ | 平均等待（单位：服务时间 1/μ） |
|---|---|
| 0.5 | 1.0× |
| 0.8 | 4.0× |
| 0.9 | 9.0× |
| 0.95 | 19× |
| 0.99 | 99× |

**利用率 92% 接 20% 新流量的标准反击**（昨天 Q3 的完整版）：ρ 从 0.92 到 ~1.1 不是「多排一点队」，而是**稳态被打破**——队列按 (λ-μ)·t 线性增长，延迟随时间发散。**容量红线不是经验值，是 ρ/(1-ρ) 的斜率决定的**：把「可接受等待」翻译成 ρ 上限（如等待 ≤ 4×服务时间 ⟺ ρ ≤ 0.8），红线就有了数学出处。

**今日案例对照**：
- **GTA VI 首日 $3.79B**：λ 在发售分钟级爆炸。Rockstar 的应对（分时段解锁、预载、排队页）= 教科书三件套——**排队（削峰）、扩容（提 μ）、降级（静态页兜底）**。注意顺序：先排队保 SLA，再扩容，最后才降级。任何一个推理网关面对突发流量都同一套。
- **ANT 两天从 $115 回到 $84**：「稳态」在金融系统里只有两天寿命。**容量水位线必须配滑动窗口复测**——昨天的压测结果不是今天的 SLA。

### 3. M/M/m 与「第 m+1 个节点」问题

m 个并行服务台（中央排队，Erlang C）：

$$P_{queue} = \frac{\frac{(m\rho)^m}{m!(1-\rho)}}{\sum_{k=0}^{m-1}\frac{(m\rho)^k}{k!} + \frac{(m\rho)^m}{m!(1-\rho)}}, \quad W_q = \frac{P_{queue}}{m\mu - \lambda}$$

工程上不用背公式，背三个结论：

1. **池化碾压分散**：m 个 M/M/1（每队专用一台）等待 ≫ 1 个 M/M/m（中央队列取头分配）。ρ→1 时差距爆炸。→ **网关中央排队 + 工作窃取**，别让客户端自己选实例（呼应昨天进阶⑥）。
2. **Erlang B/C 是呼叫中心一百年的遗产**：100 年前的电话交换容量表，今天是 GPU 集群容量表——到达率、服务率、台数、目标等待，四者知三求一。面试说「Erlang C」三个字，等于宣布你查过容量表。
3. **dispatcher 假设免费——NGINX/F5 漏洞告诉你它不免费**：今天的安全新闻是最好的反例。m 台 server 前面站着 NGINX/F5，**它就是排队模型外的第 m+1 个节点，单点、有 CVE、要补丁**。容量设计三问加第四问：**「dispatcher 挂了，m 台机器是不是集体失明？」**（主备 NGINX + health check + 降级直连预案 = 标准答案；讽刺的是今天 BIG-IP 的六个 RCE 恰好打在这个角色上。）

### 4. P50-P99 容量线设计：把直觉画成线

**设计流程四步**（面试官问「给集群画容量水位线」按这个答）：

1. **定 SLA 口径**：延迟分布的哪个分位？（内部服务 P95，计费路径 P99，广告竞价 P99.9——**分位数 = 业务的等待容忍度**）
2. **排队论定理论上限**：目标 W_q ≤ x·(1/μ) ⟺ Erlang C 反解最大 ρ ⟺ 换算成 QPS 上限 = 容量线的**理论值**
3. **压测定实测修正**：真实服务时间不是指数分布（LLM decode 近似确定性+重尾 prefill），Erlang C 系统性偏乐观 → 用压测的 (λ, P99) 散点画经验曲线，取排队论曲线的 70-80% 作为**工程红线**（理论给形状，实测给位置）
4. **水位线分档行动**：绿（<70% 正常）/ 黄（70-85% 告警+限新任务）/ 红（>85% 启动扩容，**永远不要让稳态越过红线**，因为 ρ 越接近 1，补偿所需时间也指数变长——扩容决策本身也有 queueing delay）。

**今日案例对照**：
- **Google 砍 TPU 8i 订单 20%**：需求预测错 20%，产能规划全部重画——**容量线的一半工作是需求侧 forecasting**，排队论只管供给侧。被问容量规划，先答「需求怎么估」再答「水位怎么画」。
- **Blue Origin 2029 卫星数据中心**：当地球电力/土地成为 m 的上限，Google 选择扩大「集群」的定义——面试梗可以玩：**「M/M/m 的 m 不够用了怎么办？把 m 打到近地轨道。只是光速 7ms 的往返，让 W 的下限变得很有航天特色。」** 笑点背后是严肃判断：约束转移而不是约束消失。

### 5. 模拟面试速答五连

**Q1：1000 QPS、平均延迟 500ms，系统在途多少？峰值 2000 QPS、P99 延迟 2s 呢？**
→ 稳态 L = λW = 1000×0.5 = **500 个**。峰值：**不要用 P99 套 Little's Law**（它只对均值成立）——峰值在途上界 = λ_peak × W_mean_peak，P99 数据用于定 SLA 是否破线；连接池/队列容量按峰值均值乘积 × 安全系数（1.5-2）设计。追问「P99 为啥不能套」= 因为 L=λW 的 W 是集合平均，P99 是条件分位，混用是统计口径错误（呼应 Week 26 口径纪律）。

**Q2：老板看到监控「集群利用率 92%，认为还能接 20% 流量」，你怎么说服他？**
→ 三件套：①口径三连（SM Active / MFU / goodput，prefill 还是 decode，P50 还是 P99——昨天 Day 169 的三问原样复用）②排队论：M/M/1 下 ρ: 0.8→0.92 让平均等待从 4×变 11.5×（ρ/(1-ρ)），增加 20% 流量 ρ→1.1 直接打破稳态，队列线性发散 ③给方案不说不行：排队削峰（入口限流）+ 扩容排期 + 降级预案，三线并行。**结论：92% 恰恰是「不能接」的证据，不是「还能接」的证据。**

**Q3：网关用中央单队列（M/M/m）还是每实例本地队列 + least-in-flight？**
→ 排队论答案是中央单队列（m 个 M/M/1 等待 ≫ 1 个 M/M/m）。工程折中：中央队列有单点/跨 AZ 延迟/状态成本，所以大规模实践是「**逻辑中央队列 = least-in-flight 近似**」或分层（Day 169 的哈希定会话 + 池间水位平衡）；判断标准一句话：**队列信息共享越完整，越接近 M/M/m 最优；共享有成本时，PoT 拿 90% 效果**。

**Q4：推理集群压测 P99 达标，上线一周 P99 翻倍，哪里查？**
→ 按序排查五连：①到达过程变了？（流量形态从泊松变重尾突发——ANT 式开盘冲击）②服务率变了？（长上下文占比升高 = 服务时间分布右移）③队列漂移：慢实例/热点 key（一致性哈希环倾斜）④依赖服务（reward/judge API）排队反压传导 ⑤指标口径：采样窗口、超时截断、客户端重试放大。**「压测分布 ≠ 生产分布」的第一嫌疑永远是到达过程，不是服务台。**

**Q5（设计题）：给推理集群画容量水位线，十分钟给出可执行方案。**
→ 四步：①澄清 SLA（P99 TTFT ≤ 2s / TPOT ≤ 50ms？分租户还是全局？）②理论上限：单卡吞吐基准 × 卡数 = μ；Erlang C 按 SLA 反解 ρ_max；QPS 红线 = ρ_max × μ ③压测修正：阶梯加压测 (λ, P99) 曲线，取理论值 75% 为工程红线，写入自动扩缩容阈值 ④运营闭环：红线绿黄红三档行动（昨天学的熔断三旋钮复用）、每日复测滑动窗口（ANT 两天 40% 往返 = 市场尚且不稳，你的模型负载更不会稳）、容量评审每月对照需求 forecast（Google TPU 砍单 20% 的教训：forecast 错了，水位线要敢改）。

### 金句

**「ANT 三天从 +34% 回到发行价，是给所有容量工程师上的第一课：均值会漂移，尾部会撒谎，只有分布诚实。Little's Law 说 L=λW——但那是稳态的承诺；当 λ 击穿 μ，队列以 (λ-μ)·t 的速度吞掉你的 SLA，而 ρ=0.92 到 ρ=1.1 之间没有缓冲带，只有深渊。m 台服务器前面那台 NGINX 是第 m+1 个节点，它会超时、会被打补丁、今天还有六个 CVE。容量水位线的全部要义：用 Erlang C 找形状，用压测定位置，用滑动窗口承认昨天≠今天——然后永远不要让稳态越过红线。」**
