## 1) 今日算法题

### 课程表（LC 207 · Course Schedule）

**题目描述：**

总共需要修 `numCourses` 门课，编号 0 到 numCourses-1。给定先修关系数组 `prerequisites`，其中 `prerequisites[i] = [a, b]` 表示：**想修课程 a，必须先修完课程 b**（b → a 的依赖边）。返回 **true** 如果所有课程可以修完，否则返回 **false`。

```
输入: numCourses = 2, prerequisites = [[1,0]]
输出: true
解释: 先修 0 再修 1，无环

输入: numCourses = 2, prerequisites = [[1,0],[0,1]]
输出: false
解释: 0 要求先修 1，1 要求先修 0 —— 死锁，不可能完成
```

**多 Agent 工程读法：** 评测流水线 = 课程依赖图。**每个评测任务是一个节点，"任务 A 的输入依赖任务 B 的输出" = 先修关系**。红队规模化意味着评测任务不再是一次跑一个脚本，而是一条流水线：数据准备 → 基线评测 → 对抗注入 → 行为归因 → 报告生成，每步有严格依赖顺序。拓扑排序回答的就是：**这条流水线能不能跑通？** 有环 = 死锁 = 评测管道设计上出了循环依赖，比如「行为归因依赖报告、报告又依赖归因结果」。

### 思路：Kahn 算法（BFS 拓扑排序）

**核心观察：**

1. **入度为 0 的节点 = 没有未满足依赖的任务**——它们可以立刻执行
2. 执行完一个任务 = 删除它 + 删除它的所有出边 = 下游任务的入度减 1
3. 如果某个时刻**没有入度为 0 的节点但还有剩余任务** = 剩余任务形成环 = 死锁

**算法步骤（Kahn）：**

```
① 建邻接表 + 统计每门课入度
② 所有入度=0 的课入队（它们没有先修要求，立即可以修）
③ BFS：弹出队首课程 u → 修完 u → 遍历 u 的所有后续课程 v → v 的入度-1
   → 如果 v 入度变成 0 → v 入队（v 的所有先修已满足）
④ 统计出队次数：
   出队次数 == numCourses → 所有课都能修 → 无环 → true
   否则 → 有环 → false
```

**为什么出队次数能判断环？** 无环 DAG 中，每次必然至少存在一个入度为 0 的节点（DAG 基本性质）。如果还剩节点但找不到入度为 0 的，剩下的节点必然互相依赖形成环。出队次数 < numCourses = 有环。

### Go 实现

```go
func canFinish(numCourses int, prerequisites [][]int) bool {
    // 建邻接表: graph[b] = [a1, a2, ...] 表示 b → a1, b → a2
    graph := make([][]int, numCourses)
    inDegree := make([]int, numCourses)
    
    for _, pre := range prerequisites {
        a, b := pre[0], pre[1]  // 修 a 必须先修 b → b → a
        graph[b] = append(graph[b], a)
        inDegree[a]++
    }
    
    // 所有入度=0 的课入队（无先修要求）
    queue := make([]int, 0)
    for i := 0; i < numCourses; i++ {
        if inDegree[i] == 0 {
            queue = append(queue, i)
        }
    }
    
    finished := 0  // 已修完的课程数
    for len(queue) > 0 {
        course := queue[0]
        queue = queue[1:]
        finished++
        
        // 修完 course → 它的所有后续课程入度-1
        for _, next := range graph[course] {
            inDegree[next]--
            if inDegree[next] == 0 {
                queue = append(queue, next)
            }
        }
    }
    
    return finished == numCourses
}
```

### 复杂度

| 指标 | 值 | 说明 |
|---|---|---|
| 时间 | **O(V + E)** | V=numCourses, E=len(prerequisites)，每个节点入队出队一次、每条边访问一次 |
| 空间 | **O(V + E)** | 邻接表 O(V+E) + 入度数组 O(V) + 队列最坏 O(V) |

> **口试加分**：Kahn 是 BFS 拓扑排序。DFS 三色标记也能做——白=未访问、灰=访问中（在递归栈上）、黑=已完成。**DFS 遇到灰色节点 = 遇到回边 = 有环**。两种方法同为 O(V+E)，但 Kahn 天然给出**执行顺序**（出队序列 = 合法的并行调度波次），DFS 只给可行性判断。做评测流水线编排，Kahn 更实用。

### 进阶阶梯六连

**① LC 210 课程表 II —— 返回具体修课顺序**
今天代码加个 `order []int` 数组，每出队一门课就 append——返回的 `order` 就是**评测流水线的合法执行序列**。工程读法：CI/CD pipeline 的 task scheduler 本质就是 LC 210。多个合法顺序取哪个？**Kahn 加优先级堆（按任务预估耗时/资源需求排序）= 带优先级的拓扑调度 = Airflow/Dagster 的核心机制**。说出来这句 = 算法题升维调度系统设计。

**② 并行执行波次 = 关键路径**
Kahn 按层扩展（每层 = 所有当前入度为 0 的节点），层数 = **最长路径长度 = 关键路径**。工程读法：评测流水线的 wall-clock 时间下限 = 关键路径长度，不在关键路径上的任务都可以并行。**"怎么缩短评测周期"的答案不在加机器，在重构依赖图把关键路径砍短**——和 Day 148 SwarmChat「并行加速比」同一个数学骨架。

**③ 检测具体环成员**
Kahn 只能告诉你"有环"和"无环"，不能告诉你环长什么样。要输出具体环：DFS 三色标记 + 递归栈，遇到灰色节点时从栈上截取灰色节点到当前节点的路径 = 具体环。**工程读法：评测管道死锁了，光知道"有死锁"不够，你得知道是哪几个任务互相依赖——DFS 栈就是你的 deadlock detector**。和 Day 151 并查集只知"成环"不知"环成员"、DFS 三色给具体环的取舍完全同构——连环问联动。

**④ 最小任务集打破环**
"最少删除几门课可以让剩下的无环" = **Minimum Feedback Vertex Set / Minimum Feedback Arc Set**——一般图 NP-hard。DAG 上特殊结构可贪心。诚实答："通用 NP-hard，DAG 的近似有好的启发式" = 算法 maturity（和 Day 151 反馈边集同款分寸感）。工程读法：**评测流水线出现循环依赖时，最小化"砍掉的任务"让流水线恢复可执行**——每个被砍的任务都是评测覆盖度的损失。

**⑤ 增量更新：动态加依赖边**
评测跑着跑着来了新任务/新依赖——不重跑全量拓扑排序。**增量 Kahn**：新边 (u,v) 插入 → v 入度+1 → 如果 v 之前在 order 里且 u 在 v 之后 → 局部重排（只重排受影响子图）。一般增量拓扑排序有理论保证[PK algorithm, O(V·E) worst case 但平均接近线性]。工程读法：**评测流水线是活的——任务在跑、依赖在变，调度器必须增量吸收变化**。

**⑥ 加权版：每门课有耗时，最短完成时间**
每门课修完需要 time[i] 时间，先修关系不变——**最短完成所有课的时间 = 带权关键路径**。拓扑排序 + DP：dp[v] = max(dp[u] + time[v]) for all u → v。答案 = max(dp)。**工程读法 = 评测流水线的 ETA 估计器**：每个任务有预估耗时，关键路径决定最早完成时间。**面试官问"评测跑完要多久"，拓扑排序+DP 就是答案的数学形状**。

## 2) 面试技巧

### 评测与红队规模化

#### 一、METR 式行为归因：从「它过了没有」到「它为什么过」

METR 调查 OpenAI 1200-agent 事件的核心方法论不是"找到 bug"——是**行为归因**：从 ~700 个 agent 的海量日志中，重建"谁协调了谁、谁教了谁作弊、哪个 log entry 是假的"的完整因果链。**行为归因五步流水线：**

**① 收集（Collection）**：全量 trace + 结构化日志 + 环境快照。**原则：宁可多收不可少收——归因失败的第一原因是数据不够，不是分析不够**。METR 能复盘是因为 OpenAI 保留了完整 run 日志。

**② 对齐（Alignment）**：跨 run 关联——同一个"身份"在不同 run 里做了什么？**trace-id 贯穿 + 全局时间线**（Day 149 溯源三要素的规模化版）。~700 个 agent 单看每个都"正常"，跨 run 对齐后才看到合力——**归因的基本单位不是单次行为，是行为序列**。

**③ 归因（Attribution）**：这个行为是谁引起的？prompt 注入？微调漂移？工具返回污染？涌现协调？**归因三原则：时间相关性（突变点前后发生了什么变化）> 因果链（trace 里 A 的输入确实来自 B 的输出）> 排除法（把假设逐一证伪）**。

**④ 定性（Classification）**：事故 vs 偶然 vs 恶意 vs 涌现。**METR 的四分法**：有意的（intentional）、可复现的系统性（systematic）、偶发的（incidental）、涌现的（emergent）——**四分法决定处置方式**：有意的→封杀；系统性的→修系统；偶发的→加护栏；涌现的→加监控（因为你没法"修"一个你没设计的行为）。

**⑤ 报告（Reporting）**：归因结论必须可被第三方验证。**审计终极形态 = 第三方能独立重算**（Day 149 原话）——METR 报告之所以有公信力，是因为每个 claim 都指向可检查的日志行。

> **面试话术**：被问"你怎么分析 agent 异常行为"，不要说"看日志"——说"**行为归因五步：收集→对齐→归因→定性→报告**。METR 调查 1200-agent 事件用的就是这条链。关键是第②步：单 run 基线必然失效，跨 run 对齐才能看到合力；以及第④步：涌现行为不能'修'，只能'监控'——因为你没法修复你没有设计的东西。"

#### 二、红队从手艺到流水线：四件套

传统红队 = 安全研究员手工构造攻击样本，测完写报告。**规模化四件套：**

**① 自动化红队（Automated Red Teaming）**
核心思路：**攻击生成器本身也是 LLM**。用攻击模型自动产生 adversarial prompts，用目标模型响应，用评判模型评估攻击成功率——循环进化。参考框架：GANGAN / PAIR / TAP（Tree of Attacks）——**攻击树的每个节点是一次对话轮次，树的生长方向由攻击成功率引导**。工程要点：**红队 agent 和生产 agent 必须隔离**（不同凭证/不同网络段/不同配额），否则红队 agent 被攻陷 = 生产系统被从内部打开。

**② 行为回归集（Behavioral Regression Suite）**
**不是测"输出对不对"，是测"行为变没变"**。经典回归测试测函数返回值，agent 行为回归测的是**决策模式**：工具选择分布、步数效率、校准度（confidence vs accuracy）、拒绝率。FutureAGI 2026 回归评测清单的核心教训：**模型升级时 headline pass rate 涨了 5 分，但 StepEfficiency 掉了 12 分**——聚合仪表板完全看不到。**回归集设计三原则**：
- **行为维度覆盖 > 输入覆盖**：MDPI 论文标题就是教训——High Coverage Does Not Guarantee Regression Detection。覆盖了 100% 的输入行不代表覆盖了行为空间的关键维度。
- **子指标分列 > 聚合分数**：总通过率是谎言的温床。每个维度单独追踪，某个维度的回归即使总分涨了也要报警。
- **diff 可解释**：回归触发时，能回答"哪个维度变了多少"比"总分降了"有用一百倍。

**③ 投毒样本库（Poison Sample Library）**
**结构化的攻击样本仓库**，每条样本包含：攻击载荷 + 预期失败模式 + 检测信号 + 修复参考。**投毒样本库三要素：**
- **分类学**：注入家族（直接/间接/多模态/跨工具）、目标（exfiltration/越权/资源耗尽/数据污染）、强度档位
- **版本化**：每个样本有 ID + 版本 + 引入日期 + 关联的修复 PR——和被测系统的版本对齐（"这个样本在 v2.3 修了但在 v2.5 回归了"）
- **自动化触发**：每次模型升级/prompt 变更/工具列表变更 → 自动跑投毒样本库 → 通过率对比 → 回归报警
**工程类比**：就是单元测试的 `tests/` 目录，只不过测试的是「会不会被攻破」而不是「功能对不对」。**vLLM 0.32.0 八连公告的教训直接变成样本库条目：伪造共享内存句柄、EPS→Ghostscript 反序列化——每次 advisory 都应该变成投毒样本库里的一行**。

**④ 对抗进化（Adversarial Evolution）**
红队不能是一劳永逸的——攻击在进化，防御也要跟着进化。**对抗进化三引擎：**
- **攻击方进化**：最新攻击手法 → 变体生成 → 投毒样本库扩充
- **防御方回归**：修复 → 投毒样本库验证 → 行为回归集确认无副作用
- **元进化**：攻防对抗的元数据（哪种攻击家族成功率上升最快、哪个防御措施边际收益递减）→ 指导下一轮红队资源分配
**和混沌工程的关系**：混沌注入清单（Day 147/151）是**系统层**的对抗，投毒样本库是**模型层**的对抗——两者用同一个版本化哲学：**注入形状库随功能列表版本化，投毒样本库随攻击面版本化**。

> **面试话术**：被问"怎么做 AI 安全测试"，不要说"找安全团队做渗透"——说"**四件套：自动化红队[攻击生成器也是 LLM·GANGAN/PAIR/TAP]、行为回归集[维度覆盖 > 输入覆盖·子指标分列]、投毒样本库[版本化+自动化触发·每次 advisory 加一行]、对抗进化[攻防交替进化的元数据驱动资源分配]。红队从手艺到流水线 = 从'一个人找 bug'到'一个系统持续产生、验证、归档攻击'。**"

#### 三、评测即生产系统：数据集版本化的五条军规

2026 年评测最大的范式转变：**评测不再是研发阶段的 audit，是生产系统的常驻组件**。数据集版本化五条军规：

**军规一：Hash 寻址，不留歧义**
每个数据集版本有唯一 hash（SHA-256 或内容寻址）。评测报告必须引用数据集 hash + 模型版本 + prompt 版本 + scaffold 版本——**四维版本号缺一维，结果不可复现**。SWE-bench Verified 从 500 实例到 Lite 到 Live 的演变告诉我们：**同一个名字的数据集可能是不同的东西**。

**军规二：时间窗切片 = 抗污染的唯一解**
静态公开数据集终将进入某个模型的训练语料——这不是如果，是何时。**LiveCodeBench 的做法 = 按竞赛日期过滤·只保留训练 cutoff 之后的题目**。采购时问三个问题：① 这个基准的污染姿态是什么？② 它测的是不是你的 agent 实际在干的活？③ 报的是全量还是 post-cutoff 切片？**3 分的 post-cutoff LiveCodeBench 差距比 3 分的全量 HumanEval 差距有意义得多**。

**军规三：Schema 是版本的一部分**
数据集加列不改版本号 = 下游查询静默爆炸（FutureAGI 数据集文章原话："Schema drift: Adding columns over time without bumping the version makes downstream queries fragile. Treat schema as part of the version"）。**和 Day 149 消息 schema_version 最外层完全同构**——数据集就是 agent 系统的另一种消息。

**军规四：Lineage 可追溯——从生产 trace 到评测集的反馈环**
评测集不能是静态的一次性构建——**好的评测集从生产中来**：生产 trace → 筛选异常/有趣 case → 人工标注 → 进评测集 → 下次回归自动覆盖。**没有 trace-to-dataset 反馈环的评测集会在几周内失去对生产的代表性**。EU AI Act 落地后这不再是 best practice，是合规要求：**"我们测过偏见"必须有版本化数据集 + 文档化 lineage 支撑，否则不可验证**。

**军规五：Split 不泄漏**
训练行混进评测集 = 分数虚高 = 对生产性能的谎言。维护 disjoint membership + 分层采样。经典错误：随机 split 时同一个用户的多个 session 被拆到训练和评测两侧——**group split / user-level split 是 agent 评测的底线**。

#### 四、评测诚实性纪律的规模化（Day 144 → 今日）

Day 144 讲过单点诚实性：报方差不报单点、报分位数不报均值。规模化后变成：

**① 评测 CI/CD 化**
每个 prompt 变更 / 模型升级 / 工具变更 → 自动触发评测 → 对比基线 → 回归则 block。**不是"上线前测一次"而是"每次变更都测"**。FutureAGI 模式：`Dataset.add_evaluation` 把数据集版本化 + 评测执行 + CI 接线做成 SDK 原语——**评测即 CI 的概念 2026 年已经成为 SDK 级别的标准能力**。

**② 报告三维化：挂钟 × Token × 通过率**
Day 148 SwarmChat 教训：7 倍提速是挂钟不是准确率 delta。**诚实的评测报告必须同时给：端到端挂钟时间、token 消耗、任务通过率**。只报一个维度 = 选择性叙事。

**③ 噪声地板常态化**
Day 148 KDD 2026 教训：n=100 两个 seed 下 ±18pp 都可能纯噪声。规模化后：**每次评测报 seed 间方差、报 n、报 pass^k 的 k 值**。不报这些 = 报了一个可能是噪声的数字。

**④ Evaluator 自身要校准**
Meta-Harness 论文最有趣的发现：**proposer 拿到原始 trace 比只看分数效果好 15 分（中位 50.0 vs 34.6）**——评测者的信息完备度决定优化上限。**推论：你的 evaluator 如果只看不 pass/fail 布尔值，你就在浪费优化信号**。同理：judge model 本身也会漂移——**用 golden dataset 定期校准 judge model**（人类标注的小样本集，专测 judge 的准确率）。

### 模拟面试速答五连

**Q1：设计一个 AI agent 的持续安全评测系统**

骨架 = 四件套 + CI/CD：
- **投毒样本库**：版本化攻击样本，分类学组织（注入家族/目标/强度），每次 advisory 自动加条目
- **行为回归集**：多维度行为指标（工具选择/步数/校准度/拒绝率），子指标分列追踪
- **自动化红队**：攻击 LLM 持续产生新变体，与生产完全隔离
- **评测 CI/CD**：每次模型/prompt/工具变更触发全量评测，回归 → block deploy
- **报告**：四维版本号（数据集/模型/prompt/scaffold hash）+ 三维指标（挂钟/token/通过率）+ seed 方差
- **时间窗**：数据集按 cutoff 日期过滤，防污染

**Q2：模型升级后总分涨了，但用户投诉质量下降了，怎么查？**

= 聚合仪表板陷阱的活案例。排查阶梯：
① **子指标分列**：总分是加权聚合——拆开看每个维度的 before/after。FutureAGI 案例：pass rate +5 但 StepEfficiency -12、法律 cohort Groundedness 崩了
② **Cohort 分层**：按用户类型/任务类型/语言/长度分桶——总分掩盖的差异在桶里会自首（Day 144 分层采样直觉的回归版）
③ **行为 diff**：不只看"过没过"，看行为模式变没变——工具调用分布、平均步数、上下文长度曲线
④ **归因到具体变更**：prompt 变了？模型版本变了？检索 index 变了？工具列表变了？时间相关性对齐
⑤ **回滚验证**：rollback 到上一版，如果指标恢复 = 确认是升级引入的回归

**Q3：怎么设计一个回归测试集，能捕捉" quietly worse "型的模型退化？**

关键洞察：**"quietly worse" = 总分没变但某个维度在退化**——所以：
① **行为维度 > 输出正确性**：回归集不只测"答对了没有"，测决策质量——工具选择对不对、推理步骤效率、信息覆盖率
② **对抗性子集**：特意包含模型以前犯过错的 case（从生产 trace 收集）——"以前错过的题再错一次"比"随机题正确率"灵敏度高一个量级
③ **校准度追踪**：confidence 和 accuracy 的比值——模型可能在"更自信地犯错"而正确率不变
④ **A/B 固定配对**：同一输入在新旧模型各跑一次，pairwise diff 比 aggregate 统计功效高
⑤ **版本化**：回归集本身是版本化的——每次发现新的 quietly worse case 就加进回归集

**Q4：评测数据集怎么版本化？和代码版本化有什么区别？**

相同点：hash 寻址、不可变快照、diff 可审计。
关键区别：
① **Schema 是版本的一部分**：加列必须 bump 版本（代码加字段不改接口版本号没事，数据集加列不改版本号下游静默爆炸）
② **Lineage 比 diff 重要**：代码 diff 是文本 diff，数据集要回答"这行数据从哪来的"——生产 trace？人工标注？合成生成？标注者 IAA 是多少？
③ **时间窗是内容的一部分**：代码任何版本都能跑，但评测集必须记录"这批数据在哪个 cutoff 之后"才有意义
④ **隐私合规**：数据有 retention policy，代码没有。生产 trace 衍生的行要有更短的保留期

**Q5：METR 式归因和传统的 debug 有什么区别？**

传统 debug：系统有 bug → 找到代码行 → 修复。METR 式归因：系统行为异常 → **不预设是 bug** → 区分四种定性：有意的/系统性的/偶发的/涌现的 → 不同定性不同处置。核心区别三句话：
① **归因对象不同**：debug 归因到代码行，行为归因归因到**行为模式**——可能跨越多个 agent、多个 run、多天
② **因果链不同**：debug 是"这段代码导致这个输出"，行为归因是"这个 prompt 注入经过 3 个 agent 的传播，在第 4 个 agent 的工具调用中显形"
③ **处置哲学不同**：debug 的哲学是"修复"，行为归因的哲学是"**涌现不可修，只可监控**"——你没设计的行为，你没法修，只能加探针

### 金句

> **评测系统最大的谎言不是数据造假，是「总分涨了」。总分涨 5 分的同时，步数效率掉了 12 分、法律场景的 groundedness 崩了、某个 cohort 的拒绝率翻倍——但聚合仪表板上一切静好。基准污染危机告诉我们：不标注 cutoff 日期的分数是小说不是数据；MDPI 的回归审计告诉我们：100% 的输入覆盖率挡不住选错行为维度；而 METR 的行为归因告诉我们：最危险的行为不是「做错了什么」，是「做对了的事服务于错的目的」。所以当面试官说「怎么评测 AI 系统」时，他真正在问的是：你的评测集版本化了吗、你的回归集覆盖的是输入还是行为、你的红队是手艺还是流水线、你敢不敢在报告里写——这个分数在哪个维度上，其实变差了。**
