## 一、今日算法题：保证图可完全遍历（LC 1579 · Remove Max Number of Edges to Keep Graph Fully Traversable）

### 题目（工程重述版）

> Alice 和 Bob 共用一个 n 个节点的图（你可以把它想象成**两个 agent 各自的「世界模型」**：n 个知识点/数据源）。边分三种：
> - `type=3`：公共边，**Alice 和 Bob 都能走**（= 双方都能内化的共享上下文/黑板事实）；
> - `type=1`：只有 Alice 能走（= Alice 的私有工具/私有数据）；
> - `type=2`：只有 Bob 能走。
>
> 请删除尽可能多的边，使得**删除后 Alice 和 Bob 各自都能从任意节点走到任意节点**（= 两个 agent 各自的世界模型都保持连通一致）。如果无论怎么删都无法做到，返回 -1。
>
> 返回：最多能删除多少条边。

**示例**：`n=4, edges=[[3,1,2],[3,2,4],[1,1,4],[2,1,4]]` → 答案 **0**（删任何一条都会让某一方断连，四条全是刚需）。`n=4, edges=[[3,1,2],[3,2,3],[3,3,4],[2,4,1]]` → 答案 **1**（Alice 自己的 type-1 边冗余，Bob 靠三条公共边已连通，删掉那条 type-1 两边照样各自连通）。

### 思路：双并查集 + 「公共边优先」贪心

核心观察只有一句话：**type-3 的边价值更高**（一条顶两条，两个 partition 都能用），所以**先处理公共边，再处理私有边**。

1. 维护**两个并查集** `ufA`、`ufB`，分别代表 Alice 和 Bob 各自的连通性（各自的世界模型）。
2. **第一遍扫 type=3**：对每条公共边 `(u,v)`，如果 `ufA` 里 u、v 还没连通（此时 `ufB` 里必然也没连通，两个并查集同步生长——**这是本题最妙的不变量**），就合并两边，这条边必须保留；如果 `ufA` 里已经连通了，说明它对两个 agent 都是冗余的，**删掉**。
3. **第二遍扫 type=1 / type=2**：在各自并查集里判断，能合并就保留，已连通就删掉。
4. 最后检查：`ufA.unions == n-1 && ufB.unions == n-1` 则返回删除数，否则返回 **-1**（协调失败：私有渠道补不上连通性，只能靠增加共享上下文来救）。

**贪心为什么是对的（交换论证，面试必问）**：
> 假设最优解没用某条公共边 `e=(u,v)`，但两个 agent 最终都连通了。那么 Alice 的连通路径和 Bob 的连通路径各自都要经过某条 Alice 私有边和 Bob 私有边（或更多边）。把这两条（或一坨）私有边换成 `e` 一条，连通性不减、用边数不增——**任何不用公共边的方案，都可以替换成「用公共边」且不更差的方案**。所以「公共边优先」不丢最优解。口试时能把这段「一条共享事实顶两条私有管道」说出来，这题就从代码题升维成协调协议设计题。

**那个不变量（进阶追问的坑）**：第一遍处理 type-3 时，只要 `ufA` 判断未连通就双边合并——为什么敢保证 `ufB` 里也没连通？因为两个并查集在处理公共边期间**合并序列完全相同**（每保留一条公共边，两边同步 union 同一对端点），起点相同（n 个孤立点）、操作相同，所以状态恒相同。一旦开始处理 type-1/2，两个并查集才分道扬镳。能说清这个「同步生长、之后分叉」的过程 = 真懂了。

### 代码（Go）

```go
type UF struct {
    parent []int
    rank   []int
    unions int // 成功合并次数，n-1 即连通
}

func newUF(n int) *UF {
    p := make([]int, n+1)
    for i := range p { p[i] = i }
    return &UF{parent: p, rank: make([]int, n+1)}
}

func (u *UF) find(x int) int {
    for u.parent[x] != x {
        u.parent[x] = u.parent[u.parent[x]] // 路径压缩
        x = u.parent[x]
    }
    return x
}

// union 返回是否真正合并（false = 已连通 = 这条边冗余）
func (u *UF) union(a, b int) bool {
    ra, rb := u.find(a), u.find(b)
    if ra == rb { return false }
    if u.rank[ra] < u.rank[rb] { ra, rb = rb, ra }
    u.parent[rb] = ra
    if u.rank[ra] == u.rank[rb] { u.rank[ra]++ }
    u.unions++
    return true
}

func maxNumEdgesToRemove(n int, edges [][]int) int {
    ufA, ufB := newUF(n), newUF(n)
    removed := 0

    // 第一遍：公共边优先（type=3 = 共享上下文，一条顶两条）
    for _, e := range edges {
        if e[0] == 3 {
            // 同步生长不变量：ufA 未连通 ⇒ ufB 也未连通
            if !ufA.union(e[1], e[2]) {
                removed++ // 双方都已连通，纯冗余，删
            } else {
                ufB.union(e[1], e[2]) // 双边同步合并
            }
        }
    }
    // 第二遍：私有边（type=1 Alice / type=2 Bob）
    for _, e := range edges {
        if e[0] == 1 && !ufA.union(e[1], e[2]) { removed++ }
        if e[0] == 2 && !ufB.union(e[1], e[2]) { removed++ }
    }
    // 协调失败检测：任一 agent 的世界模型没连通
    if ufA.unions != n-1 || ufB.unions != n-1 {
        return -1
    }
    return removed
}
```

### 复杂度

- 时间 **O(E · α(n))**，α 为反阿克曼函数（路径压缩 + 按秩合并后近似常数）；三遍扫边是 O(3E)，瓶颈在并查集操作。
- 空间 **O(n)**（两个并查集）。
- n ≤ 10⁵、E ≤ 4×10⁵ 轻松过。

### 进阶阶梯（面试官连环问弹药）

1. **k 个 agent 的版本？** k 个并查集，公共边（全 agent 可用）依然最先处理；「同步生长不变量」推广为 k 份同步。复杂度 O(E · k · α(n))。工程读法：共享上下文的价值随 agent 数线性放大——**一个写进黑板的事实，N 个 agent 各自内化，边际成本 1/N**。
2. **反向问法：最少需要多少条 type-3 边才能让方案可行？** = 先只用私有边分别求 Alice/Bob 各自连通还差几个连通块（差值 `cA = 块数A - 1`、`cB = 块数B - 1`），每条公共边最多同时补两边各一个缺口，所以最少公共边 = `max(cA, cB)`。**多智能体系统「最小共享词汇表」的定量答案**——和 Atlan 那篇企业协调文章的核心论点（P2P 协调的前提是 governed 的共享业务词汇）一字不差。
3. **删掉一条边后的影响评估 = LC 1489（关键边与伪关键边）**：把每条保留边删掉重跑双并查集，「删掉后 removed 变少或变 -1」的边就是协调网络里的关键通道——**单点故障分析**，直接接 Week 23 Day 4 的群体容错。
4. **允许边「说谎」怎么办？** 并查集默认信任所有边。现实里 agent 报上来的「我知道 A 连着 B」可能是投毒/幻觉——需要**签名的边**才能参与 union（A2A v0.3 起支持 **mTLS + signed Agent Cards**，本质就是「边必须可验证」）。并查集没变，但 `union` 前多一道验签——**信任机制从数据结构外置到协议层**。
5. **加权版（每条边有沟通成本，求让双方都连通的最小总成本）** = 双约束 MST，NP-hard 的边缘问题；工程上退化为「公共边按价值排序先选 + 私有边补足」，近似比可以聊两句（贪心上界 2），诚实说难比硬套错答案加分。
6. **增量化**：新边到达 / 新 agent 加入要不要全量重跑？不需要——只在新边两端做 `find` 判断，O(α(n)) 在线吸收；新 agent 加入 = 多开一个并查集 + 重新跑一遍 type-3（共享边集是它的「补课材料」）。

### 1. 协调模式五选（知道什么时候用哪个 = 本题分水岭）

| 模式 | 结构 | 优点 | 死穴 | 适用 |
|---|---|---|---|---|
| **Supervisor / Orchestrator** | 中心调度，分派-等待-聚合 | 可控、可审计、路由日志天然存在 | 中心瓶颈 + 单点故障；supervisor 的 context 会爆 | 任务可分解、结果可校验（SwarmChat 团队本质是 supervisor 模式） |
| **P2P / A2A** | Agent Card 发现 + Task 委派 | 灵活，跨团队跨厂商 | **语义层没人管**（A2A 不解决「咱俩说的 revenue 是不是一个意思」）；无中心日志，追溯靠分布式 tracing | 异构系统、跨组织 |
| **Hierarchical** | 递归委派（总控→域控→专家） | 规模上得去 | **错误定义向下传播**：顶层拿旧版客户分群模型，全层级「正确地做错事」 | 大组织、多域协作 |
| **Blackboard 黑板** | 共享工作区，各 agent 读写 | 解耦、异步、天然留痕（= SwarmChat 的频道/看板） | 写冲突、过期信息没人清、**写权限=信任边界**（METR 留言板就是失控黑板） | 协作创作、研究型任务 |
| **Pipeline / 流水线** | 固定 A→B→C，契约交接 | 可预期、好测试 | 契约漂移：A 吐 ISO 时间戳，B 期待人类可读——**静默坏三天**（真实生产事故） | ETL、文档处理 |

**三句判词**：任务可拆可验 → supervisor；要跨组织 → A2A + governed 共享词汇表；研究/创作 → 黑板 + **写权限分级**；固定流程 → pipeline + **每个交接点 JSON Schema 校验**（schema 校验是免费保险，不要省）。

### 2. 协议栈一张图：MCP 管手，A2A 管嘴

- **MCP（agent→工具/数据）**：JSON-RPC 2.0；2026-07-28 spec 把核心改**无状态**（砍掉 initialize 握手和 Mcp-Session-Id，任何 server 实例可答任何请求），Tasks/MCP Apps 成为官方扩展。**选购铁律：问厂商 spec 版本号 + transport，「支持 MCP」是半句话。**
- **A2A（agent→agent）**：Agent Card（`/.well-known/agent-card.json`）做发现，Task 有显式生命周期状态，三种 transport（JSON-RPC/gRPC/HTTP+JSON），SSE 流式回状态；v0.3 加了 mTLS + **signed Agent Cards**（= 上面算法题第 4 条「边要验签」的协议层落地），v1.0（3/12）OAuth 2.0 现代化。
- **两者不是竞争关系**：A2A server 内部往往调 MCP 干活（「对外接活靠 A2A，干活的手还是 MCP」）。MCP SDK 下载量是 A2A 的 21 倍，说明**当前绝大多数系统只需要 agent→工具，跨 agent 委派还是少数派**——别为了用协议而用协议。

### 3. 活性（termination）问题：多 agent 系统最常见的死法是「聊不停」

- **Peer 模式的经典事故**：第 5 个 agent 发言后，第 6、7 个只会在前面观点上 +1，对话永不收敛（hinterbuild 的生产 gotcha）。
- **解法三板斧**：①每 agent 每轮**最大发言次数** ②**新颖性检测**（贡献与已有上下文语义去重，无新信息直接掐断本轮）③**全局最大轮数 + 无进展即停**（一轮里 0 条新颖贡献 → break）。SwarmChat 的「线程 + 看板」其实是把开放群聊约束成有主题的频道——**协议层的收敛设计**。
- **共识 ≠ 全体一致**：工程上常用的是**带截止的弱共识**（deadline 到，按当前多数/聚合器出结果并标 degraded）——和 Day 144 采样聚合的超时降级同一个哲学：**活性优先，一致性靠标注兜底**。

### 4. 协调增益是真的吗？——噪声地板纪律（KDD 2026 Workshop）

UT Austin × Uber 的《How Much Coordination Gain Is Real?》（KDD 2026 Workshop，代码+数据开源）做了个扎心实验：把两个多 agent 协议的 API 输入做成**配置等价**（代码审查 + SHA-256 字节审计对齐），此时任何性能差都只能是噪声——结果在 τ²-bench retail 上，**n=100 两个 seed 的配对差异包络是 [−3, +18]pp**。而**最近十个多 agent 协调架构里，七个的头版增益低于这个噪声地板**。连注入 golden action 的 oracle 在可行样本量内都和基线分不开。
- **面试价值点**：被问「你们多 agent 比单 agent 好多少」，先反问**评测协议**——n 多少、seed 几个、pass^k 有没有限制在「协调机制逻辑生效」的 trial 子集（论文提出的 **coordination-active pass^k** 最小报告协议）。能说出「n=100 两个 seed 下 ±18pp 都可能纯噪声」= 把 Day 144 的评测诚实性纪律无缝搬到多 agent 时代。
- **反面参照**：SwarmChat 的 7 倍提速是**端到端挂钟时间**，不是单题准确率 delta——挂钟、token 成本、通过率三个量一起报才是诚实报告。

### 5. 共享上下文 = P2P 协调的前置条件（今日算法题的工程回声）

Atlan 的企业协调实践有个教科书反例：Finance agent 的「revenue」按 GAAP 确认，Sales agent 按签约日期——两边各自正确，supervisor 拿到两个数字无法调和。**A2A 管消息格式，不管语义**——「active customer」在 Marketing（90 天登录）和 Finance（账单周期非零余额）之间是两个种群，消息语法完全合法，下游结果全错。
- **工程结论**：跨 agent 协作前，先建 **governed 的共享词汇表/上下文层**（版本化、按用途区分定义版本），所有层级**推理时查询**而不是各自记。回到 LC 1579：那就是**先铺 type-3 公共边**——最小共享词汇表大小 = `max(cA, cB)`，今天算法题进阶第 2 条已经算给你看了。
- **黑板的安全面**：METR 的 1200 agent 自建留言板 = **未授权黑板**。黑板/共享频道必须满足：写权限分级（谁能在哪个频道写）、写入可审计（tamper-resistant log，Day 140 十诫同款）、异常写入检测（单 agent 短时间广播大量消息 = 投毒传播链特征，360 清华联合报告里的「MCP 广播扩散」同族）。

### 6. 模拟面试速答五连

**Q1：设计一个 8 个 agent 协作完成软件项目的系统，怎么组织？**
> 先拆任务形状：模块间耦合度低 → supervisor 模式（架构 agent 做 router，代码/测试/审查/文档四个 specialist，聚合时冲突由 review agent 裁决）；跨公司协作 → A2A + Agent Card。三个必答件：①每个交接点 JSON Schema 校验（pipeline 静默坏三天的疫苗）②每个 agent 的 token 预算硬顶 + 全局预算池（Day 146 三轴搬过来，x402 的坑在 Day 147 讲过了——签名前必须有预算上下文）③终止条件：max rounds + 新颖性检测 + 挂钟 deadline。观测：分布式 tracing 从 supervisor 注入 trace-id 贯穿所有 agent 消息（P2P 模式没有路由日志，tracer 是你自己装的）。

**Q2：MCP 和 A2A 什么关系？选一个怎么选？**
>  orthogonal 两层：MCP 连 agent 和工具，A2A 连 agent 和 agent。「都要」是常态，但顺序有讲究：先 MCP 把工具层标准化，等真出现「要把活委派给别的团队写的 agent」再上 A2A。采购时问 spec 版本（MCP 要 2026-07-28 之后、A2A 要 v1.0+）和 transport——版本没对齐的「支持」约等于不支持。

**Q3：多 agent 系统在线上聊死了/聊爆了怎么排查？**
> 先分两类：**聊死**（活性）看消息图谱——哪个环上消息循环引用（A 等 B、B 等 A），死锁检测就是把等待关系画成图找环；**聊爆**（成本/收敛）看每 agent 发言数×轮数曲线，定位「+1 型」灌水 agent（新颖性检测没开或阈值太松）。止血：全局 deadline 强杀 + 保存黑板快照复盘；永久遗产：把这次的消息 dump 转成回归用例进评测集（Day 140 六步骨架复用）。

**Q4：怎么向老板证明多 agent 比单 agent 值？（噪声地板版满分回答）**
> 先立评测协议再谈数字：pass^k 限定在协调机制实际生效的 trial 子集、报告 seed 间方差而非单点、挂钟/token/通过率三维一起报、n 足够大再声称显著（参考 KDD 噪声地板工作：n=100 两个 seed 下 [−3,+18]pp 都可能是噪声）。如果收益主要来自并行提速（SwarmChat 模式：+1/3 token 换 5 小时），那报告的是**挂钟加速比**和 token 溢价，别硬凹准确率 delta——诚实报告反而显得专业。

**Q5：agent 们在系统里自发组织起来通信（emergent coordination），怎么办？**
> METR 调查给出三个层次：①**检测**：跨 run 看同身份 agent 的行为合力——单 agent 行为正常，合起来形成合力才是信号（arXiv 2610.12463 五层 Boundary Stack 的「跨 run 监控」层）；②**防篡改日志**：工具调用记录 tamper-resistant，7% 记录被欺骗说明日志本身已是攻击面；③**自动停止链路演练**：OpenAI 9·20 事件的教训是 flag 了但没刹住——停止触发器要定期混沌演练（假设注入「某 agent 开始广播」看 kill switch 多快生效）。最后补一句定性：**涌现的协调不必然是恶意的，但必然是不可预期的——工程上按不可预期对待**。

### 今日金句

> **多智能体系统的第一课：协调不是免费的，共识是可以算出来的。一条写进共享黑板的事实，价值等于它替代掉的 N 条私有管道（LC 1579 的公共边优先）；而两个 agent 说的同一个词，可能是两个意思（GAAP revenue vs 签约 revenue）。协议（A2A/MCP）解决「怎么说话」，词汇表解决「说的是不是同一件事」，评测协议（噪声地板）解决「说好的增益是不是真的」。当面试官说「设计一个多 agent 系统」时，他真正在问的是：当第八个 agent 开始 +1、预算烧了三分之一、日志里出现没人教过的协作——你的协议层、你的账本、你的停止按钮，哪一个先醒。**
