## 一、今日算法题：任务联盟的最小通信成本（LC 1584 · Min Cost to Connect All Points · Prim 堆优化 MST）

### 题目（工程重述版）

> 一个任务需要 **n 个 agent** 协作完成，编号 0..n-1，agent i 的位置是 `points[i] = [xi, yi]`。为了让 agent 们互通中间结果（共享上下文、传子任务产出），可以在任意两个 agent 之间建一条**直连通信管道**，管道成本 = 两个 agent 的**曼哈顿距离** `|xi-xj| + |yi-yj|`（直观含义：每同步一轮中间结果要传多少 token，距离越远 context 越长）。
>
> 任务要求：**所有 agent 必须连通**（任意两人之间能互传消息，可以经由中转）。你可以建任意条管道。返回：**让所有 agent 连通的最小总通信成本**。

**示例**：`points=[[0,0],[2,2],[3,10],[5,2],[7,0]]` → 答案 **20**。最优连接：`0-1` 成本 4、`1-4` 成本 7、`1-3` 成本 3、`2-3` 成本 8，总 4+7+3+8=20。注意 (0,0)-(7,0) 直连只要 7，但把 2 号拉进联盟必须走它唯一便宜的出边 2-3（成本 8）——**MST 不是肉眼找最短边，是让「离联盟最近的人」逐个入伙**。

### 思路：Prim —— 已入伙联盟 vs 圈外候选，每步贪心最近的人

核心不变量一句话：**维护「已连通联盟」S，每次从圈外选一条连接到 S 的最短边，把新 agent 拉入伙；n-1 次后所有人的账记完。**

为什么贪心是对的（cut property，面试必讲）：把已入伙集合 S 看成一个割。设本步选中的最小边 e=(u∈S, v∉S)。反设最优解 T* 不含 e，则 T* 中 v 连回 S 必走另一条跨割边 e'（e' ≥ e）。把 e' 换成 e，v 侧连通性不变、总成本不增——所以存在一棵包含 e 的最优解。**「每一步的局部贪心都被某个全局最优解包含」= Prim/Kruskal 的共同心脏。**

实现（堆优化）：小顶堆存 `(cost, agent)`；`minDist[v]` = v 到当前联盟的最短已知边。每次弹出堆顶（若该 agent 已入伙则跳过——lazy deletion），入伙、累加成本，然后**用新入伙的 u 松弛所有圈外 v**（`minDist[v] = min(minDist[v], manhattan(u,v))`，变小了就压堆）。最多 n-1 次入伙 + 每条边最多入堆一次（O(n²) 条隐式边），堆大小 O(n²)。

**为什么不用朴素数组版？** 稠密图（任意两点都有边，E=n²）时数组版 Prim 是 O(n²)，常数更小；但堆版写起来短、语义清晰，且对「边稀疏/边流式到达」的推广友好——本题 E 是隐式 n²，两版同阶 O(n² log n)。工程上：邻接表 + 堆 = 教科书默认答案。

**和 Day 149 的呼应**：图连通问题的两兄弟——Day 148/149 用并查集判「连没连通」，今天算「连起来最少花多少」。**判定（connected components）是 0/1 问题，生成树（MST）是优化问题**，面试官连环问时这两把刀要一起出鞘。

### 代码（Go）

```go
func minCostConnectPoints(points [][]int) int {
    n := len(points)
    inMST := make([]bool, n)
    minDist := make([]int, n) // minDist[v] = v 到「已入伙联盟」的最短管道
    for i := 1; i < n; i++ {
        minDist[i] = 1 << 30 // 初始联盟只有 0 号，先填无穷
    }
    // 堆元素 [cost, agent]；Go 用 sort.IntSlice 语义自定义小顶堆
    h := &hp{{0, 0}}
    total, added := 0, 0
    for h.Len() > 0 && added < n {
        cur := heap.Pop(h).(pair)
        v := cur.y
        if inMST[v] {
            continue // lazy deletion：旧堆顶已被更好的入伙路径取代
        }
        inMST[v] = true
        total += cur.x
        added++
        for w := 0; w < n; w++ { // 用新入伙者松弛所有圈外 agent
            if inMST[w] {
                continue
            }
            d := abs(points[v][0]-points[w][0]) + abs(points[v][1]-points[w][1])
            if d < minDist[w] {
                minDist[w] = d
                heap.Push(h, pair{d, w})
            }
        }
    }
    return total // added<n 即图不连通；本题完全图恒连通
}

type pair struct{ x, y int }
type hp []pair
func (h hp) Len() int            { return len(h) }
func (h hp) Less(i, j int) bool  { return h[i].x < h[j].x }
func (h hp) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *hp) Push(v interface{})  { *h = append(*h, v.(pair)) }
func (h *hp) Pop() interface{}   { old := *h; top := old[len(old)-1]; *h = old[:len(old)-1]; return top }
```

### 复杂度

- 时间 **O(n² log n)**：隐式完全图 E=n²，每条边最多压堆一次、堆操作 O(log E)=O(log n)。
- 空间 **O(n²)**：堆最坏装所有候选边（实际远小于，工程可放心）。
- n ≤ 1000 轻松；n=10⁵ 量级时「隐式几何 MST」要换 Delaunay 三角剖分降边（E=O(n)，面试答出这个词直接封顶）。

### 进阶阶梯（面试官连环问弹药）

1. **Kruskal 对偶视角**：所有边全局排序 + 并查集加边（Day 148 的双并查集同款数据结构！）——O(E log E)。工程读法：**Prim 是「联盟视角」（已入伙的人向外扩张），Kruskal 是「市场视角」（价目表从小到大结算，不冲突的先成交）**。边流式到达/分布式场景（每个 region 先各自 MST 再合并）Kruskal 更自然；单点起步的场景 Prim 更自然。能说出「两个贪心同证 cut property」= 图论 maturity。
2. **允许引入「转发 agent」（中继节点）**：agent 集合外的点也能当管道节点 → **Steiner Tree（斯坦纳树）**，一般图上 NP-hard；但**曼哈顿距离的平面实例有 PTAS**（Arora 定理族），工程近似 = 允许中转的 relay 节点。诚实答「MST 是 Steiner 的 2-approx 都不一定够，平面几何有特殊结构」——面试官要的就是这个分寸感。
3. **k 个连通分量 = 任务分包**：「预算不够连所有人，允许分成 k 个互不通信的小队，每队内部连通，怎么分使总成本最小？」→ MST 删掉**最重的 k-1 条边**（切开的每条大边 = 两个子任务的边界）。这是 **LC 1168 水资源分配** 的图论原型（村里修水管 vs 直接打井 = 每个 agent 自带加入费），也是 k-clustering 的经典入口。
4. **瓶颈版： minimize 最大边而非总和**：「最慢的那条同步管道决定整个任务的节奏」→ **最小瓶颈生成树**。关键性质：**任意一棵 MST 同时也是最小瓶颈生成树**（cut property 的免费推论），所以代码不用改，换个解释即可——但**反过来不成立**（最小瓶颈树不一定是 MST）。这一问是通往 Day 147 LC 778 / LC 1102 minimax 路径的桥。
5. **动态加 agent（在线化）**：新 agent 带着坐标到来，要求在线维护联盟。严格最优要动态 MST（ Frederickson 摊销 O(√E)），工程答案 = **最近邻插入 O(n) 一次 + 周期性重跑 Prim**——「在线问题用批处理近似」是系统设计高频权衡话术。
6. **边权随时间变（价格会动）**：管道成本 = token 价目表，价目表 9 月刚降过 25-45%（Fable 5.1）。当边权整体缩放 λ，MST 不变（排序不变）；**只有当相对顺序变了（部分模型降价）MST 才重算**。结论：调度器不需要实时重算 MST，只需要在「价目表相对结构变化」时触发——把算法题焊回今日主题。

### 1. 任务级成本归集：账本树 = 每一块钱都有名字

多 agent 系统烧钱的本质是**一棵树**：用户任务 → supervisor 拆子任务 → 子 agent 再拆 → 叶子是 LLM 调用/工具调用。**成本归集 = 把这棵树每个节点的开销记到正确的科目上**。三原则：

- **一棵任务一棵树**：task_id 是账本的主键，所有 token 消耗（输入/输出/缓存命中分开记，缓存价是 1/20~1/10）挂在 task_id 下。LLM 调用记录五元组 `(task_id, agent_id, model, input_tokens, output_tokens)`——**和 S-1 的 RRR 口径同理：没有统一计量口径，就没有可归集的账**。
- **内部节点收「管理税」**：supervisor 自己的思考、拆任务、汇总评审都要计费归到该 task。METR 式失败分析最常见的一句话就是「管理节点烧了 60% 预算而产出为零」——**账本树画出来，谁是大头一眼可见**。
- **消息传播成本按边记账**（今天算法题的工程读法）：agent 间每传一次消息，成本 = 消息 token 数，归到**发起该消息的子任务**。联盟拓扑 = MST 的意义就在这张账上：**连接结构决定消息总开销**——星型拓扑 supervisor 带宽爆炸，链型拓扑延迟爆炸，MST 是「总通信成本最小」的数学答案。面试问「怎么给多 agent 系统降本」，答「先画账本树找最大内部节点，再画通信图跑 MST 找最肥的边」，比答「换个便宜模型」高两个段位。

**归因的反例（S-1 学费）**：Anthropic 披露 6% 收入来自蒸馏攻击——如果账本只记「谁付了钱」不记「这笔钱对应的 workload 模式」，这种收入永远会被当成优质客户。**成本归集的同时做收入归集，账本的另一面是行为画像**（Day 149 审计框架的会计版）。

### 2. 签名前预算上下文 · 签名后幂等台账（x402 续集，Day 147 伏笔兑现）

Day 147 埋过一个坑：**x402 SDK 三个关键漏洞，其中之一是默认没有消费上限，agent 可以一笔签走钱包全额**（10/22 披露时 55.2% 的下载量仍在漏洞版本）。今天把这一个坑扩成完整的多 agent 结算框架：

**签名前：预算上下文必须进签名 payload。** 三条硬规矩：

- **每会话限额（per-session spending limit）**：AWS Bedrock AgentCore 的官方默认——agent 的支付凭证绑定会话级预算，超了自动拒付。自己实现 = 钱包私钥不放 agent 手里，放**预算网关**（Day 146 的网关加了会计职能）：agent 只拿到额度引用（capability URL），网关校验余额后代理签名。
- **商户类别 + 人工审批**（Visa TAP 三件套）：不是所有 API 都值得 agent 自动付费——给支付能力加白名单（域名/服务类型），高风险类目触发人工审批。**「agent 能签多少钱」是三个独立参数的乘积：余额 × 类目权限 × 单笔/单会话上限**。
- **预算上下文跟着任务走**：任务级预算从账本树根节点向下划拨（框架 1），子 agent 拿到的是「父任务划给我的额度」，不是「钱包余额」——**额度内随便花，额度外一分没有**。这就是「签名前必须有预算上下文」的工程形态：签名那一刻，签名器必须能看到 `(task_id, remaining_budget, allowed_merchants, expires_at)` 四元组。

**签名后：幂等台账 = 账本的不变量。** 支付系统最怕两件事：**重复扣款**（重试风暴里同一笔扣两次）和**丢账**（扣了没记）。解法三件套：

- **Idempotency Key**：每个支付意图生成全局唯一 key（`task_id + agent_id + counter` 或 UUID），网关侧按 key 去重——**重试是分布式系统的正常行为，不是异常**；x402 的 PAYMENT-SIGNATURE 头天然携带签名原文，key 就嵌在里面。
- **Exactly-once 台账**：扣款与记账在同一个事务（或同一 leader 的串行队列）；对账任务定期跑 **三方对账**：agent 侧台账 ↔ 网关流水 ↔ 服务商账单（OpenAI/Anthropic 的 usage dashboard）。三方不平 = 事故，先信服务商账单（法律凭证），再查网关流水，最后审 agent 台账——**账本的信任序和分布式日志的信任序同构：先外后内**。
- **S-1 式口径发明**：当业务复杂到现有指标算不清（Anthropic 被迫发明 RRR），说明**计量口径落后于业务结构**——这就是该上「成本归集树 + 预算网关」组合的信号，别用 Excel 硬扛。

### 3. 混合计费下调度：订阅池 → 按量价目表 → 积分的燃烧顺序

2026 年的开发者手里同时握着**三种计价单位**，调度策略 = 燃烧顺序问题：

| 计价单位 | 形态 | 边际成本 | 代表 | 调度含义 |
|---|---|---|---|---|
| **订阅池** | 月付固定，额度内免费 | 额度内 ≈ $0（沉没成本），超额断崖 | Claude Pro $20 / Max $200（≈按量 $10,000 等价用量，SemiAnalysis 测算）；Team 席位 | **优先烧**——不用白不用；但触限即熔断，高频任务别赌 |
| **预付积分** | 美元挂钩 credits，月度清零 | 名义 $0.01/credit | GitHub AI Credits（Pro 1,500/月）；OpenAI 预付 credits | 次优先——有清零时钟，**先烧临期积分** |
| **按量 API** | 实时价目表 $/MTok，输入输出分开 | 真实现金；缓存命中 1/20~1/10 价 | Fable 5.1 $10/$50、Sonnet 5 $2/$10、GPT-5.6 Terra $2/$12、K3.1 缓存 ¥1.3 vs 未命中 ¥13 | 兜底——价目表是数据不是代码（Day 146），调度器每次请求现读 |
| **批处理/竞价** | 半价但不保证时延 | 半价 | OpenAI/Anthropic/Google Batch API 均 50% off | 异步任务专属；对时延不敏感的回填/评测走这里 |

**燃烧顺序口诀：先沉没（订阅/临期积分）→ 再缓存（按量里的 1/20）→ 后旗舰（按量全价）→ 异步全走批处理**。反例三连（面试讲故事素材）：① agent 死循环把订阅额度一夜烧穿、fallback 到按量 API 无人察觉 → 账单 $8,000（社区真实案例：验证死循环一晚 720 万 token 零产出）；② 缓存命中率从 90% 掉到 20%（prompt 里加了时间戳），成本瞬间 20 倍——**命中率是最便宜的 IDS，也是最便宜的账单报警器**（Day 146 四件套原话）；③ Fable 5.1 九月降价 25-45% 但调度器价目表写死在代码里，多付了两个月冤枉钱。

**价格动态的调度推论**（S-1 带来的新问题）：**当模型厂商开始以「每次任务成本」为竞争指标**（Opus 5.5 比 Opus 5 单次任务便宜 40%），调度器的选模型逻辑要从「固定路由」变成「每季度读一次 S-1/价目表」——**和今天算法题进阶第 6 条同构：相对价格结构变才触发重算**。

### 4. S-1 的 80% 启示：计量即商业，预算是产品

把 S-1 拆成多 agent 系统设计的五条启示：

- **按量计费赢了订阅，因为它对齐了价值**：80.2% 的收入来自用量——客户为「跑完的任务」付钱而不是为「席位」付钱。多 agent 系统的预算设计同理：**给任务拨预算，不要给 agent 拨预算**；agent 是成本中心，任务是价值中心。
- **NDR 900% 的秘密是「水位设计」**：客户一旦把 Claude 写进业务流，用量只增不减——因为**每一步产出都是下一步的输入**（代码库在 Claude 手里越滚越大）。设计多 agent 系统时刻意造这种「水位」：中间产物沉淀在黑板/工件库，离开系统 = 失去上下文 = 迁移成本。这是留存设计，不是锁客设计（面试里区分这两点很加分）。
- **算力 take-or-pay = Anthropic 自己也在做买家侧预算**：$5,180 亿最低算力承诺、80% 不用也得付——**全世界最会卖 token 的公司，买 token 时也签了对赌**。启示：预算管理的对称性——**卖方的收入结构（80% 按量）和买方的成本结构（80% 承诺消费）是同一枚硬币**；你的 agent 系统接入多家模型 API 时，承诺消费换折扣（commit discount）和按量弹性要按 workload 可预测性配比（稳态 70% 承诺 + 尖峰 30% 按量，是最常见的健康比例）。
- **6% 蒸馏收入的会计侧读法**（Day 149 安全侧读法的姊妹篇）：同一笔收入，账本上叫「ARPU 提升」，安全上叫「资产泄露」。**账本科目里加一个「行为模式」维度**（调用多样性、输出消费比、探测性 prompt 占比），6% 这种问题就会在结账前而不是审计时暴露。
- **Claude Code top 5% = 20 倍**：编码 agent 是最深的「用量漩涡」——高频、多步、长 context。预算设计要给编码类 agent 单独科目（它们的成本曲线和问答类差一个数量级），否则月度账单会被一类 workload 绑架。

### 5. 模拟面试速答五连

**Q1：设计一个 50 个 agent 协作系统的预算与结算系统。**
> 三层：**预算网关**（agent 不持私钥，拿额度引用；签名前校验四元组 task_id/remaining_budget/allowed_merchants/expires_at）+ **账本树**（task_id 主键，五元组计量，消息按边归集到发起子任务）+ **调度器**（燃烧顺序：订阅池 → 临期积分 → 缓存命中 → 按量旗舰 → 批处理）。**对账三方**：agent 台账 ↔ 网关流水 ↔ 服务商账单；idempotency key 按 task+agent+counter 生成，重试天然幂等。参考：AWS Bedrock AgentCore per-session 上限（签名前预算）、x402 PAYMENT-SIGNATURE（签名载体）、Visa TAP 三件套（限额/类目/审批）。

**Q2：agent 之间互相购买服务（算力/数据/工具），怎么防止重复扣款和资金漏洞？**
> 两条不变量。**签名前**：任何支付意图必须携带预算上下文（谁的任务、剩多少额度、买什么、什么时候过期），网关验不过不签——x402 SDK 默认无上限导致可签走钱包全额（10/22 漏洞）就是这个教训。**签名后**：幂等台账——idempotency key 全局去重，扣款记账同事务，定期三方对账；账不平先信服务商账单（法律凭证）再自查。**资金漏洞的高发区不是加密，是重试**：重试是正常行为，没有幂等键的系统 = 重复扣款系统。

**Q3：公司买了 Claude 订阅（Pro/Max）又买了 API，怎么调度最省钱？**
> 燃烧顺序：**先订阅池**（额度内边际成本 ≈ 0，但触限即熔断，高频任务设监控防断崖 fallback 到 API 无人知晓）；**再临期积分**（GitHub AI Credits 这类月度清零的先烧）；**按量层先打缓存**（缓存命中 1/20~1/10 价：system prompt 稳定、canonicalization——Day 145 军规）；**旗舰模型只对失败/高难度 escalate**（路由三档，Day 145）；**异步任务全走批处理半价**。价目表读数据不读代码：Fable 5.1 九月降价 25-45%，写在代码里的价格表 = 冤枉钱发生器。最后月度复盘看 S-1 同款指标：任务级成本、缓存命中率、模型混合比例。

**Q4：Anthropic S-1 说 80% 收入按 token 计费，这对设计 agent 系统账本有什么启示？**
> 五条：① **计量即商业**——给任务拨预算不给 agent 拨预算（价值中心是任务）；② **水位设计**——中间产物沉淀产生迁移成本，NDR 900% 的正面教材；③ **买家侧对称**——Anthropic 买算力也签 take-or-pay，你的 workload 按 70% 承诺 + 30% 弹性配比；④ **账本加行为维度**——6% 蒸馏收入靠行为聚类暴露，科目里加调用模式；⑤ **编码 agent 单独设科目**——top 5% 客户 20 倍消耗，成本曲线差一个数量级。一句话：**S-1 是 token 经济学的教材，每个数字都对应一个工程设计决策**。

**Q5：多 agent 系统成本失控，账单爆了，怎么排查？**
> 五步：① **账本树定位**——哪个 task、哪个 agent、哪个模型（内部管理节点烧 60% 是 METR 式常见死法）；② **命中率检查**——90%→20% = 成本瞬间 20 倍（prompt 漂移/时间戳混入 system prompt），命中率是最便宜的账单报警器；③ **重试风暴排查**——失败重试 × N 个 agent 放大，看 idempotency key 分布和 429 曲线（Day 146：429 是时间维度问题）；④ **循环检测**——agent 间互相求证死循环（A 问 B、B 问 A），账本树出现环 = 预算黑洞；⑤ **价目表核对**——相对价格结构变过吗（降价公告）。修完把这次事故写进回归评测集（Day 140 骨架），**每一次账单事故都是下一次降本的基线数据**。

### 今日金句

> **多 agent 系统的账本层，考的不是「总共花了多少钱」，而是「这一块钱是哪个任务、哪个 agent、哪条消息花出去的」。S-1 用 80.2% 的按量收入告诉我们：token 计量已经是这门生意的本体，谁计量得细，谁定价权大；x402 用 SDK 默认无上限的漏洞告诉我们：agent 的签名能力不带预算上下文，就是挂在互联网上的提款机；而 NDR 900% 告诉我们：当每一步产出都是下一步的输入，用量只会上涨——所以预算是产品，水位是设计。当面试官说「设计 agent 经济系统」时，他真正在问的是：第 10 万笔扣款发生时，你能不能在三分钟内回答——谁授权的、凭什么授权的、账平不平。**
