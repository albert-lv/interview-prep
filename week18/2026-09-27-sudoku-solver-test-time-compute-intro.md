## 1) 今日算法题

### 解数独（Sudoku Solver）

**题意**：编写一个程序，通过已填充的空格来解决数独问题。一个 9×9 的数独板，部分格子已填数字（`1-9`），`'.'` 表示空白。你需要**填充所有空白**，使得每一行、每一列、每一个 3×3 宫内的数字均不重复（1-9 各出现一次）。题目保证有唯一解。

```
输入:
[["5","3",".",".","7",".",".",".","."],
 ["6",".",".","1","9","5",".",".","."],
 [".","9","8",".",".",".",".","6","."],
 ["8",".",".",".","6",".",".",".","3"],
 ["4",".",".","8",".","3",".",".","1"],
 ["7",".",".",".","2",".",".",".","6"],
 [".","6",".",".",".",".","2","8","."],
 [".",".",".","4","1","9",".",".","5"],
 [".",".",".",".","8",".",".","7","9"]]
```

**关键约束**：9×9 固定大小。这是**约束满足问题（CSP, Constraint Satisfaction Problem）** 的经典模板。

### 思路：回溯搜索 + 约束传播 = 推理的最朴素形态

数独的规则本质是三个互斥约束：**每行 1-9 不重复、每列 1-9 不重复、每宫 1-9 不重复**。求解 = 在满足所有约束的前提下填充空白。

**朴素回溯**：枚举每个空格的所有候选数字，冲突就撤销换下一个。最坏情况接近穷举，但数独约束极强，剪枝后快得飞起。

**三个必会优化**（面试官期待你主动说出来）：

1. **位运算压缩约束状态**：用 9 个 bitmask（`rows[i]` / `cols[j]` / `boxes[k]`）记录每行/列/宫已出现的数字。检查 `(rows[i] >> d) & 1` 就是 O(1)。比哈希表/数组快，是数独题的标配。
2. **约束传播（Forward Checking）**：填一个数时，同步更新它影响的行/列/宫；撤销时按填入顺序逆序回滚。保证任何时刻约束视图都是准确的。
3. **MRV 启发式（Minimum Remaining Values，最少候选优先）**：永远选**候选数最少**的空格先填。直觉：最 constrained 的变量最容易爆冲突，早填早剪枝——失败分支在搜索树浅层就被砍掉，而不是深埋百万层之后。这是 CSP 教科书的黄金启发式，也是 AlphaGo 的 MCTS 里 UCB「探索-利用」的远古亲戚：**用启发式把搜索的算力花在信息增益最高的地方**。

> 🧩 **和本周主题的连接**：解数独的搜索过程，就是 o1/R1 推理时「搜索+验证」的最原始形态——回溯 = 尝试一条推理路径，约束检查 = verifier（检查比搜索容易得多），MRV = 推理策略（先攻最确定的部分），约束传播 = 每推进一步就收紧可能性空间。把这个框架记在心里，后面六天全是它的升级版。

### 代码

**Go（位运算 + MRV + 剪枝，面试标准答案）：**

```go
func solveSudoku(board [][]byte) {
    var rows, cols, boxes [9]int // 每行/列/宫的已用数字位图
    var empties [][2]int

    for i := 0; i < 9; i++ {
        for j := 0; j < 9; j++ {
            if board[i][j] == '.' {
                empties = append(empties, [2]int{i, j})
            } else {
                d := int(board[i][j] - '1')
                rows[i] |= 1 << d
                cols[j] |= 1 << d
                boxes[i/3*3+j/3] |= 1 << d
            }
        }
    }

    var backtrack func(pos int) bool
    backtrack = func(pos int) bool {
        if pos == len(empties) {
            return true // 所有空格填完
        }
        // MRV：从剩余空格中找候选数最少的一个（本题按序即可，面试可提优化）
        i, j := empties[pos][0], empties[pos][1]
        b := i/3*3 + j/3
        used := rows[i] | cols[j] | boxes[b]
        for d := 0; d < 9; d++ {
            if used>>d&1 == 0 { // d+1 不冲突
                board[i][j] = byte('1' + d)
                rows[i] |= 1 << d
                cols[j] |= 1 << d
                boxes[b] |= 1 << d

                if backtrack(pos + 1) {
                    return true
                }

                // 撤销选择
                board[i][j] = '.'
                rows[i] &^= 1 << d
                cols[j] &^= 1 << d
                boxes[b] &^= 1 << d
            }
        }
        return false
    }
    backtrack(0)
}
```

**Python（同一个思路，更短的实现）：**

```python
def solveSudoku(board) -> None:
    rows = [set() for _ in range(9)]
    cols = [set() for _ in range(9)]
    boxes = [set() for _ in range(9)]
    empties = []

    for i in range(9):
        for j in range(9):
            c = board[i][j]
            if c == '.':
                empties.append((i, j))
            else:
                rows[i].add(c); cols[j].add(c); boxes[(i//3)*3+j//3].add(c)

    def backtrack(pos):
        if pos == len(empties):
            return True
        i, j = empties[pos]
        b = (i//3)*3 + j//3
        for d in '123456789':
            if d not in rows[i] and d not in cols[j] and d not in boxes[b]:
                board[i][j] = d
                rows[i].add(d); cols[j].add(d); boxes[b].add(d)
                if backtrack(pos + 1):
                    return True
                board[i][j] = '.'
                rows[i].remove(d); cols[j].remove(d); boxes[b].remove(d)
        return False

    backtrack(0)
```

> ⚠️ **边界陷阱**：① 位图的宫编号公式是 `i/3*3 + j/3`，不是 `i/3 + j/3`；② Go 的撤销用 `&^=`（按位清除），写成 `|= 0` 会留脏位；③ 题目保证有解，返回 bool 只是工程习惯——如果面试官追问「无解怎么办」，答：回溯自然返回 false，外层生成器用它做唯一解判定（见连环问）；④ MRV 版要把 `empties` 改成每次从剩余格动态选，固定顺序版在多数测试集上已经够用，但要**会描述** MRV。

### 复杂度

| 维度 | 复杂度 | 说明 |
|---|---|---|
| 时间 | 近似 `O(1)`（剪枝后） | 理论上回溯最坏 `O(9^m)`（m=空格数），但约束剪枝让实际搜索量极小，9×9 数独实测毫秒级 |
| 空间 | `O(m)` | 递归深度 = 空格数，m ≤ 81 |

> 💡 **面试话术**：被问复杂度不要慌，先说理论最坏、再给剪枝直觉、最后补实测——「理论最坏是指数级，但数独的约束强度极高，每个空格平均候选只有 2-3 个，实际搜索树非常浅」。这体现的正是你对 **NP 问题 + 启发式剪枝** 关系的理解。

### 面试官连环问

> 💬 **问：怎么生成一个**有唯一解**的数独题目？**
>
> 🎯 答：逆向操作——从完整解开始**挖洞**：随机挖掉一个数字，用求解器验证仍然唯一解；如果不唯一就回填换别的洞。重复直到挖够（常见难度要求 25-30 个提示数）。核心是「求解器即判定器」：`solve` 返回唯一解 / 多解 / 无解三种状态，挖洞过程就是不断调用它。工程上每次挖洞做完整回溯太贵，可以缓存约束状态增量验证。

> 💬 **问：数独是 NP-hard 吗？一般化的数独（n²×n²）呢？**
>
> 🎯 答：9×9 数独是个**固定实例**，谈 P/NP 没意义；但 **n²×n² 的一般化数独是 NP-complete**（2003 年被证明，可规约到拉丁方/三元组精确覆盖）。所以不存在多项式通解，所有求解器本质都是「聪明的搜索」。这正是数独成为推理模型评测题的原因——它需要真正的组合搜索，不能靠记忆背答案。

> 💬 **问：MRV 为什么有效？还有什么经典启发式？**
>
> 🎯 答：MRV 有效因为**最少候选的变量最可能是死胡同**，浅层失败省掉深层子树——期望搜索量最小化。配套的还有：① **LCV（Least Constraining Value，最不约束值优先）**：填值时优先选对未来空格影响最小的候选，给后续留余地；② **前向检查（Forward Checking）**：每次赋值后检查所有未赋值变量是否还有合法候选，提前发现矛盾；③ **弧一致性（AC-3）**：更强的传播，把约束向邻居传播直到不动点。数独用 MRV+前向检查就够了，工业 CSP（排课、芯片布线）才上 AC-3。

> 💬 **问：还能怎么加速？并行化怎么做？**
>
> 🎯 答：单机层面——位运算（已做）+ 候选预计算 +  dancing links（Algorithm X，精确覆盖的终极数据结构，Knuth 出品）。并行层面——数独天然可并行：第一层的 9 个候选分给 9 个线程/进程独立搜索，谁先出解用谁；或者 speculative 地并行展开搜索树不同分支，失败分支直接剪。这就是**搜索的并行化 = 推理时算力扩展**的朴素版本，本周后面讲 test-time compute 时会再回来。

> 💬 **问：这个和 AlphaGo 的 MCTS 是什么关系？**
>
> 🎯 答：数独求解是**单边搜索**（只有约束，没有对手），MCTS 是**对抗/随机环境下的搜索**（有对手或转移概率）。共享的内核是「用启发式分配算力」：数独用 MRV 选变量，MCTS 用 UCB 选节点；数独用约束检查剪枝，MCTS 用 value/policy 网络评估剪枝。把数独的「确定性约束传播」换成「神经网络评估」，把「回溯」换成「采样」，就是 MCTS。Day 121 综合复习会把这个对应关系画成一张表。

### 🧠 今日核心：Test-Time Compute 到底是什么

**1. Scaling Law 有两个轴。**

预训练 scaling（Kaplan → Chinchilla → 多模态）讲的是「**训练 FLOPs 越多，模型越强**」——这个轴在 2024 年开始撞上数据墙和成本墙。o1（2024.09）打开了第二轴：**同一个模型，推理时花的算力越多，答案越准**。两条轴可以互换：小模型 + 多推理算力 ≈ 大模型 + 少推理算力（在特定任务上）。

> 🎯 **一句话本质**：预训练把世界的知识**压缩**进参数，test-time compute 决定**调用这份知识时用多深的思考**。GPT-4 的 CoT 是「想到哪说到哪」，o1 是「在脑内打草稿、验算、推翻重来」——把人类应试生的做题策略学进去了。

**2. o1 的训练配方（和 Week 17 无缝衔接）。**

o1 不是架构创新，是**训练目标创新**：大规模 RL + 长 CoT 数据，奖励来自**可验证答案**（数学 boxed、代码单测）——就是 Day 112 讲的 GRPO 引擎。RL 教模型的不是「知识」而是**思考策略**：什么时候该展开、什么时候该验算、发现矛盾怎么回溯。这正是数独求解器的「元策略」版。

**3. 三类 Test-Time 策略（本周的骨架，背下来）。**

| 类型 | 代表方法 | 机制 | 适用 | 成本特征 |
|---|---|---|---|---|
| **并行采样** | Best-of-N、Self-Consistency | 采 N 个答案，verifier 挑最优 / 多数投票 | 答案可独立验证（数学、代码） | 成本 ×N，延迟不变（可并行） |
| **顺序修订** | Self-Refine、Critique-Revise 循环 | 生成 → 自我批评 → 修订 → 再批评 | 开放式任务（写作、设计、debug） | 延迟 ×k（串行），可早停 |
| **树/图搜索** | ToT、MCTS、rStar | 把推理过程显式展开成树，评估中间节点再决定扩展方向 | 组合搜索问题（规划、证明、难题） | 最贵，但成功率上限最高 |

**4. 关键洞察：验证比生成容易。**

整个范式的地基是一个 P vs NP 直觉——**检查一个解是否正确，远比搜索一个解容易**。生成是指数搜索，验证是多项式检查。所以只要我们能造出便宜可靠的 verifier（PRM、单测、boxed 检查），就能用「采样 N 次 + 验证」把弱模型堆出强表现——这就是 Week 17 讲的 GRPO「可验证奖励上天堂」的推理时版本。**训练时用 verifier 给奖励，推理时用 verifier 做选择，同一个东西两个用法**。

**5. Compute-Optimal Scaling：算力要按难度分配。**

理想策略不是「每题都花最多算力」，而是**自适应分配**：简单题一遍过，难题多搜索。o1 系列用 RL 学出了这种分配（推理长度随难度自动伸缩）。工程上对应的是动态 best-of-N、早停、MCTS 访问次数自适应——Day 119 讲系统实现。

### 🎤 高频连环问速答模板

**Q1：一句话说清 o1 和普通 ChatGPT 模型的本质区别？**
> 不是知识更多，是**会思考**：普通模型生成 = 一次前向（系统一），o1 生成 = 推理 token 反复前向 + 自我验证（系统二）。训练时用 RL 学思考策略，推理时用更多 FLOPs 换更高准确率——scaling 的第二根轴。

**Q2：Test-Time Compute 会不会也饱和？**
> 会，且比训练 scaling 饱和得更快。理由：① 采样收益递减——best-of-N 的通过率随 N 对数增长，很快撞上模型的真实能力上限；② verifier 有准确率天花板，N 再大也选不出对的；③ 顺序修订会**错误累积**（self-refine 有时越改越差）。所以它不是免费午餐：真正work的场景需要「可验证奖励 + 组合结构」两者至少占其一。

**Q3：Best-of-N 的 N 怎么定？**
> 给面试官三层：① 理论——通过率 ≈ 1 − (1 − p)^N（p = 单次成功率），N 越大边际收益越低；② 工程——按延迟/成本预算反推，线上常用 N=4~16 配早停（第一个通过验证的解直接用）；③ 进阶——compute-optimal 是按题难度动态分配 N（难题给 64+，简单题 1 就够），这是当前研究热点。

**Q4：为什么 MCTS 这个 2006 年的老算法，在大模型推理时代又火了？**
> 三个条件 2023 年后才齐：① **节点评估器**——LLM 可以给推理中间步骤打分（"这步走得对吗"），以前只能靠 rollout 到底；② **策略先验**——LLM 本身就是动作提议分布（"下一步可以这样想"），搜索不再是均匀展开；③ **可验证叶子**——终点有 boxed/单测验真。AlphaZero 的三件套（policy 先验 + value 评估 + MCTS 搜索）被原样搬进推理，rStar、AlphaMath、TreeMind 都是这条路。**Day 114 说的「MCTS 是 AlphaZero 的改进器」，在推理模型里同样成立**。

**Q5：Verifier 从哪来？成本高吗？**
> 四类按成本排序：① **规则验证**（代码单测、数学 boxed、语法检查）——几乎免费，最可靠，优先用；② **执行反馈**（跑代码看输出、调用工具看结果）；③ **PRM/ORM**（专门的打分模型，Day 116 细讲）；④ **LLM-as-Judge**（大模型互评，最贵且有 bias）。面试加一句：**verifier 的可靠性决定整个 test-time 系统的上限**——垃圾 verifier × 再多采样 = 垃圾放大器。

**Q6：Test-Time Compute 和你的训练系统（veRL）是什么关系？**
> 一体两面：**rollout 本身就是 test-time compute**——GRPO 采样 G 条轨迹 = G 次推理时计算。所以 Week 17 的所有 rollout 优化（partial rollout、prefix caching 组内共享前缀、异步调度）本质上都是「**训练时算力 ↔ 推理时算力**的转换器」：prefix caching 让 test-time compute 复用 prefill，分离式部署让推理和训练互不排队。理解了 test-time compute，就理解为什么 veRL 把 70~90% 的工程都押在 rollout 引擎上。
