## 🧠 今日算法题：水位上升的泳池中游泳（Swim in Rising Water · LC 778）

### 题目描述

**工程重述：混沌水位 —— 推理集群的最大可容忍故障强度（Max Tolerable Chaos Level）**。

把一个推理服务网格抽象成 `n × n` 的方阵：每个格子 `(r, c)` 是一个服务实例，格上的数字 `grid[r][c]` 是**该实例被压垮所需的故障注入强度**（比如 kill 掉它的概率、p99 延迟倍率、GPU 显存压力值——抽象成一个标量）。

一次请求从入口 `(0, 0)` 流向出口 `(n-1, n-1)`，只能上下左右移动。当全局故障注入强度升到 `t` 时，所有 `grid[r][c] <= t` 的实例已经瘫痪、不可通行。

问：**请求还能走通的最小强度阈值是多少？**——即：从起点到终点存在一条路径，路径上每个格子的压垮阈值都 `<= t`，求最小的 `t`。混沌工程的叫法：**这是系统的混沌爬坡上限（chaos ramp ceiling）**。

**示例**：

```
grid = [[ 0, 2 ],
        [ 1, 3 ]]

答案：3
路径：(0,0) → (1,0) → (1,1)
解释：强度 0 时只有起点活着；强度 1 时 (1,0) 活了，但 (1,1) 需要 3；
      所以 t=3 才能走通。瓶颈 = 路径上的最大格子 = 3。
      若 t=2，(1,1) 仍瘫痪，无路可走。
      → 混沌实验只能爬到强度 2，再往上系统就不可服务。
```

### 思路

**一句话**：求的是「所有路径中，路径最大格子的最小值」——**minimax 路径（最小最大路径）**。两种主流解法：

1. **二分 + BFS/DFS（推荐，工程味最浓）**：答案在 `[0, max(grid)]` 范围内且单调——强度 `t` 能走通，则一切 `t' > t` 也能走通（**单调性 = 二分合法性**，与混沌爬坡语义完美同构：水位越高越难走，不存在「水退了路反而没了」）。二分 `t`，每次用 BFS 判定「只走 `grid[r][c] <= t` 的格子能否从起点到终点」。`O(N² log V)`。
2. **变形 Dijkstra（最小堆版，一次遍历）**：把 Dijkstra 的「距离和」换成「路径上的最大格子」——弹出堆时维护 `max(grid[cur], 到 cur 为止的路径最大值)`，首次抵达终点即为答案。`O(N² log N)`，常数更小，且天然输出「瓶颈升级顺序」（堆的弹出序列 = 各强度下连通域的扩张史）。

混沌工程读法：方法 1 是**控制面的二分探测**（"强度 50% 能活吗？能。75% 呢？"——就是 chaos day 的实操剧本）；方法 2 是**数据面的渐进排水**（一次注入就画出整张「连通域随强度扩张」的地图）。面试两种都给 = 算法功底 + 工程语感双认证。

### 代码示例（Python · 二分 + BFS 主解 + 变形 Dijkstra 对照）

```python
from typing import List
from collections import deque
import heapq

# 解法一：二分 + BFS（混沌爬坡控制面）
def swim_in_water(grid: List[List[int]]) -> int:
    n = len(grid)
    lo, hi = grid[0][0], max(max(row) for row in grid)  # 起点必须活着 → 下界不是 0

    def can(t: int) -> bool:
        if grid[0][0] > t:
            return False
        seen = [[False] * n for _ in range(n)]
        seen[0][0] = True
        q = deque([(0, 0)])
        while q:
            r, c = q.popleft()
            if (r, c) == (n - 1, n - 1):
                return True
            for dr, dc in ((1,0),(-1,0),(0,1),(0,-1)):
                nr, nc = r + dr, c + dc
                if 0 <= nr < n and 0 <= nc < n \
                   and not seen[nr][nc] and grid[nr][nc] <= t:
                    seen[nr][nc] = True
                    q.append((nr, nc))
        return False

    while lo < hi:                       # 找最小的可行 t
        mid = (lo + hi) // 2
        if can(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo

# 解法二：变形 Dijkstra（minimax 堆，数据面一次成型）
def swim_in_water_dijkstra(grid: List[List[int]]) -> int:
    n = len(grid)
    dist = [[float('inf')] * n for _ in range(n)]   # dist[r][c] = 到 (r,c) 的最小瓶颈值
    dist[0][0] = grid[0][0]
    pq = [(grid[0][0], 0, 0)]                       # (路径最大格, r, c)
    while pq:
        d, r, c = heapq.heappop(pq)
        if (r, c) == (n - 1, n - 1):
            return d                              # Dijkstra 贪心：首达即最优
        if d > dist[r][c]:
            continue
        for dr, dc in ((1,0),(-1,0),(0,1),(0,-1)):
            nr, nc = r + dr, c + dc
            if 0 <= nr < n and 0 <= nc < n:
                nd = max(d, grid[nr][nc])         # 关键：取 max 不是加和
                if nd < dist[nr][nc]:
                    dist[nr][nc] = nd
                    heapq.heappush(pq, (nd, nr, nc))
    return -1

print(swim_in_water([[0,2],[1,3]]))            # 3
print(swim_in_water_dijkstra([[0,2],[1,3]]))   # 3
```

### 复杂度

- **二分 + BFS**：`O(N² log V)`，`V = max(grid)`。BFS 每次 `O(N²)`，二分 `O(log V)` 轮。适合「阈值已知可枚举」的工程场景。
- **变形 Dijkstra**：`O(N² log N)`，单次遍历、无需二分上界，且顺带输出全图瓶颈距离场——**只跑一次就拿到任意入口出口对**。
- 为什么不是普通最短路：路径代价不是边权之和，而是路径上的**最大值**——max 不满足 Dijkstra「已确定节点不再被松弛」的常规证明？其实满足：**瓶颈值沿路径单调不降**，堆首达即最优依然成立（把松弛的 `+` 换成 `max` 后不等式链原样有效）。能说出这句证明要点 = 高分。

### Follow-up 阶梯（面试连环追问）

1. **格子的压垮阈值随时间变化（混沌强度是时间序列）？**——离线做法：把每格阈值按时间排序跑离线分治（parallel binary search）；在线做法：变形 Dijkstra 换成**可持久化堆 / 并查集按权值合并**：按格子阈值从小到大激活格子，相邻激活格子 union——**每加一格就合并两个连通块，出口与起点连通的那一刻的权值 = 答案**。`O(N² α(N))`，几乎是线性！（Kruskal 重构树的思想雏形）
2. **不止一条路径，要求 top-k 条互不相同的瓶颈路径（多逃生通道）？**——跑 k 次变形 Dijkstra + 朴素路径排除太丑；正解是**Kruskal 重构树 / 最小瓶颈路径树**：以「瓶颈阈值」为关键值建最大生成树，树上任意路径的 max 边权 = 原图 minimax——多路径问题降为树上问题（LCA + 第 k 大边）。
3. **允许一次「加固」任意一格（把它阈值降到 0），最小化答案？**——二分答案 `t`，BFS 判定中允许免费穿过**至多一个** `grid > t` 的格子（三维状态 `(r, c, used)`），`O(N² log V)`。工程版：加固预算有限，应该花在**所有瓶颈路径的公共格**上——把 minimax 距离场正反向各跑一遍，交集处就是「最高 ROI 加固点」。这一句直接接上成本工程主线（钱花在瓶颈上，不是花在平均值上）。
4. **加权版本（格子之间移动也有代价：边权 = 网络延迟）？**——**LC 1631 Path With Minimum Effort**：`effort = 路径上相邻格子高度差的最大值`，正是本题的「地形版」，解法同构（二分 + BFS / 变形 Dijkstra）。面试时说「778 是点权版、1631 是边权差版，一套代码两个马甲」。
5. **如果要求「最大流量」而不是「单路径」？**——minimax 升级为**最大流**：每条边容量 = 该实例剩余吞吐，问强度 `t` 下入口到出口的最大并发 = 残量网络最大流；混沌工程读法 = **blast radius 下的降级容量规划**（Day 146 降级梯子 L0–L3 的定量版）。
6. **逆向问法（面试常见反转）：「至少淹死多少格才能保证系统断连？」**——把「阈值」换成「删除预算」：从小到大激活格子（并查集），统计让起点出口断连所需删除的最小总权值 = **最小割**（Week 21 Day 139 的 max-flow 最小割回来了！）。混沌读法：**隔离成功 = 割集权重 ≥ 注入强度**。一张题网把两周串起来。

### 第二部分：混沌测试实战课 —— vLLM 0.32.0 八连公告教会我们的六件事

10/27–28 的 vLLM 0.32.0 公告风暴（8 个 advisories、两条 RCE）是推理基础设施混沌工程的全套教案。逐条拆：

1. **绿色 /health 是最常见的谎言**。0.31.0 时代的公告里，一个 **92 字节请求**（极端 `min_tokens`）就能让调度线程卡死，而健康检查依然通过。混沌测试的军规：**探针必须走真实工作负载**（发一条真推理、验证真返回），而不是 curl 一下端口。→ 工程动作：`/health`（进程活着）与 `/ready`（能答一条真 prompt）分级，混沌日里后者权重更高。
2. **攻击面跟着功能长**。共享内存句柄伪造 → `pickle.loads`（CVE-2026-115912）、EPS 图片 → Ghostscript（CVE-2026-115915）：多模态和 IPC 每加一个特性，就多一个反序列化面。**混沌注入清单必须随功能列表版本化**——Week 21 Day 140 的「传统五 + agentic 三」要加今天的第四条：「序列化边界（pickle/共享内存/图片解码器）」。
3. **八连公告 = 依赖树同震**。一个 engine 的 advisory 会同时打穿你镜像里所有 layer：CI 流水线、terraform 镜像 tag、在线滚动升级窗口，全要在同一天响应。**混沌测试不只测运行时，也要测你的供应链响应时延**（从 advisory 发布到生产无漏洞版本的 elapsed time——把它做成指标，比如 MTTR-dep）。
4. **修复≠发布≠部署**。官方修复在 0.32.0，但你跑的是 0.30.x 且镜像 layer 缓存没失效？下载了新镜像但没重启容器？（LinuxSecurity 的 checklist 原文：*downloading an image alone leaves their code unchanged*）。混沌日的固定节目：**故意在 staging 留一台「忘了重启」的节点，看你的部署一致性检查抓不抓得住**。
5. **恢复动作不能降低可见性**（NIST 十天条第 7 条，Day 140 已立）。紧急回滚到旧版本 = 把漏洞请回来；正确姿势是「带着补丁回滚」（rollback with patch），并在事故报告里标注「本次恢复引入了哪些临时降级」。
6. **把「92 字节请求」加进注入库**。它之所以致命，是因为所有常规压测都发「正常形状」的请求。混沌注入的形状库必须包含：极端参数组合、空 body、畸形 multipart、超长 header、负值/超界值——**攻击者按解析器边界思考，防御者也要**。

### 第四部分：模拟面试混合题四连

#### 🎭 混合题 1（系统设计）："设计一个多租户 LLM 推理网关，要求：P99 延迟 SLO、租户级成本预算、缓存命中率 90%+，你怎么做 chaos day？"（全周总装）

**答题骨架（按天的顺序装配，每步标注弹药来源）**：

1. **容量与成本基线**（Day 142）——先画 token 流量时间轴：多租户叠加 = 拼车问题的连续版；用差分/扫描线思想做**离线容量规划 + 在线水位预警**。prefill/decode 分离定容量，不许用峰值当常态（峰值是给自动伸缩的，不是给采购的）。
2. **缓存层**（Day 143 + 145）——prefix cache（PagedAttention/RadixAttention）管 KV，语义缓存管答案；LRU/LFU 选型按流量形态（重尾热点→LFU+TinyLFU 准入，时间漂移→LRU）；**命中率纳入 SLO**（90%→20% = 按 1/20 折价表成本瞬间 20 倍，Day 146 结论）。
3. **路由层**（Day 145）——RouteLLM 式分类器 cost-weighted 阈值，滞回带防跳变；highspeed 档 = 「买速度」产品化的第三决策轴。
4. **护栏层**（Day 146）——配额三轴（rate/quota/slot）独立 + 429/402 语义正确 + 降级梯子 L0–L3 + 成本异常四件套（基线/斜率 10×/结构突变/身份联动）。
5. **混沌日剧本（今天的主菜）**：
   - **注入清单**（blast radius 从小到大连跑 6 小时）：杀 1 个缓存节点（看命中率与成本曲线）→ 把某租户 quota 打穿（看 402 语义与降级梯子）→ 92 字节式畸形请求打调度器（看 /ready 探针）→ 限速网关自身 CPU（看公平性是否退化成饿死）→ 模拟 upstream 429 风暴（看重试预算与雪崩）→ 最后一小时全开（full mesh 压力）；
   - **每一注都先写假设**：「注入 X，预期指标 Y 变化 Z，回滚条件 W」——**没有假设的注入只是破坏**；
   - **指标对照板**：延迟 P50/P99、命中率、每租户 $/hr、队列深度、429/402 比例、版本差分布（Day 136 借来的）——**成本指标和延迟指标同屏，不许分开看**；
   - **复盘三问**：哪个假设错了（系统比你想象脆/韧）？哪个仪表说谎了？哪个修复提高了 MTTR-dep？

**时效性加分**："这周三 vLLM 八连公告已经替我做过半天的 chaos day——如果你的网关引擎依赖 vLLM，这轮 advisory 的响应时长就是你供应链成熟度的第一次实测。把 MTTR-dep 报给老板看。"

#### 🎭 混合题 2（排查 Troubleshooting）："周四早上，监控显示一切正常：P99 正常、错误率正常、/health 全绿。但客服说大约从凌晨三点开始，大量用户报告「回答到一半突然停住」。你怎么查？"（Day 143 + 146 + 今日 vLLM 课）

**先点破：这是 vLLM 92 字节请求的真人秀**——「到一半停住」= 流式 token 中断，是**调度/生成侧**症状；「一切正常」= 你的探针全在**进程侧**。两者同时成立只说明：故障在探针形状覆盖不到的地方。

**排查阶梯（按成本从低到高）**：

1. **先复现，再看**：拿真实用户 session 的 prompt 形状在 staging 回放（不要自己编 prompt——93% 的此类故障与特定参数组合绑定，比如 `min_tokens` 极端值 + 长 system prompt + 多模态附件）；
2. **对比「能答」与「不能答」的请求形状**（diff 不是平均值）：把凌晨三点的请求按「参数组合」分桶，找停住率突变的那个桶（Day 144 的分层采样直觉：总量正常 = 每桶都被正常桶稀释了）；
3. **查流式链路各跳的「最后一条 token 时间戳」**：网关→引擎→tokenizer detokenizer→上游转发，哪一跳之后没有下一条，故障就在哪一跳的下游；
4. **假设检验**（按本周弹药排序）：
   - KV 池水位打满 → 长请求在 prefill 队列里排队到死（Day 143：懒标记线段树的在线水位告警该响——**检查为什么没响**：阈值是不是按「平均值」设的？）
   - 调度器线程被畸形请求卡死（今日 vLLM 课：92 字节请求）→ **/ready 探针为什么没发现？**（你的 /ready 只测「进程能 accept」没测「能吐 token」）
   - 某租户触发成本护栏但未正确返回 402（Day 146：429/402 报错反了的后果——客户端疯狂重试，重试把队列塞满，**停住的真正原因是护栏的下游效应**）；
5. **止血与验证**：先上「新请求路由到健康池 + 旧池只出不进」（cell-based 隔离，混题 3 细说），再把抓到的畸形形状加进**探针形状库**和**混沌注入库**——这次事故的永久遗产是两份清单各多一行。

**黄金收尾**："凌晨三点到早上八点的五个小时里，系统的每块仪表都在说真话——但它们回答的不是用户在问的问题。**混沌测试的第一课：你的探针形状决定了你的可见性形状。**"

#### 🎭 混合题 3（可靠性设计）："我们要把推理网关从单 region 扩到 3 region，怎么设计 cell 架构与故障隔离？"（Day 145 一致性哈希 + 今日混沌水位）

**骨架**：

1. **Cell 化**：每 region 内再切 2–3 个独立 cell（独立网关、独立缓存集群、独立配额计数器）——**爆炸半径 = 1/N_cell**，这是混沌水位图里人为降低 `grid[r][c]` 的工程手段；
2. **路由**：全局层按租户一致性哈希到 cell（Day 145：虚拟节点防倾斜；会话粘性 = 缓存命中率的前提）；region 间用 geo-routing + 健康度加权的 DNS/Anycast；
3. **配额计数器**（Day 146 三轴的分布式版）：rate 用 local token bucket + 定期对账（最终一致，超卖上限 = 对账周期 × 速率，可证明）；quota 用中心化计数（强一致，走 Redis/DB）；**说清这两者的取舍 = 本题分水岭**；
4. **隔离验证 = 今天的算法**：把「cell × region」画成 grid，每个格子的阈值 = 该 cell 独立承载全量流量的能力（理论上无穷——能切走；实际上受全局配额与数据局部性约束）。**混沌剧本**：定期把一整个 cell 沉到水下（drain + blackhole），验证 ①一致性哈希搬移量 ≈ 1/N ②邻居 cell 的 P99 退化 ≤ 预算 ③配额对账无雪崩。这就是 LC 778 在 infra 层的真实运行；
5. **一句点睛**："cell 架构的目的不是『不出故障』，而是**让任何一格被淹死时，水位图重连的路径长度 ≤ 1 hop、成本增量 ≤ 预算**——这正是 minimax：路径上最糟的一格，决定你最糟的一天。"

#### 🎭 混合题 4（成本工程）："CFO 又来了：本季度推理账单超 40%，但 CEO 说用户量只涨了 15%。差异从哪来？两周内给出方案。"（Day 142 + 144 + 145 + 146 总装）

**框架（先归因分解，再动刀，全程双指标护栏）**：

1. **分解恒等式**：总成本 = 请求数 × 每请求 token × 每 token 单价。三个因子分别归因：
   - **请求数 +15%**（CEO 口径，验证）；
   - **每请求 token**：查上下文长度分布漂移（是否有人往 system prompt 塞了 10 倍内容？agent 循环失控？——Skynet 式失控循环的第一信号就是**单请求 token 数**暴涨）；
   - **每 token 单价**：查命中率（90%→20% = 20 倍成本，Day 146）、模型路由分布（是否 highspeed 档用量飙升）、供应商价目变更；
2. **结构突变检测**（Day 146 四件套）：按租户/端点/参数组合分桶看**斜率**——总量被平均，斜率会自首；
3. **动刀清单（按 ROI 排序）**：
   - canonicalization 修复（Day 145 六军规：system prompt 稳定 = 缓存命中的前提）——零成本一刀，先砍；
   - 路由阈值回调（若 highspeed 档占比异常 → 阈值回滞）；
   - agent 循环护栏（单请求 token 上限 + 循环检测，Day 146 三轴第三轴）；
   - 若仍超标 → 降级梯子 L1（非关键流量切小模型）；
4. **防复发**：把「每请求 token 分布」和「命中率」加进周报的固定行；给每个租户设 quota 硬顶 + 斜率告警（10×/hr 触发人工）。
5. **时效加分**："x402 那 55.2% 的裸奔下载量提醒我们：默认值不会自己变好。**所有护栏都要写成默认值、写进 SDK、写进 terraform，而不是写在 wiki。**"

### 高频速答六连（收官版）

1. **"这周主题一句话？"** → "推理系统工程 = **把算力变成商品**：成本的账要算清（142/143）、质量的钱要花对（144）、缓存和路由要让每一分钱复用（145）、仪表和预算要让烧钱看得见（146）、混沌测试要让仪表盘被定期证明没说谎（147）——**五个乘法因子，任何一项为零，账单或者 SLO 总有一个先爆**。"
2. **"/health 和 /ready 有什么区别？"** → "/health 答「进程没死」；/ready 要答「我现在能接一条真请求并返回真结果」。vLLM 92 字节请求演示了只有前者的世界有多危险——**混沌注入清单的第一项就是让你的 /ready 真的发推理请求**。"
3. **"缓存命中率从 90% 掉到 20%，意味着什么？"** → "按这周三的折价表（缓存命中 1/20 价），输入侧成本瞬间 20 倍——但更要命的是：**命中率是最便宜的行为异常 IDS**。先别优化，先查是谁改了什么（prompt 结构变更？租户结构突变？攻击面探测？）。**成本异常=行为异常，先归因后优化。**"（Day 146 金句回收）
4. **"混沌测试和压测有什么区别？"** → "压测问『最大能扛多少』，混沌测试问『坏了一个之后，剩下的是否还能用、仪表是否说真话』。压测发正常形状的海量请求，混沌注入发**故意 abnormal 的形状**（杀节点、畸形参数、慢下游、时钟跳变）。只有压测没有混沌 = 只练过顺风球。"
5. **"单个 advisory 如何变成系统性改进？"** → "三步：①MTTR-dep（advisory→生产无漏洞版本的时长）做成指标进周报；②把漏洞的根因模式（这次是反序列化边界）加进混沌注入清单的**永久条目**；③把『本次恢复是否降低可见性』写进事故复盘模板。一个 advisory 的终局不是升级完成，是**清单和指标里多了一行**。"
6. **"推理成本工程的最高境界？"** → "**让成本曲线成为系统的神经系统**：每一次斜率突变都被当作异常行为对待，每一分钱的去向都可归因到租户/请求/模型——Anthropic S-1 告诉我们前沿实验室 80% 收入来自按用量计费，**你的成本工程能力，本质上就是你的盈利能力**。"
