## 一、今日算法题：LRU / LFU 缓存（LC 146 / LC 460）+ 一致性哈希扩展

### 题目

**LC 146 LRU 缓存**：设计满足 `get` / `put` 均为 **O(1)** 的缓存，容量 `capacity` 满时淘汰**最久未使用**的 key。

**LC 460 LFU 缓存**：淘汰规则升级为「**使用频率最低**；频次相同时淘汰最久未使用」。两个操作仍要求 O(1)。

**扩展（系统设计入口）**：单机容量不够，要水平扩到 N 台缓存节点——如何分 key 才能让**扩容缩容时只搬运 1/N 的数据**？（一致性哈希 + 虚拟节点，后文展开。）

### 为什么今天讲它（语义缓存的算法底座）

- **应用层语义缓存** = 哈希表查「这个请求语义上答过没有」+ 容量满了按什么策略踢人 → LRU 或 LFU（加 TTL）；
- **serving 引擎的 prefix cache** = 树的形状（radix tree），但逐出策略同样要回答「踢谁」→ LRU/LFU 变种；
- **网关层路由** = 把请求映射到后端池 → 一致性哈希（带虚拟节点）。

缓存不新鲜，但 2026 年它的**经济学**是新的：下面会算，90% 命中率在 K3.1 的价目表里等于输入侧打 **0.84 折**。

### 思路：哈希表 + 双向链表（LRU 的 O(1) 骨架）

O(1) 的关键是把「使用时间序」维护成一个**有序容器**，且任意位置删除/移动都是 O(1)：

- **哈希表** `key → 链表节点指针`：定位 O(1)；
- **双向链表**按使用顺序排：最新在头、最旧在尾；`get` 命中 → 摘下节点移到头部 O(1)；`put` 满 → 删尾部 O(1)；
- 为什么是**双向**链表：删除任意节点需要前驱指针——单链表删中间节点是 O(n)。

两个容器互为索引，缺一不可：只有哈希表没有序（不知道淘汰谁），只有链表没有 O(1) 查找。

### 代码（Go · LC 146 LRU 完整实现）

```go
type LRUCache struct {
    cap   int
    cache map[int]*list.Element   // key -> 链表节点
    ll    *list.List              // container/list: Front=最新, Back=最旧
}
type entry struct{ key, val int }

func Constructor(capacity int) LRUCache {
    return LRUCache{capacity, make(map[int]*list.Element), list.New()}
}

func (c *LRUCache) Get(key int) int {
    if e, ok := c.cache[key]; ok {
        c.ll.MoveToFront(e)              // 访问 = 续命：移到头部 O(1)
        return e.Value.(entry).val
    }
    return -1
}

func (c *LRUCache) Put(key, value int) {
    if e, ok := c.cache[key]; ok {       // 已存在：改值 + 续命
        e.Value.(entry).val = value
        c.ll.MoveToFront(e)
        return
    }
    if c.ll.Len() == c.cap {             // 满了：淘汰最久未使用（尾部）
        oldest := c.ll.Back()
        delete(c.cache, oldest.Value.(entry).key)  // ⚠️ 双向索引都要删!
        c.ll.Remove(oldest)
    }
    c.cache[key] = c.ll.PushFront(entry{key, value})
}
```

- **复杂度**：get / put 均 O(1)（map 定位 + 链表头尾操作），空间 O(capacity)。
- **面试三坑**：① `Put` 已存在的 key 是**更新+续命**，不是报错也不是静默丢弃；② 淘汰时**必须同时删 map 里的键**（否则哈希表泄漏、缓存幽灵）；③ `capacity = 0` 要直接 short-circuit（`Len()==0==cap` 时 Back() 是 nil——corner case，面试官就等这个）。

### 进阶 1：LFU（LC 460）——双哈希表 + 频次链表

LRU 的问题：一次突发扫库可以让低频 key 蹭进缓存、把真正的热点挤出去（**扫描抵抗性差**）。LFU 按访问次数淘汰，抗扫描——代价是实现升级：

- 每个节点维护 `freq`；相同 freq 的节点挂在同一条双向链表里（保持 LRU 次序）；
- 维护 `minFreq`：淘汰时直接在 `freq == minFreq` 的链表尾部删 O(1)；
- `get` / `put` 命中 → 节点从 freq 链表摘下，挂到 freq+1 链表头部；若原链表空了且 freq == minFreq，则 `minFreq++`。

```python
class LFUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.kv = {}        # key -> (val, freq)
        self.fq = defaultdict(OrderedDict)  # freq -> {key: None}（按插入序=最旧在尾）
        self.minf = 0

    def _touch(self, key, val):
        v, f = self.kv[key]
        del self.fq[f][key]                     # 摘出旧频次层
        if not self.fq[f] and f == self.minf:
            self.minf += 1                      # 最低层被掏空 → 阈值上移
        self.fq[f + 1][key] = None              # 挂进 freq+1 层（最新）
        self.kv[key] = (val, f + 1)

    def get(self, key: int) -> int:
        if key not in self.kv: return -1
        self._touch(key, self.kv[key][0]); return self.kv[key][0]

    def put(self, key: int, val: int) -> None:
        if self.cap == 0: return
        if key in self.kv:
            self._touch(key, val); return
        if len(self.kv) == self.cap:            # 淘汰：minf 层最旧者
            evict, _ = self.fq[self.minf].popitem(last=False)
            del self.kv[evict]
        self.kv[key] = (val, 1)
        self.fq[1][key] = None
        self.minf = 1                           # 新节点 freq=1 → minf 重置
```

**复杂度**：get / put 均 O(1)（OrderedDict 操作 O(1)），空间 O(capacity)。**面试答法**：不要说「用堆」——堆是 O(log n)，且无法处理「同频次按时间再淘汰」；正确结构就是「频次 → LRU 链」的两级索引。

**进阶追问：LRU vs LFU 怎么选？**——访问模式有**明显热点重尾**（少数 key 占绝大多数访问）→ LFU；热点**随时间漂移**（新闻、会话、agent 多轮上下文最近优先）→ LRU（LFU 有「老热点赖着不走」的陈旧问题）。工程上还有 **LRU-2 / 2Q / ARC / W-TinyLFU（Caffeine 的方案）**：用极小的 sketch（Count-Min）做准入过滤器，挡住扫描型流量，缓存主体仍是 LRU——**准入策略和逐出策略分离**，这是工业界对 LC460 的实用回答。

### 进阶 2：一致性哈希——多机缓存怎么分 key

问题：N 台缓存节点，`hash(key) % N` 在**节点增减**时要搬运几乎全部数据（位置重排）。一致性哈希把搬移量压到 **1/N**：

- 把节点和 key 都映射到同一个环（0 ~ 2³²-1，用同一哈希函数）；
- key 顺时针找**第一个节点**负责；
- 增删节点只影响环上相邻的一段弧——**只有 1/N 的 key 需要搬家**；
- **虚拟节点**：每个物理节点在环上映射 v 个虚拟点（v 常取 100~200），打散负载、抹平哈希环的不均匀；
- 复杂度：查找 O(log N)（环上二分）或 O(1)（用平衡树 + 跳表，或网关里直接跳表）。

**今天把它和热点结合**：1M 上下文的推理集群里，**长 prompt 的 KV 块**也可以按块 hash 到分布式 KV pool（mooncake / LMCache 思路，Day 142 已挂账）——一致性哈希就是「KV 块 → 存储节点」的那张路由表。算法题的哈希环，和多机推理的 KV 环，是同一个数据结构。

### 面试官连环问（预设走位）

1. **「O(1) 怎么证明？」**——定位靠 map O(1)；移动/删除靠双向链表指针重连 O(1)；淘汰只动尾节点 O(1)。全程无遍历。
2. **「并发怎么办？」**——map + 链表不是并发安全结构：分片（N 个 shard 各持一把锁，key 再哈希选 shard，降低锁竞争）；或「get 不加锁 + 惰性删除 + put 用单 writer 队列串行化」；真正的工业缓存（Redis、groupcache）是**单线程事件循环**——呼应 Day 142 的 vLLM engine core。
3. **「容量 100 万 QPS，单机存不下？」**——分片 + 一致性哈希（上面展开）；再挂 TTL 解决「踢了不该踢的」；冷热分离（热层进程内 LRU，温层 Redis，冷层磁盘——三级缓存）。
4. **「怎么知道缓存命中率？」**——`hit / (hit + miss)`，外加按 key 前缀分桶的命中率直方图（定位「哪类请求不命中」比全局数字有用——语义缓存的 canonicalization 优化就从这里下手）。

## 二、面试技巧：模型路由与语义缓存——2026 年推理系统的「省」与「挑」

### 2.1 先立框架：请求生命周期里的五个决策点

请求从进来到出去，每一站都在「省钱」：

```
请求 → ①语义缓存查重（答过没？）→ ②路由（给谁处理？）
     → ③模型内路由（哪个 expert / 哪个档位？）
     → ④ prefix cache 复用（KV 算过没？）→ ⑤ 输出后写回缓存（下次复用）
```

①②是今天的主题；③是 MoE 专家路由 + Highspeed/Ultrafast 这类「同权重不同档位」的产品化分层；④是 Day 143 的整章；⑤决定明天的命中率。面试官问「怎么降推理成本」，把这张图拍出来再逐点展开——这就是「有计划、有节奏、有目标」的答题结构。

### 2.2 缓存分层：三层缓存，三种「相同」

| 层 | 位置 | 判断「相同」的依据 | 2026 代表作 |
|---|---|---|---|
| L1 应用层**语义缓存** | 网关 / 应用进程 | **嵌入向量近邻**（语义等价即命中）+ TTL | GPTCache、Redis + vector index |
| L2 **前缀缓存** | serving 引擎 | **token 前缀逐位相同**（canonical form 之后） | vLLM automatic prefix caching、SGLang RadixAttention |
| L3 模型侧缓存 | API 计费层 | 供应商实现，黑盒 | `cached_input` 1/10 价（K3.1 价目表） |

三层的关系：**L1 省整次调用（最贵），L2 省 prefill 算力（次之），L3 是供应商替你做了 L2 并把省下的钱分你 1/10**。命中率从 L1 到 L3 通常递增（约束越松越易命中），但省的绝对金额递减。

**面试高频：「语义缓存和前缀缓存什么区别？」**——一句话：**语义缓存回答「这个问题答过没有」，前缀缓存回答「这个问题的开头算过没有」**。前者把「2026 中国 GDP 是多少」和「中国的 GDP 在 2026 年是多少」当同一个问题；后者只有当两者 token 化后前缀一致才复用。语义缓存误命中会**答错**（相似≠相同），所以要设相似度阈值 + 关键意图字段精确匹配兜底；前缀缓存几乎不会错，只是命中率天花板更低。**安全红线：语义缓存键必须含租户标识**——否则 A 租户的「我的订单」会命中 B 租户的回答（cache_salt CVE-2025-46570 一族的翻车姿势）。

### 2.3 Canonicalization 六条军规（官方亲自下场背书）

K3.1 Hermes 指南的第一条建议就是「保持 system prompt 稳定」。展开成工程清单，缓存友好 = 对**所有参与缓存键/前缀的字段**做规范化：

1. **固定 system prompt**：锁版本号，改内容走灰度新 key；
2. **温度等采样参数进键**：temperature/top_p 不同 = 不同请求（别指望缓存替随机性兜底——除非你的缓存层本来就允许返回「语义等价」的答案）；
3. **租户 / API key / 数据域进键**：安全底线，前面说过了；
4. **RAG 检索结果的位置进键**：同一问题换一批文档，答案必须变——这是语义缓存最容易翻车的点；
5. **时间敏感意图走 TTL 短窗口**：「今天天气」「最新股价」语义命中可以，但 TTL 得按分钟算；
6. **canonical form 版本化**：规范化规则本身升级（比如改了 prompt 模板）要换 key 前缀，否则新旧模板互相污染。

**RouteLLM 论文（ICLR 2025）的同构思想**：路由分类器吃的也是「规范化之后的特征」——prompt 表征先归一，路由才稳。缓存和路由，是同一个「输入先整形、再做决策」原则的两个孩子。

### 2.4 路由三档 + RouteLLM 分类器

**三档路由**（Day 142 挂账，今天展开决策逻辑）：

- **规则路由**：按请求元数据（API key 档位、是否付费、region、合规域）→ 零延迟、零错误，覆盖不了「同一个用户的问题有难有易」；
- **模型分类器路由（RouteLLM 式）**：训练一个小分类器（bert-mini 级），输入 prompt 表征，输出「弱模型能搞定的概率 p」；**p 高于阈值走便宜模型，低于阈值走强模型**。训练信号怎么来？两种：①用强/弱模型在历史 query 上的**相对打分差**（如 Chatbot Arena 对战数据）；②线上 A/B：弱模型答案送强模型/判分器复核，统计「弱模型错了但路由过去了」的代价（cost-weighted threshold tuning——阈值不是拍 0.5，是按 **期望成本 = p_wrong × 答错代价 + 路由到强模型的溢价** 优化出来的）；
- **Cascade 级联**：一律先走弱模型，**让它自己说不说「我不行」**（置信度/自我评估），不行再升级强模型。比分类器多用一点弱模型算力，换来不用维护分类器，且天然适应模型升级（弱模型换新版，cascade 自动吃到红利）。

**面试官追问「阈值怎么定？」**——完整答法：离线在标注集上扫 p 的 ROC，把「路由错误率」控制在业务可接受范围（比如 <2%）内最大化省钱；线上再用 shadow 流量持续校准，阈值做成**可调配置**而非代码常量（模型一换代就要重调——阈值是路由系统的「学习率」）。

### 2.5 热点案例串讲（把今天的新闻讲成答案）

**案例 A：K3.1 的价目表就是一道计算题**。面试官：「90% 前缀缓存命中率，输入侧省多少？」——K3.1 口径：`(0.1×13 + 0.9×1.3) / 13 = 2.17/13 ≈ 0.167`，**≈ 83% off**。再追「对总账单呢？」——输入占比按 3:1 估（长 prompt 短回答的 agent 场景），账单整体 ≈ 1 − 0.83×0.75 ≈ **38%**。答到这一步，顺手补一句「所以 11/4 K3.1 权重开源后，自建 serving 团队的前缀缓存命中率会写进架构评审」——把算术题升格成行业判断，这就是「紧贴时事」的答法。

**案例 B：Highspeed / Ultrafast 是路由器的第三个决策轴**。同一权重、两个档位（标准 ¥13/¥68，高速 ¥26/¥136、2~3× 速度）。路由决策从二元（大/小模型）变三元：**模型 × 档位 × 是否缓存**。交互式 agent（用户在线等）→ 买速度档；离线批处理 → 标准档。再叠加 Day 144 的 test-time 预算（难题多采样），你手里就有了一张「质量-延迟-成本」三维路由表——**路由器的本质是线性规划，工程实现是查表 + 阈值**。

**案例 C：SGLang vs vLLM 之争 = 缓存抽象之争**。RadixAttention 把「最长公共前缀」做成系统核心抽象，天然适合多轮 agent（共享系统 prompt 前缀）；vLLM 的 PagedAttention 是「内存管理」视角，prefix caching 是后加的 block 级复用。被问「怎么选 serving 引擎」，别答 benchmark 分数——答**你的流量形状**：多轮对话/agent 占比高 → radix 树形状的前缀复用收益大；独立短请求多 → block 级缓存 + 高并发调度更实在。**面试官想听的是「你的流量决定你的缓存形状决定你的引擎选型」这条因果链。**

### 2.6 可靠性五连

1. **缓存雪崩**：热点 key 同刻过期 → 加 TTL 抖动（±10%）、热点 key 逻辑不过期（异步刷新）、请求合并（singleflight——十万个「同一问题」在回源时只放一个去模型）；
2. **缓存穿透**：查不存在的 key 反复打到模型 → 空值也缓存（短 TTL）；
3. **缓存击穿**（和雪崩区别：雪崩是很多 key，击穿是一个热点 key）：singleflight + 逻辑过期；
4. **路由抖动**：分类器分数在阈值边缘震荡 → **滞回带**（p > 0.6 走强模型，p < 0.4 走弱模型，中间走弱模型+复核），防止同一个用户的前后两问被拆到不同质量档，体验跳变；
5. **降级**：缓存服务挂了 → 直接穿透到模型（缓存永远不挡主链路）；路由服务挂了 → 默认走强模型（贵但不出错）。**所有省钱系统的设计铁律：省钱路径可以挂，不能拖死主路径。**

### 2.7 模拟面试速答五连

1. **「设计一个 LLM 应用的语义缓存。」**——请求 → 意图规范化（去时间词、归一实体、锁 prompt 模板）→ embedding 检索 top-k（向量库或 Redis 模块）→ 相似度 > 0.95 且关键字段精确匹配 → 命中返回答案（记 hit）；否则调模型，答案带 TTL 写回（TTL 按意图类型分档）。键 = `{tenant, prompt_version, 规范化特征}`；命中率分桶监控；命中率 < 30% 说明规范化没做好或流量太发散，优先修 canonicalization 而不是换向量模型。
2. **「为什么不直接用 TTL 就够了？」**——TTL 管「答案多旧」，管不了「这个请求跟缓存里的请求是不是同一个问题」。语义等价判断才是命中率的本体；TTL 只是答案新鲜度的兜底。两者正交，都要。
3. **「LRU 和 LFU 放 LLM 缓存里各有什么问题？」**——纯 LRU：一次用户翻历史会话 = 扫描模式，把热点挤出去（抗扫描差）；纯 LFU：上午的热点下午还赖着（陈旧）。实践用 LFU 准入 + LRU 主体的混合（TinyLFU / 2Q），或带 TTL 的 LRU——**缓存策略要服务流量形状，流量形状由产品决定**。
4. **「prefix cache 和语义缓存能一起用吗？」**——能，且必须：L1 语义缓存命中直接省整次调用；未命中过 L2，L2 把「token 前缀相同的部分」的 prefill 算力省掉。串联：语义命中率 30% × 前缀命中率 70% → 实际只有 21% 的请求走全量 prefill。**两级命中率相乘才是真实成本，面试官要的就是这句乘法。**
5. **「缓存会不会带来安全问题？」**——会，三个面：①键设计漏字段 = 跨租户串答（最致命）；②命中/未命中的时序差 = 侧信道（某 prompt 是否最近被问过，cache_salt CVE 一族）；③恶意构造「缓存投毒」：反复发送相近 prompt 污染语义缓存，让后续用户拿到被污染的答案 → 写回路径要校验答案来源可信 + 敏感问题（涉及账户数据）禁缓存。**缓存层 = 信任边界，这句话在 Day 142 说过，今天再给一遍，因为缓存越值钱它越真。**

### 2.8 今日金句

> **「推理经济学只有三条：命中率是新的 QPS，路由是新的模型选型，缓存命中是全系统最便宜的算力。路由决定一个请求值多少钱，缓存决定它要不要花钱——把这两件事做对的系统，模型慢一档也能赢。」**
