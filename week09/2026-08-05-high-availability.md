## 📝 今日核心：为什么高可用不是"不宕机"，而是"宕机了也能快速恢复"

很多人聊高可用上来就是"我们要做到 99.999%"。但面试里真正加分的是：你能讲清楚**高可用的度量指标**、**容错设计原则**、以及**故障发生时的恢复策略**。高可用的本质不是消灭故障，而是**让故障的影响可控、可恢复、可预期**。

## 1. 高可用核心指标体系（面试必背）

### 1.1 SLA / SLO / SLI 傻傻分不清？

| 指标 | 全称 | 含义 | 例子 |
|------|------|------|------|
| **SLI** | Service Level Indicator | 可量化的服务质量指标 | HTTP 请求延迟 P99 < 200ms |
| **SLO** | Service Level Objective | 对 SLI 的目标承诺 | 延迟 P99 < 200ms 的达成率 ≥ 99.9% |
| **SLA** | Service Level Agreement | 对外商务合同，违反需赔偿 | 年度可用性 ≥ 99.95%，否则赔付 |
| **MTBF** | Mean Time Between Failures | 平均故障间隔时间 | 系统平均每 90 天出一次故障 |
| **MTTR** | Mean Time To Recovery | 平均恢复时间 | 故障后平均 15 分钟内恢复 |

**面试高频陷阱题**：
> "SLA 和 SLO 的区别是什么？"

答：**SLO 是内部目标，SLA 是对外承诺**。SLO 可以定得更严格（比如内部要求 99.99%，对外 SLA 只承诺 99.95%），给自己留buffer。违反 SLA 有商务赔偿，违反 SLO 是内部复盘。

### 1.2 可用性百分比换算（快速口算）

| 可用性 | 年停机时间 | 适用场景 |
|--------|-----------|---------|
| 99%（两个9）| 3.65 天 | 内部工具、非核心系统 |
| 99.9%（三个9）| 8.76 小时 | 普通电商、内容平台 |
| 99.99%（四个9）| 52.56 分钟 | 支付核心、金融系统 |
| 99.999%（五个9）| 5.26 分钟 | 电信级、航空订票 |

**面试话术**：
> "可用性不是越高越好，每多一个 9，成本是指数级上升的。我们的核心支付链路目标是四个 9（年停机 < 1 小时），而内部运营后台两个 9 就够了。关键是**根据业务重要性分级定目标**。

## 2. 高可用架构设计原则

### 2.1 六条核心原则

```
┌─────────────────────────────────────────────────────────────┐
│                    高可用架构六边形战士                        │
├─────────────────────────────────────────────────────────────┤
│  1. 冗余(Redundancy)     │  2. 故障隔离(Fault Isolation)   │
│  3. 限流降级(Degradation)│  4. 无状态(Stateless)           │
│  5. 自动恢复(Self-healing)│  6. 可观测性(Observability)    │
└─────────────────────────────────────────────────────────────┘
```

| 原则 | 设计要点 | 常见实现 |
|------|---------|---------|
| **冗余** | 多副本、多机房、多可用区 | 主从复制、集群部署、异地多活 |
| **故障隔离** | 故障不扩散、熔断降级 | 舱壁模式(Bulkhead)、断路器(Circuit Breaker) |
| **限流降级** | 保核心、弃边缘 | 限流器、开关降级、兜底逻辑 |
| **无状态** | 状态外置，节点可随意替换 | Session 存 Redis、配置存配置中心 |
| **自动恢复** | 故障自动检测 + 自动切换 | 健康检查、自动重启、K8s 自愈 |
| **可观测性** | 提前发现，快速定位 | 监控、日志、链路追踪 |

### 2.2 冗余设计的层次

```
应用层冗余:
  ┌─────────┐  ┌─────────┐  ┌─────────┐
  │ App-1   │  │ App-2   │  │ App-3   │  ← 无状态，水平扩展
  └────┬────┘  └────┬────┘  └────┬────┘
       └─────────────┼─────────────┘
                     ▼
              ┌─────────────┐
              │   Nginx/    │          ← 负载均衡层冗余
              │   Gateway   │
              └──────┬──────┘
                     ▼
数据层冗余:
  ┌─────────┐  ┌─────────┐  ┌─────────┐
  │ Master  │──│ Slave 1 │──│ Slave 2 │  ← 主从复制
  └─────────┘  └─────────┘  └─────────┘
       │
       ▼
  异地灾备中心 (异地机房)
```

## 3. 数据库高可用设计（面试超高频）

### 3.1 主从复制架构

```
┌─────────────┐     异步/半同步/同步复制      ┌─────────────┐
│   Master    │ ──────────────────────────> │   Slave 1   │  ← 读请求
│  (写 + 读)  │ ──────────────────────────> │   Slave 2   │  ← 读请求
└─────────────┘                             └─────────────┘
     │
     │  binlog 复制
     ▼
┌─────────────┐
│   Slave 3   │  ← 异地灾备（延迟复制，防误删）
└─────────────┘
```

| 复制模式 | 机制 | 一致性 | 性能 | 适用场景 |
|---------|------|--------|------|---------|
| **异步复制** | Master 不等待 Slave 确认 | 弱 | 最高 | 读多写少，容忍延迟 |
| **半同步复制** | 至少一个 Slave 确认 | 较强 | 中等 | 金融场景（MySQL 默认半同步插件） |
| **同步复制** | 所有 Slave 确认 | 强 | 最低 | 强一致性要求，极少用 |
| **组复制(MGR)** | Paxos 协议，多数派确认 | 强 | 中等 | MySQL 官方高可用方案 |

**面试陷阱题**：
> "主从延迟怎么解决？"

答三层思路：
> 1. **预防**：大事务拆小事务、避免在 Master 上做大量统计查询；
> 2. **检测**：监控 `Seconds_Behind_Master`，超过阈值告警；
> 3. **兜底**：读请求强制走 Master（牺牲性能保一致性）、或业务层容忍延迟（最终一致性）。

### 3.2 读写分离与分库分表

```
读写分离架构:
┌─────────────┐
│   业务应用   │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  Proxy/     │  ← 中间件：ShardingSphere、MyCat、Vitess
│  Middleware │     自动路由写请求到 Master，读请求到 Slave
└──────┬──────┘
   ┌───┴───┐
   ▼       ▼
┌──────┐ ┌──────┐
│Master│ │Slave │
└──────┘ └──────┘

分库分表:
┌─────────────────────────────────────────┐
│  用户表(user) → 按 user_id % 4 分片      │
│  user_0: user_id ∈ [0, 4, 8, ...]       │
│  user_1: user_id ∈ [1, 5, 9, ...]       │
│  user_2: user_id ∈ [2, 6, 10, ...]      │
│  user_3: user_id ∈ [3, 7, 11, ...]      │
└─────────────────────────────────────────┘
```

**分库分表带来的问题**：
| 问题 | 解决方案 |
|------|---------|
| 跨分片 JOIN | 避免 JOIN，业务层组装；或宽表反冗余 |
| 跨分片事务 | 分布式事务（Seata AT / Saga / TCC） |
| 分片扩容（2 片 → 4 片）| 一致性哈希 / 双倍扩容法 / 平滑迁移工具 |
| 全局唯一 ID | Snowflake / 号段模式 |
| 排序分页 | 各分片取 Top N，内存归并（性能差，避免深分页） |

## 4. 服务层高可用设计

### 4.1 无状态设计（Stateless）

```
有状态服务（难以扩展）:
┌─────────┐  Session  ┌─────────┐
│ 用户 A   │ ────────> │ Server 1│  ← 用户 A 必须打到 Server 1
└─────────┘  绑死     └─────────┘

无状态服务（任意节点可替换）:
┌─────────┐           ┌─────────┐
│ 用户 A   │ ────────> │ Server 1│
└─────────┘  Session  │   or    │  ← Session 在 Redis，任一节都可处理
            存 Redis   │ Server 2│
                       └─────────┘
```

**无状态设计 checklist**：
- [ ] 本地不存储业务数据（全部走 DB / 缓存）
- [ ] Session / Token 外置（Redis / JWT）
- [ ] 配置外置（配置中心 Nacos / Apollo）
- [ ] 日志外置（ELK / Loki，不存本地）
- [ ] 文件存储用对象存储（OSS / S3），不用本地磁盘

### 4.2 负载均衡与健康检查

```
                        ┌─────────┐
                   ┌───>│ Server 1│  Healthy ✅
                   │    └─────────┘
┌─────────┐       ┌┴┐   ┌─────────┐
│  Client  │─────>│LB├──>│ Server 2│  Healthy ✅
└─────────┘       └┬┘   └─────────┘
                   │    ┌─────────┐
                   └───>│ Server 3│  Unhealthy ❌ (自动摘除)
                        └─────────┘
```

**健康检查机制**：
| 类型 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **主动探测** | LB 定时发 HTTP/TCP 探测 | 发现故障快 | 探测流量有开销 |
| **被动探测** | 观察实际请求失败率 | 无额外流量 | 发现故障慢 |
| **多层次** | 网络层(TCP) + 应用层(HTTP) | 覆盖全面 | 实现复杂 |

### 4.3 熔断、降级、限流（面试三连击）

```
┌─────────────────────────────────────────────┐
│           流量洪峰来了！                      │
│                                              │
│   1. 限流（Rate Limiting）                   │
│      → 入口层拦下多余流量，保护系统           │
│      → "对不起，系统忙，请稍后再试"           │
│                                              │
│   2. 熔断（Circuit Breaker）                 │
│      → 下游服务挂了，不再调用，快速失败        │
│      → "下游炸了，我先自保"                   │
│                                              │
│   3. 降级（Degradation）                     │
│      → 保核心功能，非核心功能降级或关闭        │
│      → "推荐算法不跑了，先保证下单能走"       │
└─────────────────────────────────────────────┘
```

**熔断器三态**：
```
   ┌───────────┐    失败率 < 阈值    ┌───────────┐
   │  CLOSED   │──────────────────>│   OPEN    │
   │  (正常)   │    失败率 > 阈值    │  (熔断)   │
   └───────────┘                    └─────┬─────┘
        ▲                                 │ 超时后
        │                                 ▼
        └──────────────────────────┌───────────┐
         探测成功，关闭熔断          │ HALF-OPEN │
                                   │ (半开探测) │
                                   └───────────┘
```

**面试对比题**：
> "熔断和降级的区别是什么？"

答：**熔断是被动防御**——下游故障时自动切断调用，防止拖垮自己；**降级是主动取舍**——在资源不足时，主动关闭非核心功能，保核心链路。两者经常配合使用。

## 5. 多活架构设计（高级面试题）

### 5.1 架构演进路线

```
单机房                     同城双活                    异地多活
┌─────────┐              ┌─────────┐ ┌─────────┐      ┌─────────┐ ┌─────────┐ ┌─────────┐
│  机房 A  │              │  机房 A  │ │  机房 B  │      │  北京    │ │  上海    │ │  广州    │
│ (单点)  │      →       │  主     │ │  备     │  →   │  单元 1  │ │  单元 2  │ │  单元 3  │
└─────────┘              └─────────┘ └─────────┘      └─────────┘ └─────────┘ └─────────┘
                         同城延迟 < 2ms               异地延迟 30-50ms
                         数据同步快                    数据分区，就近访问
```

| 架构 | RTO（恢复时间）| RPO（数据丢失）| 成本 | 复杂度 |
|------|--------------|---------------|------|--------|
| **冷备** | 小时级 | 可能丢大量数据 | 低 | 低 |
| **热备** | 分钟级 | 少量丢失 | 中 | 中 |
| **同城双活** | 秒级~分钟级 | 接近 0 | 高 | 高 |
| **异地多活** | 秒级 | 0 | 极高 | 极高 |

### 5.2 异地多活核心挑战：数据一致性

```
用户 A 在北京单元下单（订单写入北京 DB）
用户 A 同时在上海查询订单（上海 DB 还没同步到）

→ 看到"订单不存在"？用户体验崩了

解决方案：用户绑定单元（Unitization）
┌─────────────────────────────────────────┐
│  user_id % 3 = 0 → 北京单元（固定）      │
│  user_id % 3 = 1 → 上海单元（固定）      │
│  user_id % 3 = 2 → 广州单元（固定）      │
│                                         │
│  同一用户读写都在同一单元，避免跨单元一致   │
│  性问题。不同用户数据不同单元，天然分区。   │
└─────────────────────────────────────────┘
```

**面试话术**：
> "异地多活最大的挑战不是技术，是**数据一致性**和**业务拆分**。我们通过'用户单元化'——按用户 ID 哈希固定路由到某个单元，保证同一用户的读写都在一个单元，避免跨单元一致性。全局数据（如商品库存）用强同步或集中式处理。"

## 6. 故障演练与混沌工程

### 6.1 为什么需要故意搞破坏？

> "你不会在火灾发生时才开始检查灭火器。"

**混沌工程原则**：在生产环境（或准生产）主动注入故障，验证系统的容错能力。

| 故障类型 | 注入方式 | 验证能力 |
|---------|---------|---------|
| **节点故障** | 随机 kill Pod/VM | 自动重启、负载均衡摘除 |
| **网络延迟** | tc 命令模拟 100ms 延迟 | 超时设置是否合理 |
| **网络分区** | 隔离部分节点网络 | 脑裂处理、一致性策略 |
| **CPU/内存满载** | stress 工具压测 | 资源限制、优雅降级 |
| **依赖故障** | 模拟 DB/Redis 宕机 | 熔断、降级、兜底逻辑 |

**面试加分项**：
> "我们每季度做一次'红蓝对抗'——蓝队防守，红队（混沌工程平台）随机注入故障。最近一次演练中，我们发现 Redis 主从切换时，有个服务因为连接池没配置超时，hang 了 30 秒。修复后 MTTR 从 15 分钟降到 3 分钟。"

## 💡 面试技巧

### 技巧 1：被问"你们系统可用性目标是多少"

不要只报数字，要分层说：
> "我们的可用性目标是分级的：
> - **核心支付链路**：99.99%（四个9），年停机 < 1 小时；
> - **订单/库存系统**：99.95%（三个9+），年停机 < 4.5 小时；
> - **内部运营后台**：99.5%（两个9+），容忍日维度维护窗口。
> 核心链路通过异地多活 + 自动故障切换保障，非核心通过热备 + 人工切换降低成本。"

### 技巧 2：被问"数据库挂了怎么办"

分层回答：
> 1. **预防**：主从复制 + 半同步复制 + 监控告警，提前发现；
> 2. **切换**：Orchestrator / MHA 自动主从切换，VIP 漂移，应用无感知；
> 3. **兜底**：如果主从都挂，启用异地灾备（延迟复制，可能丢几分钟数据），同时开启降级模式（只读或排队）；
> 4. **恢复**：故障节点修复后，重新加入集群，数据同步追平。

### 技巧 3：被问"怎么保证服务发布不影响可用性"

> "我们采用**滚动发布 + 蓝绿部署**结合：
> - **蓝绿部署**：新版本（绿）部署在独立环境，流量切 1% 验证，没问题再全量切；
> - **滚动发布**：逐个节点替换，保证始终有足够实例提供服务；
> - **发布窗口**：核心系统只在低峰期发布，保留快速回滚能力（镜像版本化 + 一键回滚）；
> - **健康检查**：新节点启动后通过 readiness probe 才接收流量。"

### 技巧 4：被问"设计一个高可用的电商系统"

回答框架（5 分钟讲清楚）：
> 1. **接入层**：DNS 轮询 / 智能 DNS 就近解析 + CDN 静态资源 + WAF 防攻击；
> 2. **网关层**：Nginx / Kong / Spring Cloud Gateway，负载均衡 + 限流 + 熔断；
> 3. **应用层**：无状态微服务，K8s 自动扩缩容，健康检查自动剔除故障 Pod；
> 4. **数据层**：MySQL 主从 + 读写分离，Redis Cluster，分库分表按用户 ID；
> 5. **容灾层**：同城双活（数据库同步复制）+ 异地冷备（定期快照）；
> 6. **可观测**：Prometheus + Grafana + PagerDuty，核心指标突增自动告警 + 自动扩容。

---

## 📌 一句话总结

> 高可用 = **度量清晰**（SLA/SLO/SLI）+ **冗余设计**（多副本、多机房）+ **故障隔离**（熔断、降级、限流）+ **自动恢复**（健康检查、自动切换）+ **可观测**（监控、告警、混沌演练）。面试能讲清楚这五层，高可用架构这关就过了。
