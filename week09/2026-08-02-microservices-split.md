## 今日主题

微服务架构不是银弹，**拆得不好不如不拆**。今天聊的是：怎么判断该不该拆？按什么维度拆？拆分后怎么保证不乱？

---

## 一、核心问题：要不要拆？

### 单体 vs 微服务的 trade-off

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 部署 | 一次打包，一键部署 | 多服务独立部署，CI/CD 复杂 |
| 故障隔离 | 一个 bug 全站挂 | 单服务故障可降级 |
| 扩展 | 整体扩容，资源浪费 | 按服务按需扩容 |
| 团队协作 | 代码冲突多 | 团队自治，接口契约约束 |
| 数据一致性 | 本地事务，简单 | 分布式事务，复杂 |

### 什么时候该拆？

1. **团队规模 > 康威定律临界点** — 一个代码库 30+ 人同时开发，merge 冲突爆炸
2. **发布耦合严重** — 改一行配置要全量发布
3. **扩展瓶颈明显** — 只有订单模块压力大，却要扩容整个应用
4. **技术栈需要异构** — 推荐系统用 Python，交易系统用 Go

### 什么时候不该拆？

- 团队 < 10 人，拆完运维成本扛不住
- 业务不稳定，领域边界天天变
- 没有成熟的 DevOps / 监控体系

> 经典翻车：**为拆而拆**，拆出 50 个微服务，结果 80% 的请求要跨 5 个服务，p99  latency 飙到 2s。

## 二、怎么拆？四种拆分策略

### 1. 按业务领域拆分（DDD Bounded Context）⭐ 首推

```
电商系统：
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ 用户服务 │  │ 商品服务 │  │ 订单服务 │  │ 库存服务 │
│ User   │  │ Product │  │ Order   │  │ Stock   │
└─────────┘  └─────────┘  └─────────┘  └─────────┘
      │            │            │            │
      └────────────┴────────────┴────────────┘
                    各自独立数据库
```

**判断标准：** 一个业务概念在哪个服务里是完整的？用户服务里的"用户"包含画像、等级、权限，不需要去别处拼数据。

### 2. 按读写拆分（CQRS）

读模型和写模型分离，适合读多写少、查询模式复杂的场景：

```
    写请求 → 订单服务 → MySQL（事务性存储）
                              ↓
                         异步同步（Binlog / MQ）
                              ↓
    读请求 → 查询服务 → Elasticsearch / ClickHouse
```

### 3. 按功能层级拆分

```
┌─────────────┐
│   API 网关   │  ← 接入层：鉴权、限流、路由
├─────────────┤
│  聚合服务层  │  ← BFF：面向端适配，聚合下游
├─────────────┤
│  核心服务层  │  ← 业务域：用户、订单、库存...
├─────────────┤
│  基础服务层  │  ← 支撑：消息、搜索、推荐...
└─────────────┘
```

### 4. 避免的错误拆分方式

| 错误方式 | 后果 |
|---------|------|
| 按 CRUD 拆（一个表一个服务） | 过度拆分，全是 RPC 调用 |
| 按团队政治拆（谁强势谁独占） | 边界混乱，数据冗余 |
| 拆完共享数据库 | 假的微服务，真的分布式单体 |

## 三、拆分后的核心挑战

### 1. 服务间通信

**同步（REST / gRPC）：** 简单直观，但级联故障风险高

**异步（消息队列）：** 解耦、削峰，但要处理最终一致性、幂等、消息乱序

```python
# 面试常问：怎么选同步还是异步？
# 口诀：实时读用同步，状态变更用异步

# 订单创建 → 同步：用户要立刻看到结果
# 订单创建 → 异步发通知：用户晚几秒收到短信没关系
```

### 2. 数据一致性

拆分后每个服务独占数据库，**本地事务变成分布式事务**。

常用方案：
- **Saga 模式**：事务拆成本地事务 + 补偿，适合长流程（Day 56 已讲）
- **最终一致性 + 幂等**：业务层面接受延迟一致，用消息队列 + 去重表

```python
# 幂等实现示例：去重表
# 请求带唯一 ID（如 order_id + 操作类型）
# 先 insert 去重表，冲突则直接返回上次结果

def create_order(request_id, order_data):
    try:
        idempotency_record = db.execute(
            "INSERT INTO idempotency_keys (request_id, result) VALUES (?, ?)",
            request_id, "PENDING"
        )
    except DuplicateKey:
        # 已处理过，直接返回缓存结果
        return get_cached_result(request_id)
    
    # 执行业务逻辑
    order = do_create_order(order_data)
    db.execute("UPDATE idempotency_keys SET result = ? WHERE request_id = ?",
               json.dumps(order), request_id)
    return order
```

### 3. 服务发现与治理

```
服务注册中心（Consul / Nacos / etcd）
    │
    ├── 服务注册：启动时上报地址
    ├── 服务发现：消费者拉取可用实例
    └── 健康检查：剔除故障节点
```

### 4. 链路追踪

一个请求跨 5 个服务，出问题了怎么定位？

```
# 分布式追踪核心：Trace ID + Span

请求入口 → 生成 Trace ID: abc123
    │
    ├── 网关层    Span: gateway   (耗时 5ms)
    ├── 用户服务   Span: user      (耗时 15ms)
    ├── 订单服务   Span: order     (耗时 80ms) ← 慢！
    │   └── 库存服务 Span: stock   (耗时 60ms)
    └── 支付服务   Span: payment   (耗时 200ms) ← 更慢！

可视化：瀑布图一眼看出瓶颈在哪
```

## 四、面试高频问题

### Q1：你们是怎么做微服务拆分的？

**好的回答结构：**
1. 先讲背景：团队规模、痛点（发布慢、扩展难）
2. 拆分依据：DDD 领域分析，识别 bounded context
3. 演进过程：先粗后细，先拆分最核心的域
4. 治理配套：CI/CD、监控、链路追踪同步建设

**加分项：** 提到"我们一开始拆太细了，后来合并了 3 个服务"

### Q2：单体迁移到微服务，怎么平滑过渡？

**绞杀者模式（Strangler Fig Pattern）：**
```
┌─────────────┐
│   新 API 网关 │
├──────┬──────┤
│ 新服务 │ 单体 │  ← 逐步将流量路由到新服务
│ 订单  │ 老系统│
└──────┴──────┘
      ↓
老功能逐步从单体"绞杀"出来
```

### Q3：微服务调用失败了怎么办？

**三级防护：**
1. **超时设置** — 每个调用必须有超时，默认无限等待 = 自杀
2. **重试 + 退避** — 指数退避避免惊群，幂等保证安全重试
3. **熔断降级** — 失败率达到阈值自动熔断，走降级逻辑（返回缓存、默认值）

```python
# 熔断器伪代码（基于失败率）
class CircuitBreaker:
    CLOSED = "closed"      # 正常
    OPEN = "open"          # 熔断，拒绝请求
    HALF_OPEN = "half_open" # 试探
    
    def call(self, func):
        if self.state == OPEN:
            if time.now() - self.last_failure < self.cooldown:
                raise CircuitBreakerOpen()
            self.state = HALF_OPEN
        
        try:
            result = func()
            self.on_success()
            return result
        except Exception as e:
            self.on_failure()
            raise
```

## 五、面试技巧

### 1. 不要上来就"我们用微服务"

面试官听到"微服务"会立刻警觉：
- 是真的需要，还是跟风？
- 拆了多少个？运维跟得上吗？

**安全开场：** "我们团队 40 人的时候，单体发布一次要 2 小时回滚窗口，才开始拆的。"

### 2. 强调"演进"而非"设计"

好的回答不是"我设计了一套完美的架构"，而是：
- "第一版是单体，因为业务不确定"
- "用户量到 10w 时，订单模块 CPU 飙到 90%，先把它拆出来"
- "后来发现拆太细，又把评论和点赞合并了"

这体现的是**工程判断力**，不是背架构图。

### 3. 准备"翻车"故事

面试官最爱听的是：
> "我们一开始每个服务一个数据库，但发现用户服务和订单服务都要查用户等级，同步数据延迟导致订单价格算错。后来把用户等级做了冗余，但更新时要发消息同步……"

这说明你真的踩过坑，不是纸上谈兵。

### 4. 把"微服务"和"高可用"挂钩

不要只讲拆分，要讲**拆分后怎么保证可用性**：
- 熔断降级策略
- 多活部署
- 故障演练（Chaos Engineering）

## 六、今日一题：系统设计 — 电商系统微服务拆分

**题目：** 设计一个电商系统的微服务架构，要求：
1. 识别核心业务域
2. 说明服务间通信方式（同步/异步场景）
3. 处理订单创建时的数据一致性
4. 说明降级策略

**参考答案要点：**

**业务域划分：**
- 用户域（User Service）— 注册、登录、用户信息
- 商品域（Product Service）— 商品信息、分类、搜索
- 订单域（Order Service）— 订单生命周期
- 库存域（Inventory Service）— 库存扣减、预占
- 支付域（Payment Service）— 支付、对账
- 营销域（Promotion Service）— 优惠券、满减

**通信方式：**
```
下单流程：
用户 → API Gateway → Order Service
                         │
        ┌────────────────┼────────────────┐
        ↓同步(RPC)       ↓同步(RPC)       ↓异步(MQ)
   Inventory Service  Promotion Service  Payment Service
   （扣库存，失败则    （算价格，失败     （发起支付，
    订单创建失败）      降级为原价）        异步回调）
                         │
                    订单创建成功
                         ↓异步(MQ)
                   发送订单创建事件
                   → 短信服务、物流服务、数据分析
```

**数据一致性：**
- 订单 + 库存：同步调用，库存扣失败则订单创建失败（强一致）
- 订单 + 支付：异步，支付回调更新订单状态（最终一致）
- 订单创建 → 后续处理：MQ 异步，消费失败可重试

**降级策略：**
- 营销服务挂了 → 不参与计算，原价购买（有损降级）
- 库存服务挂了 → 开启"无库存模式"，允许超卖后人工处理（业务兜底）
- 推荐服务挂了 → 返回热门榜单（静态降级）

## 七、一句话总结

> 微服务拆分的本质是**组织问题**，不是技术问题。DDD 给了拆分的理论依据，但落地时要配合团队结构、CI/CD 成熟度、监控体系一起演进。记住：**先解决为什么要拆，再解决怎么拆。**
