## 📝 今日核心：容灾不是"备份数据"，而是"业务能活多久"

很多人一聊容灾就是"我们每天晚上全量备份"。但面试里真正区分你段位的，是你能不能讲清楚：**RTO 和 RPO 怎么定**、**不同业务该选什么容灾等级**、以及**故障发生后那黄金 30 分钟怎么操作**。容灾的本质不是备份，是**业务连续性**——灾难来了，你的系统能不能在承诺的时间内恢复，丢失的数据能不能控制在承诺的范围内。

## 1. 容灾核心指标：RTO & RPO（面试必背）

### 1.1 两个指标决定容灾成本

```
灾难发生时刻 ──────────────────────────────────────> 业务恢复
         │              │                         │
         ▼              ▼                         ▼
    数据丢失点     系统恢复点                  完全恢复
    (RPO)          (RTO)
    
RPO = Recovery Point Objective（恢复点目标）
     → 你能容忍丢多少数据？
     → 例：RPO = 15分钟 → 灾难发生时最多丢15分钟的数据
     
RTO = Recovery Time Objective（恢复时间目标）
     → 你能容忍停多久业务？
     → 例：RTO = 30分钟 → 灾难发生后30分钟内必须恢复服务
```

| 指标 | 含义 | 决定因素 | 降低手段 |
|------|------|---------|---------|
| **RPO** | 数据丢失量 | 备份频率、复制延迟 | 实时复制、增量同步、双写 |
| **RTO** | 业务恢复时间 | 自动化程度、预案成熟度 | 自动切换、蓝绿部署、热备 |

**面试高频对比题**：
> "RPO 和 RTO 的区别？给一个电商订单系统的例子。"

答：
> "RPO 问的是**丢多少数据我能接受**，RTO 问的是**停多久我能接受**。
> 
> 比如电商订单系统：
> - **RPO 必须 ≈ 0**：订单数据丢了就是钱丢了，用户付完钱订单没了，这是 P0 事故。所以订单数据要实时同步，RPO 接近 0。
> - **RTO 可以是分钟级**：订单系统挂了，30 分钟内切到灾备中心恢复，用户可能抱怨但还能接受。如果 RTO 是小时级，那流失的订单和客诉就不可控了。
> 
> 对比日志系统：日志丢了就丢了，RPO 可以是小时级甚至天级；RTO 也无所谓，日志服务挂了不影响交易。"

### 1.2 不同业务的 RTO/RPO 分级

```
┌─────────────────────────────────────────────────────────────┐
│                    业务分级容灾标准                           │
├─────────────────────────────────────────────────────────────┤
│  P0 核心业务（支付/订单） │  RPO ≈ 0     │  RTO < 5min    │
│  P1 重要业务（用户系统）   │  RPO < 1min  │  RTO < 30min   │
│  P2 一般业务（推荐/搜索）  │  RPO < 1h    │  RTO < 4h      │
│  P3 后台业务（报表/运营）  │  RPO < 1d    │  RTO < 24h     │
└─────────────────────────────────────────────────────────────┘
```

**面试加分项**：
> "我们内部有一套容灾分级矩阵，P0 业务要求同城双活（RPO≈0, RTO<5min），P1 要求热备自动切换（RPO<1min, RTO<30min），P2 温备人工切换（RPO<1h, RTO<4h），P3 冷备定期备份（RPO<1d, RTO<24h）。这样成本花在刀刃上，不搞一刀切。"

## 2. 容灾架构等级（面试核心考点）

### 2.1 五级容灾架构

```
Level 1: 本地备份（Backup）
         ┌─────────┐
         │ 生产环境 │──> 本地磁盘/磁带备份
         └─────────┘
         RTO: 天级  RPO: 天级  成本: 低

Level 2: 异地备份（Off-site Backup）
         ┌─────────┐                    ┌─────────┐
         │ 生产环境 │──定期备份──>│ 异地存储 │
         └─────────┘                    └─────────┘
         RTO: 小时~天级  RPO: 天级  成本: 低

Level 3: 冷备（Cold Standby）
         ┌─────────┐                    ┌─────────┐
         │ 生产环境 │──数据同步──>│ 冷备环境 │（关机/最低配置运行）
         └─────────┘                    └─────────┘
         RTO: 小时级  RPO: 分钟~小时级  成本: 中

Level 4: 温备（Warm Standby）
         ┌─────────┐                    ┌─────────┐
         │ 生产环境 │──实时同步──>│ 温备环境 │（运行中，但不接流量）
         └─────────┘                    └─────────┘
         RTO: 分钟级  RPO: 分钟级  成本: 中高

Level 5: 热备/双活（Hot Standby / Active-Active）
         ┌─────────┐   实时双向同步   ┌─────────┐
         │ 机房 A  │◄─────────────►│ 机房 B  │（同时接流量）
         └─────────┘                └─────────┘
         RTO: 秒级~分钟级  RPO: ≈0  成本: 极高
```

| 等级 | 名称 | RTO | RPO | 适用场景 | 年成本（相对生产） |
|------|------|-----|-----|---------|-----------------|
| L1 | 本地备份 | 天级 | 天级 | 开发测试环境 | 5% |
| L2 | 异地备份 | 小时~天级 | 天级 | 非核心数据 | 10% |
| L3 | 冷备 | 小时级 | 分钟~小时级 | 后台系统 | 30% |
| L4 | 温备 | 分钟级 | 分钟级 | 重要业务 | 60% |
| L5 | 热备/双活 | 秒级~分钟级 | ≈0 | 核心支付/金融 | 100~200% |

### 2.2 各等级详解

#### 冷备（Cold Standby）

```
灾难前：
┌─────────┐         ┌─────────┐
│ 生产环境 │  运行   │ 冷备环境 │  关机/最低配
│ (100%)  │ ─────> │  (0%)   │
└─────────┘         └─────────┘

灾难后（手动启动）：
┌─────────┐         ┌─────────┐
│ 生产环境 │  挂了   │ 冷备环境 │  手动扩容启动
│  (挂)   │         │ (100%)  │
└─────────┘         └─────────┘
         RTO: 1~4小时（启动机器+恢复数据+切换DNS）
```

**适用**：企业内部系统、后台管理、非核心服务。
**缺点**：RTO 太长，故障后手动操作多，容易出错。

#### 温备（Warm Standby）

```
平时：
┌─────────┐    实时复制     ┌─────────┐
│ 生产环境 │ ────────────> │ 温备环境 │  运行中，不接流量
│ (100%)  │               │  (20%)  │  最小规模保持热乎
└─────────┘               └─────────┘

故障时（自动/半自动切换）：
┌─────────┐               ┌─────────┐
│ 生产环境 │     挂了      │ 温备环境 │  自动扩容到100%
│  (挂)   │               │ (100%)  │  DNS/VIP切换
└─────────┘               └─────────┘
         RTO: 5~30分钟
```

**适用**：大多数互联网公司的核心业务。
**典型方案**：数据库主从 + 应用层热备（K8s 集群双机房部署，备机房 Pod 数较少，故障时 HPA 自动扩容）。

#### 热备 / 双活（Hot Standby / Active-Active）

```
平时：两个机房同时接流量
┌─────────┐    双向同步     ┌─────────┐
│ 机房 A  │ ◄───────────► │ 机房 B  │
│ (50%)   │               │ (50%)   │
└─────────┘               └─────────┘

A 机房故障：
┌─────────┐               ┌─────────┐
│ 机房 A  │     挂了      │ 机房 B  │  自动接管100%
│  (挂)   │               │ (100%)  │  DNS剔除A，流量全切B
└─────────┘               └─────────┘
         RTO: 秒级~分钟级
```

**适用**：金融、支付、航空订票等强一致要求场景。
**代价**：数据同步复杂、网络延迟敏感、开发改造成本高。

## 3. 数据备份策略（面试常问细节）

### 3.1 三种备份类型

| 类型 | 机制 | 备份时间 | 恢复时间 | 存储空间 | 适用场景 |
|------|------|---------|---------|---------|---------|
| **全量备份** | 备份全部数据 | 长 | 短 | 大 | 每周/每月一次，作为基线 |
| **增量备份** | 只备份上次备份后变化的数据 | 短 | 长（需链式恢复） | 小 | 每日执行，节省空间 |
| **差异备份** | 备份上次全量后变化的数据 | 中 | 中（只需全量+最后一次差异） | 中 | 折中方案 |

```
全量 + 增量（常见方案）：
Day 1: [全量备份: 100GB] ──────────────────────────────────
Day 2: [增量: +2GB] ──────> 基于 Day 1
Day 3: [增量: +1GB] ──────> 基于 Day 2
Day 4: [增量: +3GB] ──────> 基于 Day 3
...
Day 7: [全量备份: 105GB] ──────────────────────────────────（新的开始）

恢复时需：Day 1 全量 + Day 2 增量 + Day 3 增量 + Day 4 增量...（链式恢复，慢）

全量 + 差异（折中方案）：
Day 1: [全量: 100GB] ──────────────────────────────────────
Day 2: [差异: +2GB] ──────> 基于 Day 1 全量
Day 3: [差异: +3GB] ──────> 基于 Day 1 全量（包含 Day 2 的变化）
Day 4: [差异: +5GB] ──────> 基于 Day 1 全量（包含 Day 2+3 的变化）

恢复时需：Day 1 全量 + Day 4 差异（只需两个文件，快）
```

**面试话术**：
> "我们采用'**全量 + 增量**'组合：每周日全量备份，每天凌晨增量备份。恢复时最坏情况要链式应用 6 个增量文件，但我们做了**增量合并**——每周三自动把前半周的增量合并成一个差异备份，这样恢复时最多只需全量 + 1 个合并增量 + 1~2 个日增量，RTO 从 4 小时降到 1 小时。"

### 3.2 数据库备份的特殊考量

**MySQL 备份方案**：
```
┌─────────────────────────────────────────────────────────────┐
│                  MySQL 多层备份策略                          │
├─────────────────────────────────────────────────────────────┤
│  层1: binlog 实时流式备份  →  RPO ≈ 0（几乎不丢数据）        │
│  层2: 每日凌晨物理备份(xtrabackup) → RPO < 24h              │
│  层3: 每周全量逻辑备份(mysqldump) → 长期归档，防备份损坏     │
│  层4: 跨地域复制(异地从库) → 机房级灾难恢复                  │
└─────────────────────────────────────────────────────────────┘
```

**binlog 备份为什么重要？**
> binlog 是 MySQL 的**操作日志**，记录了所有写操作。即使凌晨的全量备份丢了，只要有完整的 binlog，就能恢复到任意时间点（Point-in-Time Recovery）。

```sql
-- 基于 binlog 的 PITR（时间点恢复）
-- 1. 恢复凌晨全量备份
mysql < full_backup.sql

-- 2. 应用 binlog 到故障前的那一刻
mysqlbinlog --start-datetime="2026-08-06 00:00:00" \
            --stop-datetime="2026-08-06 14:23:00" \
            binlog.0001 binlog.0002 | mysql
```

### 3.3 快照与持续数据保护（CDP）

```
传统备份 vs 快照 vs CDP:

传统备份:  每天凌晨 2:00 备份 ──○──────○──────○──────○──
           故障时丢 0~24h 数据
           
存储快照:  ──○─○─○─○─○─○─○─○─○─○─○─○─○─○─○─○─○─○──
           每小时/每15分钟一个快照
           故障时丢 0~1h 数据
           
CDP:      ─██████████████████████████████████████████─
           持续记录每个写操作
           故障时丢 0~秒级数据（RPO ≈ 0）
```

| 技术 | RPO | 实现方式 | 成本 |
|------|-----|---------|------|
| 传统备份 | 小时~天级 | mysqldump/xtrabackup | 低 |
| 存储快照 | 分钟~小时级 | LVM/ZFS/云盘快照 | 中 |
| 半同步复制 | 秒级 | MySQL Semi-sync | 中 |
| **CDP** | **秒级~0** | 专用存储设备/软件 | 高 |

## 4. 故障切换与恢复流程（面试加分项）

### 4.1 标准故障响应 SOP

```
┌─────────────────────────────────────────────────────────────┐
│              故障恢复黄金 30 分钟 SOP                         │
├─────────────────────────────────────────────────────────────┤
│  T+0min   │ 告警触发（PagerDuty/钉钉/电话）                  │
│           │ → On-Call 工程师确认，启动 War Room              │
│                                                             │
│  T+1min   │ 快速定位：监控 Dashboard → 定位故障域             │
│           │ → 判断：是局部故障还是机房级灾难？                 │
│                                                             │
│  T+3min   │ 局部故障：自动/手动熔断、降级、扩容               │
│           │ 机房级灾难：启动容灾切换预案                       │
│                                                             │
│  T+5min   │ 数据层切换：DNS/VIP 切到灾备中心                  │
│           │ 应用层切换：K8s 流量切到备机房                    │
│           │ 网络层切换：BGP 宣告灾备 IP 段                    │
│                                                             │
│  T+10min  │ 验证：核心链路回归测试（下单/支付/登录）           │
│           │ → 如果异常，回滚！                              │
│                                                             │
│  T+15min  │ 通知：客服/运营/管理层，发布故障公告               │
│           │ → 透明沟通，管理用户预期                          │
│                                                             │
│  T+30min  │ 复盘准备：收集日志、时间线、影响面数据             │
│           │ → 24h 内产出初步复盘报告                          │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 数据库故障切换

**MySQL 主从切换（MHA / Orchestrator）**：
```
正常状态:
┌─────────┐  半同步复制   ┌─────────┐
│ Master  │ ──────────> │ Slave 1 │
│ (写+读) │ ──────────> │ Slave 2 │
└─────────┘             └─────────┘

Master 故障:
┌─────────┐             ┌─────────┐
│ Master  │     挂了     │ Slave 1 │──Orchestrator──┐
│  (挂)   │             │ (候选)  │   自动提升为主   │
└─────────┘             └─────────┘                │
                         ▲                        │
                         └────────────────────────┘
                         
切换后:
┌─────────┐             ┌─────────┐
│ (待修复) │             │ New     │
│ Old     │ ──修复后──> │ Master  │
│ Master  │  作为从库   │ (原Slave1)│
└─────────┘             └─────────┘
```

**面试陷阱题**：
> "主从切换后，数据不一致怎么办？"

答三层思路：
> 1. **预防**：用半同步复制（至少一个从库确认），确保切换时从库数据基本追平；
> 2. **检测**：切换前 Orchestrator 会检查从库的 `Seconds_Behind_Master`，延迟过大时拒绝自动切换，改人工介入；
> 3. **兜底**：如果已经切换且发现不一致，用 pt-table-checksum 比对差异，pt-table-sync 修复，或者从 binlog 里找到丢失的数据手动补偿。

## 5. 业务连续性设计（进阶考点）

### 5.1 降级与兜底设计

容灾不只是"切到备机房"，还要考虑**备机房也扛不住全量流量**怎么办。

```
正常状态:                    灾备状态（备机房容量只有 50%）：
┌─────────┐                ┌─────────┐
│ 机房 A  │──100%流量──>   │ 机房 B  │──只能扛 50%流量──
│ (100%)  │                │ (50%)   │
└─────────┘                └─────────┘

解决方案：分级降级
┌─────────────────────────────────────────────────────────────┐
│  流量打到机房 B（50%容量）+ 自动降级策略                      │
├─────────────────────────────────────────────────────────────┤
│  100% 流量 → 核心链路（下单/支付）正常服务                    │
│   80% 流量 → 非核心（推荐/搜索）限流或关闭                    │
│   50% 流量 → 运营后台、报表系统完全关闭                       │
│    0% 流量 → 大数据计算、离线任务暂停                         │
└─────────────────────────────────────────────────────────────┘
```

**面试话术**：
> "容灾切换不是简单的'流量切过去'，要配套**分级降级预案**。我们的备机房平时只跑 30% 的 Pod，故障时 HPA 扩容到 100% 需要 5 分钟。在这 5 分钟的窗口期，自动降级引擎会关闭非核心服务，把资源全部让给支付和订单，保证核心业务不崩。"

### 5.2 混沌工程验证容灾能力

```
你不验证，就不知道容灾方案是不是纸面方案。

混沌工程实验：
┌─────────────────────────────────────────────────────────────┐
│  实验 1: 随机 kill 主库 Pod                                  │
│  → 验证：Orchestrator 能否 30 秒内自动切换？                  │
│  → 验证：应用连接池是否有重连机制？                           │
│                                                             │
│  实验 2: 模拟整个可用区网络隔离                              │
│  → 验证：K8s 是否自动把流量切到其他可用区？                   │
│  → 验证：有状态服务（如 Redis）是否能正确故障转移？           │
│                                                             │
│  实验 3: 数据库主从延迟 10 秒                                │
│  → 验证：读写分离场景下，用户刚下单查不到订单？               │
│  → 验证：业务层是否有'写后读'走主库的保护逻辑？               │
└─────────────────────────────────────────────────────────────┘
```

## 💡 面试技巧

### 技巧 1：被问"你们怎么做容灾"

不要一上来就说技术细节，先讲**分级策略**：
> "我们的容灾是**分层分级**的：
> - **数据层**：MySQL 主从半同步复制 + 异地从库延迟复制（防误删）+ 每日 xtrabackup 物理备份 + binlog 实时归档；
> - **应用层**：双机房 K8s 部署，无状态服务任意节点可替换；
> - **网络层**：BGP Anycast + 智能 DNS，故障时自动剔除异常机房；
> - **预案层**：每个 P0 系统有标准化的 Runbook，切换操作全部自动化，人工只需点'确认'。
> 
> 容灾目标是：**P0 业务 RPO≈0，RTO<5min；P1 业务 RPO<1min，RTO<30min。**"

### 技巧 2：被问"如果整个机房挂了怎么办"

分层回答，展示你对不同级别灾难的处理能力：
> "我们区分**可用区故障**和**机房级故障**：
> - **可用区故障**（单个 AZ 网络中断）：K8s 自动把 Pod 漂到其他 AZ，数据库用跨 AZ 主从，30 秒内自动切换，用户基本无感知；
> - **机房级故障**（整个数据中心断电）：启动**异地灾备切换**，DNS 切到备机房，数据库提升从库为主库，5 分钟内恢复核心链路。代价是可能丢几秒数据（异步复制的固有问题），但交易类数据走半同步，基本不丢；
> - **城市级灾难**（地震/洪水）：异地冷备，RTO 小时级，RPO 分钟级，人工介入恢复。"

### 技巧 3：被问"备份了就能恢复吗？你验证过吗"

这是面试官在挖坑，很多人备份了从来没恢复过：
> "我们每季度做一次**备份恢复演练**：
> - 随机选一个备份文件，在隔离环境完整恢复；
> - 验证恢复后的数据完整性和一致性（checksum 比对）；
> - 验证恢复后的系统能正常接流量（影子流量测试）。
> 
> 去年 Q2 演练时发现一个增量备份链中间文件损坏，导致无法恢复。从那以后我们加了**备份校验 Job**，每次备份完成后自动做恢复测试，确保备份可用。"

### 技巧 4：被问"设计一个金融系统的容灾方案"

> "金融系统的核心要求是**RPO=0，RTO<1min**，所以必须走**同城双活 + 异地灾备**三层架构：
> 
> 1. **同城双活**：两个机房同时接流量，数据库用同步复制（MySQL Group Replication 或 Paxos 协议），确保两个机房数据实时一致。任何一个机房挂了，另一个机房瞬间接管，RPO=0，RTO<1min；
> 2. **异地灾备**：第三个城市做异步复制，防同城灾难（地震、洪水）。数据有秒级延迟，RPO<1min，RTO<30min；
> 3. **备份兜底**：每日全量 + 实时 binlog 归档，极端情况下可从备份恢复，RPO 取决于最后一次 binlog 归档；
> 4. **混沌演练**：每月一次红蓝对抗，随机注入机房级故障，验证切换预案。"

---

## 📌 一句话总结

> 容灾设计 = **RTO/RPO 先定级**（不拍脑袋）+ **架构分层**（数据/应用/网络）+ **备份有策略**（全量+增量+binlog）+ **切换自动化**（Runbook + 一键切换）+ **定期演练**（混沌工程 + 恢复验证）。面试能讲清楚这五层，容灾这关就过了。
