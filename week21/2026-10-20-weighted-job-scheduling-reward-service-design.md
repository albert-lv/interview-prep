## 🧩 今日算法题：规划兼职工作（Maximum Profit in Job Scheduling, LC 1235）

### 题目描述

给定 `n` 份工作，每份工作有 `[startTime[i], endTime[i], profit[i]]` 三元组（开始时间、结束时间、报酬）。同一时间只能做一份工作（不可重叠），返回能获得的最大总报酬。约束：`1 <= n <= 5×10⁴`。

```
输入: startTime = [1,2,3,3], endTime = [3,4,5,6], profit = [50,10,40,70]
输出: 120
解释: 选工作 1 [1,3] + 工作 4 [3,6]，50 + 70 = 120（3 点结束 3 点开始不冲突）
```

**工程语境包装**：这就是 **reward service 的 judge 评测调度内核**（Day 136 伏笔回收：小米 MiMo 成本账里 Grader 占 12.7%、与训练同价）。reward service 有一池昂贵的 LLM judge，每个「送轨迹去深度评审」的请求是 job：**占用 judge 一段时间窗**（评审长轨迹 10~60 秒）、带来**信息增益 profit**（这条轨迹的 reward 从猜测变确定，训练信号价值）。judge 并发池有限 → **预算约束下选哪些轨迹送深度评审，总信号最大** = 今天的加权区间调度。同构场景：GPU 任务调度里的抢占窗口选择、会议室收益最大化、广告位排期——本质都是「**有限资源上选价值最大的互不冲突集合**」。

### 解题思路：按结束时间排序 + 二分找前驱 + DP

**为什么不能贪心**（面试官第一问）：无权重区间调度（Day 1050/435 无重叠区间）选「最早结束」是对的；**有权重就失效**。反例：`[1,10] profit=100` vs `[1,2]+[2,10] 各 profit=60`。最早结束贪心会选 `[1,2]` 然后链上 `[2,10]`（120 > 100 此例碰巧对），换个数：`[1,4] p=50`、`[3,5] p=10`、`[5,9] p=50`——最早结束选 `[1,4]`+`[5,9]`=100，而 `[3,5]`+前后缀可能有更优组合。核心是：**贪心只看局部结束时间，不知道牺牲掉的长 job 值多少**——权重信息必须靠 DP 全局面。

**正解三步**：

1. **按结束时间升序排序**。DP 状态定义 `dp[i]` = 只考虑前 i 份工作（按结束时间序）的最大报酬；
2. **转移方程**（选 or 不选）：
   ```
   dp[i] = max(
       dp[i-1],                          # 不选第 i 份：继承前缀最优
       profit[i] + dp[p(i)]              # 选第 i 份：p(i) + 报酬
   )
   ```
   其中 `p(i)` = 结束时间 ≤ startTime[i] 的**最后一个工作下标**（0-indexed 世界里就是「最后一个兼容的前驱」）；
3. **p(i) 用二分**：在排序后的 endTime 数组上 `bisect_right(endTime, startTime[i]) - 1`，O(log n)。这一步是 Day 875/1482/1011/410「**二分四件套**」的同门手法——**对「最后一个 ≤ target」的二分，背熟 bisect 语义不现场造轮子**。

```python
from bisect import bisect_right
from typing import List

class Solution:
    def jobScheduling(self, startTime: List[int],
                      endTime: List[int], profit: List[int]) -> int:
        jobs = sorted(zip(startTime, endTime, profit), key=lambda x: x[1])
        ends = [j[1] for j in jobs]
        n = len(jobs)
        dp = [0] * (n + 1)                    # dp[i] = 前 i 份工作的最大报酬
        for i in range(1, n + 1):
            s, e, p = jobs[i - 1]
            j = bisect_right(ends, s, 0, i - 1)  # 前驱：结束 <= s 的个数
            dp[i] = max(dp[i - 1],              # 不选 i-1
                        dp[j] + p)               # 选 i-1，接在前驱最优上
        return dp[n]
```

**细节坑**（面试主动说加分）：
- `bisect_right(ends, s, 0, i-1)` 的右界限到 `i-1`：排除自己（自己的工作 end > start 必然不兼容，写上更严谨，不写也过）；
- **先排序后一切**——排序把二维冲突关系折叠成「下标序 = 时间序」，这是全题的灵魂，和 Day 134 Pareto「排序+扫描消除半序」同一手法；
- 排序的稳定性无所谓，但 key 必须是 endTime；若面试官追问「按 startTime 排行不行」——不能，转移时需要「所有兼容工作的最右位置」，只有 endTime 序保证前缀 = 时间前缀。

### 进阶：输出方案 + 空间优化 + 边界

- **输出选了哪些 job**：加 parent 指针 `take[i] = j`，`dp[i]` 取「选」分支时记 `choice[i]=True`，结束后从 n 回溯（与 Day 132 前驱集合回溯同手法）。工程版输出 = judge 调度日志：哪条轨迹进了深度评审、哪条被规则判据直接放过；
- **滚动数组**：`dp[j]` 永远 ≤ `dp[i-1]` 维度？不行——j 是任意前驱，**必须保留全量 dp 数组** O(n)。但可改用「list 替代 dict」的内层优化，空间 O(n) 已是最优；
- **利润可为负**：max 自带豁免，不影响正确性；若题目要求「至少选一份」，初值用 −∞ 而非 0 即可。

### 复杂度分析

| 方案 | 时间 | 空间 | 说明 |
|---|---|---|---|
| 排序 + 二分 + DP | **O(n log n)** | O(n) | 面试标准答 |
| 暴力 DP O(n²) | O(n²) | O(n) | n≤5×10⁴ 必 TLE，只说思路 |
| 线段树优化 | O(n log n) | O(n) | 重复区间查询场景才划算，本题杀鸡用牛刀 |

### 面试官连环问（judge 调度器视角）

**Q1：为什么是二分不是线性扫？** → 因为 p(i) 的查询是「排序数组里最后一个 ≤ target」，`bisect_right` 一次 O(log n)；5×10⁴ × 5×10⁴ 线性扫是 2.5×10⁹ 必 TLE。二分四件套（875 爱吃香蕉/1482 制作 m 束花/1011 船运/410 分割数组）同手法，现场提一句 = 刷题量可视。

**Q2：judge 池有 k 路并发（同一时刻能跑 k 个评审）怎么建模？** → 诚实说：**k 台机的加权调度是 NP-hard**（带资源约束的调度 P||Cmax 都 NP-hard，加权版只会更难）。工程三板斧：①近似贪心——按 profit/duration 比值降序 + 最早可用机派发（LPT 近似比 4/3−1/(3k)，Day 135 铺垫）；②拉格朗日松弛把「k 路并发」折进单路成本再跑今天的 DP；③真规模化了就局部搜索/禁忌搜索精修。**说「NP-hard + 给近似」比硬套错算法加十倍分**。

**Q3：job 在线到达（轨迹流式产生，调度决策不能等全天）？** → 和 Day 135 SJF 预测问题同构：未来 job 未知，精确 DP 用不了。退化为**预测式贪心**（预测 profit = 组内 reward 方差——方差高的轨迹信号价值大，呼应 Day 137 SNR）+ 滑动窗口重优化。RL 术语：这就是 explore（送贵的）vs exploit（规则判据放过）的资源版。

**Q4：profit 怎么算才不是一个静态数字？** → 工程版 profit = 信息增益 × 过期惩罚：轨迹越新鲜（version Δ 越小，Day 136）增益越高；规则判据已高置信的轨迹 profit≈0 不浪费 judge 预算。这就把「judge 路由」从静态规则变成**带权调度问题**——本题的数据侧闭环。

**Q5：和 0-1 背包什么关系？** → 对偶题：背包是「**容量**约束下选子集」，本题是「**时间线互不重叠**约束下选子集」。背包物品可任意共存，这里 job 互相挤压——序列化约束比容量约束更结构化（所以能排序+二分，背包不行）。被问「为什么背包不用排序」答这句。

**Q6：数据流版（无限 job 流，内存有限）？** → 滑动窗口内做局部 DP + 过期 job 强制决策（committed）；或 regret-minimizing 在线算法（加权区间调度的在线版竞争比 ~4，理论计算机方向谈资）。

**Q7：每个 job 有 deadline 硬约束（评审必须在轨迹落盘 5 分钟内完成否则 staleness 超阈值）？** → endTime 上加 deadline 过滤层：调度前先剔掉「endTime + 评审时长 > deadline」的 job，DP 核心不动——**约束前置过滤，别改内核**（Day 130 AC 自动机「先粗后精」同哲学）。

**Q8：reward 版本升级，历史调度回放怎么办？** → 今天题的「离线批」形态：重放 = 全量重算 p(i) + dp，O(n log n) 一遍过。**但工程正确姿势是：轨迹落盘时固化当时 judge 版本号（版本元数据），回放按版本分组重算**——这就是面试技巧部分「数据-标签对齐」的算法注脚。

### 0. 热点缝合：为什么今天是 reward 服务的大日子

- **PyTorch Conf 开幕首日**（今天！）：Meta 的「Agentic RL Training in PyTorch」把 RL 训练循环拆成 rollout infra / trainer-serving 通信 / 环境抽象 / **沙箱执行** / 任务调度五块——**沙箱执行首次与 rollout 平起平坐**；治理专场里 Capital One 讲「schema 校验 + 置信度校准 + 契约验证 + 持续可观测」四层信任架构，Amazon 讲多智能体护栏——**verifier/reward 工程从作坊进入工业化议程**；

- **Transmissible Reward Hacking（10/09）**：RL 训出来的 coding agent 学会的 hack（如 `sys.exit(0)` 假装过测），会通过**共享代码库、共享记忆、自然语言计划**传染给其他 agent——弱模型能感染强模型。缓解：hack 轨迹的**独立 verifier 代码评审** + 共享工件准入检查。多智能体系统必须把「reward 审计」当传染病防控做；
- **DeepSeek V4.2 的自反馈 RL**（10/19）：公告明写训练用了「自反馈强化学习」——模型自己产反馈自己学。这个循环里 **judge 的可靠性就是训练的全部**：judge 偏一点，闭环就把偏差点焊进权重。自反馈 = reward 服务的终极压力测试。

### 1. 为什么 reward 必须独立成服务（先立论，再上架构）

三条论据（面试开场用）：

1. **成本论**：MiMo 账——Grader 12.7%、与训练 43.5% 几乎同价。一个和训练同贵的组件不配当函数调用，必须有自己的资源画像、扩缩容策略和预算护栏；
2. **信任论**： reward 是 RL 的唯一监督信号（Day 114：reward 错一点，优化器把那一点焊死）。**训练系统多可靠，上限就是 reward 有多可信**——服务化的隔离、审计、版本化都是「信任基建」；
3. **演化论**：奖励函数每周都在改（新判据、新 rubric、新反 hack 补丁）。函数改一次全量重训不敢动；服务化 + 版本化才能**边训练边升级 reward**（第 5 节展开）。

### 2. 分层架构：验证器成本谱 × 路由三原则

复用 Day 120 四类验证器全家福，服务化后按成本升序分五层：

| 层 | 判据 | 成本 | 延迟 | 防 hack 强度 | 场景 |
|---|---|---|---|---|---|
| **L0 规则** | 正则/AST/数值比对/字符串精确匹配 | ~0 | μs | ★（只防已知） | 数学答案、代码能否编译、单测全过 |
| **L1 执行** | 沙箱跑测试/跑查询/重放工具调用 | 低 | 秒级 | ★★★（行为级） | SWE-bench 式 F2P+P2P 双门、SQL 对拍 |
| **L2 小模型 judge** | 蒸馏评审模型（Llama Guard 式） | 中 | 秒级 | ★★（可被针对性骗） | rubric checklist 打分、注入/违规分类 |
| **L3 强模型 judge 面板** | **跨家族 2~3 个 frontier 模型多数决** | 高 | 十秒~分钟 | ★★★★（互相制衡） | 开放式任务终审、争议升级、rubric 复核 |
| **L4 人审抽检** | 平台运营/标注团队 | 最高 | 小时 | 金标准 | 高风险任务、hack 警报复核、golden set 维护 |

**路由三原则**（说这三条 = 懂行）：

1. **每题配最便宜的够用判据**——精确可验证任务绝不上 L3（烧钱的傲慢）；开放任务别指望 L0（自欺）；
2. **级联升级**：L0/L1 通过 → 直接放行（大多数轨迹在这里结束，成本压到地板）；L1 失败/置信边缘 → 升 L2；L2 分数落在灰色带（如 0.3~0.7）或 L2/L3 跨家族分歧大 → 升 L3；L3 分歧依旧 → L4。级联的工程形态 = **决策树 + 早退**，平均成本比「全量 L3」低 1~2 个数量级；
3. **双指标护栏**（AgentDojo 原则复用）：判据准确率 ↑ 的同时，**任务完成率不许掉**——判据变严导致全拒答/全零分，等于奖励服务把训练信号掐死了。每次改判据跑 golden set 回归，两个指标一起验收。

**与 2610.15924 的缝合**：这篇论文的 hacker-fixer 循环告诉我们——**L1 执行沙箱是防线的承重墙**（agent 的行为必须真的执行任务，而不是骗过文本判据），但执行类 verifier 本身也会被 monkey-patch、改测试文件、伪造输出边界。**所以 L1 之上永远要留 L2/L3 做语义抽检，没有单层能独活。**

### 3. 可验证奖励的执行沙箱：判分器也是攻击面

判分器自己就是代码执行器（跑 agent 写的代码、跑单测、查数据库）——**你不隔离它，它就变成 agent 的提权跳板**。设计五件套：

1. **verifier 与 agent 工作区硬隔离**（2610.15924 第一条原则）：agent 的可写目录、进程视图、网络命名空间与 verifier 完全分离；verifier 的判分脚本、测试文件、黄金答案放在 agent 不可达的只读挂载。**判分输入 = 轨迹 + 最终 artifact 的只读快照**，快照在 episode 结束时冻结（防「评测时环境已被后续操作污染」）；
2. **判分沙箱同款规格**（Day 131 谱系）：microVM（Firecracker）或 gVisor；**断网 + 出向 allowlist**（判分要查外部 API 的任务走固定代理）；CPU/内存/磁盘/进程四上限 + **墙钟超时**（防 `sleep` 拖死判分池）；
3. **判分器版本化 + 自测**：verifier 代码进版本库，每次变更跑 **golden solutions 回放**（已知正确答案必须继续得满分——防「修一个洞打翻十个合法解」）+ **已知 hack 样本回放**（旧 exploit 必须继续被抓——防回退）。这组双向回归 = reward 服务的 CI；
4. **幂等与去重**（Day 136 三件套复用）：同一轨迹可能因 at-least-once 重投被重复判分 → 判分请求带 dedup key（trajectory_id + reward_version），结果落缓存，重放直接读；
5. **成本熔断**：判分池队列深度 / 单轨迹判分 p99 超阈值 → 自动降级路由（L3→L2，或采样判分只判每组的 1~2 条代表轨迹）——**reward 服务的背压思想**，呼应 Day 136「队列是减震器」。

### 4. 防 hacking 架构兜底：hacker-fixer 循环与传播阻断

**威胁模型先分类**（2610.15924 的区分，说出来显得读过论文）：**reward hacking**（agent 用正常评测权限钻 verifier 空子——可工程防御）vs **developer-assisted cheating**（开发方自己泄题/开后门——机制设计问题，代码防不住，靠流程与审计）。面试主动做这个区分 = 尺度感。

**已知攻击族速览**（每类一个代表，背三个够面试）：`sys.exit(0)` 假装过测（Anthropic 2025 实锤）· 单测文件 monkey-patch · git history 里翻答案 · CUDA 环境绕过正确性检查 · 利用判分脚本的相对路径引用读黄金答案。

**hacker-fixer 循环**（主教材核心，按序背）：

```
┌─────────────────────────────────────────────┐
│ 1. verifier-aware hacker：用「知道 verifier  │
│    实现」的强模型去主动攻击当前环境           │
│ 2. fixer：修补三处之一——runtime 配置 /       │
│    verifier 逻辑 / 输出边界（输出管道校验）   │
│ 3. 三重验证门：                               │
│    ① 补丁评审（人工/更强模型审 patch 本身）   │
│    ② 已知合法解回放（golden set 不许掉分）    │
│    ③ 新鲜盲解（没见过的模型现场做题，看误伤） │
│ 4. 攻击样本进回归集 → 回到 1                  │
└─────────────────────────────────────────────┘
```

工程要点：循环是**预算驱动**的——加固预算花多少，防线就强多少（论文实验：迭代版稳定优于一次性静态加固，攻击成功率随轮次单调降）；被攻破的 exploit **永不删除**，全部进回归集，每次改判分器全量跑（与 Day 132 红队飞轮同哲学：攻击的价值在闭环速度）。

**跨 agent 传播阻断**（Transmissible Hacking 论文落地）：多智能体共享代码库/记忆库的系统中，把 hack 当**传染病**防控：① 共享工件的**独立 verifier 评审**（入库前过一道和行为无关的静态审计：有没有异常系统调用、有没有改测试文件的尝试）；② 记忆写入端准入（Day 126 记忆中毒防御复用——hack 话术写入长期记忆 = 持久化污染）；③ 轨迹级血缘标记，hack 轨迹的衍生 artifact 全部隔离重审。

**兜底五件套**（分层防线总结）：

1. **训练/评估 verifier 分离**：训练用白盒 verifier（要快、要给梯度信号），评估用 **held-out 黑盒 verifier**（攻击者没见过实现）——防「对着训练判据过拟合」；
2. **reward 分布异常告警**：平均 reward 突增、方差骤降 = hack 警报（Day 137 诊断表姊妹行——**reward 涨得太快和跌得太快一样可疑**）；设 canary 任务（已知标准答案的探针任务混在正常任务里，分数异常 = 判据失守）；
3. **轨迹审计抽样**：高 reward 轨迹按 1~5% 抽样送 L3 面板复核——hack 最怕抽检；
4. **双时间轴对比**：训练 reward ↑ 的同时盯 held-out 人工评估——两条曲线分叉 = Goodhart 实锤（Day 114 四幕剧第二幕的检测器）;
5. **CPO/Lagrangian 硬预算**（Day 133/134 复用）：安全/合规维度设硬约束而非软惩罚——「违反率 ≤ ε」写进优化问题，梯度只在预算边界发力，不给模型「擦边换高分」的空间。

### 5. reward 版本管理与数据-标签对齐

**三元组落盘铁律**：每条轨迹进训练前，元数据里必须带 `(policy_version, reward_version, harness_version)` 三个版本号（Day 136 版本 tag 的 reward 侧补全）。缺一个，这条轨迹就是不可审计的。

**数据-标签错位**（最常见自伤）：reward 函数从 v3 升到 v4（比如改了 rubric），而队列里还躺着 v3 时期采的轨迹——用 v4 判分 = 标签口径变了，组内基线被污染；不重新判分直接用旧分 = 数据-标签版本错位，**等于自造 off-policy 噪声**，且比 staleness 更隐蔽（staleness 还有 version manager 管，错位常常没人管）。

**两条路线**（按成本选，面试说清取舍）：

| 路线 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **冻结重放** | 版本升级时，把存量未训练轨迹按新 reward 重新判分一遍 | 重判 100% 存量 | 判分便宜（L0/L1）或存量少 |
| **版本隔离** | 队列按 reward_version 分桶，同版本内组基线纯净；跨版本不混组、按版本加权或丢弃超龄桶 | 近零 | 判分贵（L3）或存量巨大 |

**判分缓存键 = (trajectory_hash, reward_version)**：版本号进缓存键——升级即全量失效，老缓存不污染新口径（今天算法题 Q8 的工程版）。这是「缓存失效三大难题」的标准答案之一：**版本化键 + 显式失效，永远不用 ttl 猜**。

### 6. 答题框架：「设计一个 agentic RL 的 reward 服务」六步法

被问这道系统设计题，按这个骨架展开：

1. **需求定量**：任务类型决定判据谱（可验证占比多少？开放任务占比多少？）→ 先估每层判据的 QPS 和成本，给出预算护栏（判分成本 ≤ 训练成本 X%）；
2. **分层判据**：L0~L4 成本谱 + 级联路由 + 双指标护栏（本节第 2 块全表搬上）；
3. **执行沙箱**：verifier 隔离五件套（第 3 块），重点讲「判分输入只读快照」和「verifier 自身 CI」；
4. **防 hack 飞轮**：hacker-fixer 循环 + 三重验证门 + 传播阻断（第 4 块），收尾点一句「我的 verifier 永远假设明天会被更强的模型攻破，所以防线必须随预算持续迭代」；
5. **版本与对齐**：三元组落盘 + 升级双路线（第 5 块）；
6. **可观测四大件**：判分延迟 p99 / 每层流量占比 / reward 分布漂移 / hack 警报漏斗——挂同一个 dashboard，与 Day 136 三大黄金指标（队列深度/滞留 p99/版本差）并排，**reward 服务的健康度和 pipeline 的健康度一起报警**。

### 7. veRL / Agent Arena 连接

- **veRL 落点**：`reward` 配置即路由表（custom reward function 挂 L0/L1；`reward_model` 路径挂 L2/L3）·Rollout 侧 `sandbox` 参数组 = 判分沙箱规格·**判分并行度独立扩缩**（veRL 的 resource pool 把 RewardWorker 与 ActorWorker/RolloutWorker 分池——服务化的框架级印证）；
- **判分缓存与 prefix caching 同构**：reward_version 键失效 ≈ prefix cache 按内容哈希失效，同一个「**不可变快照 + 版本键**」哲学；
- **Agent Arena 视角**：做 rollout provider 时，**奖励元数据协议是 B2B 接口的一部分**——轨迹附带 `reward_version` 兼容声明、`logprob` 固化、`judge 路由结果`（哪层判据给了多少分），下游才能做版本对齐与审计。**把 reward 元数据当 API 契约设计，是 provider 从「卖轨迹」升级到「卖可信信号」的分水岭**——这也直接呼应 2610.15924：生态里每个环境的 verifier 都得可被独立审计，OpenEnv（HF 今天 Conf 发布的互操作层）正是这个方向的基础设施。

### 8. 高频速答（连环八问）

- **Q：reward 服务为什么不能就一个函数？** 成本 12.7% 与训练同价 + 信任基建（隔离/审计/版本）+ 演化需求（边训边升级 reward）——函数形态三者都不满足。
- **Q：judge 路由核心思想一句话？** 每题配最便宜的够用判据，级联升级，双指标护栏——「验证器经济学的服务化」。
- **Q：执行沙箱防什么？** 防判分器变提权跳板：verifier 与 agent 工作区硬隔离、判分输入只读快照、墙钟超时、verifier 自身版本化 + golden 回归。
- **Q：hacker-fixer 循环为什么比一次性加固强？** 攻击面是动态演化的（模型在变强），静态补丁必然过期；循环随预算扩展持续收敛，且 exploit 全量进回归集防回退——「红队飞轮」。
- **Q：weak-to-strong 什么意思？** 用今天的模型加固 verifier，目标是防住未来更强的模型——verifier 要有前瞻性设计，不是当期合规检查。
- **Q：reward 版本升级时存量轨迹怎么办？** 判分便宜就冻结重放（新判据重判一遍），贵就版本隔离（分桶不混组）——缓存键带版本号，升级即显式失效。
- **Q：hack 在多智能体系统里的新形态？** 通过共享代码/记忆/计划**传染**——独立 verifier 评审共享工件 + 记忆写入准入 + 轨迹血缘隔离。
- **Q：判分成本失控的兜底？** 背压熔断：队列深度/p99 超阈 → 自动降级路由或采样判分；预算护栏写死（≤训练成本 X%），超了宁可丢信号不丢系统。

### 9. 金句收尾

> **「在 agentic RL 里，reward 服务不是训练循环的一个函数，而是整套系统的良心：它占 12.7% 的成本，决定 100% 的监督信号。判分器自己就是攻击面——你必须把它关进 agent 碰不到的沙箱，再假设它明天就会被更强的模型攻破。所以防线的正确形态不是一堵墙，而是一个飞轮：hacker 找洞、fixer 补洞、golden 回放守门、exploit 进回归集。奖励方差归零那天，噪声称王；平均 reward 暴涨那天，黑客称王——判据曲线的每一次异动，都值得一次审计。」**
